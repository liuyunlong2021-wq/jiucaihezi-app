# 故事资料沉淀规则

用于把小说、新闻故事、剧本或口述故事沉淀成可追溯、可续跑、可直接支持创作前置检索的 Wiki。

## 目标结构

同时建立两种互补结构：

1. 来源结构树：作品 → 卷/篇 → 章/集 → 场次 → 情节拍。它保存原文、顺序和上下级，不保证每一级都需要独立文件。
2. 规范实体图：人物、地点、道具、关系和事件。结构节点通过双链指向实体；同一实体只保留一个权威页面。

推荐的最小目录是：

```text
<Wiki>/
├── index.md
├── 原始材料/
│   ├── index.md
│   └── <作品>/
│       ├── index.md
│       ├── 来源.md
│       ├── 原文.md
│       ├── 原文节点/
│       └── 节点分析/
└── 资产/
    ├── index.md
    ├── 人物/
    ├── 场景/
    ├── 道具/
    └── 关系/
```

目录只在有实际内容时创建。第一阶段只创建来源、原文和原文节点所需目录；节点分析与资产目录在第一次产生真实内容时创建。场次默认写成节点分析页内的标题，并用 `[[节点分析/0001#场次 001]]` 定位；只有需要独立创作、复用或继续细拆时才提升为单独页面。

## 第一阶段：无损结构拆分

第一阶段由文件树顶部的原生“故事拆分”功能和 Runtime 完成，模型不得负责机械拆分。所有支持的来源格式必须先由统一转换层生成完整 Markdown，拆分器只接收 Markdown；Runtime 再负责识别边界、展示预览、无损切片、稳定编号、创建最小 Wiki 结构和维护直属父 `index.md`。不得用多次 `write` 代替批量拆分，也不得把对话内存中的临时方案作为跨轮执行依据。

1. 确认来源文件和真实层级标记，例如 Markdown 标题、多语种章节编号、剧本场号或新闻段落。Runtime 将阿拉伯/全角数字、中文简繁与大写数字、日文章/話、英文 Chapter/Episode 和罗马数字归一后，仅用于比较同级标题序列与检查异常；标题前缀、独立编号、标题后缀和尾随括注均可作为显式候选，但不得从缺失编号反推正文边界。先生成拆分预览，至少检查节点总数、首尾标题、具体缺号/重号、倒序和无法归属的前后文本；无异常且不会覆盖既有文件时可直接执行，存在歧义或冲突时停止并请用户决定。
2. 每个叶子节点保存来源的连续原文切片，不总结、不改写、不清洗事实。序言、附录等无法归入章节的内容单独保留，不丢弃。
3. 使用稳定 ID、原始顺序、原文标号、父节点、来源链接或范围和内容哈希。路径只取决于原文物理顺序；重复、跳号、倒序或 OCR 错号原样保存在 `source_label`，不得决定文件名。最小 Properties 示例：

```yaml
---
type: story-source-node
id: work.node.0001
order: 1
source_label: "第一章"
parent: "[[../index|作品]]"
source: "[[../原文]]"
source_range: "第一章标题至第二章标题前"
source_hash: "<内容哈希>"
---
```

4. 文件名采用 `0001.md`、`0002.md` 等稳定顺序，不把“章、集、段”互相解释。批量写入正文和直属 `index.md` 后，校验文件数量、顺序、哈希、导航和链接。重复执行必须跳过内容相同的节点；内容不同或目标已存在时不得静默覆盖。
5. 节点很多时可以增加固定范围的中间索引，例如 `0001-0100/index.md`，但它只用于导航，不合并原始章节，也不复制资产清单。
6. 写入顺序为原文与来源、原文节点、节点 Index、作品 Index、直属父 Index、完成标记。完成标记最后写入；中断后由 Runtime 从真实文件状态续跑，不回滚覆盖用户内容。

## 第二阶段：语义细拆

语义判断由模型完成；Runtime 不替模型总结原文。Runtime 选择待处理节点并读取本批章节及相关规范实体，模型只返回包含场次、人物、地点、道具、关系、证据和待确认项的结构化语义结果。Runtime 校验来源哈希、证据、实体唯一性、双链目标和版本后，负责创建或更新章节分析页、规范实体页和受影响的直属 `index.md`。模型不得决定路径、提交顺序或用普通文件工具绕过校验。

原生语义链路可用时，先调用 `prepare_story_analysis` 取得 Runtime 选出的待处理节点和实体候选；完成判断后只向 `commit_story_analysis` 提交结构化结果。模型不得向提交动作提供写入路径，也不得把普通 `write`、`edit` 或批量写入拼成替代链路。提交后只依据 Runtime 回执报告成功、跳过、待确认、冲突和实际影响路径；继续处理时重新准备下一批。

1. 用户可以指定一章、连续多章或所有未完成章节作为批次。无论批次大小，每章都形成独立分析页；Runtime 通过比对来源节点与分析页选择下一批，中断后只重做尚未成功的章节。
2. 每个章节建立独立分析页，至少记录来源、场次、直接出现的人物、地点、关键道具，以及本章明确发生的关系或状态变化。没有证据的类别留空，并保留完成状态；分析页不存在不能解释成“没有相关资产”。
3. 每个事实尽量链接到原始章节或标题锚点。把结果分成“原文明确事实”“模型归纳”“待确认”；有直接依据且没有同名冲突的新实体可以创建来源型规范页。唯一匹配到用户已有规范实体时只链接，不自动改写正文；新增证据先留在章节分析页，用户明确确认后才可增量更新已有实体。模型归纳不得写成用户已确认事实。
4. 新名称先与现有规范实体的 ID、别名和证据消歧。不能唯一确定时写入分析页的“待确认”，不新建重复实体，也不强行链接。
5. 章节分析页的最小 Properties 示例：

```yaml
---
type: story-node-analysis
id: work.node.0001.analysis
source: "[[../原文节点/0001]]"
characters:
  - "[[人物/刘备]]"
locations:
  - "[[场景/桃园]]"
props:
  - "[[道具/酒碗]]"
analysis_status: complete
---
```

分析页是分析状态的唯一真源：分析页不存在表示未分析；已有分析页的 `analysis_status` 只使用 `complete`（已按本规则分析）和 `needs_review`（存在影响归属的歧义）。来源节点不再保存会过期的 `pending`。中断后从分析页不存在或非 `complete` 的节点继续。

## 创作前置检索

以章节、集数或场次为创作锚点时：先读对应分析页；状态为 `complete` 时再读取其中与任务直接相关的规范实体页面；分析页不存在或状态为 `needs_review` 时读取原始节点，并明确说明语义沉淀尚未完成或仍待确认。不得把 Index 摘要或资产名称当作人物、场景、道具的完整资料。
