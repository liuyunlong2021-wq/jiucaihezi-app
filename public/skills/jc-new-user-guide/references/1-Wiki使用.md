# Wiki 使用完整指南

> 给完全不懂技术的人。看完就能用。

## Wiki 是什么

Wiki 就是你的"第二大脑"。你把小说、剧本、项目文档扔进去，AI 自动帮你整理成能搜索、能画图、能追踪进度的知识库。

打个比方：你有一堆散乱的纸，Wiki 就是 AI 帮你把它们订成一本有目录、有索引、能翻查的书。

## 核心概念（可以不看）

- **.raw/** — 原材料。会话、参考资料和过程记录保留在真实位置，AI 不复制、不移动、不删除
- **wiki/** — 整理好的知识。AI 从 Raw 读取证据，将已确认结论写成结构化笔记
- **index.md** — 顶层导航，只链接 Wiki 的一级分类
- **hot.md** — 当前状态、风险和下一步
- **log.md** — 只追加的事实流水，只记录已确认的状态变化和重要 Wiki 变更
- **来源索引.md** — 重要结论到 Wiki 章节、原件/可读副本、实际处理范围和写入时指纹的对应关系

新建记忆空间只生成这四个通用文件，不猜项目类型，不预建业务目录，也没有每轮自动读取的 Wiki 文件。以后按需增加分类时，每个分类目录用 `_index.md` 说明用途并导航直属子目录。

## 项目文字同步

登录同一账号后，Web、Desktop 和已安装的支持版本 Mobile 可以在项目中心上传或下载允许的文字资料。媒体二进制、原始附件、空目录、凭据、设置、Skill、MCP、Provider、Session 和 `.raw/.sync` 不参与同步。这里描述的是同步能力，不代表 Mobile 已在 App Store 或其他公开渠道上架；下载状态以正式发布页为准。

项目中心只有两个方向明确的动作：

- **上传并覆盖云端**：以本地完整文字快照覆盖云端同名项目。
- **下载并覆盖本地**：以云端完整文字快照覆盖本地同名项目。

两者都不合并、不创建冲突副本、不自动双向同步。操作会显示扫描、上传/下载和完成进度；离线时内容仍先保存在本机。

## Wiki 读取方式

Wiki 页面都是普通 Markdown。App 不把 `README.md`、`CLAUDE.md`、`index.md`、`hot.md` 或其他页面固定注入每轮对话；模型只在当前问题需要时查询或读取相关内容。项目里已有的 `CLAUDE.md` 仍是普通用户文件，不迁移、不删除、不覆盖。

## Wiki 原生操作

查询、规划、填充、巡检和修正现在都是记忆工作台内置 Wiki 操作，不需要加载 Skill。它们共享同一套入口、链接、证据、预览、审批和写后复查规则。

## 完整操作：七步走

下面每一步都是**完整指令**，照抄粘贴到对话框，改一下方括号里的内容就能用，不用自己拼词。

### 1. 新建记忆空间

点击“新建记忆空间”创建基础 Wiki。若不知道后续该建什么，再说：

```text
请根据我的目标规划 Wiki 结构，先给方案，等我确认后再创建：
[完整描述你的目标、资料和常见问题]
```

### 2. 填内容

```
请把本轮已确认的内容填充进 Wiki：
只使用本轮对话中已经确认的信息，不扫描其他历史资料；
为重要结论登记 Wiki 章节、原始来源、处理范围和写入时指纹。
```

### 3. 查进度

```
请查看当前 Wiki 状态：
说明当前结构、最近确认事实、风险和下一步入口。
```

### 4. 搜东西

```
请查询 Wiki：
关键词：[你想查的角色名/设定名，比如"张三"或"世界观"]
```

### 5. 画关系图

```
请以 wiki/角色/主角.md 为种子生成一层局部关系图，
保存为 wiki/角色/主角-关系图.canvas。
```
生成后可直接在韭菜盒子的项目地图中查看；导出到 Obsidian 时才使用标准 JSON Canvas。

### 6. 体检

```
请对当前知识库做全库巡检：
检查导航断链、歧义链接、孤儿候选，
检查已登记来源是否变化、丢失或无法验证，
并检查主题「[要核对的事实或规则]」在相关页面中有没有明确矛盾。
```
查出问题只会列清单，不会自己改。普通未解析链接和孤儿页面只是待确认候选，不会被自动删除。

### 7. 改错

```
请预览这一项已确认修正：
文件：[Wiki 内的 Markdown 路径]
旧值：[唯一旧值]
新值：[唯一新值]
原因：[为什么错]
依据：[用户决定或可靠证据]
```
确认预览无误后再执行。语义冲突先由你决定哪个对，再形成这样一条精确修正。

## 项目做大了：加分类

Wiki 刚建的时候分类往往是猜的——比如小说一开始只建了"角色、世界、剧情"，写到一半突然觉得伏笔太多该单独建个本子记，直接粘贴：

```
请给 Wiki 加一个新分类：
新分类：[分类名，比如"伏笔"]
用途：[一句话说明放什么内容，比如"追踪伏笔埋设和回收进度"]
```

规划操作会先确认用途和归属，再建最小目录。如果新分类需要理解旧内容并填充确认事实，仍分两步执行；不要让结构规划和内容沉淀混成一次未经确认的批量改写。

是否拆分分类由实际用途决定，不能只看文件数量。

## 常见问题

### 小说太长会卡吗？

不会。基础初始化不猜测业务目录；需要什么再按目标规划、确认和扩展。

### 能自己改文件吗？

可以，也可以让 AI 按你确认的范围精确修改。

### Wiki 会和代码混在一起吗？

不会。wiki/ 和 .raw/ 是独立目录。

### 多个项目怎么切换？

每个项目有自己 wiki/，AI 自动找当前目录的。

### 怎么同步到 GitHub？

wiki/ 和 .raw/ 是普通文件夹；如果你自己用 Git 管理项目，可以按自己的仓库规则提交。它和韭菜盒子的云端覆盖操作是两套独立机制。

### 想重建？

不要删除原 Wiki 或 .raw/。想重建结构时，先保留现有资料并让 AI 接管；涉及迁移、合并或删除时，先明确确认范围。

### 巡检查出问题，为什么不直接帮我改了？

巡检官的角色就是"体检"，只负责查、不负责治。这是故意分开的：查错和改错混在一起容易查着查着手滑改错东西。查完说一声「执行修正」，交给修正官专门处理。

### 修正官会不会瞎改我的设定？

不会。能直接判断该改成什么的（比如漏改的错别字、断开的链接）它会直接改；但遇到两处设定说法不一样（比如档案说角色左脸有疤，正文写成右脸），它一定会先问你哪个对，不会自己挑一个改掉。
