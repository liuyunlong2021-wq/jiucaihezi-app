# 写作工作流（阶段8–9）

入口与确认规则以[SKILL.md](../SKILL.md)为准；本文件说明章节和复盘的具体方法。写作单位默认逐章，每章默认 2000–4000 字，用户给定的篇幅和范围优先。构思、起草、润色、检查在同一任务内完成，共用最多 3 个引擎的额度；引擎只按[引擎路由表](engines/index.md)选择。

## 阶段8：正文写作与修订

### 接续依据

1. 读运行时 Wiki 索引，从真实链接定位当前作品、章纲、角色、世界规则、伏笔，以及上一章正文和已有分析页。
2. 已有资料只读取当前任务需要的页面；来源事实、创作意图与未确认草稿分别看待。上一章没有节点分析时可读已确认原文，说明分析尚缺；不要重启开书流程。
3. 用户直接要求修改某章或一段文字时，读目标原稿和相关约束，按指定范围修订；只要点评时进入阶段9。

### 开场与催化剂

用户或已确认章纲已经确定开场、催化事件时直接沿用；用户授权代选时据已有角色与伏笔选择，并简短说明采用的方向。仅在关键方向未定且未获代选授权时提供选项：

- 第一章可给冲突切入、反常设定、悬念倒叙三种预览（各 ≤300 字），支持自定义；等待用户选择后再写正文。
- 续章可给 A/B/C 三个能触碰角色红线的催化事件及 D 自定义；选定后进入本章循环。
- 设计红线、压力和催化因果时读取[核心机制](核心机制.md)，复用已确认的人物与世界规则。

### 一章四阶段

| 阶段 | 必须完成的工作 |
| --- | --- |
| 构思 | 确定一个中心事件、场景功能、角色目标、催化因果、伏笔与章末钩子 |
| 起草 | 依人物动机推进动作与对白，保持视角、空间和因果连续 |
| 润色 | 按用户文风与人设打磨节奏、信息密度和表达；保留本轮确认的剧情 |
| 检查 | 对照[写作质量手册](写作质量手册.md)检查章纲、冲突、人设、主角作用、伏笔和钩子 |

这些是写作责任，不是固定引擎清单。基础方法已经足够时不读取引擎；发现具体问题时，再按路由表补一个对应的方法。修复后复检当前问题，完成请求即可交付。

### 草稿与确认正文

归档细则见[落位与提交](落位与提交.md)。`novel_chapter_draft`、`novel_chapter_source` 是 `wiki_save_artifact` 的 `artifact_kind` 值，不是独立工具。

1. 本章完成质检后，以 `artifact_kind=novel_chapter_draft` 保存正文；同时传作品名、章节序号和章节标题，正文不含工具自动生成的章标题。给出回执中的真实路径并等待确认。用户明确不保存时在对话中交付。
2. 用户明确确认对应的已保存草稿后，以 `artifact_kind=novel_chapter_source`、`user_confirmed: true` 提交与草稿完全一致的正文。确认不能从“继续写下一章”或批次节奏中推断；多个待确认版本时先确认对象。
3. 原文成功后检查草稿转换为确认记录的结果。返回警告时准确说明已成功和未完成项，按回执安全重试，不重复追加。
4. 提示用户在文件树手动触发「故事拆分」。不得自动调用 `prepare_story_analysis`／`commit_story_analysis`；不得用普通文件写入模拟来源节点。
5. 设计变动、新伏笔或章纲偏差按本轮要求更新对应规划和资产页；已成事实由原文及原生分析承载。

### 分批与续作

默认写一章、确认一章；用户明确要求多章时按指定范围分别保存草稿。批量确认必须能唯一对应实际草稿版本，只有被明确确认的章节才可追加原文。分批交付或汇报不改变这条规则。

前三章重视开场与留存，后续按章纲维持人物弧光与节奏。一卷完或全书完结、且用户要求巡检时，使用 `wiki-memory` 检查断链与矛盾。用户没有要求下一章时，在当前交付处结束。

## 阶段9：局部检查与全稿复盘

1. 先确定检查范围：某一段、单章、前三章、一卷或全稿；按明确范围读取，不因“复盘”自动读整本。
2. 原文及节点分析代表已成事实，规划页代表创作意图；缺失的正文或分析应说明，不用规划内容冒充已写情节。
3. 对照质量手册诊断结构、冲突、人物弧光、节奏、视角、伏笔及语言。基础检查足够时直接交付；专项问题再按引擎路由表选择主引擎和条件引擎。
4. 输出有正文依据的问题、涉及章节及修正建议。只要求诊断时不修改原稿；要求修订时转入对应文本的修订任务，遵守原文版本和来源更新保护。
5. 用户要求正式复盘报告时，用 `wiki_save_artifact` 的 `artifact_kind=novel_manuscript_review` 归档；明确只讨论或不保存时在对话中交付。
