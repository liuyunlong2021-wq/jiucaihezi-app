# 落位与提交

本 Skill 与 `wiki-memory` 在同一个项目里同时启用。**骨架、目录名、`index.md` 合同、写入顺序、冲突处理一律以 `wiki-memory` 为准**；本文件只回答一个问题：小说的产出该落到哪、谁写、走不走原生链路。

## 三条硬规则

1. **不自建目录。** 不写 `wiki/角色/`、`wiki/世界/`、`wiki/剧情/`、`wiki/文案包装/`，也不跑建库脚本。目录由原生建库创建，或第一次写真实内容时按 `wiki-memory` 的规则创建。
2. **路径不写死，按运行时给的索引定位。** 每次开工先读 `<wiki_index>`（它包含根目录、一级、二级的 `index.md`），从 `[[…]]` 行里拿真实路径。索引里没有这一项，说明还没建，问用户，不要凭本文件的名称猜路径。
3. **不手造原文节点。** `原文节点/NNNN.md` 里的 `source_hash` 是 Runtime 算的，模型写的哈希一定校验失败。正文进节点树只有一条路，见下面第 3 节。

## 1. 落位表

| 全书大纲 | `创作/大纲.md` | 本 Skill | 否 |
| 逐章规划（章纲） | `创作/章纲.md` | 本 Skill | 否 |
| 伏笔追踪 | `创作/伏笔.md` | 本 Skill | 否 |
| 文案包装（书名/简介/标签） | `创作/文案包装.md` | 本 Skill | 否 |
| 角色设计卡 | `资产/角色/<角色名>.md` | 本 Skill | 否 |
| 场景 / 道具设计 | `资产/场景/<名>.md`、`资产/道具/<名>.md` | 本 Skill | 否 |
| 稳定关系 | 交节点分析产出，或用双链写进两个实体页 | 本 Skill 或原生 | 否 |
| 章节正文 | 追加进 `原始材料/<作品>/原文.md` | 本 Skill | 否 |
| 原文节点、节点分析页、来源事实、新实体页、直属 `index.md` | 自动 | **Runtime** | 是 |

规划层页面名以 `创作/index.md` 登记的真实文件名为准（短剧项目可能叫 `集纲.md`）。

## 2. 写 `创作/` 的规则

- `创作/` 是模型产出，**不走两阶段沉淀**：不参与边界识别、不生成原文节点、不需要内容哈希。
- 落盘顺序固定：**先写正文，再登记直属 `index.md`**（`wiki-memory` 的写入合同，不因为这里不是来源材料就跳过索引）。
- 一个项目一部作品一个 `创作/`。发现已有 `创作/` 且里面已有同名页面 → 增量改写，不新建第二份。
- 规划层描述**意图**，原文节点描述**已成事实**。两处不一致时以原文节点为准，并把不一致报给用户。

## 3. 正文 → 来源树（唯一入口）

正文不是本 Skill 的记忆，是**来源材料**。每章写完后：

1. 把本章正文**追加**到 `原始材料/<作品>/原文.md`（用 `edit` 追加，不重写全文）。
2. 提示用户在文件树点一次**「故事拆分」**（机械拆分归 Runtime，本 Skill 不许用多轮写文件模拟）。
3. 拆分支持**受控刷新**，所以重跑是安全的：
   - `原文.md` 允许覆盖，前提是新内容以旧内容开头（纯追加）。
   - `来源.md` 允许整份重写，但只对 Runtime 自己生成的记录（frontmatter 里 `type: story-source`）；标记 `<!-- jc-story-source -->` **之后**用户手写的内容会原样保留。
   - 已有节点允许刷新，前提是它的正文以旧正文开头（节点 frontmatter 里的 `source_range`、`source_hash` 本来就会变，不参与比较）。
   - 以上条件不满足时拆分**拒绝写入**并报「目标文件冲突」，不会覆盖用户拆改过的内容。所以：正文只能追加，不要回头改写已拆过的旧章节；真要大改，先让用户明确同意。
4. 一次导入很多本时，让用户在文件树里**选中那个文件夹**再点「故事拆分」：里面所有可导入的文档会排队，一本一本来（弹窗显示「第 N / 共 M 本」），每本都要用户看过预览才写盘，出错可以「跳过这一本」。
5. 文件名带 `书名(作者).epub` 这类括号写法时，Runtime 会把作者识别出来，和书名一起显示在弹窗里并且可以当场改；改完按新名字重建计划（作品目录跟着变）。作者写空就不写这一行。
6. 用户确认后跑节点分析，角色/场景/道具/关系会**自动增量**沉淀到 `资产/`。单本上千章时按 `prepare_story_analysis` 返回的 `progress` 分段推进：`nextOrder` 是本次起点之后第一个未分析节点的序号，回传给 `startOrder`；`analyzed`/`remaining` 是整本进度。

**不要**把一章写成一个新的作品目录——作品目录按书建，不按章建。

## 4. 角色页为什么能和原生链路共存

原生节点分析按 **文件名 + `title` + `aliases`** 三处匹配已有页面，匹配上就只往分析页加双链，**不会重写实体页**。所以本 Skill 先写角色设计卡是安全的，设计内容不会被冲掉。

因此：

- 文件名必须等于角色的规范名（`刘备.md`），frontmatter 必须写 `title`。
- 别名、字、绰号全部写进 `aliases`，否则同一角色会被原生链路建成第二份。
- **来源事实不写进角色页**。每章考据出来的事实归节点分析页；角色页只放设计意图 + 索引需要的最少信息。一个事实只有一个权威位置。

角色页模板：

```markdown
---
type: story-character
title: "刘备"
aliases: ["玄德", "皇叔"]
---

# 刘备

## 设计

- 极致维度：守护（9/10）
- 内核动机：一句话
- 红线：不可触碰的底线
- 性格反差：如外冷内热
- 角色弧光：从 XX → 经历 XX → 变成 XX
- 与主要角色关系：一句话
```

场景页用 `type: story-scene`、道具页用 `type: story-prop`，正文结构与角色页一致（`## 设计` 一节，其余留给原生链路）。

发现 `资产/` 下已有同名或同别名页面时：补写或引用它，**不要**新建。

## 5. 不同写的东西

| 不要做 | 为什么 |
| --- | --- |
| 写 `CLAUDE.md` 的 `## [创作]` 区块 | 该文件不在运行时注入清单里，写了没人读，还会和 `wiki/index.md` 抢"当前状态"这个真源 |
| 维护 `wiki/hot.md` | 同上。进度、伏笔、钩子写进 `创作/` 下的页面，导航交给索引 |
| 自建 `wiki/角色/` 等目录 | 会和 `资产/角色/` 形成两份档案，用户看到两个"刘备" |
| 手写原文节点或伪造 `source_hash` | 原生校验会直接拒绝，且中断后续跑 |
| 用摘要替代原文 | 原文节点必须是无损切片，摘要归节点分析页 |

## 6. 与 `wiki-memory` 的分工

| 事项 | 谁定 |
| --- | --- |
| 目录、路径、`index.md` 写法、Properties 必需字段、写入顺序 | `wiki-memory` |
| 骨架缺失时怎么建 | `wiki-memory`（原生建库） |
| 冲突、重复、歧义怎么处理 | `wiki-memory`（停下来问用户，不自行裁决） |
| 小说怎么写：结构、节奏、角色、章纲、正文 | 本 Skill |
| 每次写几个引擎、按什么顺序推进 | 本 Skill |
| 什么时候该沉淀、该拆章、该跑分析 | 本 Skill 提议，用户确认 |
