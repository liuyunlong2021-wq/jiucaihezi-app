# 落位与提交

本 Skill 与 `wiki-memory` 在同一个项目里同时启用。**骨架、目录名、`index.md` 合同、写入顺序、冲突处理一律以 `wiki-memory` 为准**；本文件只回答一个问题：小说的产出该落到哪、谁写、走不走原生链路。

入口、讨论与确认规则以[SKILL.md](../SKILL.md)为准。产物类型由真实 `wiki_save_artifact` 工具的枚举决定；类型名不是工具名。章节调用必须传 `artifact_kind`、`content`、`work_name`、`chapter_number`、`chapter_title`，确认来源时还必须传 `user_confirmed: true`；作品和章节标识与实际草稿一致。

## 三条硬规则

1. **不自建目录。** 不写 `wiki/角色/`、`wiki/世界/`、`wiki/剧情/`、`wiki/文案包装/`，也不跑建库脚本。目录由原生建库创建，或第一次写真实内容时按 `wiki-memory` 的规则创建。
2. **创作产物走共享归档工具。** 当前工作台使用 `wiki_save_artifact` 按产物类型推导路径、创建 Wiki 骨架、读回正文并更新直属索引；不得传路径，也不得用 `file` 工具重复写同一份创作产物。普通 Wiki 任务仍按 `wiki-memory` 的索引读写合同执行。
3. **不手造原文节点。** `原文节点/NNNN.md` 里的 `source_hash` 是 Runtime 算的，模型写的哈希一定校验失败。正文进节点树只有一条路，见下面第 3 节。

## 1. 落位表

| 小说的产出 | 落到哪 | 谁写 | 走原生校验 |
| --- | --- | --- | --- |
| 灵感方案 / 市场分析 / 核心梗 | `创作/` 下对应页 | 本 Skill 创作，工具落盘 | 否 |
| 世界设定 / 全书大纲 / 章纲 / 伏笔 / 文案包装 | `创作/` 下对应页 | 本 Skill 创作，工具落盘 | 否 |
| 角色 / 场景 / 道具设计卡 | `资产/` 下规范实体页 | 本 Skill 创作，工具落盘 | 否 |
| 稳定关系 | 交节点分析产出，或写进两个实体页 | 内容由本 Skill 提议，用户确认后落盘 | 否 |
| 待确认章节草稿 | `创作/章节草稿/<作品>/第NNN章.md` | 本 Skill 创作，工具落盘 | 否 |
| 用户确认的章节正文 | 追加进 `原始材料/<作品>/原文.md` | 用户确认，`wiki_save_artifact` 追加 | 否 |
| 原文节点、节点分析页、来源事实、新实体页、直属 `index.md` | 自动 | **Runtime** | 是 |

规划层页面名以 `创作/index.md` 登记的真实文件名为准（短剧项目可能叫 `集纲.md`）。

## 2. 写 `创作/` 的规则

- `创作/` 是模型产出，**不走两阶段沉淀**：不参与边界识别、不生成原文节点、不需要内容哈希。
- 产物完成后由 `wiki_save_artifact` 保存正文、读回校验并更新直属 `index.md`；返回 `saved_with_warnings` 时按回执处理索引或章节确认记录未完成项，正文保留且可安全重试。
- 一个项目一部作品一个 `创作/`。发现已有 `创作/` 且里面已有同名页面 → 增量改写，不新建第二份。
- 规划层描述**意图**，原文节点描述**已成事实**。两处不一致时以原文节点为准，并把不一致报给用户。

## 3. 正文 → 来源树（唯一入口）

正文不是本 Skill 的记忆，是**来源材料**。每章写完后：

1. 先调用 `wiki_save_artifact`，以 `artifact_kind=novel_chapter_draft` 保存到 `创作/章节草稿/<作品>/第NNN章.md`，正文不含工具自动生成的章标题；展示真实路径并等待用户确认。
2. 只有用户明确确认该草稿后，才调用 `wiki_save_artifact`，以 `artifact_kind=novel_chapter_source` 追加到 `原始材料/<作品>/原文.md`，并传 `user_confirmed: true`。传入正文必须与已保存草稿一致。归档工具会阻止无确认写入、重复章节和覆盖冲突；原文读回成功后草稿页转为含 SHA-256 指纹与原文双链的确认记录，转换失败时保留草稿并报告警告，重试不会重复追加。
3. 保存原文后提示用户在文件树手动点一次**「故事拆分」**。不得自动调用 `prepare_story_analysis`／`commit_story_analysis`，也不得用多轮写文件模拟机械拆分。
4. 拆分支持**受控刷新**，所以重跑是安全的：
   - `原文.md` 允许覆盖，前提是新内容以旧内容开头（纯追加）。
   - `来源.md` 允许整份重写，但只对 Runtime 自己生成的记录（frontmatter 里 `type: story-source`）；标记 `<!-- jc-story-source -->` **之后**用户手写的内容会原样保留。
   - 已有节点允许刷新，前提是它的正文以旧正文开头（节点 frontmatter 里的 `source_range`、`source_hash` 本来就会变，不参与比较）。
   - 以上条件不满足时拆分**拒绝写入**并报「目标文件冲突」，不会覆盖用户拆改过的内容。所以：正文只能追加，不要回头改写已拆过的旧章节；真要大改，先让用户明确同意。
5. 一次导入很多本时，让用户在文件树里**选中那个文件夹**再点「故事拆分」：里面所有可导入的文档会排队，一本一本来（弹窗显示「第 N / 共 M 本」），每本都要用户看过预览才写盘，出错可以「跳过这一本」。
6. 文件名带 `书名(作者).epub` 这类括号写法时，Runtime 会把作者识别出来，和书名一起显示在弹窗里并且可以当场改；改完按新名字重建计划（作品目录跟着变）。作者写空就不写这一行。
7. 用户手动确认故事拆分后，角色/场景/道具/关系才由原生分析链路**增量**沉淀到 `资产/`。单本上千章时按 `prepare_story_analysis` 返回的 `progress` 分段推进：`nextOrder` 是本次起点之后第一个未分析节点的序号，回传给 `startOrder`；`analyzed`/`remaining` 是整本进度。

**不要**把一章写成一个新的作品目录——作品目录按书建，不按章建。

## 4. 角色页为什么能和原生链路共存

原生节点分析按 **文件名 + `title` + `aliases`** 三处匹配已有页面，匹配上就只往分析页加双链，**不会重写实体页**。所以本 Skill 先写角色设计卡是安全的，设计内容不会被冲掉。

因此：

- 文件名必须等于角色的规范名（`刘备.md`），frontmatter 必须写 `title`。
- 别名、字、绰号全部写进 `aliases`，否则同一角色会被原生链路建成第二份。
- **来源事实不写进角色页**。每章考据出来的事实归节点分析页；角色页只放设计意图 + 索引需要的最少信息。一个事实只有一个权威位置。

角色页模板：

```markdown
---
type: story-character
title: "刘备"
aliases: ["玄德", "皇叔"]
---

# 刘备

## 设计

- 极致维度：守护（9/10）
- 内核动机：一句话
- 红线：不可触碰的底线
- 性格反差：如外冷内热
- 角色弧光：从 XX → 经历 XX → 变成 XX
- 与主要角色关系：一句话
```

场景页用 `type: story-scene`、道具页用 `type: story-prop`，正文结构与角色页一致（`## 设计` 一节，其余留给原生链路）。

发现 `资产/` 下已有同名或同别名页面时：补写或引用它，**不要**新建。

## 5. 不同写的东西

| 不要做 | 为什么 |
| --- | --- |
| 写 `CLAUDE.md` 的 `## [创作]` 区块 | 该文件不在运行时注入清单里，写了没人读，还会和 `wiki/index.md` 抢"当前状态"这个真源 |
| 维护 `wiki/hot.md` | 同上。进度、伏笔、钩子写进 `创作/` 下的页面，导航交给索引 |
| 自建 `wiki/角色/` 等目录 | 会和 `资产/角色/` 形成两份档案，用户看到两个"刘备" |
| 手写原文节点或伪造 `source_hash` | 原生校验会直接拒绝，且中断后续跑 |
| 用摘要替代原文 | 原文节点必须是无损切片，摘要归节点分析页 |

## 6. 与 `wiki-memory` 的分工

| 事项 | 谁定 |
| --- | --- |
| 小说怎么写：结构、节奏、角色、章纲、正文 | 本 Skill |
| 归档产物的类型到路径映射、根目录识别、正文校验、直属索引 | `wiki-memory` 与 Runtime |
| 原生故事拆分与节点分析 | Runtime；用户在文件树手动触发 |
| 冲突、重复、歧义怎么处理 | `wiki-memory`（停下来问用户，不自行裁决） |
| 每次写几个引擎、按什么顺序推进 | 本 Skill |
| 什么时候创作、何时确认章节 | 本 Skill 与用户 |
