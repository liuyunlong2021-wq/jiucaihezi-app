# 新增模型与 NewAPI 插件固定流程

> 用途：每次给韭菜盒子服务器增加模型，或给 NewAPI 增加 Task Plugin 时，按本流程从上游合同走到公网 API 文档和真实验收。本文是方法入口；具体模型参数与已验证实例仍以各模型接入文档、适配器和代码为准。
>
> 关键来源：[[模型注册]]、[[模型矩阵]]、[[适配器收编任务插件总方案-2026-10-01]]、[[服务器运维]]、[[韭菜盒子文本模型API对外接入-2026-09-04]]。

## 1. 先判断本次要加什么

| 需求 | 服务器 / NewAPI | App 与创作面板 | 插件 |
| --- | --- | --- | --- |
| 已有 NewAPI 渠道新增一个 OpenAI 兼容模型 | 建立或复用上游渠道，登记公开模型名、映射和价格 | 文本模型按实际目录链路处理；创作模型更新注册表与能力声明 | 不需要 Task Plugin |
| 新增非 OpenAI 上游协议、需要转换请求/轮询/结果 | 增加适配器服务或复用已有服务，再配置 NewAPI 渠道 | 注册面板 API 风格、字段、素材和结果处理 | 评估是否可由 Task Plugin 承担转换 |
| 新增 NewAPI Task Plugin | 上传并激活插件，配置 type 61 渠道、URL、Key、模型与任务用量价格 | 插件公开模型名必须与客户端发送的 `model` 对齐 | 新插件的完整流程见 §4 |
| 只增加上游的模型变体 | 优先复用现有插件和适配器，核对它们的模型白名单、路由和计费事实 | 新模型名 / 能力 / 价格需要逐处登记 | 不因模型变体自动新建插件 |

不要把“NewAPI 中渠道能路由”写成“App 已接入”，也不要把代码/插件通过本地校验写成“生产可用”。

## 2. 开工前先冻结一张接入卡

开始改代码或生产配置前，先填写这些事实。未知项标“待确认”，不要猜：

| 字段 | 必填内容 |
| --- | --- |
| 上游 | 官方文档/控制台 URL、产品/端点名、文档核对日期、合同版本 |
| 上游地址 | API Base URL、具体路径、HTTP 方法；区分提交、查询、素材上传、结果下载 |
| 认证 | 认证头/参数名称、Key 类型、Key 归属和轮换方式；不记录 Key 正文 |
| 模型名 | 上游真实模型 ID、NewAPI 对外名、App `model` 值、插件 `meta.models` 值，逐项标明是否相同 |
| 请求与结果 | 必填字段、可选字段、默认值、枚举/范围、素材限制、同步/异步、状态词和结果字段 |
| 计费 | 上游成本单位与价格、对用户售价、NewAPI 计费模式/表达式、面板价格文案；记录币种和换算，不只写数字 |
| 运行位置 | 是否要适配器、容器名/网络、NewAPI 渠道类型、Base URL、部署与回滚方式 |
| 对外合同 | Base URL、公开端点、认证方式、可用模型名、请求/响应和真实验收范围 |

地址要分清楚三种：

- **上游 Base URL**：服务端连接供应商；通常是 NewAPI 渠道或适配器的配置，只有确属调用方要访问时才写进公开文档。
- **NewAPI 对外 Base URL**：韭菜盒子调用方使用的地址（当前 API 文档常用 `https://api.jiucaihezi.studio`）。
- **适配器内部 URL**：Docker/内网服务地址，只供 NewAPI 插件或渠道使用，绝不作为第三方接口地址。

认证凭据也分两层：供应商 Key 只放服务端 NewAPI 渠道或受控 Secret；韭菜盒子 API Key 是发给已授权调用方的 NewAPI Token。插件源文件、Git、日志和 Wiki 均不得出现任何 Key 正文。

## 3. 增加模型的固定顺序

### 3.1 核对上游与复用路径

1. 读供应商官方 API / 价格 / 限制文档；必要时对照官方 OpenAPI、SDK 或可控的最小请求。记录核对日期。
2. 搜索仓库已有同协议适配器、NewAPI 插件和相似模型。先复用服务与协议路径；只有上游形状确实不同才新增适配器/插件。
3. 明确 App 发给 NewAPI 的公开模型名，以及是否要映射为上游 ID。NewAPI 的 `model_mapping` 和客户端模型名是不同层，不能凭显示名称推断。
4. 明确 API 形态：文本 `chat/completions` 或 `responses`、图片 `images/generations|edits`、视频 `videos`、音频或 NewAPI 插件协议。根据当前代码和服务实际支持情况选择，不要只看模型厂商标称“兼容 OpenAI”。

### 3.2 配置服务端

1. 在 NewAPI 创建/复用渠道，准确填写渠道类型、上游 Base URL、上游 Key、模型列表和必要映射。确需适配器时，NewAPI 指向可达的适配器地址；适配器只绑定内网时，不要填宿主机 `localhost`。
2. 在 NewAPI 模型价格配置中登记模型。若有模型广场描述/价格展示，同步模型名、能力简介、计价单位与当前售价。
3. 新增/改造适配器时，按现有部署目录、Compose 网络、健康检查和源码是否 bake 进镜像确定部署命令。确认“重启”是否会加载新代码；源码 bake 进镜像时必须重建。
4. 生产渠道变更前保留可回滚的旧渠道/配置。先完成接入和并行验证，再决定是否停旧路径；禁止未验收先删旧链路。

### 3.3 登记 App 模型

创作面板模型通常涉及下列现有真源，按该模型真实使用路径改动，不能机械地全改：

- `src/runtime/creation/creationModelRegistry.ts`：模型 ID/公开 model 名、标签、任务类型、API style/路由、参数字段、素材数量与面板价格。
- `src/data/mediaModelCapabilities.ts`：客户端能力、输入文件类型/数量、字段约束等。
- 适配器/插件各自模型表：上游路由、允许字段、状态转换、usage facts、下载代理。
- `scripts/creation-models/server.mjs` 或其它模型可用性接口：只有该模型依赖该服务检测时才登记；确认别名与 NewAPI 渠道中的公开名一致。
- 文本对话模型按其当前模型目录和 Provider 配置链路接入，不要为它套用创作面板的媒体注册表。

前端发出的 `model` 必须与 NewAPI 渠道公开模型名严格一致；若渠道模型映射将其转换为上游 ID，记录映射两端。面板标签、模型 ID、上游 ID 不得混为一谈。

### 3.4 双向核对价格

至少列清三项：上游成本、用户实付价格、NewAPI 实际扣费。面板 `price` / 价格文案只是展示与客户端计划依据，不会替代服务端计费配置。单位必须一致（元/次、元/张、元/秒、token 等），并确认按实际输出量还是请求参数计费。

- 普通 Token 计费：按当前 NewAPI 该模型的输入、输出、缓存/多模态 Token 价格规则配置，记录汇率和倍率口径。
- Task Plugin 用量计费：见 §4.4。表达式系数按现有 NewAPI Task Usage 规则填写，**不能照抄 Token 计费的每百万 Token 换算**。
- 不确定实扣时先用受控低额度账号做一笔真实任务并读 NewAPI 消耗明细；不能从面板文案、插件 `usage` 响应或表达式外观推断账单正确。

## 4. 新增 NewAPI Task Plugin 的固定顺序

插件走 NewAPI Task Plugin v1。先确认生产 NewAPI 版本确实支持目标协议和所需 hook；插件合同可能随 NewAPI 版本演进，以上传前仓库里的插件文档/当前服务实际能力为准。不要假设任何上游都能被插件直接代理。

### 4.1 决定插件还是适配器

Task Plugin 是 NewAPI 中的单文件同步插件，能力受它的 hook、协议白名单、宿主请求体和网络能力限制。检查：

- 请求是否落在宿主实际支持的协议路径，如 `openai_responses`、`openai_video`、`openai_image`；当前具体列表见 [[适配器收编任务插件总方案-2026-10-01]]。原始端点不同不等于可由 `meta.routes` 改成任意代理。
- 是否需要插件无法提供的媒体字节、multipart 文件、长耗时执行、任务状态持久化、额外存储或内网执行器。需要时保留/新建适配器；插件可以只做路由和协议桥接。
- 结果下载是否需要鉴权、隐藏上游临时 URL、Range/HEAD 或宿主 `/content` 代理；检查对应 `listArtifacts` / `buildContentRequest` 等 hook 是否强制要求。

适配器是执行器、插件是协议代理时，要在文档和插件头部写清职责，不得把“加插件”误写成“适配器下岗”。

### 4.2 写插件与本地校验

1. 在 `newapi-plugins/<key>.plugin.js` 新建单文件；文件名、`meta.key`、渠道选择的插件 Key 三者一致。沿用仓库里的 NewAPI 插件文件结构。
2. 在 `meta` 中写 `apiVersion`、稳定且唯一的 `key`、名称、版本、作者、描述、`models`、支持的 `protocols`、必要的 `baseUrl`、`usageSchema`、`usageExamples`。
3. `meta.models` 必须覆盖该插件渠道会接收的**所有对外模型名**；新API模型名、面板发送的 `model` 和插件白名单逐字核对。插件处理上游 ID 的方式要明确（插件转换或渠道 `model_mapping` 二选一并实测）。
4. Key 从 `ctx.apiKey` / 渠道认证上下文读取；不硬编码、不过日志、不写 fixture 明文。Base URL 可为供应商域名或 NewAPI 可达的内部适配器 URL，必须说清由谁访问。
5. 按仓库约定添加 `newapi-plugins/__tests__/<key>.test.mjs` 并接入 focused 测试。覆盖模型白名单、请求字段/默认值、认证头不泄漏、上游成功/错误、状态映射、实际用量、响应解析和文件下载；插件静态语法约束也要有检查。
6. 执行该插件夹具、`new-api plugin lint`、fixture 校验和 NewAPI Sandbox（可用时）。本地通过只证明本地代码/合同，不证明生产上传、路由、真实上游、账单和下载。

### 4.3 上传、渠道 URL / Key / 模型名

1. 记录插件上传材料：文件路径、`key`、`version`、源码摘要/提交和预期 `protocols`。上传 NewAPI 管理后台插件页或使用受控 root API；root token 只从安全凭据存储取，命令与日志中避免输出。
2. 上传后确认插件条目存在、版本正确，并显式激活；需要升级时使用新版本并确认激活版本，不能把“上传成功”当成“正在运行”。保留上一可回滚版本。
3. 创建或修改 NewAPI Task Plugin（type 61）渠道，填：插件 key、渠道访问的 **Base URL**、供应商 **Key**、模型列表、必要的模型映射和分组。
4. Base URL 规则：优先按插件 `meta.baseUrl` 与渠道配置的回退规则填写；供应商直连用供应商 API Base URL，插件转适配器用 NewAPI 容器能解析的 Docker 服务名/内部端口。不要把公网 API Base URL、`localhost` 和内部 URL 互换。
5. 认证 Key 填对应上游的供应商凭据，不是调用方的 NewAPI Token。确认插件向上游使用的认证头/前缀与供应商合同一致。
6. 渠道模型列表填公开模型名。渠道 `model_mapping` 仅在确有上游命名差异时添加；检查一条渠道内的每个模型都由 `meta.models` 覆盖，否则会出现部分模型 unsupported。改用插件类型前确认原渠道其它模型是否也受插件支持；不支持就拆分/保留原渠道，不要造成音频或其他模型退化。

### 4.4 用量 Schema 与模型收费表达式

先选清实际计费事实，再定 Schema。表达式只能读插件 `usageSchema` 声明的 key；所有 `usageExamples[].facts` 以及每次运行时 facts 都要提供完整 key 集合，没有发生的用量传 `0`，不要省略。

Task Usage 表达式当前形式：

```text
tier("base", u("seconds") * 0.2)
```

`tier(...)` 是必需包装；`u("seconds")` 必须在当前插件的 `usageSchema` 中声明。系数是任务表达式的单价，Task Usage 结果是该笔的美元总价，**不再除以 1,000,000**。美元系数/人民币面板标价的换算必须和 NewAPI 当前价格单位及售价核对。

示例（按当前声明和宿主规则调整，不要盲抄字段名）：

| 计价事实 | `usageSchema` key 示例 | 表达式形状 | 校验重点 |
| --- | --- | --- | --- |
| 视频按秒 | `seconds`，单位 `second` | `tier("base", u("seconds") * <美元每秒单价>)` | 用实际成片秒数；缺省时长、失败任务和最大秒数 |
| 图片按张 | `image_count` 或声明的图片用量 key | `tier("base", u("image_count") * <美元每张单价>)` | 按实际返回张数；预约值与结算校正 |
| 按次 | `calls`，单位 `count` | `tier("base", u("calls") * <美元每次单价>)` | 一笔成功任务为 1；不同变体价不同则逐模型配置 |

同一插件可能同时支持多个计费维度；每个模型逐个配置对应表达式。模型映射后的计费选择优先级、插件维度覆盖规则与 usage 数值上限见 [[适配器收编任务插件总方案-2026-10-01#3. 铁律（每波都适用）]] 和 NewAPI `pkg/billingexpr/expr.md`。表达式保存成功不是账单验收，必须以真实调用的用量 facts 和实际扣款对账。

### 4.5 插件文件模板

以下是字段核对骨架，不是可直接上传的空壳插件：

```js
export const meta = {
  apiVersion: 1,
  key: '<稳定插件 key>',
  name: '<插件名称>',
  version: '0.1.0',
  author: { name: 'jiucaihezi' },
  description: { en: '<description>', zh: '<描述>' },
  models: ['<NewAPI 对外模型名>'],
  protocols: ['<宿主支持的协议>'],
  baseUrl: '<供应商或内部适配器 Base URL>',
  usageSchema: {
    calls: { type: 'number', unit: 'count', description: { en: 'Calls', zh: '调用次数' } },
  },
  usageExamples: [
    { label: '一次调用', facts: { calls: 1 } },
  ],
}

export const protocols = {
  // 只实现宿主契约中声明的 hooks；从现有插件复用精确形状。
}
```

插件协议和 hook 的字段必须对照当前 NewAPI `docs/plugin-api/v1.md` 与本仓已上传/验证插件样例，避免凭记忆写出宿主不支持的属性。

## 5. 对外 API 接入文档的写法

每个新对外模型/产品接口单独一页，避免把上游 API 文档、内部运维说明和第三方合同混成一篇。文档只描述调用者实际可用的韭菜盒子接口，不包含供应商 Key、root token、Docker 内网地址、渠道 ID/管理入口或未向调用者开放的字段。

### 5.1 固定章节

1. **标题与用途**：它做什么、不做什么；注明当前接入/验收状态与日期。
2. **接入信息表**：韭菜盒子公网 Base URL、HTTP 方法与路径、模型名、认证头、Content-Type、协议兼容范围、状态（草案/基础链路验收/生产全验收）。
3. **快速开始**：真实可用的 curl 示例，使用占位 API Key，不放真实 Key；模型名与 NewAPI `/v1/models`/授权名单一致。
4. **认证和权限**：调用方如何取得韭菜盒子 Token；明确上游 Key 由服务端管理，调用方不传供应商 Key。
5. **请求字段表**：字段、类型、必填条件、默认值、范围/枚举、互斥规则；字段以插件/适配器实际校验为准。
6. **请求样例**：为重要输入模式给独立 JSON；素材说明可访问性、格式/大小/数量、URL 与 Base64 支持情况。
7. **响应样例**：原样结构化的成功与失败响应，标出任务 ID；注明应该查询顶层 `id` 还是 `task_id`，不要混淆 NewAPI 和上游 ID。
8. **异步任务/下载**：创建、轮询路径，状态映射和终态；结果下载 URL、认证、过期时间、Range/HEAD 行为及调用方保存建议。
9. **价格和限额**：向调用方明确的价格单位、舍入/实际计量口径、并发/速率限制、结果保留期；最终结算以账户记录为准。不要把未对账的 `usage` 当价格证据。
10. **错误处理**：常见 HTTP 状态、错误格式、可重试与不可重试条件。付费创建请求不要建议盲目重试，除非幂等合同已明确。
11. **兼容范围与验收边界**：哪些已经真实测过，哪些仍未测（多模态、stream、callback、Range 等），以及变更日期。

### 5.2 发布文档前的事实核对

- Base URL 与端点在公网实际可达，且不是供应商或适配器内部地址。
- 文档模型名、NewAPI 渠道名、插件 `meta.models`、App 请求 `model` 对得上。
- 请求字段/默认值/边界从当前实现提取，并至少和一笔有效请求核对；不要从上游宣传页直接复制未实现能力。
- 响应示例来自实际 NewAPI 公网返回或标成示意。确认顶层 ID、状态、文件 URL、错误和 usage 所属层。
- 价格与真实消费记录对账。尚未对账则清楚标“价格配置待验/usage 未对账”。
- 文档明确未验收项目。纯文本成功不能推导多模态、stream、callback、真实计费都已通过。

可参照：[[韭菜盒子文本模型API对外接入-2026-09-04]]、[[韭菜盒子图片模型API对外接入-2026-09-04]] 和各视频/音频接入文档。

## 6. 从本地到生产的验收闸门

| 闸门 | 检查 | 通过证据 |
| --- | --- | --- |
| A 上游合同 | 官方 URL、模型 ID、认证、请求/响应、价格 | 接入卡已填，未知限制已标出 |
| B 本地实现 | 注册表、适配器/插件、模型白名单和映射 | focused/针对性测试、NewAPI lint/Sandbox（适用时） |
| C NewAPI 配置 | 插件版本激活、渠道类型、Base URL、Key、模型、映射、价格 | 管理页/接口读回核对；不回显凭据正文 |
| D 路由 | 用授权低额度 token 请求一个公开模型名 | NewAPI 命中预期渠道/插件和上游模型 |
| E 完整任务 | 提交、轮询、终态、响应/素材下载 | 真实结果可读取；异步 ID 和终态正确；需要时验证 Range/HEAD |
| F 账单 | usage facts、价格表达式、用户余额变化 | 对一笔真实成功任务逐字段对账；失败路径核实是否退款 |
| G 对外文档 | 按 §5 编写并登记 Wiki 入口 | 样例与生产响应一致；未测范围明确标记 |
