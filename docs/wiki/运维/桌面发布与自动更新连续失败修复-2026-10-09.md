# 桌面发布与自动更新连续失败修复

## 现象与证据

用户发现 v2.2.23–v2.2.26 GitHub 发布均失败。线上 `/updates/updater.json` 实际仍为 v2.2.22。Apple 公证凭据在 GitHub Secrets 中存在；本机终端缺少同名环境变量不表示 GitHub 缺少凭据。

| 发布 | 实际失败阶段 | 日志证据 |
| --- | --- | --- |
| v2.2.23 | Windows 原生安装验收 | 三分钟截止时一个 SDK 文件尚为空，完整摘要不一致 |
| v2.2.24 | Windows 原生安装验收 | 报 `NSIS did not install 0 expected executable and runtime files`，再次读摘要时安装已完成 |
| v2.2.25 | 公网完整文件校验 | Arm 包校验通过，随后大文件下载 20 分钟超时，清单推广未执行 |
| v2.2.26 | 三平台前端构建 | `Unsupported DeepSeek Harness queue method layout`，尚未执行签名公证 |

运行编号分别为 37724921571、37732682521、37790610381、37911799408。

## v2.2.27 修复

1. Harness 准备脚本按依赖顺序建立 permission → updateQueue → cancelSession 方法。原顺序先引用尚不存在的方法，开发机已有补丁所以不能复现，全新 npm ci 的 CI 必然失败。
2. 公网校验分为 4 MB Range 请求，每个失败区间最多四次尝试；验证 206、准确 Content-Range 和字节长度，最终仍比较整个文件 SHA256。保留签名检查及同版本资产不可变约束。
3. Windows 官方安装验收允许十分钟；截止边界以最终差异快照判断，禁止零项差异报失败。不忽略空文件或真实摘要差异。
4. 隔离升级基线使用已接入 updater 的正式 v2.2.22，验收官方安装引擎 A→B。
5. 同步旧回归用例至已实施的模型可见性、图片端点、OSS 授权/直传及 630 秒图片请求合同；未修改业务产品行为。

## 后续操作

新版本使用新 tag，不移动失败的历史 tag。普通 tag 构建只发布候选与官网安装包；正式 OTA 需显式 `workflow_dispatch` 指定 `publish_tag`、三平台验证和 `promote_updater=true`。查看 GitHub 成功状态后仍要读取线上 updater.json，确认正式版本确已变化。
