# 服务器磁盘写满与数据库崩溃应急手册

> 首次事故：2026-10-26，约 30 分钟恢复。日常定时清理规则见 [[运维/服务器运维]]「每周自动清理与磁盘告警」。

## 1. 一眼认出

同时出现下面几条，基本就是磁盘满了：

| 现象 | 位置 |
| --- | --- |
| NewAPI 后台弹「数据库出错，请联系管理员」，登录不进去 | 浏览器 |
| 所有用户对话、生图同时失败（报 502 或数据库错误），和客户端版本无关 | App |
| 系统盘接近 100%，CPU 被打高（2026-10-26 那次是 86%） | 阿里云控制台「服务器概览」 |

**原因链**：磁盘满 → PostgreSQL 写检查点文件失败（`No space left on device`）→ 数据库每秒崩溃重启一次 → 系统崩溃报告程序 `apport` 跟着处理，CPU 被吃满 → NewAPI 连不上数据库，登录、令牌验证、扣费全部失败。

**关键点**：只要腾出空间，数据库会自己完成恢复，**不需要重装、不需要恢复备份**。

## 2. 抢修步骤（在服务器网页终端执行）

本机 Mac 连不上服务器 22 端口，用阿里云「远程连接」打开网页终端，逐段粘贴。

### 2.1 确认是磁盘满了

```bash
df -h /
docker logs --tail 20 postgres 2>&1 | grep -E 'No space|PANIC|recovery'
```

`Use%` 接近 100%，并看到 `No space left on device` 或 `PANIC`，就是这个问题。

### 2.2 先清最安全的（通常够数据库起来）

```bash
docker builder prune -af
docker image prune -f
journalctl --vacuum-size=200M
find /root/new-api-new/logs -type f -mtime +3 -delete
find /var/lib/docker/containers -name '*-json.log' -size +500M -exec truncate -s 0 {} \;
apt-get clean
df -h /
```

### 2.3 确认数据库与 NewAPI 恢复

```bash
docker start postgres 2>/dev/null; sleep 8
docker exec postgres pg_isready -U newapi
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000/api/status
```

看到 `accepting connections` 和 `200` 即恢复。然后登录 NewAPI 后台，用 App 生一张图、对话一句确认。

### 2.4 空间仍紧张时再清（2026-10-26 这一步腾出约 30G）

先找大头：

```bash
docker system df
du -xh --max-depth=2 /root /opt /var 2>/dev/null | sort -h | tail -25
find / -xdev -type f -size +1G -exec ls -lh {} \; 2>/dev/null
```

按下表处理：

| 占用 | 怎么清 | 说明 |
| --- | --- | --- |
| 没有任何容器使用的镜像 | `docker image prune -af` | 运行中和已停止容器（含画布回滚备份）的镜像都会保留 |
| `/root` 下部署留下的备份目录（含 `primary.dump` / `new-api.sql`） | 先新做一份备份（见下），再 `rm -rf` 旧目录 | 新备份失败就不要删旧的 |
| `/opt/updates` 旧安装包 | `bash /root/prune-updates.sh /opt/updates 3` | 脚本不会删清单在用的版本 |

新做一份数据库备份：

```bash
docker exec postgres pg_dump -U newapi -d new-api -Fc > /root/pg-backup-$(date +%Y%m%d-%H%M).dump && ls -lh /root/pg-backup-*.dump
```

## 3. 绝对不要做

- 不要删除 `/opt/new-api/postgres`（数据库真实数据目录）。
- 不要执行 `docker system prune --volumes`，也不要删除数据卷。
- 不要在数据库恢复前重启服务器或重建 postgres 容器；腾出空间后它会自己恢复。
- 不要直接复制正在运行的数据库目录当备份，要用 `pg_dump`。

## 4. 恢复后收尾

1. 在阿里云「快照」页创建快照（2026-10-26 那次命名为「数据库恢复后-20261026」）。快照由阿里云另行保存，不占服务器磁盘。
2. 确认定时器仍在：`systemctl list-timers 'jc-*'`。
3. 在 `log.md` 记录这次的占用来源和清理结果。

## 5. 预防

- 已装每周日 04:00 自动清理，以及磁盘 ≥85% 时自动清理加告警（飞书 Webhook 暂未接，提醒只写进系统日志 `journalctl -t jc-disk-alert`）。
- 2026-10-26 那次的主要占用：无用 Docker 镜像约 24G、构建缓存约 7.7G、部署临时备份约 8G、旧安装包约 7G。数据库本身约 4.5G，不是它在涨。
- 升级 NewAPI、改渠道等大改之前，先手动打一个阿里云快照。
- 部署脚本会在 `/root` 留下整库备份（每份 1G 以上）。定时清理会删掉超过 14 天的；短期内连续部署多次时，要留意磁盘余量。
