# 适配器收编任务插件总方案（Wave 计划，2026-10-01）

> 制定：2026-10-01 · 状态：**已决策，待实施** · 上游：NewAPI `v1.0.0-rc.40`（插件子系统已就位）
>
> 一句话：把「每个转售商/厂商线路一个独立 Python 服务」的架构，改成「NewAPI 里一个单文件插件」；**能直接用官方插件的绝不自己写**，执行类和协议不覆盖的适配器**不下岗**。

相关：[[运维/本机ComfyUI接入NewAPI任务插件通道SDD-2026-10-01]]（Wave 0 的详细方案）、[[运维/本机ComfyUI模型对外接入-2026-09-26]]（现行链路）。

---

## 1. 决策（用户 2026-10-01 授权直接判断）

1. **不做「一次性全部下岗」**。每波都必须端到端验收（真出片 + 核计费 + 成片下载 + Range）之后，才允许动下一个。
2. **先试「官方插件直用」，再考虑自写**。凡是上游就是官方厂商格式（或其兼容实现）的线路，优先用 NewAPI 自带插件 + 新渠道，**零代码**。
3. **先并存，后下线**。新通道验收通过前，旧适配器与旧渠道一律不动；下线单独提交并跑回归。
4. **五个适配器永不下岗**（理由见 §6）：`comfy-adapter`、`dola-seedance-adapter`、`rh-adapter`、`seed-audio-adapter`、`attachment-processor` / `document-converter`。
5. 仓库里的适配器代码**保留为「翻译逻辑的事实源」**，即使服务下线也不立刻删代码；下线只删部署（Docker/compose/端口/计划任务），代码删除另行评估。

## 3. 铁律（每波都适用）

1. **一波一验收**：真出片一笔 + 核对用量与扣费 + 成片可下载 + Range 206。缺一项不算通过。
2. **先并存**：新渠道与旧渠道同时存在，面板切过去试；旧适配器保持在线。
3. **不下线不删码**：验收通过后才停旧服务；代码删除另开提交，且要先确认无调用者（脚本 / compose / 文档 / 监控）。
4. **不写「已通过」**：没有真实平台验证的，一律写「待验」。
5. **凭据只进渠道**：插件的源码不含密钥（宿主从渠道取 `ctx.apiKey` / `meta.auth`），仓库与插件文件里不得出现 key。

**与适配器的三处有意差异**

**验收（真跑一笔，缺一项不算通过）**

| 项 | 判定 | 通过标准 |
|---|---|---|
| 提交 | 面板提交一笔旧版 3 秒 | 返回 `task_...` 公开任务号，不报 400 |

**已知边界（不算 bug，写下来避免下次误判）**

- 参考素材透传的是 App 换好的公网 URL，而 Worker KV 的 `expirationTtl` 是 **15 分钟**：排队超过 15 分钟的任务可能取不到素材。

**判定结论（推翻了 §2 的原假设）**

原假设「疑似 Ark 兼容 → 可能零代码用官方 `doubao` 插件」**不成立**。实测上游是 `https://43.254.166.145/api/v1/videos`（自家形状，不是 `/api/v3/contents/generations/tasks`），官方插件路径逐字对不上，所以只能自写。

**为什么适配器必须留着（关键约束）**

上游创建接口**只吃 multipart**，规格原文：

> 创建接口只使用 `multipart/form-data`。即使没有图片，也应使用 multipart，不能提交 JSON。
> 图片必须上传实际文件，不能用图片 URL 或 Base64 文本代替；文件字段名必须为 `images[]`。

插件没有 `fetch` / 文件系统，拿不到图片字节 → **物理上做不了**。所以本波与 Wave 0 同构：**插件是代理，适配器是执行器** —— 适配器照样下载参考图、拼 multipart、转上游。

> 补记：宿主 v1 契约里确实有 `bodyType: "multipart"` + `parts[].fileRef`，但 `fileRef` 指的是**客户端 multipart 上传**进来的文件（`ctx.files`）。我们的 App 走 `assetFlow: newapi-upload` 发的是 URL，`ctx.files` 为空 —— 这条能力本波用不上。将来若把 App 改成直传 multipart 能再收编一层，但那是改 App，违背「App 与创作面板不改」。

**本波真正修掉的 Bug**

面板提交时顶层同时发 `ratio` 与 `aspect_ratio`（`buildDirectVideoBody` 通用尾段，`creationMediaRuntime.ts` 第 955-956 行），两者都**不在** `TaskSubmitReq` 白名单里 → 适配器永远落回自己的 `16:9` 兜底：**面板选 9:16 出 16:9，一直是这条**，与 Wave 0 同一个根因。插件通道里 body 由 `decodeRequest` 决定，`ratio` 原样到达适配器。

**你要做的（管理员页）**

1. 上传 `newapi-plugins/dola.plugin.js`（key `dola`，version `0.1.0`）并激活。
2. 新建 **type 61「Task Plugin」渠道**：plugin key `dola`、Base URL `http://dola-seedance-adapter:8789`（插件 `meta.baseUrl` 同值；适配器容器在 `new-api-new_new-api-network` 里、不映射宿主端口，所以只能走服务名）、密钥填 **Dola 用户令牌**（适配器把收到的 Bearer 原样转给上游，所以渠道密钥就是 Dola 令牌）。
3. 模型填 `dola-seedance2.5`（面板发的就是裸名，**不需要**渠道模型映射）。
4. 定价：任务用量模式，`seconds` 单价 **0.2**（等价表达式 `u("seconds") * 0.2`）→ 单笔 30 秒 = 6 元。**上线前先看一眼旧渠道这笔的实收**：旧渠道若是固定 6 元/次，两者一致；不一致就以旧渠道为准调。

**验收（真跑一笔，缺一项不算通过）**

| 项 | 判定 | 通过标准 |
|---|---|---|
| **画幅无损** | 面板提交一笔 9:16 | 成片是**竖屏**。旧渠道同参数恒出 16:9 横屏，这就是对照 |
| 提交 | 看提交响应 | 返回 `task_...` 公开任务号、状态 `queued` |
| 轮询收敛 | 面板进度 | 收敛到 `completed`。上游 `processing` 时 `query_notice` 可能非空 —— **那不是失败** |
| 成片 | 面板能播放 | `video_url` 是上游公开免签地址（规格原文：不要把 Bearer 附到视频地址上）。**上游不支持 Range，本波不要求 206** |

| 失败路径 | 故意给 1 张不可达参考图 | 适配器提交期回 400（不建任务、不扣费），面板能看到原因 |
| 参考图 | 面板选 2 张图 | 上游收到的 `images[]` 是两张 |
| **张数上限** | 面板选 10 张图 | 适配器回 400 `at most 9 images`。面板注册表写的是 30 张、对外文档也写「最多 30 张」—— 三处不一致，见 §7 |

**已知边界（不算 bug，写下来避免下次误判）**

- 适配器**无状态**：查询直接透上游，所以适配器重启不影响轮询 —— 比 Wave 0 的 comfy 干净（那边任务表在内存）。
- 上游 `url` 不承诺永久有效（规格原文），面板要及时下载。
- 适配器每次请求自己 `uuid4()` 生成 `Idempotency-Key`，入参里的幂等键被忽略 → 宿主重试提交会在上游建第二个任务、**再扣一次**。见 §7。

**先纠正原方案的两处错判**

1. **不存在 ak|sk / JWT / HMAC**。`rh-adapter` 全仓零命中，上游鉴权就是 `Authorization: Bearer <key>` + body 里 `apikey`（小写，标准链路）/ `apiKey`（驼峰，AI App）。所以**不需要** `meta.auth`，也用不上 `utils.jwtSignHS256`。
2. **不只是「一个上游」**。适配器用**自己环境变量里的** `RUNNINGHUB_API_KEY`，根本不看调用方 Authorization（所以渠道密钥填什么都行，但适配器必须配好 key）；`site: global` 的模型走 `.ai` 域并要求**另一把** key（`RUNNINGHUB_GLOBAL_API_KEY`）。

**范围**

搬的是 **35 个模型**：7 图 + 24 标准视频/3D + **4 个 AI App 视频**（`rh-aiapp` / `rh-aiapp-director` / `rh-aiapp-digital-human` / `rh-aiapp-fast-digital-human`），走 `openai_video` + `openai_image` 双协议。

> **更正（同日）**：初版把 AI App 排除在外，理由是「换 `fileName` 令牌要下载再上传，插件做不到」。**那个理由不成立** —— 插件走的是**代理**（插件 → 适配器），换令牌本来就发生在适配器内部，插件不需要下载能力。当时把「适配器要干的活」误当成了「插件的阻断」。AI App 只需：① `render` 把 `ai_app` 透出去（面板据此带 `?ai_app=true` 直连适配器）；② 查询口相应地改走 `GET /tasks/{id}?ai_app=true`（标准口查不到 aiapp 任务）。

**不收编两类**（不进 `meta.models`，继续留在旧 Custom Channel）：

| 不收 | 为什么 |
|---|---|
| 音频（`rh-suno-*` / `rh-speech-*` / `rh-music` / `rh-voice-clone` / `rh-aiapp-voice-clone` / `rh-aiapp-voice-design`） | 这些模型的 App endpoint 是 `/v1/audio/speech`，而宿主只有 `openai_responses` / `openai_video` / `openai_image`，**没有音频协议** |
| `z-image-turbo` | 这个模型名同时属于本机 comfy 条目（`local-comfy/z-image-turbo`），收进 RH 插件会**截胡**那条链路 |

**本波修掉的 Bug**

面板提交 RH 时把画幅/分辨率放顶层 `aspectRatio` / `aspect_ratio` / `ratio` / `resolution`、把模型独有字段放 `extra_fields` —— 都在 `TaskSubmitReq` 白名单之外，整段被丢，适配器只能吃自己 capabilities 的默认值。（这也解释了当年为什么要给 AI App 加 `extra_fields` + `metadata.rh_aiapp` 双重兜底：那时候就在跟同一个问题打交道。）插件通道里 body 由 `decodeRequest` 决定，原样到达适配器。

**一条 RH 专属设计（容易踩）**

面板**直连适配器轮询**：`extractTaskId` 优先读 `rh_task_id`，注释写明「永远直连 rh-adapter 轮询，NewAPI 只承担提交+计费」。而宿主会删掉 render 输出里的 legacy `task_id` —— 所以插件把适配器任务号放在 **`rh_task_id`** 上，面板的轮询链路一字不改。宿主自己另跑一份轮询（`GET /v1/videos/{taskId}`，适配器专为 NewAPI 准备的口）用于任务行与结算。

**你要做的（管理员页）**

1. 上传 `newapi-plugins/rh.plugin.js`（key `rh`，version `0.1.0`）并激活。
2. 新建 **type 61「Task Plugin」渠道**：plugin key `rh`、Base URL `http://rh-adapter:8789`、密钥随便填（适配器不读）、模型填上面 35 个（面板发的裸名，含 4 个 `rh-aiapp*` 视频模型，**不需要**模型映射）。
3. 定价：任务用量模式，**按次**（`count`），每个模型单独设价 —— 与旧 Custom Channel 的「按次计费」保持一致（面板价签就是这个）。
4. **改旧 Custom Channel 的模型列表**：把被接管的 35 个删掉，只留**音频**（否则两个渠道同时声明同名模型就是负载均衡，任务会随机落到两边）。

**验收（真跑一笔，缺一项不算通过）**

| 项 | 判定 | 通过标准 |
|---|---|---|
| **字段无损** | 提交一笔 `rh-seedance2-image`，选 9:16 + 1080p | 适配器收到的 `aspectRatio=9:16`、`resolution=1080p`；成片竖屏（旧渠道同参数恒出 capabilities 默认值） |
| `rh_task_id` | 看提交响应 | 带 `rh_task_id`（RH 数字号，global 站点带 `global:` 前缀），面板据此走 `/rh/tasks/{id}` 直连适配器 |
| 轮询不变 | 面板进度 | 沿用旧链路收敛到 `completed`（**这条不改就是成功**） |
| 成片 | 面板能播 | `url` 是 RH 公有 COS 直链（24 小时有效、无需鉴权） |
| 计费 | 用量日志 `usage_facts.calls` 与实扣 | `1 × 单价`，与旧渠道同模型实收一致 |
| 失败路径 | 故意给坏参数 / 不存在的 webappId | 任务 `failed` 且原因可见，额度退回 |
| **未接管的仍可用** | 提交一笔 `rh-aiapp` 与一笔音频 | 走旧 Custom Channel 正常出片（证明范围收窄没误伤） |

**已知边界**

- `rh_task_id` 会不会被宿主改写**未验**（README 说「known private task IDs are replaced before rendering」）。若被改写，面板会退化成走 NewAPI 轮询 —— 这是本波唯一的未验风险，见 §7。
- AI App 的**节点发现不受影响**：它是 App 自己调 `GET /api/runninghub/app-info`（仍是适配器的口），与提交走哪个渠道无关。
- 旧渠道**不能下线**：音频、RH 原生代理（`RH_CLI fork` 的 `RH_API_HOST`）、节点发现口都还在它身上。
- `RH_CUSTOM_AI_APPS` 里自定义注册的 AI App 模型 id 不在插件列表里，要收编得先把 id 加进 `meta.models` 再重传插件。

## 6. 不下岗的五个（明确写死，避免以后误删）

- **`comfy-adapter`**：它是**执行器**，不是翻译器。模板渲染、ComfyUI 提交、Topaz 放大、成片存储与 `/content` 分发都在它里面。插件没有网络/文件系统能力，装不下这些。收编只到「插件代理它」这一层。
- **`dola-seedance-adapter`**：也是**执行器**。上游创建接口只吃 `multipart/form-data`，规格原文写死「图片必须上传实际文件，不能用图片 URL 或 Base64 文本代替」；插件没有 `fetch`/`fs`，拿不到图片字节，**物理上做不到**。插件只把 `ratio` 送到它手上。
- **`rh-adapter`**：**部分收编** —— 35 个模型已移到插件（含 AI App），但适配器必须留着：① **AI App 的媒体要换成 RH `fileName` 令牌**（下载再上传）—— 这正是 aiapp 走「代理」而不是直连上游的原因；② 音频链路没有宿主协议；③ 节点发现口（`GET /api/runninghub/app-info`，App 自己调）；④ RH 原生 API 代理（`RH_CLI fork` 的 `RH_API_HOST`）。删了这四件事会一起没。
- **`seed-audio-adapter`**：上游是火山 TTS，走 `/v1/audio/speech`；官方插件宿主协议目前只有 `openai_responses` / `openai_video` / `openai_image`，**没有音频**。要动它，必须先确认官方有音频协议（`docs/plugin-api/v1.md` 的协议表）。
- **`attachment-processor` / `document-converter`**：文件与文档转换，不属于生成任务，插件机制不覆盖。

## 7. 风险与未决

| 项 | 说明 | 处置 |
|---|---|---|
| 插件契约未冻结 | 官方 README 写 "currently unreleased" | 每波都保留旧渠道回滚；升级 NewAPI 前先跑 Sandbox 干跑 |
| A 类判定依赖真实渠道 | 官方插件的模型清单/形状是否吃中转商，只有真跑才知道 | Wave 1 试验卡先花 10 分钟判定，失败即退 B 类。**Wave 2 已否证一例**：dola 的裸 IP 中转商不是 Ark 形状，官方插件用不了 |
| 计费口径会变 | 从 `tier("per_second", param("duration") * 0.2)` 变成用量事实表达式（`u("key")`） | 每个新渠道单独核对用量日志与实扣，逐波验收 |
| **dola 重试会重复扣上游积分** | 适配器每次请求自己 `uuid4()` 生成 `Idempotency-Key`，**入参里的键被忽略**；宿主重试提交 = 上游建第二个任务、再扣一次积分 | 修法很小（适配器改成读入参 `Idempotency-Key`，缺省再生成），但会动现行 type 1 渠道的行为 → **单独提交、单独验证**，不在本波顺手改 |
| **dola 参考图张数三处不一致** | 上游规格与适配器都是 **9 张**（`MAX_IMAGES = 9`）；而面板注册表写 `max: 30`，对外文档 [[运维/韭菜盒子Seedance2.5中转接入]] 也写「最多 30 张」 | 选 10 张会吃适配器 400。改注册表/对外文档属 App 侧改动，未做，先记下来 |
| dola 成片地址会过期 | 上游 `url` 不承诺永久有效（规格原文） | 面板要及时下载；将来若想让成片走宿主代理，再补 `listArtifacts` + `buildContentRequest` 两个 hook（现在有意不导出，见 §5） |
| **rh 的 `rh_task_id` 可能被宿主改写** | README：宿主要在 render 前替换「known private task IDs」，而 RH 面板恰恰靠这个号直连适配器轮询 | 验收单独盯这一条；若被改写，退路是让面板改走 NewAPI 轮询（需先确认宿主对**图片**任务的 `/v1/videos/{task_xxx}` 可达），或用 `meta.routes` 暴露 RH 原生路径 |
| **rh 旧渠道不能整体下线** | 音频、RH 原生代理、节点发现口都还在它身上；两个渠道同时声明同名模型会变成负载均衡 | 建新渠道时**必须**把旧渠道模型列表里被接管的 35 个删掉 |
| rh 双 key | `site: global` 的模型要 `RUNNINGHUB_GLOBAL_API_KEY`，适配器缺它就会用错 key（而插件侧看不出来） | 迁移前确认适配器环境变量两把 key 都在 |
| 工作量 | 6 个自写插件 ≈ 每个 100~300 行（把现有适配器的翻译逻辑搬进 JS） | 分波推进，不追求一次性完成 |
| 下线顺序 | 先并存后下线，删服务单独提交 | 见 §3 铁律 |
