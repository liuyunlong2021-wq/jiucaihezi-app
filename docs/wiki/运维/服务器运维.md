### 降配判断

停用 8091 后，机器可以降配，但不建议降到 1 GiB 内存。

| 规格 | 判断 |
|------|------|
| 2C / 1G / 30G | 不建议。Docker + NewAPI + Postgres + Redis + adapters 余量太小，容易 OOM；30G 盘也刚好贴近当前占用。 |
| 2C / 2G / 40G | 最低可用，适合极限省钱；需要接受偶发流量时余量偏紧。 |
| 2C / 4G / 50G | 推荐。价格仍低，内存和磁盘余量更稳。 |
| 4C / 8G / 70G | 当前规格，停用 8091 后偏富余。 |

迁移前必须先备份数据库和配置。不要直接重装旧服务器。

## 4. 常用操作

> 以下命令全部从 root 提示符直接粘贴运行，无需登录数据库。

### 查询渠道状态

```bash
# 所有渠道概览
docker exec $(docker ps -q -f name=postgres) psql -U newapi -d new-api -c "SELECT id, name, status, type, base_url, \"group\", substring(models, 1, 200) AS models_preview FROM channels ORDER BY id;"
```

status: `1`=启用, `2`=禁用, `3`=自动禁用

```bash
# 查单个渠道完整配置（替换 id）
docker exec $(docker ps -q -f name=postgres) psql -U newapi -d new-api -c "SELECT id, name, status, auto_ban, model_mapping, setting FROM channels WHERE id = 16;"
```

```bash
# 查模型属于哪些渠道（替换模型名）
docker exec $(docker ps -q -f name=postgres) psql -U newapi -d new-api -c "SELECT id, name, status FROM channels WHERE models LIKE '%gpt-image%' ORDER BY id;"
```

### 渠道内部配置说明

`setting` 是 JSON 字段，关键字段：

| 字段 | 说明 |
|------|------|
| `auto_ban` | `1`=错误率高时 NewAPI 自动禁用该渠道 |
| `pass_through_body_enabled` | 是否透传请求体给上游 |
| `proxy` | 代理地址（空=直连） |
| `model_mapping` | 模型名映射（空=透传，不重命名） |

### 查询任务日志

```bash
# 查某渠道最近任务（替换 channel_id）
docker exec $(docker ps -q -f name=postgres) psql -U newapi -d new-api -c "SELECT task_id, status, submit_time, start_time, finish_time, fail_reason FROM tasks WHERE channel_id = 16 ORDER BY submit_time DESC LIMIT 20;"
```

```bash
# 查任务耗时（Unix 时间戳，秒）
docker exec $(docker ps -q -f name=postgres) psql -U newapi -d new-api -c "SELECT task_id, status, (finish_time - submit_time) AS duration_sec, fail_reason FROM tasks WHERE channel_id = 16 ORDER BY submit_time DESC LIMIT 20;"
```

### 迁移前完整备份

迁移逻辑：旧服务器导出数据库和配置 → 复制到新服务器 → 新服务器恢复 → 测试通过后切域名。不要把“新服务器”理解成自动继承旧服务器；两台机器是独立电脑，必须手动搬关键数据。

最重要资产：

```text
Postgres 数据库：NewAPI 用户、Token、余额、渠道、调用记录。
配置文件：docker-compose.yml、Nginx、adapter .env。
旧服务器：迁移后至少保留 3-7 天，不要立刻释放。
```

在旧服务器执行：

```bash
mkdir -p /root/migration-backup-$(date +%Y%m%d)
BACKUP_DIR=/root/migration-backup-$(date +%Y%m%d)

docker exec postgres pg_dump -U newapi -d new-api > "$BACKUP_DIR/new-api.sql"

cp /root/new-api-new/docker-compose.yml "$BACKUP_DIR/"
cp /etc/nginx/sites-enabled/api.jiucaihezi.studio.conf "$BACKUP_DIR/"
cp -a /opt/rh-adapter "$BACKUP_DIR/" 2>/dev/null || true
cp -a /opt/creation-models "$BACKUP_DIR/" 2>/dev/null || true
cp -a /opt/jiucai-adapter "$BACKUP_DIR/" 2>/dev/null || true

tar -czf /root/jiucai-migration-backup-$(date +%Y%m%d).tar.gz -C /root "$(basename "$BACKUP_DIR")"

ls -lh /root/jiucai-migration-backup-*.tar.gz
```

备份包可以先下载到本机 Mac，再上传到新服务器；也可以用 `scp` 从旧服务器直接传到新服务器。推荐至少保留一份本地备份。

### Web 端 CORS 最小影响修复（优先用 Nginx，不重启 NewAPI）

适用场景：`https://jiucaihezi.com` 的静态 Web 端调用 `https://api.jiucaihezi.studio/v1/chat/completions` 报 `Failed to fetch`，且 `OPTIONS` 预检缺少 `Access-Control-Allow-Origin`。

优先策略：

```text
先用 Nginx 层补 CORS，然后 nginx reload。
不要为了单纯 CORS 先替换 NewAPI 二进制。
```

原因：

- Nginx reload 基本不中断现有服务。
- NewAPI 是核心网关，替换或重启会短暂影响后台、聊天、创作接口。
- 这只是 Web 跨域授权问题，不需要先动数据库或渠道配置。

操作流程：

```bash
ssh root@47.82.86.196

# 1. 备份当前 Nginx 配置
mkdir -p /etc/nginx/backups
cp /etc/nginx/sites-enabled/api.jiucaihezi.studio.conf \
  /etc/nginx/backups/api.jiucaihezi.studio.conf.$(date +%Y%m%d-%H%M%S)

# 2. 编辑 api.jiucaihezi.studio 的 /v1/ 或 /v1/chat/completions 代理 location
nano /etc/nginx/sites-enabled/api.jiucaihezi.studio.conf
```

### RunningHub Web CORS（2026-07-20）

适用场景：APP 调用 RunningHub 正常，但 Web 选择 AI 应用时，浏览器对 `/api/runninghub/` 的请求报 CORS 或预检失败。

根因不是 RunningHub 任务本身失败，而是桌面运行时不受浏览器 CORS 限制，Web 跨域请求则必须先通过 `OPTIONS`。当前生产 Nginx 已在 `/api/runninghub/` location 内处理：

- 允许 `https://jiucaihezi.studio`。
- 允许 `https://<部署名>.jiucaihezi.pages.dev` 预览地址。
- `OPTIONS` 返回 204，并允许 `Authorization`、`Content-Type`、`x-api-key` 和 `X-API-Key`。
- 真实响应回写匹配的 `Access-Control-Allow-Origin` 和 `Vary: Origin`。
- 不使用 `*`，也不允许任意来源。

修改配置前仍须备份 `/etc/nginx/sites-enabled/api.jiucaihezi.studio.conf`；修改后执行 `nginx -t && nginx -s reload`。验证：

```bash
TAG="jc-cors-$(date +%s)"

curl -i -X OPTIONS \
  "https://api.jiucaihezi.studio/api/runninghub/app-info?webappId=<应用ID>&tag=$TAG" \
  -H 'Origin: https://jiucaihezi.studio' \
  -H 'Access-Control-Request-Method: GET' \
  -H 'Access-Control-Request-Headers: authorization'

grep "$TAG" /var/log/nginx/access.log | tail -n 10
```

成功标准：公网响应为 `HTTP/2 204`，`Access-Control-Allow-Origin` 等于请求站点，且本机 access log 出现相同 tag。2026-07-20 已按此标准验证通过。完整前端根因见 [[排障/Web创作面板控制台红字排障-2026-07-20]]。

## 5. 已知问题 & 解决方案

### NewAPI `progress` 字段解析 bug（历史问题）

**现象**: Seedance 视频提交返回 500，日志报 `cannot unmarshal object into Go struct field responseTask.progress of type int`

**原因**: Seedance 上游 `progress` 返回 `{"message": "..."}` 对象，NewAPI 期望 int

**当前策略**: 创作面板主链路不再依赖 Seedance 直连代理；模型是否展示和是否允许执行由 `/api/creation/models` 结合 NewAPI 渠道状态决定。`/api/seedance/` 保留为历史/备用代理，若后续重新启用 Seedance，优先在 NewAPI/RH 适配链路里闭环。

### NewAPI 模型名自动转换

**现象**: 请求 `veo3.1-fast` 时，NewAPI 内部转换为 `veo_3_1-fast`（点号变下划线），导致找不到渠道

**解决**: 渠道 models 列表中两种写法都要加上，或用模型重定向

### 渠道自动禁用

**现象**: 渠道连续报错后被自动禁用 (status=3)

**解决**: 先查看 NewAPI 渠道错误日志和上游余额/密钥，再执行 `UPDATE channels SET status = 1 WHERE id = <id>;`。创作面板会通过 `/api/creation/models` 把自动禁用的模型标记为不可用。

### 创作面板点击后转圈消失

**现象**: 用户点击生成，任务短暂转圈后没有结果，也没有明确失败反馈。

**排查顺序**:

## 7. 分组 & 计费

- **AutoGroup**: `["0.5","1","1.2","1.5","2"]` — Token group 为空时自动匹配

- 计费公式: `费用 = 分组倍率 × 模型倍率 × (输入tokens × 基准单价 + 输出tokens × 基准单价 × 补全倍率)`
- 模型如无 `ModelRatio` 或 `ModelPrice` 配置，`/v1/models` 接口不会返回该模型

## 9. RunningHub 适配器 (rh-adapter) — 2026-06-03 更新

> **Seedance 2.0 模型注册参考**: `docs/notes/RH-模型注册手册.md`

### 架构

```
提交计费:
Studio → NewAPI /v1/* → http://rh-adapter:8789 → RH 原生 API

轮询:
Studio → Nginx /rh/tasks/{task_id} → http://172.17.0.1:8789/tasks/{task_id}
```

适配器是 Python FastAPI Docker 服务，将标准 OpenAI 格式请求翻译为 RunningHub 原生 API 调用。POST 提交走 NewAPI 渠道并产生一次计费；GET 轮询走 Nginx `/rh/tasks/` 直连 adapter，避免重复计费。NewAPI 负责用户鉴权和计费，rh-adapter 只在 Docker/内网可达，不额外增加 adapter 鉴权。

### 模型广场（NewAPI 软删除表）

表 `models`，唯一约束 `uk_model_name_delete_at (model_name, deleted_at)`。

```bash
# 查看
docker exec $(docker ps -q -f name=postgres) psql -U newapi -d new-api -c "SELECT model_name, description FROM models WHERE deleted_at IS NULL ORDER BY model_name;"

# 批量更新（base64 编码，避免 SSH heredoc 截断大 SQL）
echo '<base64>' | base64 -d | docker exec -i $(docker ps -q -f name=postgres) psql -U newapi -d new-api

# 重启刷新缓存
cd /root/new-api-new && docker compose restart new-api
```

> 本地生成 SQL → base64 编码 → 粘贴到服务器 echo pipe。heredoc 大文本经 SSH 终端会随机截断，base64 彻底解决。
