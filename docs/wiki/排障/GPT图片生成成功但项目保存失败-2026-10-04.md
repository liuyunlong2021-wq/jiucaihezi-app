# GPT 图片生成成功但项目保存失败（2026-10-04）

## 现象与证据

- 用户截图中，NewAPI 的 `POST /v1/images/generations` 消耗日志显示请求完成；Desktop 任务历史显示生成成功，但保存阶段报 `HTTP 下载失败: error sending request for url (https://relay.xiaoyiapi.xyz/v1/images/public/...)`。另有一条 `HTTP 400 bad_request` 是独立的生成失败，不属于这批已生成图片的保存问题。
- 2026-10-04 从当前开发机对截图中一条结果链接做 `HEAD` 和 `GET`：均为 HTTP 200，`GET` 返回约 2.1 MB `image/png`。这证明该条图片当时仍可取回；不能由此判定报障用户机器的 DNS、TLS 或代理具体哪一环失败。
- `creationMediaPlan.ts` 把 GPT Image 2 系列 `response_format` 固定为 `url`；`extractMediaUrl()` 在响应同时有 `url` 和 `b64_json` 时也先取 URL。于是 Desktop 必须再直接连接中转域名，连接失败便无法保存到本地项目。现行 [[运维/小易图片模型接口与NewAPI接入-2026-09-04]] 已声明该同步图片接口支持 `b64_json`，客户端须兼容两种响应。

## 修复

- GPT Image 2 系列同步生图和编辑请求改为 `response_format=b64_json`；其它图片模型继续使用原格式。
- 同一图片条目同时返回 URL 与 Base64 时优先取 Base64，复用现有项目文件写入链路；只返回 URL 时仍沿用原下载链路。
- 既有失败任务只有原始结果 URL，无法从历史记录补出图片字节。链接仍有效时可复制链接用浏览器保存，或在客户端能连通中转域名后点“保存到项目”；不需重新生成。若链接已失效，现有同步接口没有按任务 ID 回收图片的能力。

## 验证边界

- 先写红测，确认旧版确实提交 `url` 且优先选择 URL；修复后 GPT 路由、运行时和媒体任务 Store 定向测试通过。
- `vue-tsc -b` 通过；完整 focused 为 `1781/1782`，唯一失败是已有的文件树菜单断言仍未列入“新建窗口”，`HEAD` 版本源码与测试已如此。本轮不修改该无关断言。
- 未提交真实付费生图，也未在报障用户的 Desktop 环境中验收更新版落盘；本机公共链接成功不等于用户侧网络故障已恢复。
