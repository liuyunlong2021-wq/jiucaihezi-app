# 小易 GPT 图片多参考图与账号池失败

> 排障日期：2026-08-14
> 当前状态：适配器和模型可用性服务生产部署成功；官方渠道已真实成功；小易其它账号池存在间歇性不可用。

## 一、问题范围

创作面板通过独立 `xiaoyi-image-adapter` 调用小易 GPT 图片渠道后，出现以下不同结果：

- `gpt-image-2-1k` 真实生成成功。
- `gpt-image-2-低质量` 出现 `fetch failed`。
- `gpt-image-2-中质量` 和 `gpt-image-2-vip` 的 2K 任务出现 `No available 2K image accounts`。
- 多个相同参考图任务连续提交时，一个任务长时间 `processing`，后续任务又出现 `No available 1K image accounts` 或 `No available 2K image accounts`。

这些错误不是同一个根因，必须按“模型路由、分辨率账号池、请求类型、参考图数量”分别判断。

## 二、已经成功的部分

### 2.1 生产适配器已部署

生产容器构建和启动成功，容器内 `/health` 返回 `status=ok`，并列出七个公开模型：

- `gpt-image-2-1k`
- `gpt-image-2-低质量`
- `gpt-image-2-中质量`
- `gpt-image-2-vip`
- `gpt-image-2-官方`
- `gemini-3-pro-image-preview`
- `gemini-3.1-flash-image-preview`

### 2.2 NewAPI 路由和模型映射已命中预期渠道

生产 `tasks` 与 `channels` 查询确认：

| 请求模型 | 渠道 | 上游模型 | 结果 |
|---|---:|---|---|
| `gpt-image-2-1k` | 88 | `gpt-image-2` | `SUCCESS` |
| `gpt-image-2-低质量` | 91 | `gpt-image-2` | `FAILURE: fetch failed` |
| `gpt-image-2-中质量` | 92 | `gpt-image-2` | `FAILURE: No available 2K image accounts` |
| `gpt-image-2-vip` | 115 | `gpt-image-2-vip` | `FAILURE: No available 2K image accounts` |

这证明 NewAPI 没有把中质量或 VIP 请求错误送进 1K 渠道，前三个别名和 VIP canonical 模型也没有串线。

### 2.3 三参考图异步协议被小易接受

绕过 App、NewAPI 和适配器后，服务器直接向小易提交三张参考图：

```text
POST https://image.xiaoyiapi.xyz/v1/images/edits/async
multipart/form-data
model=gpt-image-2-vip
size=2048x1152
image=<三个重复的文件字段>
```

小易返回 `task_id` 和 `status=running`，随后轮询才返回 `No available 2K image accounts`。因此三文件 multipart、鉴权、VIP 模型名、异步提交和同 Key 轮询均已被上游接受；失败发生在小易内部选择 2K 图片账号之后，而不是文件上传阶段。

### 2.4 此前等待中的三参考图任务后来成功

同日 19:44，此前长时间等待的三参考图任务最终成功返回，并由 App 保存到项目 `.raw/jc-media/图片/`。这补齐了 App、NewAPI、适配器、小易异步编辑、轮询和项目落盘的端到端证据。

因此 `No available 1K/2K image accounts` 不能再表述为对应能力永久不可用；结合后来成功结果，应判定为小易账号池容量或可用性间歇波动。适配器主链路没有协议性故障。

## 三、最终确认的协议事实

### 3.1 1K、2K、4K 不是 GPT 上游模型名

GPT 上游真实模型名是 `gpt-image-2` 或 `gpt-image-2-vip`。App 的 1K、2K、4K 是用户分辨率档位，最终转换成精确 `size`：

| 档位与比例 | `size` 示例 |
|---|---|
| 1K 16:9 | `1536x1024` |
| 2K 16:9 | `2048x1152` |
| 2K 9:16 | `1152x2048` |
| 4K 16:9 | `3840x2160` |
| 4K 9:16 | `2160x3840` |

小易文档中的 GPT 示例也使用 `model=gpt-image-2` 和像素 `size`。`quality=1k/2k` 是 Gemini OpenAI 兼容转换规则，不是 GPT 模型名。

### 3.2 文生图与图片编辑不是同一种请求

- 无参考图：`POST /v1/images/generations/async`
- 有参考图：`POST /v1/images/edits/async`

用户提供的成功样例是 `gpt-image-2-vip`、`2160x3840`，只能证明 4K 竖图结果成功，不能证明 2K 三参考图编辑可用。

### 3.3 图片编辑使用文件，不直接使用 URL 字符串

小易公开合同要求 `multipart/form-data` 的 `image` 文件字段。公开 URL 可以先在服务器下载，再作为文件上传；不能把 URL 字符串直接当成已确认支持的 `image` 文件合同。

## 四、参考图与画布标记结论

- 画布上的编号、文字、箭头和笔迹是独立画布节点，不会被烘焙进原始参考图，也不会作为媒体资产上传。
- 提交时只读取被选中图片对应的原始媒体文件；编号标记本身没有媒体资产 ID，会被跳过。
- 因此红色 `1/2/3/4` 不是本次生成失败原因。
- 但编号也不会控制上传顺序。当前图片按画布纵坐标、再按横坐标排序；手工编号与实际参考图顺序可能不一致，这是语义准确性风险，不是账号池失败根因。
- 单张超过 20 MB、总计超过 64 MB 或超过 8 张会在本方边界明确拒绝；本轮任务已经取得小易 `task_id`，不属于这些本地上传限制。

## 五、失败经验与错误判读

| 错误或现象 | 已确认含义 | 不应误判为 |
|---|---|---|
| `No available channel for model ... under group ...` | 小易 Key 所属分组没有该模型的可用渠道，或模型名与该分组不匹配 | App 尺寸映射错误 |
| `No available 1K/2K image accounts` | 小易已识别分辨率，但对应账号池没有可分配账号，可能是失效、占用或容量不足 | 参考图编号导致失败 |
| `fetch failed` | 上游执行或取回阶段的网络/账号故障；仅凭该文本不能继续细分 | NewAPI 一定选错渠道 |
| 提交先返回 `running`，随后失败 | 异步提交只代表任务已创建，实际渠道或账号选择可能在后台发生 | `running` 等于开始生成成功 |
| 一个任务处理 300 秒，后续立即无账号 | 长任务可能占住有限账号槽位，连续并发会放大账号池不足 | 异步接口天然拥有无限并发 |

## 六、直连上游的排障方法

遇到中转链路争议时，使用同一 Key、同一模型、同一 `size`、同一请求类型和同样数量的参考图直接调用小易。只改变其中一个变量的测试不能作为反证。

最小判定顺序：

1. 先确认提交是否返回 `task_id`。
2. 使用提交时同一把 Key 轮询 `/v1/images/tasks/{task_id}`。
3. 若直连也返回同一错误，排除 App、NewAPI 和适配器。
4. 若直连成功而产品链路失败，再检查 NewAPI 转发字段和适配器实际 payload。

本轮两次直连得到：

- `gpt-image-2` 在 `[特价]gpt-image高质量` 分组返回无可用模型渠道；该分组实际模型应为 `gpt-image-2-vip`。
- 改为 `gpt-image-2-vip` 后，三参考图 2K 任务被接受，但最终返回 `No available 2K image accounts`。

第二次任务 ID 为 `canvas-task-mssw6zwu-f5ee0f8129d59243fb4af2b7`，可交给小易定位账号池；Wiki 不记录任何 API Key。

## 七、当前决策与未解决项

不修改 NewAPI 官方源码，也不做静默尺寸降级。新增 NewAPI/App 公开名 `gpt-image-2-官方`，适配器将其映射为小易上游真实模型 `gpt-image-2`。适配器及 `creation-models` 已部署，官方渠道在 App 中以 `0.25/张` 真实生成成功。

官方渠道首次提交曾返回 `model_price_error`，原因是 NewAPI 管理端未配置该模型价格；这在配置 `0.25/张` 后恢复成功。遇到该错误时先检查 NewAPI 模型价格，不应误判为适配器断链或小易账号池不足。

仍未解决：

- 小易账号池会间歇返回 `No available 1K/2K image accounts`，稳定容量仍不明确。
- 低质量渠道的 `fetch failed` 根因不透明。
- App 当前允许同类小易任务并发提交；上游账号池不足时，后续任务会直接失败。
- App 已取得异步 `task_id` 后仍有 600 秒客户端轮询上限；超过上限会被本地判超时。是否改为持久化长期轮询尚未实施。

后续验收应优先测试 `gpt-image-2-官方` 的文生图、三参考图编辑和 1K/2K/4K。出现账号池错误时保留任务 ID 交给小易排查，不通过自动改模型名或静默降级掩盖上游故障。
