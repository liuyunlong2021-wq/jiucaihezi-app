# 3D 编辑器吸附步长、取景框与过肩机位（2026-09-14）

> 状态：代码与 SDD 已同步；定向测试通过；真实 Desktop 手工验收仍待用户执行。

## 用户报告的两个症状

1. 想把角色往右挪一点点，结果一动就跳很远，落不到想要的角度。
2. 怎么调都调不出「一个角色过肩近景、前景带头和肩、景深里是另一个人」的构图；取景框不能上下移，只能移整个场景。

## 根因

### 一、吸附步长是 1 个世界单位（决定症状 1）

- `scene3d.ts` 的 `canvas.snap` 默认 `true`；用户场景文件里是 `snap: true` 且 `grid: false`。
- `Scene3DEditor.vue` 把 `transform.setTranslationSnap(document.canvas.snap ? 1 : null)` 硬编码成 **1**。three 的 `TransformControls` 对吸附的实现是 `object.position.x = Math.round(x / 1) * 1`，即**世界空间绝对整数格**，`y` 同样被吸附。
- 人物约 1.8 米高、屏幕上高 300+ px，所以每次吸附等于跳一整米；网格又是关的，看不到任何参照。
- 用户场景里两人分别在 `x = -2` 与 `x = -1`：往右挪一步就是另一个人的位置，不存在「一点点」。

### 二、取景框与成片不是同一件事（决定症状 2 的前半）

- 取景框是纯 CSS 装饰：宽度用 `min(86%, calc(72vh * --scene-aspect))`，取的是**视口高度**，与画布无关。
- 相机 aspect 用的是**整个画布**比例；截图 `capture()` 又裁「画布内最大的居中目标画幅矩形」。
- 三者互不相等：实测框约 155×276 CSS px，成片约 175×312，**成片比框大约 13%**，且随窗口高度漂移。框里对好的构图，截图不是这一张。

### 三、机位在切焦段、切投影时被重置（决定症状 2 的后半）

- `setLens()` / `setProjection()` 走 `createCameraControls()` 重建相机，并从 `document.camera.position` 复位。
- 而 OrbitControls 的实时机位从不写回 `document.camera`，所以现场转好的机位一点焦段就弹回旧值，重开场景也丢视角。

### 四、画幅会被旧机位改回去（调试时越调越乱的来源）

- `applyCamera()` 里 `document.canvas.aspect = source.aspect`，点已保存机位会把当前画幅换掉。用户文件里 `机位 1/2/3` 存的是 `16:9`，而画布已是 `9:16`，一点就跳回去。

### 五、过肩预设本身就不成立

- `defaultCameras` 的过肩机位是固定 `+Z 2` 偏移、近景是固定 `+Z 5` 米（实为 5 米中远景），既不管两个人之间的真实方位，也不管人物 `scale`。
- 过肩的几何前提是两人有纵深。用户场景两人同 `z`、只差 1 米，任何机位都拍不出真正的过肩层次。

## 修法

- 吸附：步长档位 `1 / 0.5 / 0.25 / 0.1` 米，默认 `0.1`；紧挨吸附开关显示当前步长（编辑器本地状态，不进 `.jcscene`）。
- 精度：检查器新增位置 `x / y / z` 数值输入（`step` 跟随吸附档位）；方向键按当前步长微调选中对象，`Shift` + 上下调高度。
- 取景：新增 `cropRect(width, height)` 作为唯一来源，取景框尺寸与 `capture()` 裁剪矩形都从它取；删掉 `72vh` 与 `86%` 猜测值。
- 构图：新增取景模式，拖动只平移机位（方向和朝向不变）；无选中时方向键同样平移机位。
- 机位：OrbitControls `end` 事件把实时机位写回 `document.camera`（不计入撤销历史）；切焦段只改 `fov`，切投影才换相机类；切换投影与焦段都不再丢失构图。
- 画幅：`applyCamera()` 不再改 `canvas.aspect`。
- 过肩：按两人真实连线重算，贴住近端人物肩后约 1.05×scale、横向偏出 0.26×scale，看向远端人物头部；近景改为人物正前方 1.15×scale、高度取头部；两人纵深不足 2 米在机位行提示。
- 辅助：新增「看向」（人物取 `Head` 骨骼，其他对象取包围盒顶部）与「临时隐藏选中对象」（只影响预览，不写进 `.jcscene`）。
- 人物同名时过肩/近景按钮补序号，避免两个按钮同名无法区分。

## 追加：过肩为什么要靠焦段（同日晚些时候）

用户指出：真实拍摄里两人很近时，不会把人拉开，而是把摄影机退远、换长焦，靠压缩空间得到过肩。这个判断完全正确，而且可以量化：

- 保持“近端头部在画面里占同样高度”时，机位距离与 `tan(垂直视角/2)` 成反比，所以焦段越长机位越远。
- 远端头部与近端头部的大小比 = 机位到近端距离 ÷ 机位到远端距离，随距离上升而上升，这就是“压缩空间”。
- 用用户真实场景（两人 `x = -1` 与 `x = -2`、`z` 相同，scale 0.95，9:16）实算：24mm 时远端头部只有近端的 36%，135mm 时升到 **74%**，机位从 0.51 米退到 2.85 米。
- 另一个关键结论：近端头部在画面横向的位置只由“横向偏移 ÷ 距离”决定，而固定偏移配合“距离随焦段变化”时两者同步缩放，所以**横向偏移必须取物理肩宽量级（约 0.19 米）而不是固定值**，否则人头会掉出画面 —— 这也是原先过肩只见一片肩膀的原因。

修法：`lens` 枚举换成等效焦距 `focal`（8–300mm，默认 50），工具栏提供 `24 / 35 / 50 / 85 / 135` 五档；相机垂直视角由焦段推算并按取景框折算（画布多出的部分只是编辑余量）；过肩/近景机位距离改为 `头部高度 ÷ (2 × 占画比例 × tan(视角/2))`，机位行显示实际焦段与距离。

## 追加：机位行重构与取景框边框看不见（用户实测反馈）

用户在三人会议室场景实测后报了两个问题：

1. **取景框左边“缺失”**。根因：全局 `box-sizing: border-box`（`src/styles/base.css`）下边框画在盒内，而当目标画幅比编辑区更宽时（用户当时是 `4:3`，画布比例约 `1.18`），`cropRect` 会让取景框撑满整个舞台宽度，它的左右边框就贴在文件树/检视面板的 `border-right` 上，两条 1px 线粘在一起 → 看着像丢了；隐藏文件树后那根线移到窗口最左边就“出现”了。修法：`.scene3d-stage` 加 `padding: 8px`，让取景框和舞台边缘永远有可见间距（同时覆盖上下边框与工具栏/机位行的粘边情况）。
2. **机位行基本没用**。根因：五个通用机位（全景/正面中景/俯拍/低机位/双人中景）都是写死的世界坐标，与场景无关；过肩按“列表里的下一个”配对，三人以上场景会配错人。修法：删掉五个写死预设（连 `defaultCameras` 一起），改为按人物列出前 6 个名字，点名字 = 这个人物的**正面中景**（正前方、头部高度、距离由焦段推算、头部占画高 20%）。用户随后又明确要求把「看向」和「过肩」一并删掉，机位行只保留人物名字这一种。

过肩的那套几何（按人真实连线、距离随焦段、横向偏移取肩宽量级）已随按钮一起删除；若以后要恢复，需重写：`shotDistance(scale, fill)` 仍在，过肩只是把它换成 `fill=0.3` 再加上肩膀偏移。

## 追加：机位打点与运镜录制（同日晚些时候）

用户要“先定第一个机位角度、再定第二个第三个，点录制后取景器自动从第一个位置移动到第二个→第三个”。

**结论：没有新造机制。** `.jcscene` 的 `timeline` 里 `action: 'camera'` 的条目本来就是机位关键帧（`evaluateScene3DAnimation` 按 `progress` 从当前机位混到条目的 `to`/`lookAt`，支持 `ease-in-out`），播放、录制、FFmpeg 导出全部建在它上面。所以打点 = 往 `timeline` 里写 camera 条目，只新增了 `scene3d.ts` 的两个纯函数（`cameraPointsFromDocument` / `applyCameraPoints`）和编辑器的“运镜”行。

关键实现点：

- 每个点 = `{ 位置, 观察目标, 焦段, 停留, 到位 }`；第一个点硬切（`at: 0` 无 `duration`），后续点 `at` 累加、`duration = 到位`、`easing: ease-in-out`；总时长 = Σ停留 + Σ到位。
- 焦段按点位插值（timeline 的 camera 条目新增可选 `focal`，`Scene3DAnimationState.camera` 新增 `focal`）—— 这条需要改动画 SDD 的“不增加焦距动画”，已在两份 SDD 同步。
- 打点只替换 camera 条目，AI 写的物体动画全保留，总时长取两者较长。
- **运镜录制不能直接调可见编辑器的 `recordVideo()`**：那个实例的画布是舞台形状，录出来比取景框宽。改为编辑器 `emit('record', document, title)` → 工作台 `recordScenePath()` → 隐藏的 `recordingOnly` 编辑器（按画幅 1920）→ 现有 `saveSceneVideo()` 转 MP4 存进视频目录。
- 顺手修的存量问题：`buildScene()` 以前用 `applyAnimation(time)`，会把正在编辑的机位拉回时间轴（改名、切阴影、撤销都会触发）；现在改成 `applyAnimation(time, false)`，重建只恢复对象状态。播放结束后用 `restoreLens()` 把视角复位到工具栏显示的焦段。

验证：`vue-tsc -b` 与 focused `1347/1347` 通过（新增往返测试：点位→timeline→逐时间点验证走位/朝向/焦段，以及混合物体动画时总时长不被覆盖）；**真实 Desktop 录制运镜 MP4 未做手工验收**。

## 追加：检视栏收回宽度 + 录制结果提示（用户实测第三次反馈）

- **右侧检视栏占着位置**：`.scene3d-workspace` 原本固定 `minmax(0, 1fr) 260px`，没选中任何对象时那一列仍然保留成一块空黑区 → 改成默认单列，只有 `inspector-open`（选中了对象）才 `minmax(0, 1fr) 260px`。注意：移动端媒体查询必须同时写上两个选择器，否则 `.scene3d-workspace.inspector-open` 的优先级会反向压过媒体查询。
- **录制成功没有提示**：状态文案一直写在工具栏末尾，而工具栏是 `overflow-x: auto`，截图/录制的回执会被截断（用户实测“录制成功了没有提示”）→ 改成压在 3D 画面上方的浮动提示：全文可读、可点击关闭、10 秒自动消失，成功/错误用左边框颜色区分。工具栏里那行删掉；`recordingError`（本机手动录制失败）保留在工具栏（错误要持续可见）并同时弹提示。

## 追加：关掉 3D 编辑器后整个界面变空白（用户实测第四次反馈）

用户操作：打开 3D 编辑器 → 把对话栏拖成窄条（“最大化”编辑器）→ 关掉编辑器 → 文件树还在，但对话框、输入框全没了，像一张白纸；必须再打开一个文档才能恢复。

根因（纯 CSS 作用域漏洞，与 3D 无关，任何预览都会中）：

- 把对话栏拖到小于 `MEMORY_CHAT_FULL_MIN(220)` 会把 `chatDockMode` 置为 `compact`；这个状态**在关闭预览后不会自动恢复**。
- `.memory-chat-compact-bar` 是 `position: absolute; inset: 0; background: var(--paper)` —— 铺满整个主列；同时 `.chat-dock-compact .memory-main > :not(.memory-chat-compact-bar) { visibility: hidden }` 把主列内容全藏了。
- 有第三列（预览/创作面板）时主列就是 56px，窄条成立；**关掉预览后主列变成满宽（1fr），窄条仍然铺满整列并隐藏内容** → 整个区域只剩一个展开按钮。移动端媒体查询里早就强制 `visibility: visible` + 隐藏窄条（因为那里预览是全屏浮层），桌面端漏了同样的保护。

修法（去根因，不丢用户偏好）：窄条只在有第三列时成立 —— 选择器加 `:is(.preview-open, .creation-open)` 限定，窄条元素的 `v-if` 同样加 `(previewResource || creationOpen)`。这样关掉预览后对话框立即回到满宽可见，而 `chatDockMode` 保持 `compact`，下次打开编辑器仍是窄条（不用重新拖）。

## 追加：竖屏媒体在预览里不居中（用户实测第五次反馈）

用户操作：点开一条运镜录制的竖屏 MP4（`1080×1920`，9:16）→ 视频跑到下方，上面留一大块空白。

先用真实文件排除猜测：`ffprobe` 确认 5 条运镜成片都是 `1080×1920 / 120 帧 / 4 秒`，与取景框 9:16 严格一致，成片本身没问题。再用 `/tmp/media-preview-repro.html` 把 `MemoryWorkbench` 的规则原样搬出来量 `getBoundingClientRect`，`1736×1013` 的窗口下复现出同一现象。

根因（`.memory-media` 的网格行是 `auto`）：

- 媒体元素挂在 `display: grid; place-items: center` 的 `.memory-media` 里，网格只有一条 `auto` 行。
- `auto` 行的高度由**媒体自身**撑开，于是媒体元素的包含块（网格区）就等于它自己的高度，`max-height: 100%` 这一百分比**永远无法解析**（按规范降级为 `none`）。
- 实测：容器 `1036×937`，竖屏媒体渲染成 `996×1771` —— 溢出容器 874px，`scrollHeight 1811 > clientHeight 937`。溢出部分既没被裁掉也没被居中，`.memory-media` 的 `overflow: auto` 又把这块滚动区交给浏览器，一点击（视频拿到焦点/重排）视野就落在视频中段，看起来就是"跑到下面去了"。
- 与 3D 无关，任何竖屏素材（图片/视频同理）都会中；横屏素材因为 `max-width` 先命中比例不出问题，所以一直没暴露。

修法（一行声明，不加新机制）：`.memory-media` 显式给行高 `grid-template-rows: minmax(0, 1fr)`，让网格区等于容器高度、`max-height: 100%` 能解析；溢出既然不可能再发生，`overflow: auto` 收成 `overflow: hidden`，顺手堵掉"居中内容溢出后滚不回去"的经典坑。

同一份复现页上的修复前后对照（`1736×1013`）：

| | 媒体区 | 媒体实际尺寸 | `scrollHeight` |
| --- | --- | --- | --- |
| 修前（图片/视频一致） | `1036×937` | `996×1771`（溢出） | `1811` |
| 修后（图片/视频一致） | `1036×937` | `505×897`（完全落位） | `937` |

顺带排除的两个假设：把对话内容加到 3400px 高，预览列仍是 `985`（= 视口高度），说明工作台那行不会被聊天内容撑开，不需要给 `.memory-workbench` 补 `grid-template-rows`。
