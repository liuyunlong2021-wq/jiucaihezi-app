# 视频保存链路与原生下载加固（2026-10-04）

## 检查结论

用户在 [[GPT图片生成成功但项目保存失败-2026-10-04]] 后要求检查视频，并寻找更精简、稳定的下载方式。图片截图没有提供视频失败样本；本次结论来自代码审查与故障测试，不能认定用户的视频已经发生同一故障。

桌面视频保存到项目已经通过 `downloadProjectMedia → http_download_to_project` 流式写入同目录 `.part` 文件，完整接收后才改为正式文件。确认了以下缺口：

1. 旧 Comfy 任务缺少 `planSnapshot.apiStyle` 时，没有用模型注册表补回下载路由，可能继续下载 `http://frps:...` 内网地址。
2. 普通 CDN 视频重试保存直接复用原链接，没有重新查询已经完成的任务，签名链接过期后可能一直失败。
3. 原生下载使用固定总超时，即使一直收到数据，耗时超过 300 秒的项目下载（缓存通道为 120 秒）仍会被切断。
4. HTTP 200 空文件、JSON/HTML 错误页面，以及未请求 Range 却返回的 206 部分文件，可能被标记为项目保存成功。
5. 连接错误仅输出 reqwest 顶层说明，隐藏底层原因；临时连接失败或 502/503/504 没有有限自动重试。

## 实施

- `taskUsesContentEndpoint` 在历史快照缺失时按模型注册表补 `apiStyle`，继续只对既有 Comfy/omni 合同走带鉴权的 NewAPI content 地址；其它视频保留原 CDN 合同。
- 公网视频“重新保存”先通过已有 `pollTask` GET 查询结果，取回服务端当前提供的链接；查询失败仍尝试原链接。已有错误 content 地址的恢复分支保留。查询不会提交生成 POST；服务端若仍返回相同失效链接，客户端无法自行签发新链接。
- 两个原生下载命令共用客户端下载设置和 GET 发送逻辑：连接超时仍为 10 秒，下载超时改成连续等待数据的上限，每次读到数据后重新计时。
- 连接失败、等待超时和 502/503/504 在收到文件体之前最多补一次 GET，间隔 300 ms；401/403/404 不重试。文件体中途失败仍清理临时文件，交由用户重试保存。
- 项目下载拒绝空文件、206 部分内容和常见图片/音视频扩展名对应的 JSON/HTML 响应，不影响 `.gltf` 等可合法使用 JSON 的文件类型。原有断流清理和临时文件完成后改名保留。
- 下载错误展示底层错误链，移除 reqwest 的结果 URL，避免把带签名的查询参数写进错误详情。

## 下载方式选择

继续复用现有 Rust/reqwest 原生流式下载与项目写盘，无新增依赖。视频保存到项目避免整段视频在 Rust 与 WebView 间做 Base64 往返。Dola“下载链接”另存为及无项目回退仍使用现有 Base64 通道，本轮共用超时、发送重试与错误诊断；项目文件完整性检查只在流式项目保存路径执行。

不同供应商的 `/content`、Range 和签名 URL 合同不同，未经确认强行改路由会破坏现有视频能力。当前原生客户端能力足够解决已复现的问题，本轮未新增服务端视频中转或通用断点续传。依据：[reqwest 0.12.28 read_timeout 官方文档](https://docs.rs/reqwest/0.12.28/reqwest/struct.ClientBuilder.html#method.read_timeout)、[RFC 9110 的 206 部分内容合同](https://www.rfc-editor.org/rfc/rfc9110.html#name-206-partial-content)。
