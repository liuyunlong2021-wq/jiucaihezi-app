# 创作 Skill 与 Wiki 联动升级经验

> 2026-10-24。来源：漫剧制作升级、一次真实 Seedance 流水线试跑及其后续修复。对应实现已提交 `204744db`。本页是后续短剧/小说升级的方法入口，不是新功能实施计划，也不表示短剧已完成同等升级。

## 1. 已验证的通用原则

| 原则 | 升级下一条路线时怎么做 |
| --- | --- |
| Skill负责创作，Wiki承载持久资料，Runtime负责实际落盘与确定性校验 | 先复用当前Skill、统一归档工具和文件树，不另造一套创作内核。保存成功不等于用户确认或作品质量通过。 |
| 先定产物目录，再改Skill | 为每类产物确定类型、唯一文件路径、直属index及版本归属；新建模板、归档合同、Skill、交付入口必须一致。动态实体按真实内容创建，不预填事实。 |
| 每个Skill明确输入与输出 | 列清本轮消息、必读Wiki正文、版本/集数/实体、产物路径和允许修改范围。不能只写“参考项目资料”。从index定位，再读取正文，不全库扫描。 |
| 刚保存不等于实际读过 | 当前步骤实际read对应正文；本轮已读的相同版本可复用，修改后重读。漫剧运行中流水线已有读取版本校验，其他路线须评估并补适配与测试，不能宣称已全局强制。 |
| 不同产物与版本分开，同一产物修订原位更新 | 策划、分集规划、正文分别保存；原作与改编版明确区分。修改前读完整目标，保留未改范围，不用新文件名制造重复副本。 |
| 自动保存有明确边界 | 三创作模式的完整产物自动归档，普通模式只在用户要求时保存；用户明确不要保存时遵守。讨论、提问、错误和未完成片段不能冒充完整作品。确认闸门和原始来源保护继续保留。 |
| 上下文辅助理解，Wiki提供项目事实 | 始终理解用户本轮意图；历史旧稿不能替代当前对应Wiki正文。用户明确修订时更新指定范围；来源、版本或意图有冲突时指出具体差异，不机械认定旧文件或旧聊天优先。 |
| 优先利用现有缓存和DSH能力 | 目前保留DSH会话、历史管理与缓存链路。先观察真实命中和NewAPI扣费，重点防旧信息干扰、容量失控与恢复错误，不因上下文长就立即拆会话或重写运行时。 |
| 用户手动操作优先，AI写入仍守边界 | 文件树手动删除沿既有确认/废纸篓流程；只读项目检查不偷偷补建被删目录。不能把用户手动权限直接扩成AI任意删除权限。 |

上下文与Wiki的权责约定仍需通过后续真实修改任务验证；目前并未实现一套自动解决所有内容冲突的机制。

## 2. 真实试跑暴露的问题

| 观察到的问题 | 根因与已采用的处理 | 可复用的验收点 |
| --- | --- | --- |
| 资产已生成，但没有逐项实际读取人物小传/场景道具说明 | 模型沿用刚生成的聊天。强化Skill输入合同，运行中漫剧流水线通过真实read/read_image文件版本记录校验；写入不算读取，过期读取拒绝。 | 先测未读拒绝、读后修改拒绝、重读成功；再检查所选正文在语义上是否确实对应当前实体。 |
| 来源路径与“第001集”拼成无效链接，摘要也复制该标记 | 路径和显示文字未分开。漫剧派生正文按所在文档换算相对路径，集号作为标签，索引摘要只保留可读文字。原始材料不改写。 | 深层目录、中文路径、相对定位、索引摘要分别核对；不能只测文件写成功。 |
| 进度同时写complete与running | 阶段和状态缺少一致性约束。完成阶段统一为completed，拒绝同时blocked。 | 真实文件、进度JSON、最终宣言一致；旧进度不因读回被批量改写。 |
| Seedance没有图片就省略参考图，用户后续无法直接上传使用 | 把图号误当成“已上传凭证”。最终合同改为每张@图单独一行、按段独立编号、镜内引用同一资产。 | 即使没有图片也提供本段资产绑定；正文不带待上传等操作备注，不声称核验过图片。 |
| 视频提示词含工程镜映射、全片时间、跨段指代，声音九维散在镜头里 | 混淆制作过程和最终消费者需要的内容。最终提示词五模块、自包含，九维集中在角色图行，内部信息留工程稿/进度。 | 按“视频模型第一次看到这一段”审稿。通用经验是区分内部过程与正式交付；五模块及@图规则不直接套到短剧正文。 |
| App显示缓存未提供，但后台命中很高 | 首次请求缺缓存字段导致官方精确整轮汇总不披露总数。保留官方统计，仅App追加已报告部分与请求覆盖次数。 | 完整、部分缺失、全部缺失、明确0、重试和历史恢复分别测试；未知不当0，部分累计不冒充完整总量。 |

格式与文件校验不能证明人物选择、改编逻辑、创作质量或全部资产语义正确；这些仍要真实阅读验收。

## 3. 流水线、缓存与恢复的边界

流水线要建立在已经能独立工作的步骤上。用户只要求单个产物时，不强迫跑完整流程；目标明确的整条流水线无需逐步重复询问保存许可。

- 进度以实际成功保存的产物为依据，不以模型说“已完成”为依据。来源/前置产物哈希能发现变化，但不证明语义正确，也不是Git版本备份。
- 恢复前读取当前进度和真实文件，核对来源是否变化；不能从头重复已成功步骤，也不能在上游修改后沿用过期下游。未来短剧的跨集影响分析需要单独设计，不能声称漫剧已有自动依赖重算。
- 缺关键资料明确阻塞并说明原因；用户取消优先。自动继续要有无进展停止条件，不能无限催促，也不为此重新开放目标管理、后台作业或子代理工具。
- Skill白名单、可执行工具、资源路径和归档类型共同限制能力。工具种类与调用次数分开统计：一轮120次工具调用，不表示暴露120种工具。
- 缓存命中不代表历史消失；旧信息仍在输入里。保持有用前缀稳定，不为凑缓存塞入无关资料。Wiki正文修改后必须读取新版本。
- 本轮已报告缓存约240万token，不能据此保证所有模型、渠道、会话和计费方式都相同；实际费用以NewAPI账单为准。不把缺失的缓存写入字段解释成零费用。
- 保留用户已有目录与来源；新旧同类目标并存时报告歧义，不自动搬迁、删除或合并。未实现创作项目自动Git备份，不把代码提交当成用户作品备份。

## 4. 升级下一条路线的步骤与验收

| 顺序 | 必须得到的结果 | 验证方式 |
| --- | --- | --- |
| 1. 审计现状 | 当前Skill、归档类型、建库模板、依赖和真实调用链；先识别哪些能力已经存在 | 静态源码与现有测试对照，不能凭名称判断缺功能 |
| 2. 对齐读写合同 | 逐Skill明确本轮消息、必读正文、原作/改编版、集/实体范围、唯一产物路径及缺项处理 | 用户确认业务关系，目录与工具合同相互校验 |
| 3. 补缺陷测试再实施 | 缺资料、读错/未读/过期、修订覆盖范围、索引、旧库兼容、状态一致性等可复现 | 先失败后修复；测试可观察行为，避免只匹配Skill里一句话 |
| 4. 验证单步交接 | 创建/导入→资料→规划→正文，各步能独立读写和交付 | 真实SDK模拟验证工具执行、拒绝边界、保存回执与冷恢复，不当作真实模型质量证明 |
| 5. 真实小样 | 选一份明确来源，完成至少一集，再做一次定向修改 | 只读监督实际读了哪些文件、保留哪些原文、修改哪些段落、index与回执是否一致 |
| 6. 决定是否组合流水线 | 仅在单步正确且用户明确需要时组合 | 测中断、缺项、重试、取消、上游变更与完成状态；记录真实耗时/缓存/费用，不预先承诺节省比例 |

逐Skill审计表建议固定为：

| Skill/触发任务 | 本轮要求 | 必读Wiki正文与版本 | 输出类型及唯一路径 | 允许修改范围 | 缺项/冲突处理 | 验收证据 |
| --- | --- | --- | --- | --- | --- | --- |
| 待审计填写 | 不复制整段历史作输入合同 | 填真实路径定位规则，不写笼统“项目资料” | 与建库/归档共用合同 | 保留无关内容 | 指明具体缺项 | 测试＋真实调用/产物 |

短剧下一轮优先核对：原作与改编版资料的边界，整体方案与分集规划的关系，逐集写作所需人物/场景/道具、前集结束状态及未解决伏笔，用户修改上游规划时的影响范围。哪些应成为单独文档、哪些由现有页面承载，须审计后确定，不在本经验页先定新目录或新增Skill。
