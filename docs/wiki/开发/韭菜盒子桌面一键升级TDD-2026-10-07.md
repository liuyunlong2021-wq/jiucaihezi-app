# 韭菜盒子桌面一键升级 TDD

> 日期：2026-10-07 · 状态：运行时与发布链路已实施，原生发布验收中
> 范围：macOS Apple Silicon、macOS Intel、Windows x64 安装版
> 当前基线：v2.2.19；本文件不预占下一发布版本号
> 用户目标：在 App 内点击升级，自动下载、安装、重启，保留项目和创作记录

## 1. 可验证目标与实施顺序

1. 锁定更新与数据保留合同，先写失败用例 → 验证：实际更新服务与安装协调逻辑的行为测试；不是只匹配源码字符串。
2. 接入官方 updater 与安装前收尾 → 验证：更新失败不影响 App 启动，多窗口/后台任务均纳入安装检查，失败不触发安装。
3. 补齐三平台最终产物签名、更新清单与保留策略 → 验证：真实签名校验、缺包阻断、原子发布和清理回归。
4. 发布接入版，再验证后续版本升级 → 验证：三平台真实安装版跨版本升级及数据保留。未完成平台必须明确记为待验收。

核心通过标准：用户在 App 内完成更新，无需打开网页下载、拖拽替换或手工解压；重启后的原生版本正确，项目、登录配置、会话、草稿和任务记录保留。

## 3. 产品行为

### 3.1 入口与流程

- 设置的「关于 / 更新」区域显示当前版本、检查结果、版本说明和更新操作；启动后异步检查，发现新版用非阻塞提示，用户可以稍后处理。
- 默认先提示，点击「下载更新」后下载；下载期间可继续创作。不在后台擅自安装或重启。
- 下载完成显示「安装并重启」与「稍后」。下载进度显示已下载字节；服务未提供总长度时显示不定进度，不伪造百分比。
- 检查失败与下载失败显示简短原因和重试入口；后台检查失败不重复弹窗。用户手动检查时必须看到失败状态。
- 存在任务时显示阻塞项及「稍后」；用户可明确选择「任务结束后安装」。这次同意只对当前进程、当前目标版本有效；重启、撤回或目标变化后重新确认。
- 升级后从现有持久状态恢复工作台；从原生版本确认升级成功后，才显示完成提示。不以安装器启动成功或下载完成作为升级完成。

### 3.2 状态与并发

主流程：`idle → checking → available → downloading → ready → preparing → installing`。检查无新版回到 `idle`；错误带失败阶段返回可重试状态；准备遇忙返回 `ready` 并显示阻塞项。安装发出后由新进程验证结果。

Rust 持有进程级的检查/下载/安装状态和官方更新对象，Vue 只订阅状态和发出操作。复用 Tauri app events 同步各工作台窗口；重建或切换窗口时读取快照。每个进程只允许一个下载和一个安装，不为每个窗口复制更新 Runtime。

用户撤回等待安装时立即清除许可；后续任务空闲不能再触发安装。安装准备失败时释放新任务准入锁并返回可继续工作的状态。未知、断联或未响应的工作窗口不能当作空闲窗口。

官方 updater 下载的内存/磁盘行为与取消接口在接入时核对锁定版本：首期只承诺前台进程内重试，不宣称断点续传、退出后保留完整下载或跨进程复用缓存。真实大包测量下载期间内存增长，超过可接受范围则在公开发布前解决。

## 4. 技术落点与平台合同

### 4.1 复用边界

- 使用 Tauri 2 官方 `tauri-plugin-updater`；尽量由 Rust 调用官方检查、下载、安装 API，避免将任意 URL、任意公钥或安装命令暴露给前端。
- 更新 IPC 仅对本地桌面工作台窗口授权；截图窗、Mobile、远程页面和 MCP 工具不直接取得安装权限；独立截图编辑会话同样占用进程任务门闩，直到复制、保存或取消完成。复用既有 capability 与窗口识别机制。
- updater 在桌面目标编译和注册；不拖入移动构建。Rust 正常窗口启动与更新检查相互独立，服务器断网仍正常打开工作台。
- 初始化前验证内置配置；可恢复的注册失败记录诊断并把更新入口标为不可用，不能对更新错误使用 `unwrap/expect` 导致 App 退出。配置缺失与初始化失败的真实测试是接入前置门禁。
- 一个更新模块、一组受限 IPC、一个设置入口；复用 `App.vue`、已有设置 UI、退出生命周期和项目保存逻辑。不建立第二套下载框架、Agent Runtime、任务数据库或远程更新服务。

### 4.2 三平台产物

| 平台 | 安装位置与更新方式 | 最终更新产物 |
| --- | --- | --- |
| Mac ARM | 正常安装到可写的 Applications 位置，原位更新 `.app`，随后重启 | 最终 `.app.tar.gz` + `.sig`；架构 `darwin-aarch64` |
| Mac Intel | 同上，CPU 架构保持 x86_64 | 最终 `.app.tar.gz` + `.sig`；架构 `darwin-x86_64` |
| Windows x64 安装版 | NSIS 复用原安装位置和安装范围；默认 `passive` 展示进度，按需出现系统权限确认 | 最终 NSIS `setup.exe` + `.sig`；架构 `windows-x86_64` |

使用 Tauri v2 格式。配置采用 `createUpdaterArtifacts: false`，因为构建后还需签名、公证与 App stapling；流水线显式生成最终 `.app.tar.gz` 并签名，避免提前生成的包被后续修改。Windows 直接使用 NSIS EXE；`.nsis.zip` 是 `v1Compatible` 格式，本产品不需要引入旧格式。格式和平台限制以 [官方 Updater 文档](https://v2.tauri.app/plugin/updater/) 为准。

Mac 在 DMG 只读挂载位置或权限不足时，展示「先安装到应用程序目录」/权限说明，保留官方手动安装出口；不能绕过系统权限写入。Windows 标准用户安装和已有机器级安装分别验收，不能承诺所有安装位置免管理员授权。

Windows 便携 ZIP 保留既有下载能力，不把解压版当作已安装 NSIS 版自动迁移。安装类型以原生可靠信息确认，未知时不自动安装；便携用户通过安装版进行一次显式迁移，并验证新安装位置仍读取原有数据。iOS/Android 不使用该桌面自更新链路。

### 4.3 数据与退出收尾

安装准备的唯一通过条件是：所有工作窗口与原生后台都已报告空闲，所有保存成功，并且新任务暂时停止进入。不能仅检查当前窗口的 `mediaTaskStore.hasRunning`。

1. 点击安装后，取得进程级安装锁；下载期间不限制正常任务。进入准备阶段时暂停新任务准入，覆盖工作台、MCP 创作桥接及 Gateway 远程提交，显示「正在准备升级」。
2. 检查 Harness/工具执行、媒体生成/轮询/上传/下载/保存、FFmpeg/导出、画布和文件写入。忙时恢复准入、返回阻塞状态，不自动取消付费任务。等待安装时仅观察空闲，不长期冻结工作台。
3. 全部空闲后，要求所有工作窗口完成现有草稿、会话元信息、编辑文档、画布和窗口状态持久化；对隐藏/最小化窗口也要取得完成确认。保存失败或超时中止安装。
4. 保存完成后在准入锁下再次核对任务状态，防止检查期间新建任务或远程任务穿透。新窗口在准备期间不能启动新的任务。
5. 复用已存在的 Harness 客户端 close、原生进程树收尾和 Gateway 生命周期，等待进程退出、文件句柄与数据库连接释放；失败则停止安装并恢复可用服务。
6. 调用官方 install；Windows 按官方安装器退出/重启语义处理，Mac 安装成功后执行 relaunch。不对所有平台无条件重复调用重启。安装的具体系统行为以 [官方 JS API](https://v2.tauri.app/reference/javascript/updater/) 及锁定版本的 Rust 实现为准。

用户项目、素材、凭据、用户 Skill、模型配置、Harness 会话和数据库不作为更新包安装目标。Harness 官方持久文件沿用唯一真源，不能创建第二份消息快照来恢复工作台。升级成功验证依赖原生版本与原持久文件。

App 包内的 Harness、创作 MCP、Storyboarder 等运行资源必须整包一致更新；禁止只替换 EXE 或主程序。数据库结构有变化时才执行迁移：先使用 SQLite backup API 或受控的 `VACUUM INTO` 获得一致备份，再以现有事务机制迁移；不能运行中直接复制主数据库并丢弃 WAL/SHM。本文不要求每次升级备份全部项目或无关数据库。

## 5. 密钥、发布与清理合同

### 5.1 密钥与验证

- 使用 Tauri CLI 生成一对官方格式的 updater 密钥；检查公私钥能真实签名/验证测试产物后，才配置正式流水线。
- 公钥以内容内置 App，私钥和密码进入 CI Secrets，并保留受控备份；私钥不写入仓库、发布资产、命令输出或文档。旧 PEM 留作历史文件，实施时不擅自删除。
- 更新只接受可信 HTTPS 清单和官方签名验证通过的产物；平台/架构由原生识别，版本必须高于当前版本。用户输入、远程指令不能覆盖公钥或安装目标。
- updater 签名与 Apple Developer ID/公证分别负责更新信任和系统运行信任。SHA256 可用于运维检查，不能代替 updater 签名。
- 验证损坏包、错误密钥包及清单签名与文件不一致都必须拒绝安装。签名失败不进入「准备升级」，旧版继续运行。

### 5.2 最终产物与清单

Mac 顺序：构建 `.app` → 修复并签名嵌套代码 → 最终 App 的 Apple 公证与 `.app` stapling/校验 → 构建首次安装 DMG 与更新 tarball → 对最终更新 tarball 进行 Tauri 签名 → 发布前解包、签名/公证及资源核验。保留 DMG 公证验证能力。可以复用可接受的公证提交，关键是两个分发载体的验证都通过。

Tauri build 若提前生成 tarball/`.sig`，后续 codesign 或 stapling 会改变内容，因此流水线必须废弃提前生成的更新产物，在所有修改结束后重打包并重新签名。Windows 对最终安装器签名，签名后不再改文件字节。

官网继续读取 `/updates/latest.json`；桌面更新器读取 `/updates/updater.json`。后者使用官方静态 JSON，包含 `version`、版本说明、可选 `pub_date`，以及三个平台各自的 `url` 与 `signature`。`signature` 是 `.sig` 内容，不是签名文件的路径或 URL。三平台条目必须完整有效，使用 [官方静态清单合同](https://v2.tauri.app/plugin/updater/)。

发布顺序：三个平台完成 → 上传到不可变的 `/updates/<版本>/` → 对源文件校验签名、对线上字节读回核对摘要 → 验证三个平台条目 → 上传清单临时文件 → 同文件系统原子 rename 到正式 `updater.json` → 更新官网清单 → 清理旧版。任一平台失败、缺包、摘要不符或签名失败，正式更新清单保持上一个可用版本。

同一版本的更新包一旦被正式清单引用，不能使用 `--clobber` 重建不同字节继续发布；应提升版本并发新 tag。构建时的临时资产和正式已推广资产需要在发布脚本中明确区分。

清单设短缓存/重新验证，更新包使用版本固定 URL 和长期缓存。检查超时不阻塞 App 启动；清单发布后的实际缓存行为必须从公网核对。首期使用既有服务器，不默认增加 CDN 服务、灰度系统或增量更新。

### 5.3 撤回与磁盘保留

- 清理仍保留最近 5 版，并额外保护 `latest.json`、`updater.json` 各自指向的版本和已登记的上一可用更新版。新增 pin 用现有清理脚本的参数/读取方式表达，不建立版本数据库。
- 更新清单或必要 pin 解析失败时，停止删除并报警；不能把「无法读出版本」当作没有保护版本。未接入 updater 的历史部署可按明确的兼容规则处理文件缺失。
- 撤回有问题的更新：恢复上一份有效 `updater.json` 并处理缓存，再发更高版本的修复包。默认版本比较阻止已升级用户自动降级；撤回只阻止尚未安装用户继续取得问题版本。
- 不承诺官方 updater 自带自动回滚。安装中断或新版本无法启动时，使用已保留的正常安装包进行恢复；存在数据库迁移时按对应备份/兼容性合同操作，不能盲目降级读取新版数据库。

## 6. 先红后绿的测试矩阵

以下为目标用例矩阵；实际覆盖与尚未执行项见第 8 节，不能将合同检查视为全部功能通过。行为测试执行实际模块；第三方替身仅用于确定性模拟网络和安装结果，不能用调用替身通过替代真实签名或平台验收。

| 编号 | 给定条件 / 操作 | 必须断言 | 验证层 |
| --- | --- | --- | --- |
| U01 | 更新配置缺失、无效或注册返回错误 | 工作台照常创建，更新入口解释不可用，无启动 panic | 实际初始化分支 + 原生启动 |
| U02 | 更新服务器断网、超时或清单无效 | 主窗口正常可用，手动检查有错误，后台检查不弹循环提示 | 行为 + 原生断网启动 |
| U03 | 当前版本相同/更高；平台缺失/错误；包与签名不匹配 | 不安装；有效新版只取得本机架构；无效完整清单被拒绝 | 真实官方检查/签名集成 |
| U04 | 两个工作窗口同时点击检查、下载、安装 | 同一进程只有一份下载/安装；两窗口状态一致，旧结果不能覆盖新状态 | 并发行为 |
| U05 | 下载中断、未知总长度或下载错误 | 字节/进度正确，失败可重试；零安装、零退出，不宣称下载已完成 | 传输行为 |
| U06 | 更新包被截断/篡改或使用另一私钥签名 | 官方验证拒绝，实际安装入口零调用，旧版持续运行 | 官方真实签名集成 |
| U07 | 另一窗口正生成、保存或导出；Gateway 正提交任务 | 全 App 安装检查报告忙，不自动取消任务或关闭进程 | 协调行为 |
| U08 | 安装准备/保存期间出现远程任务或新窗口提交 | 新任务被准入锁阻止；不得发生「检查为空闲后新任务穿透」 | 并发故障注入 |
| U09 | 编辑器/画布保存失败、窗口无响应、收尾超时 | 不调用 install；释放锁，恢复可操作状态；重试时重新核对 | 协调行为 |
| U10 | 用户撤回「任务结束后安装」，随后任务结束 | 不安装、不重启，许可不会随重新打开窗口复活 | 行为 |
| U11 | Mac 只读 DMG 或权限不足；Windows 未确认安装类型 | 不擅自迁移；显示真实原因和正确的手动恢复入口 | 平台测试 |
| U12 | 升级包含 App 包内 Harness/MCP/Storyboarder 资源 | 所有资源版本一致；新版真实对话、MCP 与 3D 最小用例成功 | 原生安装版 |
| U13 | Mac 签名、公证完成后修改产物字节 | 原签名不通过；只有重打包并重签的最终包可发布；App stapling 验证通过 | 发布集成 |
| U14 | 任一平台失败、资产缺失、上传读回摘要不符 | 正式 updater 清单字节不变，其他平台不被误推广 | 发布脚本集成 |
| U15 | 清单写入中断；公网有旧缓存 | 读取者只能得到旧完整或新完整 JSON；失败保留旧版；短缓存策略实际生效 | 文件系统 + 公网 |

## 7. 分阶段闸门与上线

| 阶段 | 工作与门禁 | 通过证据 |
| --- | --- | --- |
| G0 合同红测 | U01–U10、U14–U16 关键失败用例先复现缺失能力；明确已有退出/保存/准入接入点 | 逐项红灯及失败原因；没有调用真实安装器 |
| G1 更新运行时 | 官方检查/下载/验证、全局协调、入口和错误处理 | 上述行为用例绿灯，U03/U06 真实签名集成通过，类型/相关 Rust 检查通过 |
| G2 发布产物 | 三平台最终包、私钥配对、App 公证票据、静态清单、原子发布、清理 pin | U13–U16 通过；无测试私钥进入正式产物/Secret |
| G3 安装升级验收 | U11/U12/U17/U19；需要迁移时增加 U18 | 三平台真实旧→新升级记录、版本/架构/数据核验、失败场景结果 |
| G4 正式接入发布 | 桌面构建与既有回归通过，原生启动门禁保留；公开更新清单前核对最终包和公网响应 | tag/commit、CI run、最终包摘要/签名、线上清单和验证记录 |

接入版记为 A，后续版记为 B，具体版本在实施发布时由统一版本脚本确定：

1. 现有 v2.2.19 没有 updater，无法由服务器远程补入该能力。用户需手动安装 A 一次，Windows 便携用户通过安装版完成显式迁移。
2. 先在本机/CI 的隔离测试清单下，以正式签名的候选包验证 A→B；不能为验证一次更新就给所有用户推送未经验收的 B。
3. A 正式发布并正常运行后，B 在三个平台完成跨版本验收，再推广正式 updater 清单。从 A 开始，后续用户可在 App 内更新。
4. 现有项目和生产用户目录不充当测试 fixture；使用隔离的数据副本，保留测试前后摘要和必要功能记录。

首期不增加自动强制升级、差分包、热替换程序、自动降级、长期后台下载进程或独立升级框架。断点续传、灰度和额外下载源只有明确需求/测量证据时另立合同。
