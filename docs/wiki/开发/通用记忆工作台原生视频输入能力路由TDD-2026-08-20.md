# 通用记忆工作台 Gemini 原生视频读取复验

> 状态：已验证，App 无需修改
> 日期：2026-08-20
> 范围：Desktop 记忆工作台通过 NewAPI 读取 MP4

## 1. 验证结论

1. Desktop 记忆工作台已用 `gemini-3.7-flash` 真实读取 MP4，模型返回了按时间段划分的画面、文案和品牌内容。
2. 当前链路“选择本地 MP4 -> Studio 构造 `video_url` -> NewAPI -> Gemini”可用，不需要 FFmpeg、抽帧、Skill 或新的附件路由。
3. `gemini-3.7-flash-high` 的失败是 NewAPI 返回 `503 No available channel`，属于模型别名/分组/渠道可用性问题，与 MP4 格式和 Studio 附件构造无关。
4. 先前的 `source.base64.media_type` 图片 MIME 校验错误不是通用 Studio 视频链路故障；若在特定模型/渠道重现，只排查该 NewAPI 渠道的协议转换。

## 2. 现有合同

- `src/utils/directMessageBuilder.ts` 已将 `video/*` 附件构造为 `video_url`，并保留真实 MIME 和 Base64 数据。
- `src/runtime/memory/memoryChat.ts` 已将记忆模式的原生附件交给共享消息构造器，再发往 `/v1/chat/completions`。
- WebM 等其他 `video/*`、GIF、音频、通用文件和 Office/PDF 文字转换链路保持现状。
- NewAPI 请求透传在原故障发生前始终关闭，不属于本次根因。

## 3. 能力与可用性边界

- Gemini 对话模型的原生视频能力，不等于 NewAPI 中每个模型别名都存在可用渠道。
- `503 No available channel` 必须先用纯文字请求验证模型路由，不得误报为视频不支持。
- `inputModalities` 元数据当前不参与记忆工作台的附件发送决策。仅修改该元数据既不会修复 503，也不会改善已能工作的 MP4，本轮不实施。
- 不根据模型名称对附件做本地过滤，不恢复历史上已删除的 `resolveCurrentModelAttachments()`。

## 4. 真实复验记录

### 4.1 不可用模型

- 模型：`gemini-3.7-flash-high`
- 结果：`API 503: No available channel for model gemini-3.7-flash-high under group Gemini全家桶 (distributor)`
- 判定：请求止于 NewAPI 模型分组/渠道选择，未进入 MP4 附件验收。

### 4.2 可用模型

- 模型：`gemini-3.7-flash`
- 输入：Desktop 记忆模式上传本地 MP4，请求查看视频内容。
- 结果：成功返回青岛啤酒“百年国潮 / 1903”主题、`00:00-00:14` 分段画面和文案，证明模型实际看到了视频。
- 判定：Desktop + Studio + NewAPI + Gemini 原生 MP4 读取真实通过。

## 5. 实施决定

- App 业务代码零修改。
- 不修改 `modelInputCapabilities.ts`、`agentStore.ts`、`directMessageBuilder.ts`、`memoryChat.ts`、`newApiAttachments.ts` 或 `MemoryWorkbench.vue`。
- 不增加 MIME 白名单、五模态前置预检、FFmpeg、Whisper、Skill、MCP 或本地媒体处理。
- NewAPI 只需单独修复或下线 `gemini-3.7-flash-high` 别名的渠道路由，不改 Studio 附件链。

## 6. 回归保护

- 现有 MP4 测试必须继续得到 `video_url: data:video/mp4;base64,...`。
- 现有“未知视频 MIME 原样保留并继续构造 `video_url`”测试必须继续通过。
- 图片、GIF、音频、通用文件和 Office/PDF `textContent` 的现有行为不得因视频能力改动而变化。
- 本轮无业务代码改动；已执行的附件、视频和工作台定向测试 `84/84` 通过，`git diff --check` 通过。
