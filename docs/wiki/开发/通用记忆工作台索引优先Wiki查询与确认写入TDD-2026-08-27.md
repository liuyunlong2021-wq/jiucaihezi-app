# 通用记忆工作台索引优先 Wiki 查询与确认写入 TDD

> 日期：2026-08-27  
> 状态：待实施  
> 范围：Wiki 查询、根据 Wiki 创作、回答后的确认写入  
> 前置：[[通用记忆工作台原生Wiki能力与五Skill退役TDD-2026-08-26]]、[[通用记忆工作台轻上下文任务运行时TDD-2026-08-26]]  
> 参考：[my-llm_wiki](https://github.com/liuyunlong2021-wq/my-llm_wiki)

本 TDD 优先于 [[通用记忆工作台轻上下文任务运行时TDD-2026-08-26]] 中关于 Wiki 查询、Wiki 创作和“回答后再次调用 write/edit”的旧路径。轻上下文 TDD 继续约束普通文件、Terminal、MCP、Skill、媒体和 3D 任务；本 TDD 不改变这些能力。

## 1. 用户决策

通用记忆工作台的核心不是通用 Agent 自由探索，而是：

```text
用户问题
  -> 程序读取 wiki/index.md
  -> 程序一次性收集相关 Wiki 页面
  -> 模型根据用户问题与 Wiki Context 汇总回答
  -> 回答下显示“写入 Wiki”
  -> 用户确认后程序直接写入
```

模型负责理解问题、生成检索条件、综合资料和组织答案；程序负责索引读取、路径解析、页面收集、目录创建、文件写入、索引更新和结果验证。

明确目标文件的写入不应再次启动通用工具循环。用户点击“写入 Wiki”后，优先由程序直接保存已经生成的内容，不增加模型请求。

## 2. 根因

当前 Wiki 任务的失败不是本地文件慢，而是职责边界错误：

1. `selectMemoryTools()` 对一个 Wiki 请求同时开放 `wiki`、`read`、`glob`、`grep`、`write`、`edit` 和 `mkdir`。
2. `runDirectChatCompletion()` 允许模型在只读工具和写入工具之间自由往返。
3. `wikiRuntime.searchWiki()` 能返回候选证据，但没有把“索引导航、相关页面收集、链接扩展”封装成一次确定性查询。
4. 模型看到多个工具后可能重复检查 Wiki，直到耗尽请求上限，仍未进入写入阶段。
5. “写入 Wiki”按钮目前仍把确认动作重新交给模型，而不是把已确认回答交给文件服务。

因此，继续增加模型轮数、保留更多工具结果或恢复 `64` 轮循环都不是根因修复。

### 2.1 当前 `wiki_context` 草案仍不够

仅把现有 `wiki_search` 重命名为 `wiki_context` 不能达到目标。若工具仍只返回逐字命中的几行，模型仍然需要自行 `read/glob/grep`，或者会漏掉由 `index.md` 路由到的规范、进度、资产和相邻页面。

`wiki_context` 必须同时承担四件确定性工作：

1. 从入口读取导航和创作路由。
2. 从问题、标题、路径、别名、章节和关键词确定候选页面。
3. 对候选页面做有限的一跳 Wiki 链接扩展，并标明扩展原因。
4. 返回覆盖度、缺失路由和来源路径，让模型知道“已查到什么”和“没有查到什么”。

它不是另一个自由文件工具，也不是向量数据库；它是 Wiki 的查询编排边界。

## 3. 参考项目对照

`my-llm_wiki` 的核心合同与本 TDD 一致：

- 三层结构：Raw Sources、Wiki、Schema。
- 三个核心操作：Ingest、Query、Lint。
- `index.md` 是内容目录和 LLM 导航入口。
- Query 先读索引，再深入相关页面。
- Wiki 是持久化、互相链接的知识产物，而不是每次从所有原始文件重新发现知识。

该项目还提供向量搜索、知识图谱、Deep Research、队列和自动摄取等增强能力。本 TDD 不引入这些能力：当前产品首先需要可靠、快速、可解释的本地 Markdown 查询与确认写入。

## 3.1 冲突设计处置

| 现有设计 | 执行新 TDD 后的处理 |
| --- | --- |
| Wiki 查询同时开放 `wiki_search/read/glob/grep` | 从默认 Wiki 查询路由移除，改为只开放 `wiki_context` |
| 模型先查 Wiki、再自行枚举相关页面 | 由 `wiki_context` 内部完成入口、候选和一跳扩展 |
| “写入 Wiki”按钮再次发送一条模型指令 | 退役；按钮直接提交已保存的持久化草稿给程序写入 |
| 写入前先让模型调用 `mkdir` | 退役；文件服务一次写入时自动创建父目录 |
| `wiki` 的 `search` action 作为普通查询入口 | 退役为兼容/维护能力；普通查询不再调用 |
| `wiki` 的 `scaffold/status/validate/audit/graph/evidence/replace/extend` | 保留，仅在用户明确执行 Wiki 管理、巡检或修正时开放 |
| `read/glob/grep/write/edit/mkdir` 低层工具实现 | 保留给明确文件任务、已有页面修改和兼容调用；不进入 Wiki 查询主链路 |
| 五个 Wiki Skill 的旧合同和历史 TDD | 不删除历史证据；不再作为运行时合同、默认路由或模型提示词来源 |
| 轻上下文 TDD 的 Wiki 三请求循环 | Wiki 专用查询/创作路径改用本 TDD 的 `1-2` 次模型请求；其他任务仍遵循轻上下文 TDD |

“删除”首先指从默认路由、工具 schema 和提示词中删除；历史文档、归档和无调用者确认前的实现不做物理删除。只有新链路和回归测试稳定后，才清理确认无调用者的旧查询包装。

## 4. 产品合同

### 4.1 Wiki 查询

用户输入“查询 Wiki”“根据 Wiki 回答”“查一下角色设定”等请求时：

1. 程序确定当前唯一 Wiki 根目录。
2. 程序读取 `wiki/index.md`；开发项目兼容 `docs/wiki/CLAUDE.md` 入口。
3. 根据用户问题和入口中的链接、标题、别名、分类、关键词匹配候选页面。
4. 程序并行读取候选页面，并按入口直接指向、标题命中、关键词命中和链接邻接排序。
5. 结果合并为一个有路径、标题、章节和正文的 `Wiki Context`。
6. 模型只根据“用户问题 + Wiki Context”回答，不再自行枚举或重复读取文件。

### 4.2 根据 Wiki 创作

用户输入“根据 `wiki/index.md` 创作下一集”等请求时，程序按入口路由收集：

```text
入口
  -> 创作规范
  -> 当前进度
  -> 总纲
  -> 当前分卷/分集大纲
  -> 上一章/上一集结尾
  -> 本次涉及的角色、场景、道具、伏笔
```

只读取入口能够到达且与当前请求相关的页面，不读取整部小说，不把全部对话历史当作记忆。

### 4.3 确认写入

每条 Wiki 查询或创作回答可附带一个“写入 Wiki”按钮。按钮绑定的是本次回答的持久化草稿：

```text
answerMarkdown
targetPath 或 targetDirectory
title
summary
sourcePaths
writeMode: create | append | replace
```

用户点击后：

1. 程序校验目标路径属于当前项目 Wiki。
2. 程序自动创建缺失的父目录。
3. 程序按 `create/append/replace` 执行一次写入。
4. 新页面写入时，程序更新直属目录 `_index.md` 或 `wiki/index.md` 的最小导航项。
5. 程序追加一条 `log.md` 记录。
6. 程序重新读取目标确认写入成功，并显示确定性结果。

点击按钮不调用模型、不启动 `read -> mkdir -> write` 工具链、不要求模型复述正文。

## 5. 模型与程序边界

| 工作 | 负责方 |
| --- | --- |
| 判断用户问题需要哪些 Wiki 主题 | 模型生成查询条件；程序执行检索 |
| 读取 `index.md` | 程序 |
| 解析 Wiki 链接和目录 | 程序 |
| 查找候选页面 | 程序 |
| 并行读取页面 | 程序 |
| 总结、比较、创作和引用来源 | 模型 |
| 判断目标路径是否合法 | 程序 |
| 创建目录、写入、追加、覆盖保护 | 程序 |
| 更新索引和日志 | 程序 |
| 验证写入结果 | 程序 |

模型不是文件系统控制器。模型只在需要语义理解时参与，不负责确定性文件生命周期。

## 6. 最小运行时设计

### 6.1 `wiki_context` 查询能力

新增一个面向 Wiki 任务的确定性查询能力，优先复用现有 `wikiRuntime`、项目文件服务和路径校验，不另建记忆数据库。它必须是一个“查询编排器”，不能只是现有 `wiki_search` 的别名。

输入：

```ts
{
  question: string
  mode?: 'query' | 'continuity'
  scope?: 'active' | 'all'
  entryPath?: string
  hints?: string[]
  maxPages?: number
  maxTokens?: number
}
```

输出至少包含：

```ts
{
  entry: { path: string; content: string }
  sources: Array<{
    path: string
    title: string
    reason: 'entry-route' | 'title' | 'path' | 'keyword' | 'wikilink'
    sections: string[]
    content: string
  }>
  matchedRoutes: string[]
  missingRoutes: string[]
  expandedPaths: string[]
  omittedPaths: string[]
  coverage: 'complete' | 'partial' | 'none'
}
```

内部流程：

```text
确定 Wiki 根目录
  -> 读取 index.md/CLAUDE.md
  -> 解析入口直属链接、别名、分类和创作路由
  -> 从 question/hints 提取有限检索词
  -> 按标题、路径、别名、章节、正文命中排序
  -> 读取候选页面
  -> 对候选页面做一跳 Wiki 链接扩展
  -> continuity 模式补齐规范、进度、大纲、上一章/集和资产路由
  -> 按 maxTokens 选择完整章节
  -> 返回来源、覆盖度、缺失项和省略项
```

精度合同：

- `index.md` 或开发项目入口是每次查询的第一事实源；入口读取失败不得假装完成全库搜索。
- `query` 模式至少覆盖入口直接命中的页面、问题命中的页面和必要的一跳链接页面。
- `continuity` 模式优先覆盖入口中标记的创作规范、当前进度、总纲、分卷/分集大纲、上一章/上一集结尾及相关角色、场景、道具、伏笔；缺失项必须显式返回。
- 页面正文按章节截取，不能只返回一行命中摘要；每个片段必须带文件路径和标题。
- 默认最多返回 `12` 个页面；具体上限按模型可用上下文动态收紧。
- 默认不读取 `log.md`、`归档/` 和 Raw 对话记录，除非用户明确要求历史或归档。
- 结果按相关度后稳定路径排序，保证相同输入在同一快照下可复现。
- 无匹配返回 `coverage: 'none'`；有入口但资料不全返回 `coverage: 'partial'`；不能把 `partial` 伪装为完整资料。
- `omittedPaths` 必须可见，模型只能基于返回内容回答；不能自行退回 `read/glob/grep`。
- 首版使用现有本地扫描和内存缓存；只有真实用例证明逐字/入口检索持续漏召回，才另写 TDD 评估 BM25 或向量检索。

### 6.1.1 是否足够达到目标

在 Wiki 结构遵守入口路由、页面标题/别名清晰、相关页面存在内部链接的前提下，以上能力足以覆盖当前目标：查询规则、汇总工作进度、按大纲续写小说/剧本，以及生成资产提示词。

它不能保证发现用户从未在入口、标题、别名、正文关键词或内部链接中表达过的隐含关系。遇到这种情况，正确行为不是继续扩大扫描，而是返回 `coverage: 'partial'`，列出 `omittedPaths/missingRoutes`，让用户补充关键词或指定页面。这样才能同时满足“尽量完整”和“不会把整库塞进模型”。

对百万字项目，真正决定效果的不是把所有正文一次发给模型，而是：

```text
短入口稳定
  + 创作路由明确
  + 页面标题/别名可检索
  + 关键页面有 [[Wiki 链接]]
  + 查询结果带覆盖度和来源
```

如果这五项成立，`wiki_context` 是足够的；如果入口和链接混乱，任何单一工具名都不能保证连续创作不失忆。

### 6.2 模型请求边界

`wiki_context` 首先是程序内部的查询编排能力，不是默认暴露给模型的自由工具。标准 Wiki 查询优先在首个模型请求前完成 Context 组装：

```text
首选形态：程序预先构造 Wiki Context -> 模型一次回答
受限形态：模型请求一次 wiki_context -> 程序执行 -> 模型一次回答
```

首选形态覆盖绝大多数“查询 Wiki”和“根据 Wiki 创作”请求，避免为本地检索额外消耗一次模型请求。受限形态只用于程序无法从当前问题确定足够检索条件、或用户明确要求补充检索的情况。

形态 B 也只能执行一次 `wiki_context`。工具结果返回后，下一次模型请求不得再携带 `wiki_search/read/glob/grep/wiki` 工具；模型不能把 `wiki_context` 当成可重复调用的搜索接口。

`wiki_context` 的一次执行可以读取多个本地页面，但对模型表现为一个工具调用；模型不能逐页驱动文件读取。

Wiki 查询默认最多 `1` 次模型请求；受限补充检索最多 `2` 次模型请求；不恢复 `64` 轮循环。只读搜索不能因为模型重复调用而延长任务。

### 6.3 查询与写入分离

“写入 Wiki”按钮不属于模型工具调用路径，而属于 App 文件操作路径：

```text
回答完成 -> 保存持久化草稿 -> 用户点击 -> 程序写入 -> 程序验证
```

模型需要整理成长期页面时，在回答阶段生成 `answerMarkdown/title/summary/target` 元数据；不在点击后重新生成。若模型未返回建议目标，按钮必须要求用户选择目标，不猜测路径。

如果用户要求“修改已有页面”而不是保存当前回答，才进入独立的 `read target -> model patch -> program edit -> verify` 流程。

## 7. 路由规则

| 用户意图 | 程序预处理 | 模型能力 | 禁止能力 |
| --- | --- | --- | --- |
| 查询 Wiki | 构造 Wiki Context | 回答 | `wiki_search/read/glob/grep/write/edit/mkdir` |
| 根据 Wiki 创作 | 按入口收集创作资料（`mode: continuity`） | 创作 | 全库枚举、Raw、`wiki_search/read/glob/grep` |
| 点击写入 Wiki | 直接保存持久化草稿 | 无 | 所有模型请求 |
| 明确写入指定文件 | 校验目标并准备内容 | 生成内容 | 反复检查、重复创建目录 |
| 修改已有 Wiki 页面 | 读取目标并提供最小上下文 | 生成 patch | 无关页面搜索 |
| 普通聊天 | 不读取项目 | 直接回答 | 所有 Wiki 工具 |
| 明确 MCP/媒体/3D | 进入既有独立能力链路 | 仅对应能力 | Wiki 查询循环混入 |

“查询 Wiki 并写入”只有在用户明确要求同一条消息直接写入时才合并；单纯查询默认只回答并显示确认写入按钮。

## 8. `index.md` 合同

`index.md` 保持短小、稳定和人工可读：

- 只包含 Wiki 根目录、分类入口、创作入口和必要的操作说明。
- 顶层页面使用 `[[页面]]` 或 `[[目录/_index]]` 链接。
- 不把百万字正文复制进 `index.md`。
- 页面新增或移动时，由程序更新直属导航项；不让模型自由重写整份入口。
- 索引更新失败不回滚已成功保存的正文，但必须显示“正文已写入、索引待更新”。
- 入口不存在或同时存在多个 Wiki 根目录时，停止自动查询并提示用户选择。

## 9. 失败与安全边界

- 路径越过项目根目录、指向 Raw、系统骨架或项目外文件时，程序拒绝。
- 目标文件存在且写入模式为 `create` 时，不覆盖，提示用户改用追加或替换。
- 用户未指定目标目录时，写入按钮使用模型返回的建议目标；建议目标缺失则打开最小目标选择，不猜测相邻目录。
- Wiki Context 不足时，模型必须明确说明缺少页面或来源，不自行补充项目事实。
- `wiki_context` 失败只允许一次明确降级：返回入口读取错误或要求用户指定页面；不得退回自由 `read/glob/grep` 循环。
- 取消查询时停止未完成的并发读取；取消后不执行写入。
- 写入完成后不再请求模型宣布成功，避免写入成功却因最后一次模型请求失败而显示失败。

## 10. 红灯测试

### 10.1 查询收口

1. “查询 Wiki 中的角色设定”在首个模型请求前由程序直接注入 Context；不开放任何 Wiki 工具。只有无法确定检索条件时才开放一次 `wiki_context`，仍不开放 `wiki_search/read/glob/grep/write/edit/mkdir`。
2. `wiki_context` 一次执行会读取入口、匹配候选、扩展一跳链接并返回相关页面，不能触发第二次同目标扫描。
3. 返回结果包含 `matchedRoutes/missingRoutes/expandedPaths/omittedPaths/coverage`，并为每个页面提供路径、标题、章节和正文。
4. `continuity` 模式覆盖入口标记的创作规范、进度、大纲、上一章/集和相关资产；缺失资料显式返回。
5. Wiki 查询默认一次模型请求；受限补充检索最多两次模型请求；模型重复请求 `wiki_context` 时运行时拒绝第二次并要求直接回答。
6. 查询结果不包含 Raw 对话和归档内容，除非用户明确要求。
7. 无匹配或 `coverage: partial` 时模型不生成未被来源支持的项目事实。

### 10.2 创作资料收集

1. “根据 `wiki/index.md` 创作下一集”读取入口指向的规范、进度、大纲、上一集结尾和相关资产页面。
2. 创作任务不读取整部小说，不枚举项目根目录，不加载 Wiki Skill。
3. 相关页面不足时显示缺少来源，而不是调用无限搜索。
4. 创作回答保留来源路径和建议写入目标，供按钮使用。

### 10.3 确认写入

1. 点击“写入 Wiki”不增加模型请求。
2. 指定 `wiki/工作进度/2026-08-27.md` 时一次程序写入，自动创建父目录。
3. 指定 `wiki/工作进度` 时程序按日期或标题生成稳定文件名，一次完成写入。
4. 新页面成功写入后更新直属 `_index.md` 和 `log.md`，失败分别报告，不重复写正文。
5. `create` 不覆盖现有文件；`append` 和 `replace` 的行为可测试且需保留审批边界。
6. 写入成功后 UI 显示确定性路径，不要求模型再生成结束语。
7. 写入按钮使用回答阶段保存的草稿和建议目标；点击后模型请求数保持不变。

### 10.4 能力隔离

1. 普通 Wiki 查询不发送 MCP、媒体、3D、Terminal schema。
2. 明确 MCP、媒体或 3D 口令仍进入各自现有链路，不受 Wiki 查询收口影响。
3. Raw、系统骨架和项目外路径保护保持通过。
4. Web、Desktop、Mobile 均使用相同查询语义，各平台只替换现有文件适配器。

### 10.5 冲突退役

1. 默认 Wiki 查询的工具集合中不存在 `wiki_search`、`read`、`glob`、`grep`、`write`、`edit` 和 `mkdir`。
2. 模型系统提示词不再要求查询 Wiki 前自行执行 `read -> glob -> grep`。
3. 旧五 Wiki Skill 不进入模型目录、Skill 自动选择或 Wiki 查询结果。
4. `wiki` 管理 action 仍可被用户明确激活；其 `search` action 不作为普通查询实现。
5. “写入 Wiki”按钮调用程序写入函数，不调用 `runMemoryChat()`。
6. 轻上下文 TDD 的 Wiki 专用旧测试被迁移或标记为本 TDD 的兼容维护测试，不能继续约束默认查询路由。

## 11. 性能验收

固定同一脱敏 Wiki、同一用户问题和同一模型，记录：

| 指标 | 目标 |
| --- | --- |
| Wiki 文件服务调用 | 查询最多一次入口读取加一次批量页面收集；页面读取在程序内并行 |
| Wiki 工具执行 | 默认 `0` 次；受限补充检索最多 `1` 次 `wiki_context`，禁止重复同目标执行 |
| 查询模型请求 | 默认 `1` 次，受限补充检索最多 `2` 次 |
| 点击写入模型请求 | `0` 次 |
| 查询前端工具轮 | `0-1` 轮 |
| 写入确认耗时 | 不包含模型等待，仅受本地文件服务耗时影响 |
| 结果正确性 | 返回所有入口路由到且与问题相关的页面，不返回无关 Raw/归档 |

Codex 的外部耗时只作参考，不作为同渠道基准。真实模型验收必须记录模型 ID、Provider、输入 Wiki 快照、请求次数、工具执行次数、总耗时、来源路径和最终答案；未执行的环境不得记为通过。

## 12. 最小实施顺序

```text
1. 为 wikiRuntime 增加一次性 Wiki Context 查询、覆盖度和连续创作路由 -> 验证：10.1、10.2 红灯转绿
2. 将 Wiki 查询路由从通用文件工具切换为 wiki_context -> 验证：不再发送自由 `read/glob/grep`
3. 为回答保存持久化草稿并让按钮走程序写入 -> 验证：10.3 红灯转绿
4. 程序化更新 index.md、直属 _index.md 和 log.md -> 验证：写入后导航与日志可复查
5. 将旧 Wiki Skill 查询/沉淀路径从默认运行时和提示词中退役；保留历史文档和兼容实现直到无调用者 -> 验证：冲突处置门禁
6. 保留已有修改页面、MCP、媒体、3D 和 Raw 安全链路 -> 验证：10.4 红灯转绿
7. 执行自动测试、跨平台测试和三次真实模型前向 -> 验证：第 11 节
```

不先重写 Direct Engine，不新增向量数据库、RAG 服务、摘要 Store、任务队列或新的聊天模式。优先把现有 `wikiRuntime`、项目文件服务、模型上下文组装和回答按钮串成一条确定性主链路。

## 14. 非目标

- 不删除 MCP、媒体、3D、Skill 或普通文件能力。
- 不把 Wiki 拆成新的 UI 模式。
- 不恢复跨任务记忆、64 轮循环或完整聊天记录注入。
- 不默认引入向量数据库、Embedding、BM25 服务或远程 RAG。
- 不让模型自动写入 Wiki；写入必须由用户点击确认或用户明确要求直接写入。
- 不修改历史 Wiki、归档文档或既有 TDD 的历史结论。

## 15. 完成判定

本 TDD 只有在以下条件全部满足后才能标记为已实施：

1. 查询 Wiki 不再出现重复检查导致的工具预算耗尽。
2. 明确目标的“写入 Wiki”点击动作不产生模型请求。
3. 查询、创作和写入均能提供可复查的来源路径与确定性文件结果。
4. 自动测试、TypeScript、Web/Desktop 构建和差异检查通过。
5. Desktop、Web、Mobile 至少各完成一次真实 Wiki 查询和确认写入验收。
6. 三次固定模型前向均记录请求数、耗时、工具执行数和答案正确性。

在第 5、6 项完成前，状态只能写“代码与自动测试已通过，真实模型/平台验收待执行”。
