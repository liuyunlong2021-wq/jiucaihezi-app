# 输入法组合态回车误发送修复 TDD

> 状态：已实施，待真实设备验收
> 范围：通用记忆工作台对话输入框

## 1. 问题

中文输入法正在显示候选词时，用户按回车本应完成候选上屏；当前输入框把这次回车误判为发送操作，导致内容直接提交。

## 2. 根因假设

共享输入框原本已经检查 `event.isComposing`，但部分 WebView 在输入法候选回车时只上报 `keyCode === 229`，或过早把 `isComposing` 置为 `false`。原判断缺少 229 兼容，而且不在候选菜单处理之前。

## 3. 最小方案

在共享发送入口最前面增加组合态保护：

```ts
if (event.isComposing || event.keyCode === 229) return
```

组合态回车只交给输入法处理；普通回车的既有行为保持不变。发送按钮不改。

## 4. TDD 验证

先写回归测试：

1. `isComposing: true` 的 `Enter` 不调用发送。
2. `keyCode: 229` 的 `Enter` 不调用发送。
3. 普通 `Enter` 仍调用发送。
4. `Shift+Enter` 的既有换行行为不变。

## 5. 验收

输入中文拼音并选择候选字母 `C`，按回车后 `C` 留在输入框且未产生新消息；点击发送按钮后才提交。英文普通回车发送、换行和移动端输入行为均无回归。

## 6. 边界

本 TDD 不改发送按钮、不新增输入法检测器、不调整候选菜单和其他快捷键；真实 WebView、Desktop、iPhone/iPad 人工矩阵在实施后执行。

## 7. 当前验证

记忆工作台定向测试 `55/55`、`vue-tsc -b` 和 `git diff --check` 通过。完整 focused 未在并行创作取消改动合入后重跑；真实 WebView、Desktop、iPhone/iPad 人工矩阵仍待执行。

## 8. 实施结论与复用经验

1. 组合态保护必须是 `handleComposerKeydown()` 的第一条逻辑，先于 `@` 候选、Escape、方向键和发送分支；否则候选回车仍可能被菜单截获。
2. 保留原生 `event.isComposing`，并用 `event.keyCode === 229` 覆盖部分 WebView 的候选回车兼容路径；不新增组合态 Store、计时器或自定义输入法检测器。
3. 回归测试断言保护位于函数入口，而不只检查发送条件含有 `229`，防止以后调整分支顺序后重新截获输入法事件。
