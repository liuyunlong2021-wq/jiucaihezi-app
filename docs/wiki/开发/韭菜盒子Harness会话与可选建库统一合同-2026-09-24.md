# 韭菜盒子 Harness 会话与可选建库统一合同

> 日期：2026-09-24
> 状态：用户已确认；现行终局合同，P1-P4 生产链路与 TDD 已实施，待真实 Desktop 跨重启验收
> 范围：Desktop 记忆工作台的聊天、对话选择器、Harness Session、记忆按钮和文件树建库
> 替代：`.raw/对话记录` 作为新对话真源、`.raw/记忆索引`、记忆/查询双开关、打开项目后必须先“创建记忆空间”的合同

## 1. 一句话结论

用户打开韭菜盒子即可聊天：**Harness Session 是完整 Agent 上下文、工具轨迹、持久化和压缩的唯一运行时真相；韭菜盒子只管理 UI、对话目录、能力选择和项目文件。**

`.raw` 不再是开始聊天的前置条件。文件树现有“建立改编 Wiki”按钮同时建立改编 Wiki 与素材目录；未来其他一键建库模板复用同一入口，但本期不增加模板选择器。

## 2. 数据所有权

| 数据 | 唯一所有者 | 存放位置 | 禁止事项 |
| --- | --- | --- | --- |
| 完整对话、工具轨迹、压缩历史 | Harness Session | App 管理的 Harness 数据目录 | 不再复制成每轮 Raw Markdown，不再由 UI 重建最近三轮 |
| 对话标题、排序、工作区与 Session 映射 | 韭菜盒子对话目录 | 既有 App 本地持久层 | 不保存消息正文、工具正文或第二份压缩摘要 |
| Wiki、剧本、合同等正式作品 | 项目文件树 | 用户项目 | 不塞进 Harness 私有存储 |
| 文档、图片、视频、音频素材 | 项目文件树 | 新合同见 §4 | 不因删除对话而删除项目资产 |
| 旧 Raw 对话 | 兼容来源 | `.raw/对话记录/*.md` | 迁移成功后不得继续双写 |

## 3. 打开即聊

1. 选择或打开项目后，聊天区立即可输入，不检查 `.raw/对话记录`，不显示“创建记忆空间”空状态。
2. 新建对话时只创建一个对话目录项和稳定 Session ID；第一次发送时由 Harness 创建持久 Session。
3. 同一对话始终映射同一 Harness Session：
   - `conversationId` 是韭菜盒子的稳定 UI 标识；
   - `sessionId = jc-v1-<conversationId>`；
   - 重开 App、切换对话和 Harness 进程重启均恢复该 Session；
   - 正常续聊只发送当前消息，不附带最近三轮或 Raw 全文。
4. Harness 运行数据退出项目 `.raw/临时任务`，进入 App 管理的数据目录；项目目录里不因普通聊天自动出现 Runtime 文件。
5. Desktop 不再显示或保存 `@DH` 选择态：所有对话自动进入 Harness。`@排版`、`@影音`、`@MCP`、`@3D` 通过官方 `dsh-mcp-client` 成为 Harness 原生工具；韭菜盒子只把调用转交给既有执行器，不再切换第二套 Agent Runtime。Web/Mobile 现有能力不因 Desktop 收口而削弱。

## 4. 文件树“一键建库”

现有“建立改编 Wiki”按钮维持单击即建，不增加向导。本期在原 Wiki 骨架之外增加：

```text
.raw/
├── 文档/
├── 图片/
├── 视频/
└── 音频/
```

规则：

1. 建库只补缺失目录和文件，不覆盖、不移动、不删除已有内容。
2. `.raw/文档|图片|视频|音频` 是一键建库直接创建的用户资料目录；本期不顺带重写既有媒体保存链路。
3. 既有 `.raw/jc-media/文档|图片|视频|音频` 继续可读、可写、可预览、可引用；不批量迁移。
4. 未点击建库也可以正常文字聊天；普通聊天不会为了准备目录而创建 `.raw`。
5. 未来“一键建库模板”只负责项目文件结构与模板内容，不能创建 Agent Runtime、对话存储或另一套记忆系统。

## 5. 记忆与查询按钮退役

前端删除：

- “记忆 开/关”按钮及状态；
- “查询 开/关”按钮及状态；
- 对话元数据中的 `memoryEnabled` / `memoryQueryEnabled` 编辑入口；
- 与按钮相关的提示、失败状态和样式。

后端/运行时删除：

- 回答后生成 `.raw/记忆索引/<conversationId>.md`；
- 发送前自动调用旧 `memory_search` 查询当前对话索引；
- 为最近三轮、Raw 全文和记忆索引拼装第二套上下文；
- 因记忆开关产生的模型摘要请求。

Harness Session 默认且始终保留当前对话的完整历史，并在需要时使用官方 Compaction，因此不再向用户暴露“是否记住当前对话”的假开关。

Wiki 搜索不受影响：用户选择 `@文件`、Skill 或后续 MCP 后，Harness 仍可搜索项目中的正式 Wiki 文件。项目知识与聊天上下文不是同一种记忆。

## 6. 对话选择器与 Harness Session

对话选择器保留现有交互：搜索、新建、切换、重命名、删除。

对话正文显示也必须来自 Harness：打开对话时，薄适配层调用官方 `SessionQueryEngine.readSession(sessionId)` 读取完整、已校验的 Session 事件，并把当前可见的 `user/message`、`assistant/message` 和需要展示的工具事件投影到现有聊天 UI。实时运行继续消费官方通知流；历史读取和实时流最终落到同一套 UI 节点，不建立本地消息副本。

当前 `dsh-sdk-client` JSON-RPC 尚未公开 Session 历史读取方法，因此实施时只给现有 runner 增加一个基于官方 `ctx.sessionQuery` 的薄查询请求，或直接采用官方后续公开的等价接口。禁止读取、解压或解析 `$DSH_HOME` 物理文件。**在 Session 历史能够完整恢复到 UI 之前，不得停止旧 Raw 对话的读取能力。**

最小目录记录：

```text
conversationId
sessionId
workspaceKey
title
createdAt
updatedAt
legacyRawPath?   # 仅旧对话迁移期存在
migratedAt?      # 仅旧对话迁移成功后存在
```

语义：

- **新建**：创建目录记录；首次发送创建 Harness Session。
- **切换**：按 `sessionId` 恢复 Harness Session，不读取 Raw 拼历史。
- **重命名**：只改目录标题，Session ID 不变。
- **删除**：先从目录移除，使 UI 不再可见；项目正式文件与素材不删除。当前 SDK 未提供单 Session 删除接口，不解析 Harness 私有存储强删；接到官方删除接口后再做物理回收。“清除全部本地数据”可以整体清除 App 管理的 Harness 数据目录。

对话目录是导航索引，不是第二份对话数据库。目录损坏不能改写 Harness Session；Harness Session 损坏也不能用不完整目录伪造正文。

## 7. 旧 `.raw/对话记录` 一次迁移

旧项目首次打开时继续列出有效 Raw 对话。用户打开其中一条时：

1. 沿用 Raw 中的 `conversationId`，计算稳定 `jc-v1-<conversationId>`。
2. 若对应 Harness Session 已存在，直接恢复，不再移交历史。
3. 若不存在，将旧 Raw 的完整可见轮次一次性作为“既有对话移交”交给 Harness。
4. 只有 Harness 成功完成首轮并持久化后，目录才写入 `migratedAt`。
5. 迁移失败不写标记，Raw 保持可重试；不得创建半迁移空 Session 冒充成功。
6. 迁移成功后，旧 Raw 保留为只读历史证据；新轮次只进入 Harness，不再双写 Raw。

不做后台全量迁移，不扫描所有旧对话，不在升级时阻塞用户。

## 8. 实施顺序与验收

### P1：打通 Session 历史显示与对话目录

- 接入官方 `sessionQuery.listSessions/readSession` 能力的最薄桥接。
- 用轻量目录驱动现有对话下拉，历史 Session 投影到现有聊天 UI。
- 实施旧 Raw 一次移交、成功标记、重命名与逻辑删除。

验收：完成两轮对话后退出 App；重开仍能看到两轮正文和必要工具轨迹，继续发送时 Harness 能引用前两轮事实，且没有读取 Session 物理文件。

### P2：取消前置门禁与旧记忆

- 删除创建记忆空间入口和 `memoryReady` 发送门禁。
- 删除记忆/查询前后端链路。
- 新对话直接建立目录映射并运行 Harness。

验收：一个没有 `.raw` 的空项目打开后可以立即完成两轮连续对话；第二轮只发送本轮消息。旧 Raw 对话打开后续聊成功，迁移后不再新增 Raw 轮次。

### P3：建库与素材路径

- 扩展现有 `applyAdaptationWikiScaffold()`，增加四个 `.raw` 素材目录。
- 新保存路径改为 `.raw/<类型>/`；保留旧 `jc-media` 读取兼容。

验收：重复点击建库幂等；已有同名内容不覆盖；四类新资产分别进入对应目录。

### P4：Harness 存储出项目

- 将 `DSH_HOME` 与 route patch 移到 App 管理目录，并按工作区隔离。
- 项目中不再生成 `.raw/临时任务/deepseek-harness`。

验收：没有 `.raw` 的项目可跨进程恢复 Session；切换项目不会串会话；API Key 不落盘。

## 12. 与官方 Harness 的关系

### 12.1 原则

1. **工具面跟随官方 profile（`--profile sdk`）**：官方自带的工具不增、不删、不按工具做产品级开关，官方默认启用的全部对模型可见，官方新增工具默认生效。产品自己的能力（`@排版`/`@影音`/`@3D`、外部 MCP）一律通过官方 `dsh-mcp-client` 挂载，不修改官方工具本身。产品侧只负责展示（中文标签，见 `DEEPSEEK_TOOL_LABELS`）与登记。
2. **只允许两类覆盖**：① 指向自家网关的 provider 配置（官方 profile 不绑厂商，必须给）；② 已明确决策的字段，逐条登记在 §12.3。
3. **覆盖一律用官方字段写进 route patch**。patch 按顶层键整体替换 `config`（`applyEntryPatches` 里是 `target[key] = value`，不是深合并），所以必须给全量键：实测给 `tool-subagent` 少写 `provider`/`toolName` 会把它们一并抹掉。
4. **官方没有的能力不自己造**：需要 SDK 尚未公开的能力时，只在协议边缘补最薄的桥，并在 §12.4 登记为待上游收口。

### 12.3 偏离登记

| 项 | 官方 | 我们 | 性质 |
| --- | --- | --- | --- |
| provider | profile 不绑厂商（`llm-pi-ai` 无 config） | 指向韭菜盒子网关：`apiKeyEnv` / `api: openai-completions` / `baseURL` / `models` | 必需 |
| 重试次数 | `DEFAULT_MAX_RETRIES = 5` | `retryPolicy.maxRetries: 1`，`retryableCodes` 保留官方那 6 类 | 有意：一次上游抖动不该被放大成 5 倍等待 |
| 模型上下文/输出 | `DEFAULT_CONTEXT_WINDOW = 262144`、`DEFAULT_MAX_TOKENS = 32768` | 显式写同样的值 | 形式差异：产品本地上下文计算依赖这两个常量，钉住避免两边漂移 |
| 子代理派发 | `backgroundMode: continuable`（该模式下 `run_in_background` 默认 true） | `one-shot`（默认等结果） | 有意：continuable 下父代理只拿到 id，会误判完成并重复派活 |
| MCP 工具调用超时 | `6e4`（60 秒） | `toolCallTimeoutMs: 900000` | 有意：生图/生视频/3D 导出是长任务 |
| Harness 数据目录 | 调用方给 `DSH_HOME` | AppData/`deepseek-harness/workspaces/<cwd sha256 前 12 字节>`，按项目隔离 | 有意：Runtime 不落用户项目 |
| 权限模式 | `DSH_PERMISSION_MODE ?? 'workspace-write'`；`workspace-write → approval: ask`、`danger-full-access → never` | 由 `@文件` 决定：开 → `danger-full-access`，关 → `workspace-write` | 有意：`@文件` 是唯一本机开关。沙箱内操作本来就不弹窗，「零弹窗」的前提是操作在工作区内 |
| 会话标识 | 官方自生成 UUID | `jc-v1-<conversationId>` | 有意：对话目录需要稳定映射 |
| 子代理审批 | 委派继承 `approval: never`（`source: delegation`） | 未干预 | 与官方一致 |
| SDK server 源码 | 0 处改动 | 4 处 vendor patch | 临时，见 §12.4 |

### 12.4 待上游收口的临时差异

`scripts/prepare-deepseek-harness.mjs` 安装时给官方 `dsh-sdk-jsonrpc-server` 打 4 处补丁；任一处布局不符即抛错，不会静默降级：

1. `agent/assistant-stream` → `session.assistant-stream` 通知（钉住的 SDK 不发增量文本，UI 需要流式）。
2. `createSession` → 先 `sessionPersistence.stat()`，已持久化的会话走 `agents.resume`（SDK 0.1.7 会对已存在的会话重新 create，历史读不回）。
3. `inject` 增加 `sessionQuery`。
4. JSON-RPC 增加 `session/list`、`session/read` 两个请求。

上游公开等价接口后整体删除，改走官方调用。

### 12.5 可回收的自研等价实现（官方已有接口）

| 我们的做法 | 官方接口 | 回收路径 |
| --- | --- | --- |
| `runner.mjs` 在 `harness.run()` 的 `onNotification` 里按 `params.sessionId` 手过滤 | `client.subscribe(filter: NotificationFilter)`、`client.subscribeSessionTree(sessionId)`。官方注释写明：「The runtime notifies for every session in its context, so this client applies the scope.」 | 换成 `client.prompt()` + 带 filter 的订阅；手过滤是这条官方作用的等价实现，留着不会出错 |
| `deepSeekSessionTurns()` 手写事件投影（只取 `user/message`、`assistant/message` 和工具进度） | 官方有 `session-projection` 插件，但 SDK client 尚未公开该接口 | 上游公开后改用官方投影；在此之前事件 schema 变化只会表现为投影缺失，不会报错，改 SDK 版本时要一并核对 |
