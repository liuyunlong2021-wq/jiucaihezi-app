## 2. 根因：为什么始终控制不了

按 AGENTS §0 追溯，真实使用链路是"电脑开着韭菜盒子 → 手机打开 → 连上 → 选对话 → 发任务 → 看结果"。前四步就有结构性断点：

1. **每次重启都要重新配对。** `remote_bridge_start` 绑定 `0.0.0.0:0`（随机端口），地址 `local_ip:port` 写进配对 offer，手机凭证只存这个地址。电脑重启 App、重开桥或 DHCP 换 IP 后，手机拿旧地址必然连不上，配对页也没有改地址入口。信任本应锚定 Desktop Noise 公钥，却被绑在一个易变地址上。
2. **桥默认关闭，且不会自动恢复。** 只有设置页"开启"按钮会调用 `remote_bridge_start`，App 启动时不恢复。人不在电脑前就无法补开。
3. **只能控制电脑当前打开的那个对话。** `DesktopRemoteHost.assertCurrentSession` 拒绝非当前 Session（`SESSION_NOT_CURRENT`），手机无法选项目或对话。人不在电脑前时，"电脑上恰好开着对的对话"无法保证。
4. **出门就断。** 只有 LAN；Mini Relay 排在 G4。
5. **电脑睡眠/关窗即离线。** 无托盘驻留、无防睡眠（G5）。
6. **测试替身掩盖了 1–3。** Rust 端到端测试固定 `127.0.0.1` 与当前 Session，正好绕开以上全部断点。

V2 合同把"可靠同步"（G1/G2）排在"可达"（Relay/常驻，G4/G5）之前。协议是对的，但这个顺序让用户一个月里一次稳定使用都没有。**本计划把"连得上、选得到"提到最前面**，再在真实使用中完成 G1/G2 的正确性闸门。

**M3b 实施方案（2026-10-25 用户确认：配对时带房间号与密钥，不用登录账号；先本地 TDD，部署前再问）**

用户反馈：让用户另装 Tailscale 是错误的产品设计；与 Codex 手机端一样，应由我们自己的中继让两端都只做出站连接，用户除了扫码配对什么都不用装。Tailscale 降为“已在用的人可选”。

- **房间**：Desktop 首次开启手机控制器时生成 `roomId`（128 位随机，hex）与 `secret`（256 位随机），存系统钥匙串，与 Noise 身份同级。中继只存 `sha256(secret)`，首个 Desktop 连接写入（房间号不可猜，先到先得即可）。
- **下发**：二维码 offer 增加 `relay: { url, roomId, secret }`；认证回包也附带同一 `relay`，已配对的手机在家连一次即可拿到，不必重扫。
- **连接**：Cloudflare Worker `api.jiucaihezi.studio/relay/v1/rooms/<roomId>/{desktop|mobile|data/<id>}`，`Authorization: Bearer <secret>`，Durable Object `RelayRoom` 一房一实例，Hibernation API。Desktop 常驻一条 `desktop` 控制连接；手机连 `mobile` 后中继给 Desktop 发 `{"type":"open","id"}`，Desktop 为它另开 `data/<id>`，中继把两条连接按原样转发二进制帧。Desktop 不在线时手机得到 503 `DESKTOP_OFFLINE`；密钥不符 403。
- **复用现有协议**：两端各做一个“本地隧道”——Desktop 把每条 `data` 连接接到本机 `127.0.0.1:<桥端口>`，手机在本机开临时端口接到 `mobile` 连接——Noise 握手、配对、认证与 M0–M2 全部业务一行不改；中继只见密文。
- **候选顺序**：上次成功的地址 → 其余局域网/Tailscale 地址 → 中继。心跳 `ping`/`pong` 由 Cloudflare 自动应答，不唤醒 DO。

### 手机选创作模式（2026-10-26，用户按“第一性原理”重排后的第 1 项）

#### 发布顺序与验收

1. **配套版本**：核对手机包与可供测试者下载安装的 Desktop 包来自兼容源码；记录两个版本、构建号与 commit。过去的 Desktop dev 真机成功不等于正式安装版已验证。
2. **本地门禁**：focused、Rust、iOS 原生构建及 `audit:ios-app`；记录 Bundle ID、版本、签名、IPA 大小和 SHA-256。先查 Apple 后台已有构建号，再生成用于上传的正式构建，不猜构建号。
3. **签名与审核材料**：核对 Apple Distribution 签名、描述文件、审核联系方式、隐私/支持入口及配对操作说明。审核员需要一台可运行 Desktop 的电脑；若审核环境无法配对，先解决审核可访问性，不声称仅安装手机即可独立创作。
4. **内部 TestFlight 真机**：从 TestFlight 安装；首次权限与扫码/粘贴配对；电脑明确允许；局域网与蜂窝中继；新建/选择对话、三创作模式、发消息/停止/审批；查看 Wiki、图片、视频；电脑重启后免配对、手机锁屏/前后台与切网恢复、吊销后拒绝访问。只使用专门测试项目，费用相关操作另行明确。
5. **外部 Beta 审核**：内部验收通过后提交。首个外部构建需 Apple 审核；获批后用少量外部账号验证邀请安装和首次配对，再开放公开链接。不得把上传或审核中写成已可下载。
