## 2. 根因：为什么始终控制不了

按 AGENTS §0 追溯，真实使用链路是"电脑开着韭菜盒子 → 手机打开 → 连上 → 选对话 → 发任务 → 看结果"。前四步就有结构性断点：

1. **每次重启都要重新配对。** `remote_bridge_start` 绑定 `0.0.0.0:0`（随机端口），地址 `local_ip:port` 写进配对 offer，手机凭证只存这个地址。电脑重启 App、重开桥或 DHCP 换 IP 后，手机拿旧地址必然连不上，配对页也没有改地址入口。信任本应锚定 Desktop Noise 公钥，却被绑在一个易变地址上。
2. **桥默认关闭，且不会自动恢复。** 只有设置页"开启"按钮会调用 `remote_bridge_start`，App 启动时不恢复。人不在电脑前就无法补开。
3. **只能控制电脑当前打开的那个对话。** `DesktopRemoteHost.assertCurrentSession` 拒绝非当前 Session（`SESSION_NOT_CURRENT`），手机无法选项目或对话。人不在电脑前时，"电脑上恰好开着对的对话"无法保证。
4. **出门就断。** 只有 LAN；Mini Relay 排在 G4。
5. **电脑睡眠/关窗即离线。** 无托盘驻留、无防睡眠（G5）。
6. **测试替身掩盖了 1–3。** Rust 端到端测试固定 `127.0.0.1` 与当前 Session，正好绕开以上全部断点。

V2 合同把"可靠同步"（G1/G2）排在"可达"（Relay/常驻，G4/G5）之前。协议是对的，但这个顺序让用户一个月里一次稳定使用都没有。**本计划把"连得上、选得到"提到最前面**，再在真实使用中完成 G1/G2 的正确性闸门。

## 3. 重排后的路线

```text
M0 连得上（局域网）   → M1 闭环真机验收 → M2 任选对话
→ M3 异地（先 Tailscale，零代码；后 Relay） → M4 可靠性（原 G2） → M5 常驻/推送/发布（原 G5）
```

每阶段只有通过对应的真机记录才算完成；未执行的真机、公网与 TestFlight 验收不得写成已通过（AGENTS §4）。

### M0 连得上：配对一次，重启不失联

| 改动 | 位置 | 验证 |
| --- | --- | --- |
| 端口固定：首次随机选取后持久化，重启复用；被占用才换端口并上报新地址 | `remote_bridge.rs` `remote_bridge_start` | Rust：重启 core 后端口不变；端口被占用时返回新地址 |
| 用户开过桥则 App 启动时自动开启（持久化开关，默认仍关闭） | `App.vue` 启动绑定处 / `DesktopRemoteSettings.vue` | TS：开关持久化；启动时按开关调用 start |
| 手机凭证改为"Desktop 公钥 + 地址列表"；连接按"上次成功地址 → 其余候选 → 手动地址"依次尝试，信任只认公钥钉扎 | `remote_client.rs` `mobile_remote_connect`、`MobilePairingView.vue` | Rust：地址变更但公钥相同可重连；公钥不同时拒绝 |
| 配对页提供"编辑电脑地址"（可填 IP、`.local` 主机名或 Tailscale 主机名） | `MobilePairingView.vue` | UI 测试 |
| 双端诊断：Desktop 显示监听地址/已连设备/最近错误；手机显示正在尝试的地址与失败原因（超时、拒绝、公钥不符） | 两端设置/配对页 | `describeRemoteError` 测试 |

**实施状态（2026-10-25，源码与自动化）**：前三行已实施——`bind_listener` 复用 `app_data_dir/remote-bridge.json` 中的端口、被占才换；`start`/`stop` 记录开关，`setup` 中 `remote_bridge::autostart` 按开关在启动时开桥（默认仍关）；Desktop 认证回包报上 `addresses`（IP + Bonjour `名.local`），手机凭证新增 `addresses`，`connect_first` 按"上次成功 → 其余候选"逐个连接，单地址 4 秒建连上限，公钥不符优先报 `DESKTOP_KEY_MISMATCH`。新增 Rust 红→绿 7 项，Rust 全量 `505 passed / 2 ignored`，focused `2252 passed / 2 skipped`。**未做**：手机"编辑电脑地址"界面、双端诊断、真机闸门。升级后需重新配对一次（旧凭证里的随机端口已无效，且旧电脑没有保存过端口）。

真机闸门：配对一次 → 退出并重启 Desktop → 手机**不重新配对**即可连上；换一个 Wi-Fi 或 IP 后手动改地址仍可连。记录设备、版本、网络与结果。

### M1 闭环真机验收（收窄后的 G1）

不再新增协议，先在当前 DSH 0.2.1 运行时上把已经写好的 G1 跑通一次：

1. 重新构建 Desktop dev 与 iOS debug 包（两端版本一致，避免 9/28 的 `commandId` 版本错配）。
2. 真机：发送 → 首个 token 前看到 sending/accepted → 工具步骤 → 一次审批 → 最终官方历史 → 回到电脑继续同一对话。
3. 故障注入：切换工作台页面、手机切后台再回来、断开 Wi-Fi 后重连；命令只执行一次。
4. 发现的问题按"先写红测、再修"处理。

闸门即 V2 §14 G1 的真机闸门；窗口关闭后的无人值守不在此阶段。

### M2 任选对话（把 V2 G3 的导航提前）

| 改动 | 说明 |
| --- | --- |
| `project.list` / `session.list` / `session.create` | 读取现有 `harnessConversationCatalog`，只返回 V2 §6 允许的投影（不含绝对路径） |
| Host 由"只认当前 Session"改为"认授权 Session" | 删除 `assertCurrentSession` 的强绑定，改为按目录校验；Desktop UI 当前选中的对话不随手机切换 |

闸门：电脑停在 A 对话，手机在 B 对话发任务并完成审批；电脑切到 B 能看到同一 run 与最终历史；两端同发同一 Session 时一方得到 `SESSION_BUSY`。

### M3 异地

**M3a（零代码，先用起来）：Tailscale。** Mac 与 iPhone 装 Tailscale 并登录同一账号；M0 完成后，手机把电脑地址改成 Tailscale 主机名或 `100.x` 地址即可，Noise 端到端加密不变。这正是 [[架构/产品架构]] §3.2 里 vibetunnel 采用的"不自建中继"路线，适合你本人立即使用。产出：一页使用说明 + 一条蜂窝网络真机记录。

**M3b（产品化）：Mini Relay。** 面向不装 Tailscale 的普通用户，按 V2 §5.4/§11.2 实施。优先评估在现有 Cloudflare Gateway（`gateway/`）上用 Durable Objects 承载 WSS 配对房间，只转发 Noise 密文；部署、鉴权、日志权限先核实（V2 G4 第一条）。M3b 不阻塞 M4。

## 4. 不做

- 不在手机上运行 Agent、模型或 Skill；不镜像项目文件；不做远程桌面或终端复刻（V2 §12.2）。
- 不另建通用代理或多渠道插件。
- 不为 Mobile 删减 Desktop 任何现有能力；驻留、防睡眠与自动开桥都是可选新增。

## 5. 建议的第一个动作

从 M0 开始，按 TDD 先写三条红测：①重启后端口不变；②地址变更、公钥相同时可重连；③开过桥时启动自动开启。转绿后出一对 Desktop/iOS 包做 M0 真机验收，紧接着跑 M1。M0+M1+M3a 完成后，你本人即可在家里和外面控制电脑上的当前对话；M2 完成后可以任选对话。
