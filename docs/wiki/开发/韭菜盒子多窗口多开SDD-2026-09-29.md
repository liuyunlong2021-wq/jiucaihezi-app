# 韭菜盒子多窗口多开 SDD

> 状态：**第 0~5 步已实施**（自动验证通过）；真机验收待跑
> 日期：2026-09-29
> 范围：桌面端同时打开多个窗口，每个窗口绑定一个工作区
> 前提：**不引入多进程**；前端组件层目标零改动

## 1. 决策

对齐 **VS Code 的单进程多窗口模型**（我们是同类桌面应用），状态组织方式参考 **DH 官方的工作区并存语义**。

不做的事先说清楚：**不学 DH 官方那种「一个 host 服务多客户端」**。那是 web 应用的形态（`dsh web` 起 HTTP 服务 + 浏览器标签页），多开对它是免费的；我们是桌面 App，照抄会变成自建一套本地 HTTP 服务、把窗口降级成浏览器——代价远超收益。

## 2. 官方两侧的事实（都是查过的，不是印象）

### 2.1 VS Code（同类形态）

- 单进程多窗口：`requestSingleInstanceLock()`，第二次启动把 argv 交给已有实例并开新窗口
- 每个窗口一个 renderer（**独立 JS realm**），共享 main process
- 状态分两级：`workspaceStorage/<hash>`（每窗口/每工作区）+ `globalStorage`（共享）
- 同一文件夹第二次打开 → **聚焦已有窗口**，不新建
- 菜单是 app 级的，跟随焦点窗口

### 2.2 DH 官方

- **一个 host 进程 + 浏览器前端**：`dsh-web-app` = "the dsh browser-surface bundle"；`dsh-web-frontend` = "vite build over the dsh-client-web shell library; dist/ served by apps/cli's dsh web"。**多开 = 多标签页**
- **工作区是「并存」不是「切换」**：`ctx.workspaceRegistry.list()` 返回**全部**活动工作区（`dsh-api-workspace-controller/lib/index.js:68`），客户端 `dsh-client-ui-workspace` 只是 "Workspace picker plugin"——决定你在看哪个，不决定哪个活着
- **并发限制是 per-session**：`throw new RemoteError("session/agent-busy", "prompt rejected", …)`（`dsh-api-session-controller/lib/index.js:802`），不是全局
- 每个会话自己的状态：`running: this.ctx.agents.get(session.id)?.status === "running"`（同文件 `1782`），按会话广播 `api-session/status` / `api-session/activity`（`2833-2845`）
- 删除工作区前要检查 `workspace/session-active`（同文件 `302`）——工作区与活动会话的从属关系是显式的

## 4. 核心洞察：前端几乎零成本

调研列出了一长串「模块级单例」——Pinia stores、`selectedConversation`、`MemoryWorkbench.vue` 的全部 ref、`runtimes` Map、`mcpClient` 连接池……

**这些全都是每窗口一份**，因为 Tauri 每个窗口是独立 JS realm。多开时天然隔离，**前端组件一行都不用改**。

真正跨窗口共享的只有三类：

1. **localStorage**（同 origin 共享，且只有 `jcTheme` 监听了 `storage` 事件）
2. **Rust 进程全局**（`MCP_PROCESSES`、`window-state.json`、远程桥 `activeHost`）
3. **capability 授权**（按窗口 label 匹配）

所以本方案不是「重构一切」，而是**把「唯一」从进程下沉到窗口**。

## 5. 产品边界

### 5.1 本次做

1. 单实例：第二次启动不新起进程
2. runner 归属化：收割只收「owner 窗口已不存在」的
3. 建窗 command + `ws-<hash>` 窗口 label
4. 新窗口的 capability 授权
5. 前端按窗口区分 `jc_project_dir`
6. 菜单入口（新窗口打开工作区）

### 5.2 本次不做（附理由）

- **「一个工作区只在一个窗口打开」是强制约束，不是妥协。**
  `deepSeekHarness.ts:1155-1159` 的 abort 会 `stopRuntime`，把**同工作区**其它对话的运行一起打断；而 `ensureRuntime` 按 cwd 只有**一个** runner 槽（`1021-1049`），切权限档/切模型也会杀重建。允许两个窗口绑同一工作区，会立刻暴露成「点 A 窗口的停止，B 窗口的任务死了」。**VS Code 也是这么做的**（同一 folder 第二次打开 → 聚焦已有窗口）。用它把问题挡在门外，比现在去改 runtime 生命周期划算得多。
- **不改 `abort` 连坐**：同上，属于 runtime 生命周期重构，不在本轮。
- **不碰远程桥 `activeHost` 单例**：手机控制器一次只能连一个窗口，多窗口时以最后挂载的为准。已知限制，写进文档而不是假装没有。
- **不做单窗口内的工作区并存**：官方 `list()` 全并存，但多窗口天然给出了「并存」的观感。除非要「一个窗口里同时盯两个项目」。
- **不引入多进程**：多进程各自一份 Rust 全局状态、各自一份 runner，比多窗口更糟。

## 6. 实施步骤

### 第 0 步：单实例（止血，与多开解耦）

- 加 `tauri-plugin-single-instance`；第二次启动把焦点还给已有实例。
- **依据**：现在双击 Dock 图标会起**第二个完整进程**（各自一份 Rust 状态、各自一份 runner），且无任何提示。这比多窗口更糟，且与多开无关。
- 验证：双击图标 → 进程数不变，焦点回到已有窗口。

### 第 1 步：runner 归属化（核心）

`reap_stdio_processes_blocking`（`mcp.rs:205-245`）只遍历**本进程**的 `MCP_PROCESSES`，所以：

| 场景 | 后果 |
| --- | --- |
| 新**进程** | 表是空的，收不到别人 → 不是障碍 |
| 新**窗口**（同进程） | `main.ts` 每窗口都跑一次 → **把别的窗口的 runner 全杀了** ← 真障碍 |

它的原意写在 `mcp.rs:240` 注释里：dev 的 F5/HMR 重挂会丢掉指向运行时的句柄，不清理就会撞 `already owned by an active write handle`。

改法（保留原意，只加归属）：

- `McpStdioProcess` 加 `owner_window: String`（`mcp_spawn_stdio` 从调用窗口取 label）
- 收割时**只收 owner 窗口已不存在的**：dev 重挂照旧收（label 同名但旧 realm 已死），多窗口不收
- 窗口关闭时收掉该窗口的 runner（现在只有 app 退出才收）

验证：
1. 两窗口同时跑任务，互不打断
2. dev 下 F5 重挂 → 旧 runner 被收，不出现 `already owned by an active write handle`（原意图不回归）
3. 关掉一个窗口 → 它的 runner 被收，另一窗口任务不受影响

### 第 2 步：建窗 command + 窗口 label

- 加 `open_workspace_window(cwd)`：`WebviewWindowBuilder::new(app, label, …)`
- **label 复用仓库既有约定**：`ws-<sha256(cwd)[:12]>`——与 `deepSeekHarness.ts:828-831` 算 `DSH_HOME` 目录用的是同一个哈希。同工作区天然同 label，于是「已打开就聚焦」免费得到
- `window-state.json` 改成**按 label 键**存（`{"main": {…}, "ws-ab12…": {…}}`），否则多窗口互相覆盖几何
- `.on_navigation` 里两处硬编码 `"main"`（`lib.rs:1292-1298`、`1303-1309`）改成按 URL 反查所属窗口

验证：两窗口几何位置各自独立恢复；第二次打开同一工作区 → 聚焦已有窗口。

### 第 3 步：授权新窗口（配置，一行）

`src-tauri/capabilities/default.json:4` 的 `"windows": ["main"]` → `["main", "ws-*"]`。

Tauri 官方 capability schema 明确写支持 glob：

> List of windows that are affected by this capability. **Can be a glob pattern.** If a window label matches any of the patterns in this list, the capability will be enabled…

不匹配 = 新窗口零权限（fs / dialog / 自有命令全无），直接跑不起来。

验证：新窗口起来后 fs、dialog、`allow-app-commands` 里的自有命令均可用。

### 第 4 步：前端按窗口区分（很小）

- `jc_project_dir`（`src/stores/projectStore.ts:21`）从单值 → `jc_project_dir:<label>`。
- `getCurrentWindow().label` 是**同步**的：`new Window(window.__TAURI_INTERNALS__.metadata.currentWindow.label, { skip: true })`，不需要异步注入。
- `src/main.ts:99-104` 的 `mcp_reap_stale_harness` **保留不动**（第 1 步已让它安全）。
- **入口不用改**：所有窗口渲染同一个工作台，靠「这个窗口绑哪个工作区」区分。我们本来就没有 vue-router，反而省事。
- `src/services/desktopProjectDrop.ts:79` 已经是按窗口注册拖拽的，写对了。

验证：两个窗口各自打开不同工作区，互不影响。

### 第 5 步：菜单入口（对齐 VS Code）

- macOS 菜单加「在新窗口打开工作区…」（`⌘⇧N`）；「打开最近」每项支持在新窗口打开。
- 菜单是 app 级的（`src-tauri/src/lib.rs:1409` `app.set_menu`），这一点与 VS Code 一致，不用改。

## 7. 验收标准

1. 主窗口开工作区 A，菜单开新窗口 → 绑工作区 B
2. **两窗口同时跑任务，互不打断**（第 1 步的核心验收）
3. dev 下 F5 重挂 → 旧 runner 被收，不出现 `already owned by an active write handle`
4. 两窗口几何位置各自独立恢复

6. 双击 Dock 图标 → 不新起进程，焦点回到已有窗口
7. 第二次打开同一工作区 → 聚焦已有窗口，不新建

## 9. 实施记录（2026-09-29）

第 0、1 步已实施。**两处与上面的设计不同**，都是实施时才发现设计不够：

### 9.1 归属改成 `(窗口 label, 页面 realm)`，不是只有 label

设计里只写了「按窗口 label 判归属」。实施时发现那样会**把原来的 bug 带回来**：dev 的 F5/HMR
重挂时窗口 label 不变（还是 `main`），只看 label 就分不出「上一代页面留下的孤儿」和「本页面的
活进程」——旧 runner 收不掉，下一轮 resume 依旧撞 `already owned by an active write handle`。

改成二元组：`realm` 由前端每次页面挂载生成（`MCP_REALM_ID`，`src/services/mcpStdioTransport.ts`），
随 spawn 上报；窗口 label 由 Rust 从注入的 `WebviewWindow` 取，前端不传。于是「同窗口旧 realm」收、
「另一个窗口」不收，两件事同时成立。

### 9.2 单实例只在正式构建启用

设计里没提。实施时发现：锁是按 bundle identifier 加的，**dev 与正式包同 ID**。所以
「先开着已安装的旧版，再跑 `pnpm tauri dev`」会把 dev 进程交给那个旧包——你以为在测 HEAD，
实际看的是旧版本。那比多开本身更难查，所以加了 `not(debug_assertions)`。

代价：第 0 步在 dev 里不可验，只能装正式包双击 Dock 图标验。

### 9.3 验证边界

- 自动：Rust `459 passed / 0 failed / 1 ignored`（新增 6 条归属单测）、focused `1666/1666`
  （新增 2 条合同测试）、`vue-tsc` 干净、`cargo check --release` 通过
  —— 单实例那段只在 release 编译，不跑 release 检查等于没验。
- **真机：没有。** 第 1 步要验「两个窗口同时跑任务互不打断」，而现在还开不出第二个窗口
  （第 2 步未做）；第 0 步要装正式包。**两步目前都不能写成已验收。**

## 10. 入口补齐：Windows 没有菜单栏（2026-10-03）

### 10.1 缺口

第 5 步只做了 **macOS 菜单**（`jc:new-window`，`⌘⇧N`）。那段菜单构建**整块在
`#[cfg(target_os = "macos")]` 里**（`src-tauri/src/lib.rs` 的 `app.set_menu` 段），
所以 **Windows 上既没有菜单项、`⌘⇧N` 也没有落点**。命令 `open_new_window` 早就有，
`src/main.ts` 也已在 `listen('jc:new-window')` → `invoke('open_new_window')` —— **只缺触发点**。
用户是在 Windows 上撞到这个：mac 能新建窗口，Windows 找不到入口。

### 10.2 已实施（提交 `0047189f` / `19d9ca15`）

- **空状态**（没有工作区时）：`ProjectFileTree.vue` 的 `pft-empty-list` 里「打开本地文件夹」下面加一项
  「新建窗口」（带文字，`v-if="isDesktop && !isMobile"`）。
- **有工作区时**：同一个文件树的动作行（`pft-actions`，原先放在「刷新」右边）。
- 两处 + macOS 菜单**都调同一条 Rust 命令**，不各自实现建窗（契约测试钉住）。
- 实验过一版放**工作台顶栏**（`.memory-topbar-actions`，设置左边），**已撤**：那是应用级动作没错，
  但和创作面板/模型/设置挤一排、语义也重叠。
- **失败提示不能走 `errorMsg`**：那个 ref 会把整棵文件树 `v-show` 掉，为一次开窗失败清空用户手里的树不合理。
  单开一条 `newWindowError`（`.pft-status pft-error`，渲染在面板顶部，两种状态都可见）。

### 10.3 位置定案与实施（2026-10-03）

用户 2026-10-03 定为 **logo 那一行**，即 `.pft-project-row`：

```text
[ logo + 工作区目录名 + 展开箭头 ]   ← 整体是一个按钮（点击 = 切换项目文件夹）
[ 新建窗口 ]                         ← 目标位置：紧随其后
[ 隐藏文件树 ]
```

改动点：把动作行（`pft-actions`）里那个按钮**挪到** `.pft-project-row` 内、
`pft-project-trigger` 那个按钮**之后**、「隐藏文件树」之前。已按用户提供的图标位置实施，两个操作按钮保持 4px 间距且不收缩，移除动作行原按钮；空状态入口保留。

两个坑，实施时别踩：

1. `logo + 目录名` 是**一个**按钮，新建窗口必须是它**之后**的独立按钮，不能塞进去。
2. 目录名会被挤：加按钮后要给 `.pft-project-name` 补 `min-width: 0` + 省略号，否则长项目名会顶掉按钮。

**文件树被折叠/隐藏时，Windows 上没有入口**（macOS 还有应用菜单）。

## 10. 第 2 步实施记录（2026-09-29）

### 10.1 工作区的传递方式与设计不同

设计里写「`jc_project_dir` 从单值 → `jc_project_dir:<label>`」。实施时发现这不够：
**label 是哈希，反推不出路径** —— 光靠 `jc_project_dir:<label>` 无法知道新窗口该绑哪个工作区。

改成两层：

1. Rust 建窗时把工作区路径注入窗口全局变量（`window.__JC_WORKSPACE__`），前端**同步**读到，
   作为该窗口的初始工作区。不走 URL query 是因为生产环境的 App 入口带 query 跳平台不稳；
   不走 Rust 侧登记表是因为那样只能启动后异步补，会先闪一下「没有项目」。
2. `jc_project_dir:<label>` 保留，负责**窗口内切换项目后**的记忆。回落旧的全键，
   老用户升级不丢当前项目。

### 10.2 提前做了第 5 步的菜单入口

不加入口的话，第 2 步又是「写了但开不出来」，第 1 步也永远验不了。所以把菜单项提前：
⌘⇧N「在新窗口打开工作区」。

菜单是应用级的（`app.set_menu`），它不知道哪个窗口在工作 —— 所以走
「Rust 转给聚焦窗口 → 前端带自己的工作区回调 `open_workspace_window`」。
项目选择器在 `ProjectFileTree.vue`（3100+ 行），没动它。

### 10.3 补上了第 1 步推迟的那件事

窗口销毁时收掉该窗口的 runner（`reap_window_stdio_processes`）。之前推迟是因为只有一个
窗口时那就是死代码；现在能开出第二个窗口了，不收就会漏 —— 应用的还活着，退出路径不会跑，
而它会一直握着会话的跨进程内核写锁。

### 10.4 三个实现细节

- `#[tauri::command]` **不能定义在 crate root**：它会在当前模块导出 `__cmd__*` 宏，crate root
  上就是宏重定义。命令放进了 `commands/workspace.rs`（仓库惯例）。
- 那段 70 行初始化脚本从 `setup` 搬到了 `WORKBENCH_INIT_SCRIPT`。搬完逐字节比对过（60 行，
  `diff` 无差异）—— 这种大块搬运不比对一下，很容易在里面踫一个字符。
- 几何状态按 label 分文件（`window-state-<label>.json`）。旧的单文件回落**只给 `main`**：
  本机那个 `window-state.json`（2026-09-29 07:41）就是主窗口的几何，新工作区窗口如果也回落它，
  会正好压在主窗口上 —— 真机验收时看起来像「按了 ⌘⇧N 没反应」。不回落则交给系统层叠摆放，
  一眼就能看出是新窗口。这是我实施时自己埋的坑，回归测试已锁住。

### 10.5 缺口已修：一个工作区一个窗口（Rust 登记表）

上面第 2 步设计时想靠「label = `ws-<hash(cwd)>`」把「一个工作区一个窗口」白拿过来。
第 2 步实施时就发现这不够，当时记成「已知毛刺」；后来做「⌘⇧N 开空窗口」时它成了硬伤，
所以补成显式记账：

- **label 是建窗时定死的，而窗口能在里面换工作区** —— 空的 `win-1` 选了一个工作区，
  或 `ws-A` 切到 B，label 就与它正在显示的东西脱钩了。只认 label 的话这两个场景全都漏。
- **漏了会怎样**（比原来记的症状严重）：两个窗口各有自己的一份前端运行时表（每个 webview
  是独立 realm），但 `DSH_HOME` 是按 cwd 取的**同一个目录** —— 同一个工作区起两个 runner，
  第二个会撞会话写锁，表现成「这个窗口发消息，那个窗口报 already owned by an active
  write handle」。原先记的「点 A 停止、B 的任务死了」只是它的一种表现。
- 实现：`commands/workspace.rs` 里一张 `HashMap<工作区 -> 窗口 label>`。
  `open_workspace_window` 与新的 `claim_workspace` 都查它；认领新的会清掉本窗口名下的旧记录
  （一个窗口同时只显示一个工作区），否则窗口切走后那个工作区在别处会永远被当成「已经打开」。
  死窗口的记录不主动清，查询时发现就删 —— 比多挂一个销毁回调少一处会漂移的地方。
- 前端：`projectStore.selectProject` 从同步改成**先认领再改状态**，被拒绝时保持原值并让
  调用方提示（`ProjectFileTree` 显示「这个工作区已经在另一个窗口打开了」）。
  主窗口的项目是从 localStorage 恢复的、没走 `selectProject`，所以在 `mountApp` 里补了一次认领。
- 认领失败一律**放行**：登记表出问题不该让用户连项目都打不开。

### 10.6 顺带改掉的两件事（同一次评审）

1. **⌘⇧N 改成 VS Code 的「新建窗口」**：不再把当前工作区复制一份到新窗口，而是开一个**空**
   窗口（label `win-<最小可用序号>`，不注入工作区），由用户在里面选最近项目或打开本地文件夹。
   同时修掉「新窗口显示的还是同一个项目」的真正原因：`projectStore` 的回退链让**任何**窗口都
   回落旧的全键 `jc_project_dir`，空窗口一开就显示上一个项目 —— 现在只有 `main` 回落。
2. **macOS 菜单中文化**：Tauri 不随系统语言本地化系统菜单项（默认英文），必须自己传文案。
   顺带去掉了「服务」子菜单（列出的是别的 App 提供的系统服务，用户机器上是 Instruments 那几项）。
   改叫「编辑」之后 macOS 也不再自动追加 AutoFill / 开始听写 / 表情与符号 —— 正好和 VS Code 一致。
