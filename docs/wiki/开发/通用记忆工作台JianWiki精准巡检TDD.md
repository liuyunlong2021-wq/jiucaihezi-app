> 日期：2026-08-05

> 范围：`public/skills/jc-jian-wiki/`、原生 Wiki `audit`、对应测试、新手指南和现行 Wiki 合同

## 1. 根因

`jc-jian-wiki` 的唯一核心能力，是只读检查现有 Wiki，并把可验证的问题交给用户或修正 Skill。当前包却包含 50 行主 Skill、1 份重复 Reference、331 行 Python 扫描器、41 KB 的打包 Markdown helper 和 Python 缓存。

这造成五个问题：

1. App 原生 `wiki audit` 已覆盖断链、孤儿候选和现行/归档分层；随包 Python/Node 再实现一套相同机械扫描，普通用户还要承担运行时差异。
2. Python 扫描器混入换皮漏改、时代穿帮、映射撞车、伏笔回收、原创/临摹模式等个人创作规则，不属于通用个人或企业知识库。
3. 原生 `audit` 把“某目录文件数是其他目录三倍”直接列为现行风险。文件数量不能证明结构错误，这会把正常的大分类误报为问题。
4. 当前链接判断按文件名兜底；同名页面分布在不同目录时会把歧义链接误判为有效。普通未解析链接和孤儿页也可能只是待生长内容，不能天然算必修错误。
5. 当前 Skill 默认写巡检报告，并要求一套固定严重度和项目分类；这与前面已经确定的“按需写派生文件、没有固定业务 Schema”冲突。

## 2. 对照结论

Obsidian 官方 Help 提交 `8a59e12f6bcffb487ae8d6a40773e41e9c6017bc` 表明：

- 内部链接可以先指向尚不存在的笔记，用户以后再创建目标；未解析链接不自动等于错误。
- Backlinks、Outgoing links 和 Graph 是导航与关系视图；官方没有规定每篇笔记必须有入链，也没有固定 frontmatter、命名风格或目录数量阈值。
- 路径和同名页面会影响链接解析，因此审计必须区分精确路径、唯一文件名和歧义文件名。

`claude-obsidian/wiki-lint` 可借鉴“孤儿、未解析链接、旧结论、缺少交叉引用分开报告”和“修复前确认”，但不照搬它的固定 `wiki/meta/` 报告、强制 frontmatter、英文命名规范、Dataview Dashboard、全局 Canvas、定期自动运行、DragonScale 地址或 Embedding 重复页检测。

本阶段不增加向量库、Embedding、Dataview、定时任务、后台索引或新依赖。

## 3. 唯一职责

检查用户指定范围内的 Wiki 健康度和事实一致性，给出带真实页面证据的只读问题清单。

Jian Wiki 负责：

- 机械完整性：导航断链、歧义链接、孤儿候选和现行/历史分层。
- 用户指定主题内的语义一致性：同一事实、规则、状态、名称或关系在多页中的明确冲突。
- 修复后的复检：重新检查原问题，区分已解决、仍存在和新发现。
- 用户明确要求时，把结果保存为现有巡检目录中的 Markdown 派生报告。

Jian Wiki 不负责：

- 自动修复、补链、改名、移动、删除或改写事实。
- 默认扫描 Raw、附件、全部项目文件、历史会话或互联网。
- 根据目录大小、写作风格、项目类型或不存在的统一 Schema 判错。
- 生成 Canvas、Bases、统计看板或自动更新 `hot.md`、`log.md`、CLAUDE。

## 4. 触发与边界

当用户明确要求检查已有 Wiki 的健康度、一致性、断链、遗漏修改、矛盾或复检时触发，例如“巡检 Wiki”“知识库体检”“检查有没有断链”“这些规则有没有互相冲突”“按上次报告复检”。

以下请求不应触发：查询一个事实、把新内容写入 Wiki、规划目录、直接修复已确认问题。它们分别属于 `jc-cha-wiki`、`jc-raw-wiki`、`jc-everything-wiki`、`jc-xiu-wiki`。

同时存在 `wiki/` 与 `docs/wiki/` 时先请用户确认唯一知识库；不存在 Wiki 时停止，不替用户建库。

## 5. 精准巡检合同

### 机械巡检

1. 用户要求全库健康检查时，可扫描 Wiki 内全部 Markdown；用户指定目录、页面或上次报告时，只检查该范围和解析所需的一层相关页面。
2. 解析真实 Markdown 文本中的 Wiki 链接，忽略 fenced code、inline code、HTML 注释和转义示例。
3. 链接解析先匹配精确相对路径，再匹配唯一文件名；同名目标不唯一时报告“歧义链接”，不得任选一个目标。
4. 当前导航页中指向不存在目标的链接是明确风险。普通事实页中的未解析链接先列为“待确认候选”，因为它可能是尚未创建的规划页。
5. 没有入链的普通页面只列为“孤儿候选”；系统页、导航页、派生报告和用户明确保留的独立页不因此报错，更不得建议自动删除。
6. `归档/`、`log.md` 和页面明确标为历史、已归档或已替代的内容单列“历史卫生”，不阻断现行 Wiki。
7. 不根据文件数量、目录比例、页面长度、命名风格、frontmatter 缺失或空白占位自动判错，除非当前 Wiki 自己有明确合同。

### 语义巡检

1. 从用户指定主题提取 1-3 个辨识度高的实体、规则或状态词，定位相关现行页面；没有主题时不宣称已完成全库语义一致性检查。
2. 读取真正包含相关主张的段落；只有引用页、来源页或反向引用会改变判断时，才扩展一层。
3. 只有两个页面对同一对象、同一属性和可比较时间范围给出不兼容结论时才报告冲突。历史变化、不同适用范围和补充信息不是冲突。
4. 报告双方页面、原始主张和无法自行裁决的原因；不按文件时间、新旧目录或模型常识擅自选赢家。
5. 需要 Raw、原件、代码、Git 或互联网才能证明真伪时，标为未验证；只有用户明确要求继续查证时才扩大证据范围。

## 6. 输出与写入

- 默认直接在对话中报告：实际检查范围、明确风险、待确认候选、历史卫生、未执行的检查。没有问题时也必须说明检查边界，不能写成“整个知识库绝对正确”。
- 每项至少包含真实页面、链接或冲突双方、问题原因和可执行下一步；有行号时附行号，没有时不得编造。
- 只有用户明确要求“保存巡检报告”时，才写入 Wiki 已有巡检目录；没有既定目录时先让用户指定，不自动创建 `meta/`、`巡检报告/` 或 Dashboard。
- 保存的报告是可重新生成的派生文件，不替代事实页，不追加 `log.md`，不更新 `hot.md`。
- 确定性机械修复交给 `jc-xiu-wiki`；语义冲突先由用户确认正确事实，再交给 `jc-raw-wiki` 或 `jc-xiu-wiki` 执行。Jian Wiki 只负责复检。
