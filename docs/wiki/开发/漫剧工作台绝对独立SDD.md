# 漫剧工作台独立 App SDD

> 日期：2026-07-24
> 状态：架构已确认，待实施
> 范围：独立漫剧 App、分集 Raw 对话、Wiki Skill 编排、Direct Engine、Web/Desktop 构建与发布
> 依据：`AGENTS.md`、[[开发/Wiki四Skill产品化升级SDD]]、[[开发/创模式Raw账本与对话Wiki移除SDD]]、[[开发/电商工作台绝对独立SDD]]、[[开发/制作工作台零隐式上下文SDD]]
> 替代关系：本文替代“漫剧工作台挂载在主 App `WorkspaceLayout/Rail` 内”的方案；不改变现有主 App、制作工作台、电商工作台、文武道创或 OpenCode 的现行行为。主 App 只有在独立产品完成等价验收后才精简。

## 1. 一句话决断

漫剧工作台是一个可独立安装、独立访问、独立更新的产品，不是主 App 里的新模式或新入口。用户只和模型对话、选择模型、选择 A/B/C 或填写 D；工作台把每集完整对话追加到项目 `.raw/分集对话记录/`，每轮让模型先读取当前集完整对话，再自行调用查询 Wiki Skill 获取已确认事实，最后生成、修改、确认并审计剧本。

```text
当前集完整 Raw 对话（已包含本轮用户消息）
  -> Direct Engine 模型理解本轮意图
  -> 模型调用 jc-cha-wiki 查询当前项目 Wiki
  -> 模型按漫剧规则回复
  -> 完整回复追加到当前集 Raw

用户明确确认
  -> jc-raw-wiki 写入正式正文与确认事实
  -> jc-jian-wiki 巡检
  -> 有语义冲突时等待用户裁决
  -> 新增事实交给 jc-raw-wiki，确定的旧事实修正交给 jc-xiu-wiki
```

产品同时交付两个独立前端：

```text
漫剧 Desktop App（Tauri 安装包）
漫剧 Web App（manju.jiucaihezi.studio）
```

两端共享业务合同，但分别构建和发布。这不是一个普通 Skill，也不是 OpenCode Agent、现有 Chat 的皮肤或主 App 的路由分支。产品由独立 App Shell、Direct Engine、项目文件服务、漫剧规则包和 Wiki Skills 组成。

## 2. 根因

旧 `jc-duanju-world` 同时承担建制、写作、文件更新、上下文、交互和审计，导致产品流程被压进一个长 Skill。继续缩短 Skill 只能缩短说明，不能解决以下产品问题：

1. 用户无法直接看到和切换“当前正在讨论哪一集”。
2. 完整分集讨论没有稳定、可检查、可跨设备携带的项目内来源。
3. 草稿、确认事实和正式正文的写入时机只能靠模型猜测。
4. 用户必须理解模式、Skill、会话和工具，才能完成本应自然的写作流程。
5. 现有创模式会话、OpenCode Session 和制作工作台都不是“分集完整对话 + 每轮 Wiki 查询”的合同。

根因不是缺少更复杂的 Agent，而是缺少一个以项目文件为真源、以分集对话为工作上下文、以 Wiki 为确认记忆的独立产品。把它继续放进主 App，只会让用户面对与写漫剧无关的模式、面板和依赖，也会让主 App 越来越重。

## 3. 产品边界

### 3.1 产品构成

| 层级 | 职责 |
| --- | --- |
| 漫剧 App Shell | 项目选择、集数选择、输入输出、模型选择、确认动作和错误状态 |
| 漫剧工作台 Runtime | Raw 追加、请求构造、Skill 调度、确认与巡检编排 |
| Direct Engine | 当前模型请求、SSE、取消和多轮工具调用 |
| 漫剧写作规则包 | 核心梗、催化事件、人物反应、三角引擎、压力值、格式和验收标准 |
| Wiki Skills | 建库、查询、填充、巡检和修正 |
| `ProjectFileService` | Web/Desktop 统一读取和写入当前项目文件 |
| 项目文件树 | 唯一可恢复状态和用户可检查的事实来源 |

### 3.2 绝对禁止的依赖

漫剧工作台不得依赖或创建：

- 主 App 的 `App.vue`、`WorkspaceLayout`、`ActivityRail`、路由入口或功能开关。
- `ChatPanel`、`useChat()`、普通 Chat 消息或 Chat 输入框。
- `creativeSessionStore`、`sessionStore`、`conversations`、`messages` 或任何 UI 会话数据库记录。
- OpenCode `ses_*`、sidecar、文模式、武模式或 Agent 配置。
- 创模式、道模式、模式选择器、Skill 选择器、MCP 或 Web 搜索。
- 独立 Pinia 持久化 Store、工作台运行记录、向量库、隐藏摘要或第二套记忆。
- “当前有效草稿”副本、草稿 ID、工作台阶段数据库或集数数据库。
- 通过环境变量把主 App 整包切换成漫剧外观的伪独立构建。

删除文、武、创、道以及所有 App 会话记录后，只要项目文件仍在，漫剧工作台必须可以恢复全部集数和完整讨论。

### 3.3 允许复用的公共能力

- 公共模型/Provider 选择器、密钥解析和模型能力判断。
- `runDirectChatCompletion` 的流式请求、取消和工具循环。
- Desktop/Web 项目工具执行器中的 `skill`、`wiki`、`read`、`glob`、`grep`、`write`、`edit`。
- `ProjectFileService` 的项目内文件读写、版本冲突检测和 Web/Desktop 适配。
- 已经稳定的 Markdown 渲染、附件选择和必要基础控件。

共享公共实现不等于依附任何模式。漫剧 App 必须拥有独立入口、独立 App Shell、独立 Tauri 配置、独立 Web 构建产物和独立发布通道。公共代码只在实际复用时抽取，不先为四个产品重构整个仓库。

### 3.4 产品套件与仓库决断

四个产品留在同一个仓库，分别构建和发布：

| 产品 | 职责 | Web | Desktop 标识 | 发布标签 |
| --- | --- | --- | --- | --- |
| 主对话 App | 通用对话 | `jiucaihezi.studio` | 现阶段保留 `com.jiucaihezi.desktop` | 现阶段保留 `vX.Y.Z` |
| 漫剧 App | 漫剧建制、分集写作与审计 | `manju.jiucaihezi.studio` | `com.jiucaihezi.manju` | `manju-vX.Y.Z` |
| 电商 App | 商品内容与电商生产 | `ecommerce.jiucaihezi.studio` | `com.jiucaihezi.ecommerce` | `ecommerce-vX.Y.Z` |
| 制作 App | 媒体制作与交付 | `production.jiucaihezi.studio` | `com.jiucaihezi.production` | `production-vX.Y.Z` |

主 App 暂不改 Bundle ID，避免现有安装被系统识别为另一款 App、丢失原更新关系。未来是否迁移为 `com.jiucaihezi.chat` 单独立项，不是本 SDD 的前置条件。

仓库目标不是复制四份代码，而是：

```text
产品入口与壳：各自独立
稳定公共能力：按需共享
业务 Runtime：归各产品所有
账号与 API：继续共用
项目文件：仍由 ProjectFileService 管理
```

漫剧是第一个验证产品。只有漫剧的独立构建、发布、登录、更新和业务闭环全部成立后，才把同一发布模板用于电商和制作；不得先并行搭三套半成品。

## 4. 唯一事实源

漫剧项目只有一个项目文件树，分为两个语义区域：

```text
项目根/
├── .raw/
│   └── 分集对话记录/              # 未加工的分集完整对话，追加写
│       ├── 第001集/
│       │   └── 对话.md
│       ├── 第002集/
│       │   └── 对话.md
│       └── 第003集/
│           └── 对话.md
└── wiki/                          # 已确认事实和正式正文
    ├── 作品/
    │   ├── 正文/
    │   └── 大纲/核心梗.md
    ├── 角色/
    ├── 世界/
    ├── 场景/
    ├── 道具/
    ├── 伏笔/
    ├── 来源索引.md
    ├── hot.md
    ├── log.md
    └── index.md
```

`.raw/分集对话记录/` 和 `wiki/` 不是两套记忆系统，而是同一项目文件树的原始记录区与确认事实区：

- 当前集 Raw 是本集工作上下文。
- Wiki 是跨集确认记忆。
- 未确认建议、旧草稿和讨论只能留在 Raw。
- 正式正文、确认设定和已发生状态只能写入 Wiki。
- 模型不依赖 App 隐式记忆；每轮通过当前集 Raw 与 Wiki 查询获得所需信息。

## 5. 建库合同

### 5.1 冷启动

没有当前项目时，工作台只显示“创建或选择项目”。有项目后先执行 `wiki inspect`：

| 检查结果 | 工作台行为 |
| --- | --- |
| 没有 Wiki | 显示唯一主操作“创建漫剧 Wiki” |
| 已有一套 Wiki | 接管现有 Wiki，验证类型和必要入口 |
| 同时存在 `docs/wiki/` 与 `wiki/` | 停止并要求用户选择唯一 Wiki |
| Wiki 不是漫剧结构 | 停止并说明不能静默改造成漫剧 Wiki |

用户点击“创建漫剧 Wiki”后，工作台内部使用 `jc-everything-wiki`：

```text
skill(jc-everything-wiki)
  -> wiki.inspect
  -> 读取漫剧项目 Reference
  -> wiki.scaffold(type: manju)
  -> wiki.validate(type: manju)
  -> 创建 .raw/分集对话记录/第001集/对话.md
```

建库只建立结构，不编造核心梗、人物、场景、道具或剧情。建库完成后立即进入第001集对话。

### 5.2 当前合同缺口

实施前必须先统一以下现行矛盾：

1. 漫剧项目 Reference 已声明 `.raw/分集对话记录/`，但 `wiki.scaffold(manju)` 当前只创建 `wiki/`。
2. `jc-everything-wiki` 当前明确禁止 Studio 自动创建会话副本，而漫剧工作台要求自动追加分集 Raw。
3. 旧 Python scaffold、旧短剧 scaffold 和原生 Wiki runtime 的 Raw 目录命名不一致。

根因修复是让 `manju` 原生建库合同明确创建 `.raw/分集对话记录/`。该例外只属于漫剧工作台，不恢复普通 Chat 或创模式的项目 Raw 账本。

### 5.3 建制不是建库

`jc-everything-wiki` 只建骨架。后续几轮确定核心梗、人物和故事起点属于漫剧建制：

```text
建库完成
  -> 用户提交故事雏形、新闻或灵感
  -> 模型查询 Wiki
  -> 确认唯一核心梗
  -> 确认初始人物及必要场景/道具
  -> 用户点击“确认建制”
  -> jc-raw-wiki 将确认事实写入 Wiki
  -> 生成第一轮 A/B/C/D 催化事件
```

用户看到的是一段连续对话，不需要知道内部 Skill 已从建库切换到查询和填充。

## 6. 分集 Raw 合同

### 6.1 路径

```text
.raw/分集对话记录/第{三位集号}集/对话.md
```

集号从 `001` 开始。工作台通过扫描目录得到已有集数，不维护集数数据库。

### 6.2 内容格式

Raw 使用可直接阅读、可稳定追加的 Markdown。每条可见消息有稳定边界：

```markdown
# 第001集完整对话

<!-- jc:turn id="turn_20260724_130001_a1b2" role="user" created-at="2026-07-24T13:00:01+08:00" -->
## 用户

把这一场改得更狠一点，主角不能忍。
<!-- /jc:turn -->

<!-- jc:turn id="turn_20260724_130042_c3d4" role="assistant" created-at="2026-07-24T13:00:42+08:00" -->
## 编剧

修改后的场景正文……
<!-- /jc:turn -->
```

Raw 只保存用户可见输入和模型最终可见回复：

- 不保存 Wiki 查询结果、工具参数、工具回执或隐藏推理。
- 不保存流式中间片段、网络错误、审批过程或系统提示词。
- 附件先进入当前项目，Raw 只记录项目相对路径、名称和类型，不复制二进制。
- 消息只追加，不覆盖、不重排、不删除；正式更正通过后续消息表达。

### 6.3 追加时序

用户发送：

```text
生成 turnId
  -> 将用户消息追加到当前集 Raw
  -> 追加成功后重新读取当前集完整 Raw
  -> 发起模型请求
```

模型完成：

```text
Direct Engine 得到完整最终文本
  -> 将模型回复追加到同一 Raw
  -> 追加成功后才允许下一次发送
```

用户消息没有成功写入 Raw 时不得调用模型。模型回复已经生成但追加失败时，UI 必须保留该回复并阻止下一轮，直到重试追加成功，不能让可见对话和 Raw 分叉。

### 6.4 Web/Desktop 一致追加

工作台通过 `ProjectFileService` 读写，不让 Vue 组件直接调用 Desktop `dev_append_file`。最小跨端实现是：

```text
readText(path) -> 拼接一个完整 turn -> writeText(expectedRevision)
```

发生 revision conflict 时重新读取并按 `turnId` 去重后重试。Desktop 原生追加命令可以保留给其他用途，但不能形成 Web/Desktop 两套漫剧记录语义。

## 7. 集数选择与恢复

工作台顶部用集数选择器替代“新建对话”：

```text
[第003集 ▼]  [新建下一集]
```

### 7.1 选择已有集

```text
扫描 .raw/分集对话记录/
  -> 用户选择第002集
  -> 读取第002集/对话.md
  -> 渲染全部用户/编剧消息
  -> 后续输入继续追加到第002集
```

### 7.2 新建下一集

```text
扫描最大集号 N
  -> 创建第N+1集/对话.md
  -> 切换到新集
  -> 读取确认 Wiki
  -> 生成新集第一轮催化事件
```

不存在“当前集”持久化字段。页面存活期间只在组件内保留当前选择；刷新后默认打开编号最大且存在 Raw 的一集。用户可从下拉框切换。

## 8. 每轮请求合同

### 8.1 输入组装

用户消息先写入 Raw，因此请求不再单独重复追加“本轮消息”。模型请求固定由以下内容组成：

```text
system:
  漫剧工作台运行规则
  + 可用 Skill 清单
  + 只读/写入权限边界

user:
  [当前项目]
  [当前集号]
  [当前集完整对话.md 全文，其中最后一条就是本轮用户消息]

tools:
  当前阶段允许的最小工具集合
```

不在模型调用前由应用猜测角色、场景、道具或关键词，也不由应用提前查询 Wiki。模型先看完整分集对话，再决定本轮要查什么。

### 8.2 强制查询流程

普通回复、催化事件生成、写戏和改稿都必须先完成：

```text
模型读取完整本集对话
  -> skill(name: jc-cha-wiki)
  -> wiki.search / read / glob / grep 查询相关事实
  -> 必要时沿双链继续读取角色、场景、道具和正文
  -> 生成最终回复
```

查询范围由模型根据当前集对话和最后一条用户消息决定。应用不预组装“本轮针对性 Wiki 查询结果”。查询结果作为同一次 Direct Engine 工具循环的证据返回模型。

工作台必须检查 `RunDirectChatCompletionResult.toolCalls`。如果本轮没有加载 `jc-cha-wiki`，或者没有发生至少一次面向当前 Wiki 的查询/读取，则本轮最终文本无效，不得追加为编剧回复。UI 显示“本轮未完成 Wiki 查询”，允许原输入重试。

### 8.3 工具权限按阶段收窄

| 阶段 | 允许工具 |
| --- | --- |
| 建库 | `skill`、`wiki.inspect/scaffold/validate`、确定性的项目文件创建 |
| 普通讨论/催化/写戏/改稿 | `skill`、只读 `wiki`、`read`、`glob`、`grep` |
| 用户明确确认后填充 | 上述只读工具 + `write`、`edit`，并加载 `jc-raw-wiki` |
| 巡检 | `skill`、`wiki.audit`、只读 `read/glob/grep` |
| 用户确认修正 | `skill`、`wiki.replace/link/extend` 或受限 `write/edit`，并加载 `jc-xiu-wiki` |

普通对话阶段不向模型提供 `write`、`edit`、终端、MCP 或搜索工具，从权限上保证未确认草稿不能进入正式 Wiki。

### 8.4 上下文上限

当前集完整 Raw 是硬输入合同。V1 不做隐藏摘要、不做向量召回、不静默裁剪旧轮次。

若“固定规则 + 当前集完整 Raw + 预留输出”超过所选模型上下文，工作台必须在发送前明确阻止请求，并提示用户选择更大上下文模型或进入下一集。不能表面声称发送了整集，实际只发送最近几轮。

## 9. 漫剧创作核心合同

### 9.1 约束优先级

```text
唯一核心梗
  > 用户明确选择的催化事件
  > 人物的红线、性格与决策算法
  > 时间、地点、场景空间和道具物理法则
  > 压力值调度
  > 剧本格式与交付验收
```

压力值只负责提示下一步优先推动谁或哪组冲突，不能覆盖用户已选催化方向，也不能强迫角色做出不符合人设的行为。

### 9.2 唯一核心梗

- 一部剧只能有一个核心梗。
- 建制阶段必须先确认核心梗，再进入正式催化循环。
- 所有 A/B/C 催化事件都必须服务同一个核心梗。
- 单场爽点、辅助梗和反转可以存在，但不能取代或偏离核心梗。
- 当前“30条爽点库”不能直接等同于“30个核心梗”；实施前必须明确哪些条目可作为全剧核心梗，或者建立独立核心梗合同。

本工作台不要求传统主题、预设主线、完整大纲或预定结局。故事通过用户选择的催化事件与人物自然反应向前生长。

### 9.3 催化事件

每次需要推进方向时，模型基于核心梗与当前 Wiki 生成：

- A、B、C：三个真正不同、均服务核心梗的催化事件。
- D：用户自定义催化事件。

催化事件必须触碰人物红线、制造选择或改变局面。角色、场景、道具能自然咬合时使用三角引擎；缺少合适场景或道具时自然降级，不为形式强凑。

用户点击 A/B/C，或者填写 D 后发送，属于明确确认催化方向。工作台将其作为可见用户消息写入 Raw，再调用 `jc-raw-wiki` 写入对应集纲或当前确认事实，然后生成场景草稿。

### 9.4 人物、场景和道具

```text
催化事件发生
  -> 这个人基于自己的性格、红线和经历会怎么选择
  -> 当前时间和地点允许他做什么
  -> 场景空间迫使或阻止他做什么
  -> 道具的归属、功能、代价或物理法则改变什么选择
  -> 行动造成新的事实和压力
```

人设决定自然反应；场景和道具不是装饰，而是选择条件。模型每轮通过 Wiki 查询读取实际存在的实体，不在应用层建立额外角色状态或道具状态对象。

### 9.5 正文格式与审计

生成场景和正式正文必须读取漫剧写作规则包中实际关联的格式与质量 Reference。格式、可拍摄性、台词、冲突、反转和结尾钩子是交付约束，不是推动剧情的上游计划。

正式写入前至少检查：

- 是否仍服务唯一核心梗。
- 催化事件是否真实改变人物处境。
- 人物反应是否符合已确认人设。
- 场景与道具是否遵守既有事实和物理规则。
- 是否出现无法拍摄的心理解释或作者说明。
- 每场格式是否符合短剧写作格式规范。

## 10. 确认与 Wiki 写入

### 10.1 不靠自然语言猜确认

普通“发送”只表示继续讨论，不表示正式确认。以下 UI 动作才产生写入事件：

| 用户动作 | 确认内容 |
| --- | --- |
| `确认建制` | 核心梗、初始人物和用户明确接受的设定 |
| 选择 A/B/C 或提交 D | 当前催化方向 |
| `确认本场` | 当前场正式正文与该场实际发生的状态变化 |
| `确认本集` | 当前集正式正文、集级状态和来源范围 |
| 冲突面板中的 `采用此版本` | 用户明确裁决的语义方向 |

这些动作必须同时以普通可读文字追加到 Raw，使项目仅凭文件也能还原用户确认了什么。

### 10.2 `jc-raw-wiki` 写入

确认后，工作台启动受限填充轮次：

```text
skill(jc-raw-wiki)
  -> 读取漫剧项目 Reference
  -> 读取当前集 Raw 的尚未处理范围
  -> 读取现有 Wiki 和来源索引
  -> 只写确认事实或正式正文
  -> 创建必要双链和回链
  -> 更新来源索引的 Raw 路径与 turnId 范围
  -> 状态确实变化时更新 hot.md，并向 log.md 追加事实
  -> validate
```

`jc-raw-wiki` 不负责追加 Raw。Raw 由工作台确定性记录；Skill 把它当只读证据。

### 10.3 草稿边界

- 模型生成的场景第一次出现时是草稿，只写 Raw。
- 用户提出修改后，新版本仍只写 Raw。
- 旧版本不删除；完整讨论自然说明它已被后续版本替代。
- 只有点击 `确认本场` 或 `确认本集` 后，正文才进入 `wiki/作品/正文/`。
- Wiki 中不存在“当前草稿”“草稿副本”或工作台临时状态页。

## 11. 巡检与修正闭环

### 11.1 本场确认

本场写入后只检查本轮触及的正文、角色、场景、道具、伏笔和状态页面，重点做语义一致性检查。不能每确认一句话就全库扫描。

### 11.2 本集确认

本集写入后运行：

```text
skill(jc-jian-wiki)
  -> wiki.audit 机械巡检
  -> 读取本集正文及双链实体
  -> 检查人物、场景、道具、时间线、压力和伏笔的一致性
```

巡检只报告，不静默修改。

### 11.3 语义冲突

发现冲突时工作台显示：

```text
已有 Wiki 事实
本集确认内容
冲突位置与直接影响
[保留旧事实] [采用本集版本] [继续讨论]
```

- 本集只是让人物产生新的成长、关系或状态：使用 `jc-raw-wiki` 增量填充。
- 用户确认旧 Wiki 事实本来就错了：使用 `jc-xiu-wiki` 预览并修正。
- 用户没有裁决：保持双方来源，不修改正式事实，不生成下一轮催化事件。

## 13. 最小实现架构

### 13.1 独立产品根

不搬迁或重写现有主 App。第一阶段只新增独立漫剧产品根，并复用已经稳定的公共模块：

```text
apps/manju/
├── index.html
├── src/
│   ├── main.ts
│   ├── ManjuApp.vue
│   ├── components/ManjuWorkbench.vue
│   └── runtime/
│       ├── manjuTranscript.ts
│       └── manjuWorkbench.ts
└── src-tauri/
    ├── tauri.conf.json
    └── 必要的 Tauri 壳与权限
```

职责：

| 文件 | 最小职责 |
| --- | --- |
| `ManjuApp.vue` | 独立 App Shell、项目文件树与工作台布局；不挂主 App Shell |
| `ManjuWorkbench.vue` | 项目/Wiki 空状态、集数选择、Raw 对话展示、输入、模型选择和确认按钮 |
| `manjuTranscript.ts` | 扫描集数、创建集、读取完整 Raw、按 turnId 冲突安全追加 |
| `manjuWorkbench.ts` | 构造 Direct 请求、限定工具、验证必经查询、执行确认/巡检编排 |

### 13.2 公共能力边界

必要修改控制在既有公共边界：

- `wikiStructures.ts` / `wikiRuntime.ts`：让 `manju scaffold` 创建约定 Raw 目录并验证。
- 漫剧项目 Reference 与 Wiki Skill 合同：统一分集 Raw 命名和专属自动记录例外。
- 复用现有模型选择、API 请求、Skill loader、项目工具和项目文件服务。
- 为独立入口提供最小构建命令和 Tauri 配置，不改主 App 默认构建结果。

第一款独立 App 不提前建立大型 monorepo 包体系。已有模块能直接安全复用就直接复用；只有出现第二个真实调用方且依赖边界清楚时，才抽到 `packages/` 或共享 crate。

不新增 Store、数据库表、路由后端、任务队列、Agent 框架、摘要器或检索服务。漫剧 Desktop 不打包 OpenCode sidecar，也不编译或注册文武道创、电商、制作的 UI 与 Runtime。

### 13.3 构建隔离

必须有四个可机械验证的边界：

1. `build:manju:web` 只生成漫剧 Web 产物。
2. `build:manju:desktop` 只生成漫剧 Desktop 前端产物与安装包。
3. 漫剧构建产物中不存在 OpenCode runtime、主 App 模式入口或其他工作台代码块。
4. 主 App 现有 `build`、`build:desktop` 和开发启动命令在迁移期保持原行为。

不接受“同一份完整主 App bundle，运行时隐藏菜单”的实现，因为它没有减轻安装包、依赖和回归范围。

## 14. 错误、取消与并发

| 情况 | 行为 |
| --- | --- |
| 用户消息 Raw 追加失败 | 不发模型请求，保留输入，允许重试 |
| Wiki 查询失败 | 不生成假回复，不追加 assistant，显示真实错误 |
| 模型没有调用查询 Wiki | 丢弃本轮候选文本，不追加 Raw，允许原输入重试 |
| 模型请求失败或取消 | 用户消息保留在 Raw，不追加伪造的编剧回复 |
| 流式回复中断 | 不把不完整片段写入 Raw；重试仍以最后一条用户消息为输入 |
| 最终回复 Raw 追加失败 | 保留可见回复并阻止下一轮，直到追加成功 |
| Wiki 正式写入失败 | Raw 不回滚；标记“未完成确认写入”，允许从相同确认范围重试 |
| 多窗口同时追加 | 使用 revision + turnId 去重重试，不覆盖另一窗口内容 |
| 当前集超过模型上下文 | 发送前阻止，不静默裁剪或摘要 |

Raw 是 append-only 证据，因此模型失败不要求删除已经成功写入的用户消息。

## 15. Web、Desktop 与发布

Web 与 Desktop 使用同一相对路径、同一 Raw 格式和同一请求合同：

- Desktop 项目文件落真实文件系统。
- Web 项目文件落现有浏览器项目文件系统。
- 两端都通过 `ProjectFileService`，不在工作台中分叉业务逻辑。
- 导出项目时，`.raw/分集对话记录/` 与 `wiki/` 必须一并导出；重新导入后可恢复工作台。
- Desktop 独有的终端和 OpenCode 能力不参与漫剧工作台成功标准。

### 15.1 Web 发布合同

漫剧 Web 建立独立 Cloudflare Pages 项目，绑定：

```text
manju.jiucaihezi.studio
```

它不是 `jiucaihezi.studio/manju` 路由，也不与主 App 共用一份 SPA 构建产物。两个 Pages 项目可以共用同一 Git 仓库，但必须使用各自的构建命令、输出目录、环境变量和部署记录。

四个产品共用 `api.jiucaihezi.studio`，不为每个前端复制后端。新增 Web 来源必须加入现有网关、CORS 和 OAuth 回调白名单，并做真实预检与登录回调验证。

浏览器的 IndexedDB、OPFS、`localStorage` 和 Cookie 按 Origin 隔离，因此：

- `jiucaihezi.studio` 的浏览器本地项目不会自动出现在 `manju.jiucaihezi.studio`。
- V1 通过项目导入/导出携带 `wiki/` 与 `.raw/`，不虚构跨子域本地存储共享。
- 四端使用同一账号系统不等于天然免登录；V1 允许各子域用同一账号分别登录。
- 统一 SSO 或云端项目同步只有在单独立项后才能加入，不是漫剧首发条件。

### 15.2 Desktop 身份合同

漫剧 Desktop 固定使用：

```text
productName: 韭菜盒子·漫剧
identifier: com.jiucaihezi.manju
deep link: jiucaihezi-manju://
updater: https://api.jiucaihezi.studio/updates/manju/latest.json
```

它拥有独立图标、窗口标题、安装包文件名和版本号。它可以和主 App 同时安装，不能覆盖主 App 的应用目录、Bundle ID、Deep Link 或更新清单。

现有 Apple Developer 团队和 Developer ID 证书可继续签名、公证多个独立 App；每个 App 仍需独立 Bundle ID。当前继续使用 Developer ID 直发安装包，不把 Mac App Store 上架设为首发门槛。未来进入 App Store 时，每个产品分别创建记录和接受审核。

### 15.3 更新与 CI 合同

当前仓库的 `.github/workflows/build.yml` 只识别 `v*`，并在 `/opt/updates/latest.json` 生成主 App 清单。主 App 的现有安装已经依赖这两个入口，因此迁移期保留不变；新产品使用独立标签和更新目录：

```text
v1.3.1             -> /opt/updates/latest.json
manju-v1.0.0       -> /opt/updates/manju/latest.json
ecommerce-v1.0.0   -> /opt/updates/ecommerce/latest.json
production-v1.0.0  -> /opt/updates/production/latest.json
```

每个产品的安装包放在自己的目录：

```text
/opt/updates/{product}/{version}/
```

CI 可以复用同一套签名、公证、上传步骤，但输入必须显式包含产品名、产品配置和版本。清理旧版本只能清理当前产品目录，不得扫描或删除其他产品版本。现有 `v*` 工作流先继续代表主 App；是否将主 App 迁移到 `/updates/chat/`，必须另做兼容旧客户端的迁移设计，不能顺手改。

### 15.4 发布边界

一次漫剧发布必须独立通过：

- Web：漫剧构建、产物审计、Pages Production 部署、子域访问和 API CORS。
- macOS：Apple Silicon 与 Intel 构建、Developer ID 签名、公证、安装启动和更新检查。
- Windows：x64 安装包或便携包构建、启动和更新合同。
- GitHub：`manju-vX.Y.Z` Release 只包含漫剧产物。

主 App、电商和制作不因漫剧发版自动升版本或重发。

## 16. 实施顺序

### Task 0：冻结实施合同

- 统一漫剧 Reference、`jc-everything-wiki`、`jc-raw-wiki` 与原生 Wiki runtime 对 `.raw/分集对话记录/` 的定义。
- 明确“30条爽点”与“唯一核心梗库”的关系。
- 确认漫剧产品名、Bundle ID、Deep Link、Web 子域和更新目录不与现有产品冲突。

验证：Skill 合同和原生 scaffold 测试对同一路径、同一职责得出一致结果；产品身份矩阵没有重复值。

### Task 1：独立空壳与发布通道

- 建立独立漫剧 Web 入口和 Tauri App Shell。
- 接入公共模型/Provider、账号、`ProjectFileService` 和必要基础 UI。
- 建立 `manju-v*` 构建路由、独立安装包与 `/updates/manju/latest.json`。
- 建立独立 Cloudflare Pages 项目和 `manju.jiucaihezi.studio`。
- 不加入漫剧业务逻辑，不改主 App 默认入口和发布结果。

验证：空壳能在 Web、macOS Apple Silicon、macOS Intel 和 Windows 启动；漫剧发版不覆盖主 App 的安装、Deep Link、Web 站点或更新清单。

### Task 2：建库与 Raw

- `manju scaffold` 创建 Wiki 骨架和 `.raw/分集对话记录/`。
- 实现集数扫描、创建、读取和冲突安全追加。
- 第一次建库创建第001集对话文件。

验证：Web/Desktop 新项目建库后目录一致；并发追加不丢消息、不重复 turnId。

### Task 3：独立工作台 UI

- 实现项目/Wiki 空状态、顶部集数选择、完整对话显示、输入、附件和模型选择。
- 不挂载 `ChatPanel`，不创建任何 App 会话记录。
- 不挂载 `WorkspaceLayout` 或主 App Rail。

验证：删除文武道创注册和 App 会话数据后，仍能进入工作台、切集和查看完整 Raw。

### Task 4：查询后回复

- 用完整当前集 Raw 构造 Direct 请求。
- 接入 Skill loader 和只读项目工具。
- 验证每轮实际加载 `jc-cha-wiki` 并查询当前 Wiki。
- 最终回复成功后追加 Raw。

验证：角色、场景、道具相关改稿会查询对应事实；没有查询时不会写入回复。

### Task 5：建制与催化循环

- 接入核心梗确认、人物确认和 A/B/C/D 催化交互。
- 接入漫剧写作规则和剧本格式规则。
- 保持剧情由催化事件和人物自然反应推进，不增加主题/主线/结局步骤。

验证：三组催化事件都服务同一核心梗；用户选择后下一场不偏离方向。

### Task 6：确认、填充和巡检

- 接入确认建制、确认本场、确认本集。
- 使用 `jc-raw-wiki` 写正式事实和正文。
- 本场做相关页检查，本集运行 `jc-jian-wiki`。
- 语义冲突经用户裁决后再使用 Raw 或 Xiu。

验证：未确认草稿只在 Raw；确认正文进入唯一正式路径并有来源索引、双链和回链。

### Task 7：独立产品完整回归

- Web/Desktop、切项目、切集、刷新、取消、失败、重试、并发写和上下文超限。
- 建库、查询、填充、巡检、修正五 Skill 闭环。
- 安装、签名、公证、更新、Pages、CORS、登录和项目导入导出。
- 既有主 App Chat、创模式、制作工作台、电商工作台和 OpenCode 行为不变。

验证：漫剧从独立 URL 和独立安装包完成真实模型闭环；主 App 的自动测试、构建和现有安装升级链路不回归。

### Task 8：复制发布模板，最后精简主 App

- 漫剧真实发布稳定后，复制已经验证的产品壳和 CI 参数化方式给电商、制作。
- 只共享稳定公共能力，不复制漫剧业务 Runtime。
- 电商和制作分别完成自己的等价验收后，才从主 App 移除对应入口与依赖。
- 主 App 最终收敛为通用对话产品，但保留现有 Bundle ID，除非另有迁移 SDD。

验证：四个产品可以独立构建、安装、访问、更新和回滚；发布任一产品不会改变另外三个产品的版本或产物。

## 17. 验收标准

### 17.1 独立性

1. 漫剧拥有独立 Web 入口、App Shell、Tauri 配置、Bundle ID、Deep Link、构建产物和更新清单。
2. 漫剧工作台不导入或调用主 App Shell、`WorkspaceLayout`、`ChatPanel`、`useChat`、会话 Store、OpenCode 或模式 Store。
3. 漫剧安装包不包含 OpenCode sidecar，也不包含主 App、电商或制作入口。
4. 一次完整写作不会产生 `creative_*`、`sess_*` 或 `ses_*`。
5. 清空 App conversations/messages 后，重新打开项目仍能恢复全部分集对话。
6. 工作台只从项目文件扫描集数和内容。

### 17.2 Raw 完整性

1. 用户消息在请求模型前已经进入当前集 Raw。
2. 只有完整模型回复进入 Raw；工具结果和错误不进入。
3. 第002集请求只携带第002集完整 Raw，不携带其他集 Raw。
4. 切换回历史集可继续讨论并追加同一文件。
5. 多窗口写入不丢失、不覆盖、不重复同一 turnId。

### 17.3 查询合同

1. 每轮最终回复前，模型已经看到当前集完整 Raw。
2. 每轮实际加载 `jc-cha-wiki`，并发生至少一次当前 Wiki 查询或读取。
3. 查询关键词和文件范围由模型根据对话决定，应用不提前猜测。
4. 查询失败或未查询时不追加编剧回复。

### 17.4 创作合同

1. 建制确认一部剧只有一个核心梗。
2. 每轮 A/B/C 均服务核心梗，D 允许用户给出新方向。
3. 人物选择符合人设，场景与道具真实限制行动，压力值不覆盖用户方向。
4. 未确认正文只在 Raw；确认正文只存在一个正式 Wiki 位置。
5. 每场格式符合短剧写作格式规范，本集确认后完成一致性巡检。

### 17.5 可携带性

1. 项目完整导出后包含 `wiki/` 与 `.raw/分集对话记录/`。
2. 在另一台设备导入项目后，不依赖原设备数据库即可继续指定集数。
3. Wiki 双链、来源索引和 Raw turn 范围仍可追溯。

### 17.6 发布隔离

1. `manju-vX.Y.Z` 只构建和发布漫剧，不改变主 App、电商或制作版本。
2. 漫剧 Web 只部署到自己的 Pages 项目和 `manju.jiucaihezi.studio`。
3. 漫剧 Desktop 只读取 `/updates/manju/latest.json`，其他产品更新不会被识别为漫剧更新。
4. 漫剧和主 App 可以同时安装、同时启动，项目与账号行为互不覆盖。
5. 四产品共用 `api.jiucaihezi.studio` 时，各 Web Origin 的 CORS 与登录回调均经过真实验证。
6. 主 App 在漫剧等价验收前没有删除对应能力或改变现有升级身份。

## 18. 成功定义

普通用户完成下面闭环时，漫剧工作台才算成立：

```text
打开 manju.jiucaihezi.studio 或安装“韭菜盒子·漫剧”
  -> 创建项目
  -> 创建漫剧 Wiki
  -> 在第001集讨论并确认唯一核心梗和人物
  -> 选择 A/B/C 或填写 D
  -> 模型每轮读取整集 Raw 并自主查询 Wiki
  -> 多轮改稿
  -> 确认本场/本集
  -> 正式正文和确认事实进入 Wiki
  -> 巡检冲突由用户裁决
  -> 新建下一集继续写
```

整个过程里，用户只需要打开漫剧产品、选择模型、对话、选择催化方向和确认结果；不需要进入主 App，不需要理解模式、Agent、Skill、上下文、会话或文件写入。

产品级成功还要求：漫剧能够独立安装、独立访问、独立发布、独立更新和独立回滚；验证成立后，同一套产品壳与发布模板才有资格用于电商和制作，最后再精简主 App。
