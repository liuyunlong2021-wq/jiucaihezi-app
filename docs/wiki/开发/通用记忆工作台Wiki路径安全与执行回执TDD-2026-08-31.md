> 前置：[[通用记忆工作台WikiAgent索引渐进读取与确定性事务规范-2026-08-29]]、[[通用记忆工作台WikiAgent统一路由与白名单TDD-1-2026-08-30]]、[[通用记忆工作台AgentLoop定向增强与清理TDD-SA4-2026-08-30]]

## 1. 目的与边界

本 TDD 解决两个真实风险：

1. Wiki 读取和写入存在多套路径解析逻辑，模型给出合法路径时可能被错误拒绝，或因程序猜测路径而读写错误目标。
2. Wiki 写入失败、取消或验证失败时，模型原始回答可能仍被显示为“已完成”，用户无法区分答案和真实执行状态。

产品仍只有一个 `WikiAgent`。本 TDD 不创建 `FileAgent`、第二套文件系统、第二个 Agent Loop 或第二套 Receipt 协议；Wiki 中的页面就是受授权范围约束的项目文件。

## 2. 根因原则

### 2.1 采用 OpenClaw 的原则

OpenClaw 采用的是**安全规范化**：先确定工作区 root，再把输入解析为可校验的绝对路径，最后检查路径是否位于授权 root 内。它不是标题搜索、相似文件名匹配或自动补全路径。

本产品借鉴以下行为：

- 工作区/Wiki root 是所有文件操作的安全边界。
- 读写工具在执行前统一校验输入。
- 非法输入返回结构化工具错误，而不是静默修正。
- 工具结果同时包含用户可见内容和程序结构化状态。
- 每个工具调用都必须有对应的真实结果；失败、取消和未执行调用也不能缺失结果。

本 TDD 只适配现有 `wikiRuntime`、`wikiTwoPhase` 和 `memoryChat`，不搬运 OpenClaw Runtime。

### 2.2 路径决策

- 允许绝对路径，但仅允许授权 Wiki root 内的绝对路径。
- 相对路径一律相对于当前 Wiki root 解析。
- `.`、`..`、重复分隔符和平台分隔符按标准路径规则规范化。
- 不自动补 `.md`，不把目录名猜成文件名。
- 不把 `0825` 猜成 `08-25`，不根据标题、索引相似文本或文件名相似度猜目标。
- 找不到目标时返回精确错误，模型必须重新请求真实路径或向用户说明无法完成。
- 路径规范化不改变用户可见的 `requestedPath`；程序同时记录规范化后的 `canonicalPath`。

## 4. 路径合同

### 4.1 输入与输出

模型和用户可以提交：

```json
{ "path": "角色/关羽.md" }
```

或授权范围内绝对路径：

```json
{ "path": "/项目/wiki/角色/关羽.md" }
```

程序统一返回：

```json
{
  "requestedPath": "角色/关羽.md",
  "canonicalPath": "角色/关羽.md",
  "root": "/项目/wiki",
  "kind": "file"
}
```

`canonicalPath` 是 Wiki 内部唯一身份。后续读取、指纹、计划确认、写入和回执都使用它。

### 4.2 允许与拒绝

| 输入 | 结果 |
| --- | --- |
| `角色/关羽.md` | 解析为 Wiki root 内 canonical file path |
| `./角色/关羽.md` | 去掉 `.`，解析为同一 canonical path |
| `角色/../场景/赤壁.md` | 标准化后解析；仍须检查未越界 |
| `/项目/wiki/角色/关羽.md` | root 内绝对路径，转换为 canonical path |
| `/其他项目/关羽.md` | 拒绝，`PATH_OUTSIDE_ROOT` |
| `../../关羽.md` | 拒绝，`PATH_OUTSIDE_ROOT` |
| `https://example.com/a.md` | 拒绝，`PATH_INVALID` |
| `角色/关羽.md\u0000.tmp` | 拒绝，`PATH_INVALID` |
| `角色`（需要文件但实际为目录） | 拒绝，`PATH_EXPECTED_FILE` |
| `角色/不存在.md` | 拒绝，`PATH_NOT_FOUND` |
| `关羽`、`0825`、`角色/关羽` | 不猜测、不补全；按真实路径返回 `PATH_NOT_FOUND` 或 `PATH_EXPECTED_FILE` |

解析器必须拒绝符号链接或解析后越出 root 的目标。目录操作和文件操作分别校验目标类型；不能以“存在即可”代替类型检查。

### 4.3 错误合同

错误至少包含：

```json
{
  "code": "PATH_NOT_FOUND",
  "message": "Wiki 路径不存在：角色/关羽.md",
  "requestedPath": "角色/关羽.md",
  "canonicalPath": null,
  "retryable": true
}
```

固定错误码：

- `PATH_INVALID`：空路径、NUL、URL、非法格式或无法规范化。
- `PATH_OUTSIDE_ROOT`：绝对路径或 `..` 解析后越出授权 Wiki root。
- `PATH_NOT_FOUND`：目标不存在。
- `PATH_IS_DIRECTORY`：调用要求文件，但目标是目录。
- `PATH_EXPECTED_FILE`：调用要求目录，但目标是文件，或目标类型与操作不符。
- `PATH_SYMLINK_ESCAPE`：符号链接解析后越出授权 root。

错误不得改写为“没有 Wiki 内容”。缺索引、读取失败和权限不足都必须作为真实 Observation 返回。

## 5. Wiki Apply 与 Receipt 合同

### 5.1 预检和 canonical plan

1. 接收模型最小 `actions`。
2. 对每个操作解析 `requestedPath` 和 `destination`。
3. 将所有路径替换为 canonical path，并校验文件/目录类型、旧值和并发指纹。
4. 用 canonical 操作生成 `planId`；同一用户确认计划在路径表述变化后不能变成另一份计划。
5. 预检失败时零写入，返回对应错误 Receipt。
6. 预检通过后复用现有一次 `wiki apply`、写后重读和回滚链路。

### 5.2 Receipt 最小结构

Receipt 只由程序生成，模型文本不能生成或覆盖它：

```json
{
  "status": "succeeded",
  "planId": "wiki-plan-...",
  "actionIds": ["action-1"],
  "operations": [
    {
      "actionId": "action-1",
      "kind": "replace",
      "requestedPath": "角色/关羽.md",
      "canonicalPath": "角色/关羽.md",
      "status": "succeeded",
      "changed": true,
      "verified": true
    }
  ],
  "changedPaths": ["角色/关羽.md"],
  "verifiedPaths": ["角色/关羽.md", "角色/index.md"],
  "rollback": { "attempted": false, "succeeded": null },
  "error": null
}
```

失败、取消和部分成功必须保留已经执行的操作及其状态：

```json
{
  "status": "failed",
  "planId": "wiki-plan-...",
  "operations": [],
  "changedPaths": [],
  "verifiedPaths": [],
  "rollback": { "attempted": false, "succeeded": null },
  "error": {
    "code": "PATH_OUTSIDE_ROOT",
    "message": "目标不在授权 Wiki 根目录内"
  }
}
```

允许的顶层状态只有：`succeeded`、`failed`、`cancelled`、`partial`。没有显式 `status` 的 Wiki 写入结果不能被归类为成功。

### 5.3 成功回执约束

只有同时满足以下条件，最终回答才可以说“已完成”或“已写入”：

- 所有实际执行的 Wiki 操作均通过路径和权限预检。
- 一次 `wiki apply` 返回成功或可明确归类的部分成功。
- 正文、受影响的 `index.md`、链接和指纹完成写后重读验证。
- 没有待处理回滚或并发冲突。

否则：

- 保留模型答案，避免丢失用户可复制内容。
- 单独显示程序失败/取消状态卡。
- 最终措辞不得把模型原始成功措辞当作事实。

## 6. Agent Loop 收口

沿用 OpenClaw 借鉴的最小循环边界：

1. 每个助手消息中的 `tool_call` 都必须有同 `tool_call_id` 的 Observation/Result。
2. 路径错误、未授权、未连接、执行失败和取消都生成真实失败结果；不能跳过结果直接进入成功收尾。
3. 取消后不发起新的模型请求或工具副作用；已收到但未启动的调用生成 `cancelled` Observation。
4. 同一失败路径调用不得原样连续重试；模型必须修正路径、换动作或结束回答。
5. 只有收到真实工具结果后，模型才允许生成最终处理结果。
6. Wiki 写入失败时，循环可以让模型解释或重新规划，但程序不得自动扩大路径范围、工具白名单或 Skill 授权。

## 7. TDD 测试矩阵

### 阶段 T1：统一 canonical resolver

**RED**

- 相对路径和 root 内绝对路径解析为同一 canonical path。
- `.`、`..`、重复分隔符规范化后不能越出 root。
- root 外绝对路径、越界路径、URL、NUL 输入均返回固定错误码。
- 文件/目录类型不匹配返回 `PATH_EXPECTED_FILE` 或 `PATH_IS_DIRECTORY`。
- 不自动补 `.md`，不按标题或相似名称猜目标。

**GREEN**

- 在 `wikiRuntime.ts` 提供唯一 resolver。
- `resolveWikiFile()`、`resolveWikiTarget()` 和 `applyWiki()` 全部复用它。
- 保留现有 root 越界、URL、NUL 和符号链接安全检查。

**REFACTOR**

- 删除重复路径分支和自由文本错误拼接。
- 不新增第二套路径工具或模糊匹配库。

### 阶段 T2：预检与 canonical plan

**RED**

- 同一操作用相对路径和 root 内绝对路径提交时生成相同 canonical `planId`。
- 任一操作路径越界、类型错误或指纹冲突时零写入。
- 预检失败时返回具体错误和原始请求路径。

**GREEN**

- 所有操作先解析、校验，再进入现有一次 `wiki apply`。
- 计划、指纹、验证和回滚统一使用 canonical path。

**REFACTOR**

- 只保留一个预检入口；不在 UI、模型提示词或平台适配器中重复路径判断。

### 阶段 T3：结构化 Receipt 与成功收口

**RED**

- 写入失败、取消、验证失败和回滚失败均不能返回成功 Receipt。
- 没有 `status` 的 Wiki 结果不能默认成功。
- 模型回答“已完成”但程序失败时，状态卡显示失败且最终答案不宣称完成。
- 成功必须包含 changed/verified paths；部分成功保留逐操作状态。

**GREEN**

- 复用现有 `DirectToolResult`、`normalizeMemoryToolResult`、`onProgramStatus` 和 `applyWiki()`。
- Receipt 只由程序生成，界面单独展示答案和状态。

**REFACTOR**

- 删除依赖自由文本解析成功状态的调用方。
- 保持现有 UI 字段兼容，避免新增第二套状态协议。

### 阶段 T4：Agent Loop 收口验收

**RED**

- 每个 Wiki tool call 都有配对 Observation。
- 取消后的未启动调用不产生副作用，但仍有 `cancelled` Observation。
- 工具失败后不跳过结果直接进入成功收尾。
- 同一失败调用不得原样连续重试。

**GREEN**

- 复用现有 `buildToolResultMessages`、取消检查和工具执行器。
- 只补齐缺少的配对、上限和重复调用保护，不重写 Agent Loop。

## 8. 云端/本地一致性验收

同一组路径和 Wiki 操作分别使用云端模型与本地 MLX 模型运行。模型来源不同不改变程序合同：

| 检查项 | 云端 | 本地 MLX |
| --- | --- | --- |
| 相对路径与 root 内绝对路径 | 相同 canonical path | 相同 canonical path |
| 越界、缺失、类型错误 | 相同错误码 | 相同错误码 |
| 工具调用与 Observation 配对 | 相同 | 相同 |
| 写入、验证、回滚 Receipt | 相同字段和状态语义 | 相同字段和状态语义 |
| 模型声称成功但程序失败 | 不得显示成功 | 不得显示成功 |

模型输出格式差异可以由现有宽容解析处理，但不能改变路径安全、工具白名单、事务和真实回执结果。

## 9. 实现顺序与门禁

1. T1 路径 resolver -> 单元测试与 Wiki 读写回归。
2. T2 canonical plan -> 预检、冲突和零写入回归。
3. T3 Receipt -> 失败/取消/验证/回滚回归。
4. T4 Agent Loop -> Observation 配对、取消和重复调用回归。
5. 云端/本地一致性矩阵 -> 真实模型验收后再清理兼容分支。

每一阶段必须先有 RED，再有 GREEN；阶段门禁未通过不得进入下一阶段。未执行的真实模型、MCP、Desktop/Web/Mobile 和付费能力测试必须标记为未验证。

## 10. 完成定义

- Wiki 读取、写入和事务计划只使用一个 canonical resolver。
- root 内相对/绝对路径均可用，root 外和模糊路径均明确拒绝。
- Wiki 写入只有程序 Receipt 能证明成功；模型文本不能伪造成功。
- 每个工具调用都有真实 Observation；失败、取消和未执行调用不丢失。
- 云端与本地模型接受同一安全、事务和回执合同。
- 没有新增 Agent、文件系统、通用路径猜测器或第二套 Receipt 协议。

## 11. 明确不做

- 不禁止所有绝对路径。
- 不实现标题搜索、模糊路径、相似文件名、自动扩展名或日期格式猜测。
- 不因缺失 `index.md` 自动扫描整个目录。
- 不让模型直接维护索引、来源、日志、指纹或 Receipt。
- 不把模型输出的“成功”当作程序执行成功。
- 不复制 OpenClaw 的 Gateway、Workspace、Memory、渠道、多 Agent 或完整 Runtime。
