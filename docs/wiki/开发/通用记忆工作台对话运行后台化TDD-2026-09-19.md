# 通用记忆工作台对话运行后台化与草稿即时清空 TDD

> 日期：2026-09-19
> 状态：已实施；用户实测已确认条 1、2（草稿即时清空、切项目后台运行），条 3（运行中可继续输入）已修复待复测；真实 Desktop/Web 人工验收矩阵待执行
> 范围：`src/components/memory/MemoryWorkbench.vue` 单文件；对话运行态归属、composer 清空时机、切换边界
> 不涉及：Raw 持久化格式、`runMemoryChat` 运行时、媒体/3D/创作链路

## 1. 用户目标

1. 点发送那一瞬，输入框立刻清空并可继续输入，不必等这一轮跑完。
2. 发送后可以切到另一个对话、另一个项目干别的活；原对话在后台继续跑，切回来能看到已落盘的结果。
3. 运行中同一条对话不允许再发第二轮（并发写同一条 Raw 会互相覆盖）。

## 2. 根因审计

一条运行的全部状态都挂在组件上，而组件在项目切换时**不重建**（`src/App.vue:66` 常驻渲染，项目切换走 `src/components/memory/MemoryWorkbench.vue:687` 的 `watch(projectOwner)`）。所以这套状态实际绑定的是「屏幕上正在显示的那一条对话」，而不是「发起运行的那一条对话」。

### 2.1 草稿被当成运行的一部分

`send()`（`MemoryWorkbench.vue:1466`）在 `await runMemoryChat(...)` 返回之后才执行：

```text
MemoryWorkbench.vue:1618  input.value = ''
MemoryWorkbench.vue:1619  setEditorText(composerRef.value, '')
```

同时输入框可编辑性由全局 `sending` 门控：`MemoryWorkbench.vue:3034` `:contenteditable="!sending"`。

这两处合起来就是症状一：整轮结束前既不清空也不能改。

### 2.1.1 「不能改」是单独一个毛病

`:contenteditable="!sending"` 以及 composer 上另外 12 处 `:disabled="sending"`（附件按钮、命令芯片、标签移除、@ 提及浮层、拖放）存在的理由只有一条：**运行态是组件级单例，那时候改 composer 会直接影响正在跑的那一轮**。

运行态改为「派发瞬间取快照」后这个理由就不存在了：composer 里的东西属于**下一轮**，与正在跑的这轮无关。所以这些门控应当整片撤销，只留发送键变成停止键。

### 2.2 切走即中断

| 位置 | 现状 |
| --- | --- |
| `MemoryWorkbench.vue:806` | `openProject()` 开头 `if (sending.value) stop()` |
| `MemoryWorkbench.vue:1354` | `selectConversation()` 开头 `if (sending.value) stop()` |
| `MemoryWorkbench.vue:1376` | `deleteConversation()` 停止运行（**这条必须保留**，见 3.4） |
| `MemoryWorkbench.vue:713` | `onBeforeUnmount()` → `abortController?.abort()` |
| `MemoryWorkbench.vue:348` | `memoryRunGeneration` 是**全局**计数器 |

`stop()`（`:1662`）会 `memoryRunGeneration++`，一次性失效所有运行。这套设计的隐含前提是「同时只允许一件事在跑」。

### 2.3 需要搬家的运行态

`MemoryWorkbench.vue`：`sending:254`、`streamingText:256`、`pendingUserTurn:257`、`status:260`、`pendingMemoryToolApproval:288`、`runVisible:297`、`runElapsed:298`、`runSteps:299`、`runMetrics:300`、`pendingProgramStatus:302`、`abortController:341`、`memoryRunGeneration:348`。

模板里 `sending` 门控出现在 16 处（`:2735`、`:2834`、`:2934`、`:2942`、`:2946`、`:2956`、`:2965`、`:2972`、`:2986`、`:3008`、`:3014`、`:3029`、`:3034`、`:3043`、`:3045`、`:3050`）。

`error` / `contextNotice` 被非运行路径共用（如预览失败写 `error`，`:1463`），**不搬家**，只把运行错误拆进 run。

## 3. 目标合同

### 3.1 运行归属

新增组件内运行注册表：

```text
runs: Map<`${owner}::${resource.path}`, MemoryRun>
MemoryRun = { owner, resourcePath, conversationId, generation, controller,
              status, streamingText, steps, elapsed, metrics, userTurn,
              programStatus, approval, startedAt }
```

- 用 `owner` 前缀：不同项目的 Raw 路径（`.raw/对话/conversation-*.md`）可能同名，只按路径索引会串项目。
- 注册表留在组件内，不抽新模块：`onBeforeUnmount` 本来就要中断运行，「卸载 = 退出工作台」是现有语义，抽模块只会多一份需要同步的生命周期。
- `sending` 改为 `computed(() => Boolean(activeRun.value))`，`activeRun` 取当前对话对应的 run。**这一条让 16 处模板门控，以及 `:1313`、`:2044`、`:2075`、`:2088` 等「阻止当前对话重复操作」的守卫语义自动变正确**，无需逐个改写。

### 3.2 草稿即时清空

`send()` 在建立 run 记录之后、`await runMemoryChat(...)` 之前立即执行 `input.value = ''`、`setEditorText(composerRef.value, '')`、`editingTurnId.value = ''`，并 `resizeComposer()`。

失败与中断分支不再重复清空；「恢复上一次输入」不属于本轮目标。

### 3.2.1 运行中 composer 保持可用

- `:contenteditable="true"`（不再跟 `sending` 联动）。
- 附件按钮、命令芯片（`@Skill`/`@文件`/…）、已选标签的移除按钮、`@` 提及浮层、文件拖放全部不再按 `sending` 禁用。
- 只有发送键例外：运行时它是停止键，所以「运行中发不出第二条」由按钮本身保证，不需要禁用输入框。
- 同一条对话运行中按 Enter 不动作（`send()` 的 `sending.value` 守卫），草稿原地保留。
- 唯一仍按运行态禁用的控件是消息级「编辑并重新发送」：它改写历史轮次，等这轮结束再动更安全。

### 3.3 落盘无条件，改视图有条件

- **无条件**：`appendMemoryRound` / `replaceMemoryRound`、`recordConversation`（自动索引）、`programStatuses`（按 turnId 索引，turnId 全局唯一）。
- **有条件**（仅当 run 仍是屏上那一条：`conversation.value?.resource.path === run.resourcePath && projectOwner.value === run.owner`）：`opened.value = ...`、`streamingText` 渲染、`openMediaPlanInCreation()`、`rememberConversation()`、`status` / `error` / `runVisible` / `contextNotice`。
- `rememberConversation()` 还要额外满足 `run.owner === projectOwner.value`，否则会把 A 项目的对话塞进 B 项目的 `conversations` 列表。

### 3.4 允许与禁止

| 场景 | 结论 |
| --- | --- |
| 不同对话 / 不同项目并发运行 | 允许。各写各的 `.md`，互不干扰 |
| 同一条对话再发一条 | 禁止。运行时发送键就是停止键（不是被禁用的发送键）；同对话按 Enter 不动作，草稿原地保留 |
| 运行中继续输入 / 加附件 / 改标签 | 允许。这些内容属于下一轮，派发时已取过快照 |
| 运行中删改历史轮次（编辑并重新发送） | 禁止。改写历史要等这轮结果落盘后再做 |
| 切项目 / 切对话 | 允许，不再 `stop()` |
| 删除正在运行的对话 | 仍然先停该对话的 run。授权随对话消失，继续跑会用旧授权落盘（`:1375` 现有注释） |
| 退出工作台（卸载） | 仍然中断。当前实现不支持跨重启续跑，不伪装支持 |

`startNewConversation():864` 的 `sending.value` 守卫去掉：新建对话不影响任何已有 run。

### 3.5 工具审批不能串对话

`pendingMemoryToolApproval`（`:288`）是单例，必须搬到 run 上：

- 审批请求写进 `run.approval`。
- 审批条只渲染**屏上那条对话**的 run 的审批（模板 `:2994`）。
- 后台 run 的审批挂起等待，用户切回该对话时才可见、才可答复。
- `settleMemoryToolApproval()` 只结算当前 run。

这是本方案唯一新增的复杂度。不做就会出现「A 对话后台弹的审批被 B 对话的点击答掉」。

## 4. 非目标

- 不做同对话排队（已确认先禁用发送）。升级路径：run 上加 `queue: []`，一轮结束时自动派发下一条。
- 不做后台运行通知、未读计数、声音提醒。
- 不改 `runMemoryChat` 与 `src/runtime/memory/memoryProject.ts` 的读-改-写实现，**不给 `mutateConversation` 加锁**（同对话已被发送按钮挡住，加锁是多余的）。
- 不做跨重启续跑、断点恢复。
- 不改移动端布局。
- 不为工作台引入全局 store。

## 5. 红灯测试

实施前在 `src/components/memory/__tests__/memoryWorkbench.test.ts` 增加源码级断言（沿用该文件现有正则扫源码风格），先确认旧实现全部失败：

1. 清除输入的语句出现在 `beginRunStatus()` 之后、`await runMemoryChat(` 之前。
2. `openProject()` 与 `selectConversation()` 函数体内不含 `stop()`。
3. `deleteConversation()` 仍然停止被删对话对应的 run。
4. `sending` 声明为 `computed`，不再是 `ref`，也不再有 `sending.value = ` 赋值。
5. 存在以 `owner` 为前缀的运行注册表 key。
6. 改视图前有「run 是否仍在屏上」的守卫；`rememberConversation()` 调用带 owner 判断。
7. 工具审批绑定到 run，而非组件单例。
8. composer 不因运行态被禁用：无 `:disabled="sending"`（消息级编辑按钮除外）、无可编辑性开关、`@` 提及与拖放不按 `sending` 拦截。

现有断言 `memoryWorkbench.test.ts:814`（匹配 `stop()` 实现）与 `:857` 会随实现变更同步调整。

## 6. 最小实施方案

1. 定义 `MemoryRun` 类型与 `runs` 注册表；`activeRun` / `sending` 改 computed。
2. `send()` 改为：创建 run → 立即清空草稿 → 所有回调写 `run.*` → 视图改写加守卫。
3. `stop()` 改为按 key 停单条 run；`deleteConversation()` 调按 key 版。
4. 删除 `:806`、`:1354` 的 `stop()`；放开 `:864` 的新建守卫。
5. 审批搬家到 run，模板按当前 run 渲染。
6. 同对话运行中禁用发送按钮并加提示文案。

预计净增约 120–180 行，全部在 `MemoryWorkbench.vue` 内。

## 7. 验收矩阵

### 自动验证

- 记忆工作台定向测试通过。
- `pnpm run test:focused` 通过。
- `vue-tsc -b` 通过。
- `git diff --check` 通过。
- 现有对话、附件、编辑重发、媒体计划、创作面板测试无回归。

### 人工验收（真实 Desktop + Web）

1. 发一条长任务：输入框立刻清空、可继续输入；发送按钮禁用并给出提示。
2. 同对话运行中再按发送：不发出第二条。
3. 切到本项目的另一条对话：原 run 继续，步骤条不再挂在新对话上。
4. 切到另一个项目操作，再切回来：回答已落盘，能直接看到。
5. 后台运行需要工具审批：审批条不出现在其他对话；切回原对话才能答复。
6. 删除正在运行的对话：立即停止，且不再落盘。
7. 退出工作台：运行中断（当前有意行为，按现状验收）。

真实 Desktop/Web 窗口未实测前，不得写成已通过。

## 9. 完成标准

- 发送后输入框立即可用，不再等待整轮结束。
- 切换对话/项目不中断运行；结果是落盘真源，切回即可见。
- 同对话并发被挡住，同一条 Raw 不会被并发读-改-写覆盖。
- 后台 run 的任何状态（步骤、错误、审批）不会显示到别的对话上。
- 删除对话仍会停止其运行。
- 未执行的真实环境验收明确标为待验证。

## 10. 已知前提（实施前确认）

- 本方案成立的前提是 `MemoryWorkbench` 在项目切换时不重建。若将来改成 `<MemoryWorkbench :key="projectOwner">`，注册表会随组件销毁，方案当场失效 —— 实施时留一行注释锁住该前提。
- 上游通道是否支持「请求还在飞的时候发起第二个请求」需要实测。若不支持，跨对话并发会退化为串行或限流报错，届时按通道行为调整，不影响本方案结构。

- 已按 §6 完成，改动集中在 `src/components/memory/MemoryWorkbench.vue`（+184 / −115）。

## 12. 实施后新增的已知边界

- **草稿不按对话隔离**：`input` 是视图级状态，切对话时不清空（改动前就如此）。现在运行中也能输入，于是「在 A 写完下一条 → 切到 B → 发送」会把草稿发到 B。这是用户可见且可自行避免的行为，本轮不改为按对话存草稿。
