## 1. 要解决的问题

2026-10-26 实测，特价渠道 MiniMax 成片「保存到项目失败」：

- `HTTP 下载失败：520`：Cloudflare 回源失败。
- `续传响应与已有文件不一致，未追加`：断点续传时，代理返回的 ETag 或范围与第一次不同。

现在的下载链路是：App → Cloudflare → NewAPI `/v1/videos/{task}/content` → 插件 `buildContentRequest` → 上游签名地址。NewAPI 会把每次请求（包括重试和续传）都完整转发一遍，几十 MB 的视频要穿过两层代理。

App 端已经先修了「续传不一致就卡死」和「520–524 不重试」（`src-tauri/src/commands/media_download.rs`）。这只能让下载出错后自己恢复，链路本身不稳定的问题还在。

约束：不能把上游地址暴露给用户；尽量复用现有能力，不新建通用代理。

## 2. 方案：成片只从上游拉一次，转存到现有 R2，App 从 R2 下载

```
App ──GET /api/creations/videos/{task}/content (Bearer)──▶ NewAPI 扩展
                                                         │ 1. 校验任务属于该用户且已成功
                                                         │ 2. R2 已有该成片 → 跳到第 4 步
                                                         │ 3. 没有 → 后台开始搬运（宿主 content 通道取一次 → 写临时文件 → PUT 到 R2）
                                                         │    请求最多等 60 秒；没搬完就回 503 + Retry-After: 15（result_preparing）
                                                         │ 4. 搬完后 302 跳转到 R2 签名读取地址（6 小时有效）
App ◀──────────── 302 ───────────────────────────────────┘
App ──GET（Range 续传）──▶ <account>.r2.cloudflarestorage.com
```

结果：

- 用户只看到我们的 API 域名和我们的 R2，看不到上游。
- 重试和续传都直接打到 R2。R2 支持 Range，ETag 固定，不会再出现「续传不一致」。
- 每个成片只从上游拉一次。之后无论重下多少次、多少台设备下载，都不再占用服务器带宽。R2 不收出站流量费。

## 4. 关键设计点

1. **对象名固定，不需要额外存储**：`video-results/{user_id}/{task_id}.mp4`。先用 HEAD 查 R2 是否已有，不加数据库表。路径里带 user_id，不同用户之间不可能互相取到。
2. **先校验归属再查 R2**：先在进程内请求宿主 `GET /v1/videos/{task}`，返回 200 且状态为成功，才去查 R2。否则只要知道任务号，就能拿到别人的成片。
3. **同一任务只搬一次**：用进程内 singleflight（按 task_id 加锁）防止并发重复搬运。没抢到锁的请求等待同一个结果。
4. **落盘前做磁盘保护**：R2 的 PUT 必须带 Content-Length，所以成片要先写到 `/data/video-relay` 下的临时文件。单个文件最多 1 GiB；剩余空间不足「1 GiB + 2 GiB 余量」时直接返回 503；无论成功失败都删除临时文件，NewAPI 重启时清空这个目录（参考 2026-10-26 服务器磁盘写满事故）。
5. **只认真视频**：宿主返回 200 且 Content-Type 为 `video/*` 才写入 R2；返回 409（上游未就绪）、4xx 或 JSON 错误页时，原样返回给 App，由 App 现有逻辑重新查询或重试。
6. **自动过期**：在 R2 上给 `video-results/` 设置生命周期规则，7 天后自动删除。在 Cloudflare 控制台配置，代码里不写删除逻辑。
7. **App 兼容旧服务器**：App 先请求新地址；遇到 404（服务器还没部署新路由）就退回旧的 `/v1/videos/{task}/content`。服务器和 App 不要求同时升级。
8. **范围**：所有 `usesNewApiContentEndpoint` 判定为走 content 回收的模型都改用新地址，不只特价渠道。这些模型原本走的就是同一条链路。

## 10. 按回执调整：后台搬运与「准备中」（2026-10-26，用户确认）

- 服务器：搬运改为后台进行，不会因为请求方断开而中止，单次最长 10 分钟。请求最多等 60 秒（低于 Cloudflare 回源 100 秒的上限），60 秒内没搬完就返回 `503`，带 `Retry-After: 15`，错误码为 `result_preparing`。搬运失败后不会缓存失败结果，下一次请求会重新搬运。新增单测「慢搬运先回准备中，后台完成后 302，且只拉取一次」，先红后绿，r2direct 共 7 项，`go test -race -count=3` 通过。

## 14. 真实验收暴露服务器瓶颈，FK 改为直连上游（2026-10-26，用户确认方案 A）

- 开发版重新下载 4 条特价渠道成片：中转每 60 秒回一次 503「准备中」，行为符合设计。但服务器 4 路并发从上游拉取各用了 3 分 49 秒到 5 分 47 秒，合计约 450 KB/s；之后上传 R2 只有 2 条成功（p9lq 35.7 MB、0DtH 39.8 MB），faMH、a46E 上传失败，原因没有记录下来（中转失败时不写日志，这是疏漏）。17:51–17:52，App 在「准备中」之后遇到连接被断开（`peer closed connection without sending TLS close_notify`），重试 4 次后放弃。NewAPI 没有重启，也没有 OOM。
- 结论：服务器到上游、服务器到外网两个方向都慢，任何经服务器转发大文件的方案都受这个瓶颈限制。用户自己直接从上游下载很快。用户确认接受暴露上游地址，FK 改为直连上游。
- FK 插件 0.6.1：`render` 在 SUCCESS 时，把任务快照里的上游签名 `videoUrl`（只认 https）作为 `video_url` 透传；没有时仍退回宿主 artifact 地址。新增插件测试，先红后绿。
- App：`urlSafety.isPublicUpstreamResultUrl` 只认 https 且主机不是 `api.jiucaihezi.studio` / `tian-shu.net`。`pollTask` 对 content 回收模型，只信任插件放在顶层 `video_url` 里的这类地址（适配器的 `metadata.url`，比如 comfy 内网地址和 Omni 地址，仍按任务号重建 content 地址）；保存时不再把这类地址改写成 content 地址；重新下载时，content 回收模型也会重新查询任务，让旧任务存的 content 地址换成直连地址，comfy 仍然得到 content 地址。新增 2 项 App 测试，先红后绿；focused 2371 项通过，2 项失败是之前就有的升级合同测试（撤掉改动后对照确认，与本次无关）；vue-tsc 通过。
- 部署顺序不受限制：插件还没上传时，`video_url` 仍是宿主的相对 content 地址，App 照旧走 content（经 R2 中转）。插件上传并激活 0.6.1 后，新任务和重新下载的旧任务都会直连上游。R2 中转继续保留，作为没有公开签名地址的渠道的兜底。
- 已知限制：宿主不会在任务完成后再去上游重新查询，所以签名过期后重新查询拿到的还是旧链接。这一点和改动前的 content 通道一样，不是新引入的问题。
