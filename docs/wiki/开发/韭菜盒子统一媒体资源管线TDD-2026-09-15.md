> 日期：2026-09-15

> 范围：图片、视频、音频与 3D 媒体的稳定引用、运行时展示、模型提交和生成结果落盘  
> 依据：[[开发/韭菜盒子原生媒体编排能力SDD]]、[[开发/创作媒体上传链路独立改进TDD-2026-08-24]]、[[排障/创作画布本地图片视频预览空白-2026-08-13]]

## 1. 一句话目标

把媒体从“在组件之间传递的大字符串”升级为产品原生资源：产品内部只传稳定引用，展示时生成可释放的本地播放地址，提交时由模型适配器按合同选择文件、远程 URL 或临时 Base64，生成结果落盘后以项目资源为主引用。

## 2. 三条不可退化原则

### 2.1 稳定引用是资源身份

- `ProjectResource`、项目相对路径和已登记的 `jc-media` 引用是资源身份。
- `asset:`、`blob:`、`data:`、`http(s):` 地址都是某一时刻、某一用途下的运行时产物，不是资源身份。
- Vue 状态、Pinia、任务历史、画布文档、会话记录和 `localStorage` 不得把运行时 URL 当作本地资源的唯一身份。
- 运行时 URL 失效后，必须能从稳定引用重新解析；不能要求用户重新选择原文件。

### 2.2 提交策略由接口合同决定

- 模型支持 multipart 时，直接提交 `File`/`Blob`，不先上传成 HTTPS URL。
- 模型只接受可公网访问 URL 时，才把本地资源上传到现有 Gateway 临时媒体入口，再提交返回的 HTTPS URL。
- 模型强制接受 Base64 或 Data URL 时，才在请求边界临时编码，请求完成或失败后立即释放。
- 页面组件不得自行决定提交格式，不得为了统一参数形状而提前把所有素材转成 Base64。

### 2.3 落盘后的本地资源是主引用

- 生成结果落盘成功后，`ProjectResource` 是展示、再次引用、画布回流、下载和任务恢复的主引用。
- 上游远程 URL 降级为 `sourceUrl`/`originalUrl` 等来源信息，只用于审计、失败恢复或明确的“复制来源链接”。
- 本地文件存在时，不得继续依赖远程 URL 进行日常预览；远程 URL 过期不能让已落盘结果变成不可用。

## 3. 当前根因

### 3.1 展示链路把媒体当文本

记忆工作台预览通过 `ProjectFileService.readBinary()` 调用 Rust `dev_read_file`。该命令读取完整文件后同时生成 UTF-8 文本和 Base64；前端再 `atob`、复制 `Uint8Array`、构造 Blob URL。视频只有完成整条链路后才开始解码，不能渐进读取。

创作画布的 `getMediaRuntimeUrl()` 也通过 `dev_read_file` 把图片、视频和音频变成 Data URL。该路径源于一次 `asset://` 与 Leafer/视频首帧提取不兼容的修复；它解决了空白预览，但把兼容兜底扩散成了通用媒体路径。

### 3.2 选择文件时过早物化提交数据

普通创作参考文件在点击生成时统一执行 `FileReader.readAsDataURL()`。AI 应用动态媒体字段更早：选中文件后立即读完整字节、复制、转 Data URL、写入 Vue 响应式 `fieldValues`，随后同步 `JSON.stringify` 并写入 `localStorage`，同时把完整字符串绑定到输入框 `value`。

记忆对话的图片、视频、音频附件在导入项目后仍立即生成 Data URL 放入临时附件状态。资源虽然已有 `projectPath`，运行时仍以大字符串参与界面更新和提交物化。

### 3.3 结果落盘发生 Base64 往返

Desktop 生成结果使用 Rust `http_download_base64` 下载，Base64 经 IPC 进入 JavaScript；`writeProjectMedia()` 再解码为字节并通过项目文件服务写回本地。大视频因此走“Rust 二进制 → Base64 → JS 字符串 → JS 字节 → Rust 文件”的往返。

### 3.4 产品已有正确能力但没有统一入口

以下实现已经证明正确方向可行：

- 文件树 Desktop 预览直接使用 `convertFileSrc()`。
- 文件树 Web 预览使用 OPFS Blob URL，并在关闭时释放。
- `mediaFileReader.resolveForDisplay()` 能把登记媒体解析为本地地址。
- `mediaThumbnail` 已有图片缩略图缓存和 Rust 视频缩略图生成。
- 会话和媒体任务已经能够持久化项目路径并剥离部分内嵌媒体。

根因不是缺少新媒体库，而是这些能力没有成为所有入口必须复用的产品合同。

## 4. 统一数据合同

### 4.1 持久层只保存定位信息

继续复用现有 `ProjectResource`，不新建第二套全局媒体数据库：

```ts
interface StableMediaReference {
  kind: 'project' | 'managed' | 'remote'
  mediaKind: 'image' | 'video' | 'audio' | 'model3d'
  resource?: ProjectResource
  assetId?: string
  sourceUrl?: string
  mimeType?: string
  name?: string
}
```

约束：

- `project` 必须以 `resource.runtime + owner + path` 定位。
- `managed` 继续复用现有 `jc-media`/`media_assets` 身份。
- `remote` 只适用于尚未落盘或明确保持远程的结果。
- 不持久化 `displayUrl`、Blob URL、Tauri asset URL 或 Data URL。
- 不要求立即新增名为 `StableMediaReference` 的公共类型；现有类型能表达合同就直接复用，避免平行抽象。

### 4.2 展示层使用租约

统一展示解析结果必须表达释放责任：

```ts
interface MediaDisplayLease {
  url: string
  release(): void
}
```

- Desktop 项目媒体：返回 `convertFileSrc(absolutePath)`；`release()` 为空操作。
- Web OPFS 媒体：从 Blob 创建 Object URL；`release()` 负责 `URL.revokeObjectURL()`。
- 远程媒体：透传已校验的 HTTP(S) URL；`release()` 为空操作。
- Data URL 只作为旧数据只读兼容输入，不作为新展示结果。
- 相同资源在同一界面生命周期内应复用租约，避免重复生成 Object URL。

### 4.3 缩略图与原媒体分离

- 图片/视频卡片、任务列表、聊天记录和画布卡片优先展示缓存缩略图。
- Desktop 视频缩略图复用 `dev_generate_video_thumbnail`，不再把完整视频交给 WebView 抽首帧。
- 只有用户点击播放、查看原图或模型提交时才访问原媒体。
- 缩略图也是派生产物，不能取代原资源身份。

### 4.4 提交层使用源，不使用展示 URL

```ts
type MediaSubmissionSource =
  | { kind: 'file'; file: File | Blob; filename: string; mimeType: string }
  | { kind: 'remote-url'; url: string }
  | { kind: 'base64'; dataUrl: string }
```

`MediaSubmissionSource` 是一次请求内的临时值，不进入任务持久化。模型注册表/运行计划必须明确提交合同：

```ts
type MediaInputTransport = 'multipart' | 'url' | 'base64'
```

不根据 `assetFlow !== 'none'` 一律先上传。适配规则固定为：

1. `multipart`：从稳定引用直接得到 File/Blob 并提交。
2. `url`：远程安全 URL 直接使用；本地资源先走现有 Gateway 上传，得到临时 HTTPS URL。
3. `base64`：在最终请求装配时读取并编码；不得进入页面状态和任务快照。

### 4.5 生成结果主从关系

任务成功但尚未落盘：

```text
主引用 = 已校验远程结果 URL
状态 = remote-only
```

落盘成功后：

```text
主引用 = ProjectResource
来源信息 = 原远程 URL
状态 = local
```

落盘失败时保留远程 URL 和失败原因，允许重试；不得伪装成已有本地资源。

## 5. TDD 红灯合同

实施前先增加最小失败测试，证明现状违反合同。

### 5.1 稳定引用与展示解析

- Desktop 项目图片、视频、音频解析展示地址时不得调用 `dev_read_file`。
- Desktop 返回的展示地址来自 `convertFileSrc`，不是 `data:` URL。
- Web OPFS 返回 Blob URL；同一租约释放一次且只撤销自己创建的 URL。
- 同一稳定引用可在旧 URL 释放后重新解析。
- 展示解析不能改变或覆盖资源身份。

### 5.2 记忆工作台预览

- 点击项目图片、视频、音频时不调用 `readBinary()`。
- 从创作画布切到预览时，媒体解析与画布保存是两个独立职责；预览测试不能依赖媒体 Base64。
- 关闭或快速切换预览必须释放上一条 Web Object URL，过期异步结果不能覆盖新预览。

### 5.3 创作画布

- 图片节点持久化内容只能包含项目资源定位，不包含 `data:image/...;base64`。
- 视频卡片恢复时调用缓存缩略图能力，不读取完整视频生成 Data URL。
- 音频时长和播放使用展示租约，不调用提交物化函数。
- 关闭画布后释放 Web Object URL；Desktop 本地 URL 不执行错误撤销。

### 5.4 普通参考文件与 AI 应用字段

- 选择图片、视频或音频后，`cpState.fieldValues` 和 `localStorage` 不包含 `data:` URL。
- 媒体输入框只显示文件名或资源标签，不把运行时 URL 绑定到 DOM value。
- 点击生成前，普通 `cpState.files` 保持 File/资源引用，不统一执行 `readAsDataURL()`。
- 同一个本地资源不得因预览和提交各读取、编码一次 Base64。

### 5.5 提交传输选择

为三种 transport 各写一个请求合同测试：

- `multipart`：请求体是 `FormData`，本地文件直接成为表单项；不调用临时上传，不生成 Data URL。
- `url`：已有安全 HTTP(S) URL 直接使用；本地资源只上传一次，最终模型请求使用返回 URL。
- `base64`：仅最终请求装配阶段产生 Data URL；请求完成后任务持久化快照不含该值。
- 数量、大小、MIME 和模型能力校验在物化大文件前完成。

### 5.6 生成结果落盘

- Desktop 远程结果能够直接下载到当前项目的目标文件，不返回媒体 Base64 给 JavaScript。
- 写入使用临时文件和原子完成策略；下载失败不能留下伪成功目标文件。
- 落盘成功后任务的主定位为 `directory + projectPath`，远程地址迁移到 `sourceUrl`，`resultUrl` 清空。
- 本地文件存在时，预览、再次引用和加入画布都不读取远程 URL。
- 重启应用后，远程 URL 已失效也能从项目资源恢复媒体。

### 5.7 历史兼容

- 旧任务、旧画布或旧媒体记录中的 Data URL 可以只读打开。
- 有项目上下文时，旧 Data URL 落成媒体文件并替换为稳定引用。
- 迁移失败保留旧数据且明确报错，不以空字符串覆盖。
- 新保存的画布、任务、会话和创作参数不得新增媒体 Data URL。

## 6. 最小实施范围

### Phase 1：统一展示入口

1. 在现有项目文件/媒体解析模块中增加 `ProjectResource -> MediaDisplayLease`，不另建 Store。
2. 让记忆工作台预览复用文件树已经验证的 Desktop/Web 行为。
3. 让 `MediaViewer` 接受稳定引用或已解析租约，组件不自行读取媒体字节。
4. 将创作画布的图片、音频播放接入展示租约；视频卡片接入现有 Rust 缩略图。

验证：本地媒体预览链路中没有 `dev_read_file`、`atob` 或 `readAsDataURL`。

### Phase 2：引用状态瘦身

1. AI 应用动态媒体字段只保存文件/项目资源引用和展示标签。
2. 普通创作文件保留 `File` 或项目资源引用，移除提交前统一 Data URL 物化。
3. 记忆对话附件只保存 `projectPath` 等元数据，缩略图通过展示解析器按需获得。
4. `saveCpState()` 明确过滤任何媒体运行时数据。

验证：选择上限允许的最大音频/视频后，`localStorage`、DOM value 和持久化状态均不出现媒体 Data URL。

### Phase 3：提交合同收口

1. 给模型规格补充或推导明确的 `MediaInputTransport`。
2. 在 `creationMediaRuntime` 最终请求边界解析稳定引用。
3. multipart、URL 上传和 Base64 三条路径分别复用现有请求函数，不新增第二套任务引擎。
4. 提交失败、取消或完成后释放 File/Blob/Data URL 临时对象。

验证：三种 transport 的合同测试通过；本地路径和 asset URL 从不直接发送到云端。

### Phase 4：结果直接落盘

1. 增加 Rust“下载到项目文件”命令，沿用现有 URL 安全、鉴权头、超时和项目路径校验。
2. 将 `mediaTaskStore` 和 `creationMediaCache` 的 Desktop 项目落盘切到该命令。
3. 落盘后任务主引用切换为项目资源，远程 URL 仅保留为来源。
4. 独立“下载到用户选择位置”继续使用现有保存流程，不与项目落盘混为一条路径。

验证：生成视频落盘过程中，Tauri IPC 不传输媒体 Base64。

### Phase 5：迁移和删旧

1. 迁移旧画布/任务/会话中的内嵌媒体。
2. 删除已经无调用者的旧画廊组件和重复读取函数。
3. 将通用 `readMediaDataUrl()` 限制为协议适配器内部函数，或在调用清零后删除。
4. 保留文本读取、文件导出、哈希和格式解析真正需要的原始字节能力。

## 9. 明确保留的 Base64 边界

以下情况不属于缺陷：

- 上游只返回 `b64_json`；收到后应尽快落盘并剥离长期状态中的大字符串。
- OpenAI 兼容或其他模型协议明确强制 Base64；只允许在最终请求边界临时生成。
- 旧数据迁移输入。
- 小型、派生且受大小上限约束的缩略图，但优先保存成文件并使用本地地址。

以下情况继续允许读取原始字节：文件导出、哈希、格式解析、图片压缩和 3D 解析。它们不得借机把大媒体写入响应式状态或持久化 JSON。

## 10. 非目标

- 不引入新的云存储、图片床、CDN 或第二套上传服务。
- 不把本地播放 URL 暴露给云端模型；它只对当前运行时有效。
- 不把所有远程媒体强制下载后才能预览；未落盘结果可以先使用安全远程 URL。
- 不在预览性能改造中重写画布、任务队列或模型注册表。
- 不以提高文件大小限制代替根因修复。

## 11. 对旧设计的修订

本 TDD 修订旧文档中“媒体二进制读取继续统一经过 `ProjectFileService.readBinary()`”的表述：

- 稳定身份仍统一使用 `ProjectResource`。
- 展示不读取完整字节，统一解析运行时播放地址。
- 提交是否读取字节由模型 transport 合同决定。
- 只有真实字节消费者继续使用 `readBinary()`。

历史 `dev_read_file -> data:` 方案保留为已解释的兼容证据，不再作为新媒体能力的实现标准。

## 12. 完成定义

只有同时满足以下条件，才能把统一媒体资源管线标记为完成：

1. 新产生的本地媒体在状态、画布、任务和会话中只有稳定引用，没有媒体 Base64。
2. 所有产品预览入口复用同一展示解析合同。
3. 三种模型提交方式由适配器按合同选择，页面不再预编码。
4. Desktop 生成结果直接流式落盘，不经 JavaScript Base64 往返。
5. 落盘后 ProjectResource 成为任务和 UI 的主引用，远程 URL 仅为来源。
6. 旧数据可迁移或只读兼容，失败不造成数据丢失。
7. 自动检查与四平台人工验收分别留下真实证据。
