# 通用记忆工作台对话记忆索引摘要模型接口约束 TDD

> 日期：2026-09-03
> 状态：已实施并修订（Opus 与 Ollama Provider 分流；本地自动验证完成）
> 范围：点击“写入 Wiki”后，当前 assistant 输出的 `summary + keywords` 生成请求

## 1. 目标

根治“索引模型返回的 JSON 无效”。模型仍负责生成 `summary + keywords`，但返回格式由 API 的严格 JSON Schema 约束；程序再次校验通过后，才拼装并写入 Wiki 索引。

## 2. 当前根因

问题不是 Wiki 文件写入，而是摘要请求把不同 Provider 强行套进同一个接口合同：

- Opus 的隐藏推理与普通正文共用补全预算，`max_tokens=300` 时 JSON 可能在半截被截断；即使加大预算，网关也可能忽略 `response_format`，返回非 JSON 正文。
- Ollama 的 OpenAI 兼容层不会可靠执行 `think:false`，Qwen 会把预算花在 `reasoning`，最终 `message.content` 为空。

因此 Prompt 只能描述内容，不能承担 Provider 的协议适配；程序必须按 Provider 选择真实可用的结构化接口。

## 3. 固定模型合同

### 3.1 输入

只发送当前待索引的 assistant 正文，不发送用户问题、整段 Raw、conversation ID、turn ID、文件路径或 Markdown 索引：

```json
{
  "role": "user",
  "content": "当前 assistant 回答的完整文字"
}
```

### 3.2 System Prompt

固定为：

```text
你是对话记忆索引器。
请只根据用户消息中的这条 assistant 回答生成可检索的对话记忆索引。
必须返回 summary 和 keywords 两个字段，不得返回其它字段。
summary：用中文写一条可独立理解的事实简介，概括这条回答确定了什么或解决了什么，1-2句，最多240个字符。
keywords：返回1-12个简洁关键词；关键词必须来自或明确概括这条回答中的主题、实体、路径、技术名词或决策；每个关键词最多32个字符。
不要补充输入中没有的事实，不要写 Markdown，不要写解释，不要输出代码围栏。
```

### 3.3 接口级响应约束

请求必须携带严格 JSON Schema；不能只依赖 Prompt：

```json
{
  "response_format": {
    "type": "json_schema",
    "json_schema": {
      "name": "conversation_memory_summary",
      "strict": true,
      "schema": {
        "type": "object",
        "additionalProperties": false,
        "properties": {
          "summary": { "type": "string" },
          "keywords": {
            "type": "array",
            "items": { "type": "string" }
          }
        },
        "required": ["summary", "keywords"]
      }
    }
  }
}
```

不支持 `json_schema` 的模型或网关不得静默降级为 Prompt-only；应返回“当前模型不支持索引结构化输出”，且不写入索引。`json_object` 只能作为已确认兼容网关的临时适配，不等同于本合同。

### 3.4 Provider 请求适配

普通远程模型使用 `/v1/chat/completions`：保留上面的 `response_format`，`max_tokens=800`。

Opus 使用 `/v1/chat/completions` 的强制工具调用：工具名固定为 `emit_conversation_memory_summary`，参数严格复用上述 Schema，并设置 `tool_choice` 强制调用；不再依赖 Opus 网关是否执行 `response_format`。

Ollama 使用原生 `/api/chat`，不走 `/v1/chat/completions` 兼容层：

```json
{
  "stream": false,
  "think": false,
  "format": { "type": "object", "properties": { "summary": { "type": "string" }, "keywords": { "type": "array", "items": { "type": "string" } } }, "required": ["summary", "keywords"], "additionalProperties": false },
  "options": { "temperature": 0.2, "num_predict": 256 }
}
```

Ollama 原生响应的 `message.content` 与 OpenAI 响应的 `choices[0].message.content` 进入同一个程序校验器；`reasoning` 永远不作为正文。

## 4. 程序合同

1. 只读取 `message.content`；`reasoning`、`reasoning_content` 不是索引正文，不能拿来解析。
2. 不做代码围栏删除、首尾大括号截取或 JSON 猜测修复。
3. 对响应再次执行 Schema 校验，并 trim、去重关键词；`summary` 最多240字、关键词每项最多32字、总数1-12个；校验失败不调用 `writeConversationMemoryIndex`。
4. `conversationId`、`assistantTurnId`、Raw 路径、索引文件路径、正链和 Markdown 全部由程序生成，模型不能提供或覆盖。
5. 只有“模型请求成功 + Schema 校验成功 + 文件写入成功”才显示“已写入 Wiki”。

## 5. TDD 测试矩阵

先写测试，再改实现：

1. 普通远程请求体包含固定 System Prompt、当前 assistant 正文和完整 `response_format.json_schema`；预算为800。
2. Opus 请求体使用固定严格工具、`tool_choice` 强制调用和800预算。
3. Ollama 请求体使用原生 `/api/chat`、`think:false`、Schema `format` 和 `num_predict=256`。
4. 合法 `summary + keywords` 响应通过校验，并生成固定路径和正链。
5. 缺少 `summary`、缺少 `keywords`、关键词不是字符串数组、超过长度或多于12个关键词时拒绝。
6. 多余字段、Markdown 代码围栏、解释文字和截断 JSON 均拒绝。
7. 只有 `reasoning` 或 `reasoning_content`、没有 `message.content` 时拒绝，不把推理当摘要。
8. 校验失败时文件服务的 `createText`/`writeText` 调用次数为零。
9. 重复点击同一 assistant turn 仍保持一条索引记录，程序生成的 ID、路径和正链不受模型响应影响。

## 6. 最小实施顺序

1. 抽出固定 Schema、Prompt 和纯响应解析函数，先补上述单元测试。
2. 普通远程索引请求加入 `response_format.json_schema`；Opus 改用强制工具调用；Ollama 改走原生 `/api/chat` 并关闭 thinking；删除大括号截取和 reasoning fallback。
3. 保留现有 `writeConversationMemoryIndex`，仅在解析通过后调用；运行定向测试、TypeScript 和 `git diff --check`。

## 7. 明确不做

- 不把模型输出改成只返回关键词；本合同明确保留 `summary + keywords`。
- 不让模型生成 conversation ID、turn ID、文件路径或 Markdown。
- 不增加第二次“修 JSON”模型请求。
- 不用 Prompt、正则或字符串截取替代接口级结构化约束。

## 8. 验收标准

- 支持结构化输出的模型：合法响应稳定写入，非法结构在接口或程序校验层被拒绝。
- 不支持结构化输出的模型：明确失败且不产生半条 Wiki 索引。
- 现有查询、正链、幂等更新和跨平台文件服务行为不改变。
