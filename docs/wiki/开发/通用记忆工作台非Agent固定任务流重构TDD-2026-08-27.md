# 通用记忆工作台 Skill-first 能力内核重构 TDD

> 日期：2026-08-27  
> 状态：待实施  
> 目标：把默认产品收敛为“本地 Markdown/Wiki 工作台 + Skill 方法 + 显式能力”  
> 优先级：本 TDD 取代 [[通用记忆工作台轻上下文任务运行时TDD-2026-08-26]] 的默认 Agent Runtime、64 轮开放循环、关键词工具路由和跨任务对话记忆；继承 [[通用记忆工作台原生Wiki能力与五Skill退役TDD-2026-08-26]] 和 [[通用记忆工作台索引优先Wiki查询与确认写入TDD-2026-08-27]]

## 1. 产品决定

产品不再是“模型自由挑选所有工具的通用 Agent”，也不建设一套把每种任务写死的工作流引擎。

唯一主链路是：

```text
用户任务
  + 用户明确选择的 Skill
  + 用户明确连接的 @Wiki / @MCP / 文件 / 媒体能力
  -> 程序先准备可确定的材料
  -> 模型按 Skill 生成文字或请求当前已连接的能力
  -> 程序执行并回传结果
  -> 模型输出最终结果
```

三者边界固定：

- **Wiki** 保存事实、设定、进度和长期外部记忆。
- **Skill** 保存方法、规则、渐进式资料和工作步骤。
- **能力内核** 负责模型请求、文件、Wiki、MCP、媒体、3D、路径安全、审批和三端执行。

结论：**可复用的用户方法都可以做成 Skill，但底层能力不做成 Skill。** Skill 可以组合能力，不能代替能力。

Wiki 和 Skill 使用同一种渐进式披露思路，但负责不同的树：

```text
Skill 方法树：catalog -> SKILL.md -> references/scripts/assets
Wiki 事实树：wiki/index.md -> 分区 index.md -> 具体事实页
```

模型在同一次资料选择中决定两棵树需要的分支，程序一次并发读取，不为 Skill 和 Wiki 分别建立工具循环。

## 2. 根因与删除目标

当前慢和不稳定不是模型能力不足，而是默认运行时承担了过多产品决策：

1. 用正则从自然语言猜 Wiki、文件、MCP、Terminal 和 Skill。
2. 每次任务可向模型暴露大量工具 Schema。
3. 模型在多轮中重复发现 Skill、读文件、选工具和自我修复。
4. 对话历史和工具结果继续累积，简单任务也支付长任务成本。
5. 一个巨大 Runtime 同时承担产品路由、记忆、工具循环和失败恢复。

本 TDD 不通过增加更多路由、模式或中间层修复，而是逐项移除上述职责。

## 3. 唯一架构

```text
MemoryWorkbench
  -> Explicit Connections
       - selected Skills
       - @Wiki
       - selected files / attachments
       - selected MCP tools
       - media / 3D panel
  -> Skill Runner
       - preload deterministic context
       - call model
       - execute only connected capabilities
       - stop at final output or bounded limit
  -> Existing Capability Kernel
       - Provider / HTTP streaming
       - ProjectFileService
       - wiki_context / wikiRuntime
       - Skill loader / package resources
       - MCP client
       - Media / 3D runtime
       - approval / path protection / platform adapters
```

不新建通用工作流 DSL、节点编辑器、路由模型、向量库、任务队列或第二套 Provider。

## 4. Skill 合同

### 4.1 继续使用现有标准结构

```text
skill-name/
├── SKILL.md
├── references/   # 按需读取
├── scripts/      # 确定性、重复性工作
└── assets/       # 模板和资产
```

保留三级渐进式披露：

1. 目录只载入 `name + description`。
2. 用户选中 Skill 后载入完整 `SKILL.md`。
3. 只有 Skill 明确需要时才读取 `references/` 的具体文件。

继续复用现有 `SkillConnection`、`resolveSkillUriContent()`、Skill 包存储和资源读取，不建第二套 Skill 格式。

Wiki 采用同样的三级结构：

1. 默认只载入短 `wiki/index.md`。
2. 模型根据当前任务选择分区入口。
3. 模型再选择当前任务确实需要的角色、剧情、场景、道具、伏笔或其他事实页。

明确文件路径或简单精确查询可由程序直接预取；长篇创作、跨分区查询和路径不明确的任务使用统一资料选择阶段。

### 4.2 只增加最小能力声明

Skill 默认是纯文字能力。需要外部能力时，复用标准 `SKILL.md` frontmatter 的可选 `allowed-tools` 字段，声明所需工具：

```yaml
---
name: research-and-save
description: 查询外部资料，整理后建议写入 Wiki。
allowed-tools: wiki, mcp__github__search
---
```

首批只允许已存在的工具名：

```text
wiki
wiki_context
read
write
edit
mkdir
mcp__<server>__<tool>
已有媒体和 3D 工具名
```

- `allowed-tools` 只决定该 Skill 可以请求什么，不代表用户已批准副作用。
- 用户明确选择的 `@Wiki/@MCP/文件` 与 Skill 声明取交集；缺少连接时直接提示用户补选，不自动扩权。
- 用户明确点选的能力可直接连接；写入、删除、Terminal 和项目外操作仍逐次确认。
- 首批不把 Skill 步骤编译为 JSON/YAML 工作流。步骤仍写在 `SKILL.md` 正文，由模型按顺序执行。

### 4.3 Skill Creator 的责任

`skill-creator` 继续生成标准 `SKILL.md + references/scripts/assets`，只补两项：

1. 询问该 Skill 是纯文字，还是需要 Wiki、文件、MCP、媒体或 3D。
2. 仅在确有需要时写入最小 `allowed-tools`。

不让 Skill Creator 生成新的工具实现、通用工作流引擎或隐式权限。

### 4.4 Wiki Creator

`wiki-creator` 不从零发明，而是以已退役的 `jc-everything-wiki` 为设计来源做最小重写。它是一个“Wiki 导航架构设计 Skill”，不是第六个 Wiki 基础 Skill，也不恢复旧五 Skill 依赖。

```text
public/skills/wiki-creator/
├── SKILL.md
└── references/
    └── wiki-architecture.md
```

首版不创建 `scripts/` 和 `assets/`；重复的确定性写入已由原生 Wiki Runtime 执行。

#### 输入

- 用户要建立或接管 Wiki 的明确目标。
- 用户指定的文档、文件夹或已有 Wiki 摘要。
- 原生 `wiki inspect` 的现有路径、入口和冲突结果。

#### 输出

```ts
interface WikiCreatePlan {
  directories: string[]
  files: Array<{
    path: string
    content: string
  }>
}
```

`WikiCreatePlan` 至少包含：

- 短 `wiki/index.md`：说明 Wiki 用途、当前入口和分区导航。
- 实际需要的分区 `index.md`：例如角色、剧情、场景、道具、伏笔、状态或创作规范。
- 仅为当前材料已确认的内容创建必要初始页，不生成空占位树。

分区不固定。小说可以有角色/剧情/场景/伏笔，公司知识库、日记和记账必须根据实际用途生成不同结构。

#### 删除旧 Everything Wiki 过度设计

- 不强制把项目分成开发、小说、漫剧、电影、电视剧、广告等固定类型。
- 不强制创建 `CLAUDE.md`、`hot.md`、`log.md`、`来源索引.md` 或 `方向.md`。
- 不管理、规划、扫描或迁移 `.raw/`。
- 不通过多个 Skill 在“建骨架”与“填充内容”之间互相转派。
- 不自行逐文件调用 `mkdir/write/edit`。

#### 执行边界

```text
wiki-creator 生成 WikiCreatePlan
  -> 程序完整校验所有路径与冲突
  -> 用户一次预览确认
  -> 原生 wiki scaffold plan 一次批量落盘
  -> 程序验证入口和链接
```

写入成功后不再请求模型生成回执。

## 5. Skill Runner

Skill Runner 是现有能力的薄编排层，不是新 Agent 平台。

### 5.1 输入

```ts
interface SkillRunInput {
  userText: string
  selectedSkillNames: string[]
  wikiSelected: boolean
  selectedFiles: string[]
  selectedMcpTools: string[]
  attachments: ResolvedDirectAttachment[]
}
```

保留当前多 Skill 显式选择能力，按 UI 选择顺序载入；不再自动发现或替用户选 Skill。

### 5.2 执行阶段

```text
1. Compile Connections
   验证 Skill 存在，读取 SKILL.md，解析 allowed-tools，与用户连接取交集

2. Preload
   直接内联附件正文、明确文件、已选 SKILL.md 和短 wiki/index.md

3. Select Context
   明确路径和简单查询由程序直接预取
   其他任务由模型一次返回 Skill 资源与 Wiki 文件清单

4. Read Context
   程序并发读取所有通过校验的 Skill 资源与 Wiki 文件

5. Model / Capability Loop
   模型基于完整材料输出最终结果
   只有 MCP 或依赖前结果的后续操作时继续
   每轮只能请求已连接能力

6. Final
   显示最终文字、媒体面板入口或可确认的写入提案
```

统一资料选择结果不是通用工作流 DSL，只是两类受限路径：

```ts
interface ContextRequest {
  skillResources: Array<{
    skillName: string
    path: string
  }>
  wikiFiles: string[]
}
```

路径必须属于当前已选 Skill 或当前 Wiki 根目录；重复路径去重后一次并发读取。

### 5.3 受限行为

首批只保留以下行为，优先映射现有工具实现，不重写底层：

```ts
type SkillAction =
  | { type: 'request_context'; request: ContextRequest }
  | { type: 'read_skill_resource'; path: string }
  | { type: 'read_file'; path: string }
  | { type: 'wiki_context'; question: string }
  | { type: 'call_mcp'; tool: string; arguments: Record<string, unknown> }
  | { type: 'propose_write'; files: Array<{ path: string; content: string }> }
  | { type: 'open_panel'; panel: 'media' | 'scene3d'; payload?: unknown }
  | { type: 'final'; content: string }
```

实施时不必新建一套工具协议。现有 `read`、`wiki_context`、MCP 工具、媒体计划和写入计划能表达上述行为时，直接复用；`SkillAction` 是产品白名单，不是要求复制 Runtime。

### 5.4 有界限的循环

- 无工具任务：`1` 次模型请求。
- 明确路径或简单精确 `@Wiki` 查询：程序直接预取，默认 `1` 次模型请求。
- 长篇创作、跨分区 Wiki 查询或需要 Skill Reference 的任务：“选资料 + 最终生成”默认 `2` 次模型请求。
- 一次 MCP：最多“生成参数 + 总结结果” `2` 次模型请求。
- 渐进资料或多步 Skill：最多 `6` 次模型请求/工具轮，超限就保留当前结果并让用户继续，不自动扩容。
- 不恢复 `64` 轮循环，不把完整工具历史带入后续新任务。

`6` 是防止失控的产品上限，不是工作流步数。Skill 正文可以有任意多个不需要工具的思考步骤；只计算实际模型请求与工具回传。

## 6. 典型任务

### 6.1 普通生成

```text
用户文字 + 附件正文
  -> 模型一次
  -> 回答
```

没有选 Skill 时允许普通生成，不为这一行逻辑创建“默认 Skill”。

### 6.2 `@Wiki`

```text
用户问题
  -> 载入短 wiki/index.md
  -> 明确查询由程序直接预取；其他查询由模型选择分区与具体文件
  -> 程序并发读取
  -> 模型生成回答/创作内容
  -> 回答下提供“写入 Wiki”
```

`@Wiki` 是长期记忆能力，不重建五个 Wiki Skill。查询、入库、巡检、索引和双链继续是原生产品能力。

### 6.3 `@Skill`

```text
用户任务 + 已选 SKILL.md + 已选材料
  -> 按 Skill 生成
  -> 需要时按需读取 references
  -> 回答
```

Skill 是方法，不自动获得 Wiki、MCP 或写入权限。

### 6.4 `@Skill + @Wiki`

```text
用户任务
  -> 程序载入 SKILL.md + wiki/index.md
  -> 模型一次选择 Skill References + Wiki 具体文件
  -> 程序并发读取
  -> 模型按 Skill 方法使用 Wiki 事实生成
```

这是长篇小说、剧本和资产提示词的默认组合。

### 6.5 `@Skill + @MCP + @Wiki`

```text
模型按 Skill 生成 MCP 参数
  -> 程序调用用户已选 MCP
  -> MCP 结果回传模型
  -> 模型按 Skill 生成最终文字或写入提案
  -> 用户确认后程序写入 Wiki
```

写入不需要再请求模型；程序保存已显示或已确认的内容。

## 7. 副作用与安全

- Wiki/文件只读可由用户的显式连接一次授权当前任务。
- `write/edit/mkdir/move/delete`、Terminal、项目外路径、付费 MCP 和媒体生成继续走现有审批。
- 模型输出的路径、MCP 参数和写入计划由程序校验，不解析自然语言目录树。
- 批量写入在执行前完整校验；任何越界、重复或冲突使整份计划失败。
- 已有用户文件默认不覆盖。
- Skill 的文字不能关闭上述校验或扩大当前连接。

## 8. 保留与删除边界

### 8.1 必须保留

- Provider 配置、模型目录、上下文窗口、流式 HTTP 和错误处理。
- `ProjectFileService`、附件转换、路径保护和平台适配。
- `wiki_context`、`wikiRuntime`、索引、双链、校验和批量写入。
- Skill 目录、安装、`SKILL.md` 加载、渐进资源读取和 Skill Creator。
- MCP Client、服务器鉴权、工具 Schema 和调用。
- 媒体、创作画布、3D、同步、账号和 Desktop/Web/Mobile 已有能力。
- `directEngine` 中仍被上述能力使用的 HTTP、流式、工具回传、取消和度量零件。

### 8.2 新链路覆盖后删除

- `selectMemoryTools()` 及全部关键词工具猜测。
- `runMemoryChat()` 中的通用产品编排、模式分支和自动 Skill 目录提示。
- 快速/记忆模式、跨任务对话记忆、自动 Raw 检索和全局聊天历史累积。
- 普通任务中的全量工具 Schema、`3/5/64` 多套预算和为开放 Agent 服务的历史压缩。
- 仅有旧 Agent Runtime 调用且经 `rg` 证明无其他调用者的策略、状态和测试。

不允许为了“删 Runtime”而重写它里已经可复用的底层零件。先让新 Skill Runner 调用现有零件，再按无调用者证据删除旧编排。

## 9. TDD 验收合同

### 9.1 先写红灯

1. 未选能力的普通任务不包含工具 Schema，只发起一次模型请求。
2. 用户选择 Skill 后直接加载它，不调用 `skill` 工具让模型再选一次。
3. 用户未选 `@Wiki`时，Skill 不能调用 `wiki_context`。
4. 明确路径的 `@Wiki` 任务在第一次模型请求前已经包含目标正文。
5. 长篇创作任务的第一次模型请求只携带 `SKILL.md + wiki/index.md`，返回一份 `ContextRequest`。
6. `ContextRequest` 中的 Skill 资源和 Wiki 文件在同一阶段并发读取，模型不为两棵树分别循环。
7. 只选一个 MCP 时，模型只能看到该 MCP 工具，不能看到其他 MCP 或项目工具。
8. Skill 请求未连接能力时直接失败并告知缺失连接，不自动扩权。
9. 写入提案必须经路径校验和用户确认，确认后不再请求模型。
10. 渐进资源只能读取当前已选 Skill 目录中的 `references/scripts/assets`。
11. 达到 `6` 次上限时停止，不进入无限循环。
12. 新任务不携带上一任务的对话和工具结果。
13. `wiki-creator` 生成的计划必须包含短 `wiki/index.md` 和实际需要的分区入口，不强制固定项目类型或 Raw 结构。
14. `wiki-creator` 只输出 `WikiCreatePlan`；所有目录与文件由原生 `wiki scaffold plan` 一次确认、批量落盘和验证。

### 9.2 保留能力回归

- Wiki 查询、创建、修改、巡检、双链和索引更新仍可用。
- 用户 Skill、内置 Skill、安装、预览、渐进资源和 Skill Creator 仍可用。
- MCP 连接、鉴权、调用和错误显示仍可用。
- 媒体与 3D 继续使用现有独立面板。
- Desktop、Web、Mobile 现有文件和附件能力不因重构减少。

### 9.3 性能记录

自动测试记录逻辑请求数、暴露工具数、输入 token 和工具耗时。真实模型验收固定模型、Provider、项目快照和用例，不在未实测时声称通过。

首批对照用例：

```text
1. 读取一个明确 Markdown 并总结
2. @Wiki 查询角色设定
3. @Skill + @Wiki 续写下一集
4. @Skill + @MCP 查询后生成结果
5. 点击“写入 Wiki”保存已显示回答
6. wiki-creator 分别为小说和通用资料生成不同的 WikiCreatePlan
```

## 10. 实施顺序

```text
1. 锁定现有保留能力和调用图
   -> 验证：现有回归测试 + rg 调用者清单

2. 给现有 Skill frontmatter 补 allowed-tools 解析和安全校验
   -> 验证：纯文字、未知能力、缺少连接和多 Skill 顺序红绿测试

3. 实现薄 Skill Runner 与统一 ContextRequest，支持明确路径预取和双树资料选择
   -> 验证：简单任务一次模型请求；长篇创作两次请求且资料并发读取

4. 基于旧 jc-everything-wiki 最小重写 wiki-creator，对接已有 WikiCreatePlan
   -> 验证：无固定项目类型、无 Raw 依赖、无空目录，批量落盘后入口可用

5. 接入精确 MCP 工具和剩余渐进资源读取
   -> 验证：只暴露所选能力，结果顺序回传，6 轮上限有效

6. 接入写入提案、确认和媒体/3D 面板入口
   -> 验证：副作用审批、路径保护和现有面板回归通过

7. MemoryWorkbench 改用显式 Connection 调用 Skill Runner
   -> 验证：不再使用关键词猜工具，新任务无跨任务记忆

8. 逐项移除旧 Runtime 编排和快速/记忆模式
   -> 验证：每次删除前 rg 无保留调用者，全部回归通过

9. 执行固定真实模型矩阵
   -> 验证：记录真实请求数、总耗时、输入 token 和结果正确性
```

不允许先删光 Runtime 再研究替代。每覆盖一个真实入口，立即删除该入口的旧编排；最终只留有真实调用者的能力零件。

首批禁止新增依赖、Agent 框架、工作流框架、数据库、向量索引、队列、后台任务、摘要 Store、路由模型或 Hermes/OpenClaw/Pi 嵌入。

## 12. 完成定义

- 普通任务、`@Wiki`、`@Skill`、`@MCP` 及其显式组合共用一条 Skill-first 主链路。
- 纯文字与明确路径任务默认只请求模型一次；双树渐进任务默认两次。
- Skill 和 Wiki 保留统一渐进式披露，模型一次选择两棵树需要的资料，程序并发读取。
- `wiki-creator` 已以旧 `jc-everything-wiki` 为来源完成最小重写，只设计导航并输出 `WikiCreatePlan`。
- 模型不再从全量工具中自主选择，不再自主发现 Skill。
- Wiki 和 Markdown 文件是唯一长期事实源；新任务默认不携带之前对话。
- 写入、删除、Terminal、项目外操作和付费能力仍有明确确认。
- 旧关键词路由、快速/记忆模式、64 轮循环和无调用者的 Runtime 编排已删除。
- Provider、文件、Wiki、Skill、MCP、媒体、3D、审批和三端能力没有减少。
