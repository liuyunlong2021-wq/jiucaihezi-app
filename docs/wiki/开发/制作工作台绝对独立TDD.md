# 制作工作台绝对独立 TDD

> 日期：2026-07-24
> 状态：已实施（2026-07-24；专项、类型检查、Web/Desktop 构建通过）
> 范围：制作工作台的独立运行时、显式输入、业务 Wiki 产物和公共媒体交接
> 替代关系：本文替代 [[开发/制作工作台零隐式上下文SDD]] 中 `wiki/制作/运行/`、运行历史扫描、`.design.json` 双写和媒体任务回写的设计。六个制作入口、用户明确的 Wiki 绑定及其真正业务 Wiki 产物继续保留。

## 1. 目标

制作工作台和电商工作台一样，是独立产品 surface，不是 Chat、创模式或任何模式会话的变体。用户在当前页面明确提供资料、图片、模型和步骤 Skill，模型只做一次无工具直连；成功后保存真正的制作成果到 Wiki。媒体生成仍由用户确认后交给公共媒体能力。

```text
当前用户信息 + 当前选择资料/原始附件 + 当前模型 + 当前步骤静态 Skill
  -> 单轮直连模型请求（无工具、无隐式上下文）
  -> 当前结果卡 + 对应制作业务 Wiki 文件
  -> 用户确认 MediaPlanCard
  -> CreationPanel -> mediaTaskStore
```

“独立”的验收是：不挂载 Chat、不切换文武创道、不等待 OpenCode、不读取模式会话，也能完成六个入口。不是删除仍服务其他功能的模式。

## 2. 根因与取舍

当前 `ProductionWorkbench` 已经使用 Direct Engine，但外面仍包着一套工作台私有的持久化系统：

- `wiki/制作/运行/<run-id>.json` 记录、扫描和恢复历史；
- 每个角色、场景、道具结果额外写 `.design.json`；
- 媒体任务提交后再回写制作运行记录。

这些文件不等于制作成果。它们只服务工作台历史和状态恢复，却让一次直接调用变成多套状态同步。电商已经验证：用户需要的是当前结果与可定位的真实产物，不需要工作台另建一套运行数据库。

本 TDD 保留真正的业务交付：风格、角色、场景、道具、分镜和视频提示词。也保留用户主动建立的项目 Wiki 绑定，因为它是制作项目的明确资料配置，不是运行历史。删除的是工作台自身的运行历史、结果双写和媒体回写账本。

## 3. 运行时合同

### 3.1 独立入口

1. Rail 的“制作”直接激活 `ProductionWorkbench`；不读写 `chatModeStore`，不切换创模式。
2. 制作激活时 `ChatPanel` 不挂载，继续采用与电商相同的互斥 `v-if`/`v-else-if`。
3. 制作模型目录调用 `fetchModels({ skipOpenCode: true })`。模型选择器是公共能力，不等待 OpenCode。
4. 本 TDD 不新增移动端制作入口；现有 Desktop/Web Rail 入口是本次范围。移动端是否需要制作工作台另行设计。

### 3.2 单轮请求

六个入口仍是：风格、角色、场景、道具、分镜图、分镜视频。每个入口有一个固定的受限步骤 Skill/Profile，来源于现有领域 Skill，但只保留本步骤的领域规则和输出合同。

请求只包含：

- 当前步骤；
- 当前模型和 Provider；
- 当前用户文字；
- 用户本次手动选择的文档内容，或用户已绑定 Wiki 的当前场次锚点及其双链实体资料；
- 用户本次上传的原始附件；
- 当前步骤的静态 Skill/Profile 和输出合同。

请求不包含 Chat 历史、创模式会话、`creative_*`、OpenCode、`wiki/hot.md`、最近运行、项目文件清单、绑定范围以外资料、MCP、工具定义或媒体任务结果。`tools` 恒为 `[]`，`allowToolCalls` 恒为 `false`。一次点击只发一次当前模型请求，失败显示真实 Provider 错误，不换模型、不转交其他模式。

用户可选择若干项目文件或上传原件，页面以可移除标签展示。用户也可主动“绑定项目 Wiki”：选择一个 Wiki 根目录和一篇场次/正文锚点后，系统只解析该锚点明确的 `[[双链]]`，自动填入对应角色、场景、道具资料。根目录、锚点和每一条自动填入资料都必须显示为可移除标签；用户可以改绑、解除或排除单条实体。绑定配置可以持久保存到 `wiki/制作/绑定.json`，但绑定根目录本身、未被双链指向的页面和正文中的自然语言名字都不得进入模型请求。

## 4. 输出和存储合同

### 4.1 只写业务成果

模型成功后写入以下制作成果。每张当前结果卡显示“定位文件”，打开 FileTree 对应业务文件；页面重载后不恢复制作历史。

| 步骤 | 业务成果路径 |
| --- | --- |
| 风格 | `wiki/世界观/style-design.md` |
| 角色 | `wiki/角色/<名称>/制作-角色提示词.md` |
| 场景 | `wiki/场景/<名称>/制作-场景提示词.md` |
| 道具 | `wiki/道具/<名称>/制作-道具提示词.md` |
| 分镜图 | `wiki/分镜/<名称>/制作-分镜提示词.md` |
| 分镜视频 | `wiki/分镜/视频/<名称>/制作-视频提示词.md` |

名称来自当前模型结果或用户本次明确指定的名称，必须通过现有项目路径校验。已有用户资料只能作为输入，不能被覆盖；制作结果只写到上表的专属“制作-...”文件。资产卡一张对应一个业务文件，不写同内容的 `.design.json`。

没有项目时，第一次成功运行创建项目和上述结果所需的最小父目录。它不再创建 `wiki/制作/运行/` 或空的制作历史目录；用户只有主动绑定 Wiki 时才创建或更新 `wiki/制作/绑定.json`。

### 4.2 明确删除

- 删除 `ProductionRunRecord`、`listProductionRuns()` 和页面启动时的历史恢复。
- 删除 `productionWikiDesignPath()`、所有 `.design.json` 双写以及其测试。
- 删除 `saveProductionMediaTask()` 和 `production-media-plan-submitted/failed` 回写制作 Wiki 的监听。
- 删除只为上述功能存在的 `wiki/制作` 目录骨架和测试夹具。

保留并继续使用 `ProductionWikiBindingRecord`、绑定保存/恢复、用户发起的 Wiki 根目录扫描、场次锚点、双链解析、单条实体排除和资料变更检查。它们是用户明确的资料配置，不是隐藏上下文。不给旧运行记录和 `.design.json` 做迁移或删除；新版本不再读取、扫描或改写它们。

## 5. 公共媒体合同

模型只给出可审阅的提示词和对象卡，不能提交付费任务。角色、场景、道具、分镜图和分镜视频都必须使用现有 `MediaPlanCard` 显示模型、比例、参数和素材，用户确认后才调用：

```text
MediaPlanCard -> preparePublicMediaPlan -> CreationPanel -> mediaTaskStore
```

制作工作台不调用 `mediaTaskStore.submitTask()`，不复制轮询、落盘、画布或任务恢复。公共媒体结果属于公共媒体任务和画布；制作当前卡可显示本轮提交态，但不把 `taskId`、完成结果或错误双写回 Wiki，也不自动进入下一次模型请求。

## 6. TDD 验收

先写失败测试，再做最小实现。每项测试直接证明边界，不以“隐藏 Chat”或文本约定代替运行时隔离。

### 6.1 独立性测试

1. Rail 选择 `production` 时不调用 `chatModeStore.setMode()`；`ProductionWorkbench` 挂载而 `ChatPanel` 不挂载。
2. 制作工作台及其运行时不得 import `useChat`、`creativeSessionStore`、`openCodeSyncStore`、Chat 消息或 OpenCode 客户端。
3. 模型加载断言为 `fetchModels({ skipOpenCode: true })`；模拟 OpenCode 未就绪时制作模型选择器仍可用。

### 6.2 请求合同测试

1. 六个步骤分别构造请求，断言只有当前文字、当前手选资料、原始附件、模型和对应 Profile。
2. 断言 `tools: []`、`allowToolCalls: false`，没有 Chat、session、热缓存、历史运行、MCP 或媒体结果；已绑定时只允许当前锚点和该锚点双链解析出的未排除实体进入请求。
3. 空文字、空资料、空附件时拒绝请求；任意一项非空即可请求。
4. 文档或 Wiki 页面只有被用户本次选中，或被用户已绑定 Wiki 的当前锚点明确双链指向时才进入请求；移除、排除、改绑或解除后即不再进入下一次请求。

### 6.3 结果测试

1. 风格、每张资产卡、分镜图和分镜视频只创建表中一个业务文件；不存在 `wiki/制作/运行/` 和 `.design.json`。只有用户主动绑定时才存在 `wiki/制作/绑定.json`。
2. 结果文件定位动作只定位该业务文件，页面刷新后不扫描或恢复旧制作运行卡。
3. 失败或取消不创建业务成果文件；重试只创建新的明确成果，不能覆盖用户作为输入选择的原文件。
4. 旧 `wiki/制作/运行/` 文件保持原样，且不会被列表、请求或媒体事件读取；当前 `绑定.json` 只恢复用户已确认的 Wiki 根目录、锚点和排除项。

### 6.4 媒体和回归测试

1. 每一种媒体动作先显示 `MediaPlanCard`；未确认前没有媒体提交。
2. 确认后只经过 `preparePublicMediaPlan -> CreationPanel -> mediaTaskStore`；制作组件没有任务提交、轮询或媒体结果落盘代码。
3. 媒体提交、成功和失败都不改写制作 Wiki、Chat 或下一轮模型输入。
4. 电商、Chat、文武道、普通创模式和公共媒体任务的现有定向测试继续通过。

门禁：制作专项 Node 测试、`pnpm exec vue-tsc -b`、`pnpm run build`、`pnpm run build:desktop`、`git diff --check`。人工验收覆盖 Desktop/Web 的六入口直连、模型选择器、选资料/移除资料、业务文件定位、媒体确认和真实任务结果。

## 7. 实施顺序

1. 先改写制作专项测试，让旧的运行记录、`.design.json` 和媒体回写断言失败，同时保留“用户绑定 Wiki 后自动填入锚点双链资料”的合同。
2. 收敛 `productionWorkbench.ts` 为六个受限 Profile 和显式本次输入，保留现有 `singleTurnWorkbench` 直连合同。
3. 从 `ProductionWorkbench.vue` 删除历史恢复和媒体回写状态；保留可见的 Wiki 绑定与自动资料标签。模型目录改为跳过 OpenCode，结果只保留当前卡和定位业务文件。
4. 将制作输出存储收敛为业务文件写入，删除运行账本和 `.design.json` 相关 API、测试与死引用。
5. 用 `MediaPlanCard` 统一所有制作媒体确认，继续交给现有 CreationPanel。
6. 运行专项、类型、Web/Desktop 构建和人工真实模型/媒体链路验收。

## 8. 完成标准

删去 Chat、文武创道和 OpenCode 运行时后，只保留应用壳、公共模型目录、当前步骤静态 Skill、项目文件服务和公共媒体能力，制作工作台仍能完成：

```text
当前制作信息/资料 -> 单轮模型直连 -> 对应制作 Wiki 成果 -> 用户确认 -> 公共媒体任务
```

同时，仓库中不再有为制作工作台历史而存在的运行账本、结果双写或媒体回写链路；唯一持久配置是用户主动建立、全程可见的 Wiki 绑定。这才是制作工作台的绝对独立。
