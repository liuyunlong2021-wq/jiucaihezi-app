# 韭菜盒子权限审批通道落地方案（2026-09-28）

> 状态：**设计已定稿，未实施**。所有机制都已在官方包里查证，带出处；不需要再探测。

## 1. 现状：中间那档是「拒绝」，不是「询问」

`权限` 三档上线后（`40855a0e`），**「工作区内修改」越界时仍然是 fail-closed 拒绝**：

```
sandbox escalation to "danger-full-access" requires approval,
but no approval channel is available
```

根因：DH 路径下 **没有任何东西应答 `approval/request`**。全仓库 `run.approval` 从来没有被赋值过（`desktopConversationRuntime.ts` 只有初始化 `null`、读、清空三处），所以 `ToolApprovalStrip` 永远不渲染。

## 2. 官方语义（三层，逐条有出处）

### ① Harness 内：`approval/request` 是瀑布式 seam

`@deepseek-ai/dsh-user-approval`：

- 应答者是 `approval/request` waterfall 监听器，返回结果即为该 agent 作答，否则 `next()` 委托。
- **「没有最终应答者时，请求解析为 `unavailable` 并以拒绝方式关闭；服务自身绝不会提示人类。」**
- 结果词汇是**闭集**（`lib/types/types.d.ts:24-26`）：`allowed-once | rejected | cancelled | unavailable`
- 每次询问写一对 durable 事件：`approval/asked` + `approval/decided`（只写日志，不进模型上下文）。

### ② 转发：`dsh-api-remotes` 把它声明为可远程转发的 waterfall

```js
API_REMOTE_FORWARDED_EVENTS = [ …, { event: "approval/request", mode: "waterfall" }, … ]
```

转发骨架（`dsh-api-remotes/lib/index.js:199`）—— **「客户端不回 → `next()` → 落到 fail-closed」是刻意设计的安全底线**，我们照抄这个语义：

```js
function forwardWaterfall(queue, event, request, context, next) {
  const dispatch = { event, request, resolve: (outcome) => {
    if (outcome 是真的答复) settled.resolve(outcome.value);
    else Promise.resolve().then(next).then(settled.resolve, settled.reject);
  } };
  if (!queue.push(dispatch)) Promise.resolve().then(next).then(…);
}
```

### ③ 客户端 & 沙箱侧

- 客户端（`dsh-client-ui-approval`）渲染浮层，回 `allowed-once / rejected / cancelled`。
- 沙箱（`dsh-bash-sandbox`）被拒时给模型追加：
  `[sandbox: escalation available — retry this exact command once with sandbox_permissions (the narrowest wider mode that suffices) + justification; the approval prompt asks the user]`
  模型带 `sandbox_permissions` 重试**同一条命令**，升权**只对该次调用生效**。
- **推论**：官方模型里不存在「以后都允许」—— 那对应的是**换档位**。

`dsh-acp/lib/index.js:1116` 是应答者的现成范例（骨架可直接照抄）：

```js
ctx.on("approval/request", (request, next) => {
  const record = ownedRecord(request.agent);
  if (record === void 0 || request.callId === void 0) return next();   // 不归我管 → 交给下一个

                { optionId: 'reject-once', name: 'Reject', kind: 'reject_once' }],
    };
    … // 发给客户端，等它回
  });

```

## 3. 我们的实现：加第 6 处 vendor 补丁（不改外部插件）

**为什么不用外部插件**：`route.cordis.yml` 确实支持 `- insert: - id/name`（`dsh-sdk-app/cordis.patch.yml` 自己就这么挂 `sdk-jsonrpc-server`），但审批需要**双向**通道，而两个方向现成的机制都在同一个 JSON-RPC server 类里：

| 方向 | 现成机制 | 出处 |
|---|---|---|
| harness → 客户端 | `this.transport.notify(方法, 参数)` | 补丁 #1（`prepare-deepseek-harness.mjs:40`） |
| 客户端 → harness | 新增 `case` + `this.ctx.get(服务)` | 补丁 #5（同文件 122-146 行） |

所以第 6 处补丁挂在**同一个类**里最省事，也复用了已有的幂等守卫测试（`scripts/__tests__/deepseek-harness-patch.test.mjs`）。

### 补丁 #6 的形状（两段）

**a. 注册应答者 + 推送**（与补丁 #1 同位置、同风格）：

```js
this.disposers.push(ctx.on("approval/request", (request, next) => {
  const sessionId = String(request.agent?.session?.id ?? "");
  if (!sessionId || request.callId === void 0) return next();      // 不归我管 → 交给下一个
  const requestId = crypto.randomUUID();
  this.transport.notify("session.approval", {
    requestId, sessionId, toolCallId: request.callId, toolName: request.toolName,
  });
  return this.pendingApprovals.register(requestId);                // ← 等 session/approval 回执
}, { global: true }));
```

**b. 新增回执方法**（锚在 `case "shutdown"` 之后，与补丁 #5 同一锚点纪律）：

```js
case "session/approval": return this.approval(params);

async approval(params) {
  const settled = this.pendingApprovals.settle(params.requestId, params.decision);
  if (settled === void 0) throw new Error("unknown approval request: " + params.requestId);
  return { ok: true };
}
```

`pendingApprovals` 是个简单的 Map + Promise：`register(id)` 返回 Promise，`settle(id, decision)` resolve 它。
**必须带超时**：轮次结束或 runtime 关闭时全部 resolve 成 `cancelled`（官方 README：审批只在未结束的轮次内有效；空闲时发起会抛异常）。

### runner.mjs

照补丁 #5 的 `permission` 通道形状加 `approval` 命令通道，并把 `session.approval` 通知转发给前端。

### 前端

- `deepSeekHarness.ts`：`notify` 里处理 `session.approval` → `input.onApproval?.({ id, message })`；新增 `approval` 请求发送函数。
- `desktopConversationRuntime.ts`：**`run.approval` 真正赋值**（这是全仓库缺的那一处），复用已有的 `settleApproval`。
- `MemoryWorkbench.vue`：`ToolApprovalStrip` 已存在，不需要新建组件。

## 4. 必须拍的两个决定（建议已给）

### 「允许」后的粒度

官方只有 `allowed-once`，**没有「以后都允许」**。我们 UI 的 `ToolApprovalStrip` 有三档 `once / always / reject`。

**建议：`always` = 本会话切到「完全权限」**（复用 `permissionTier = 'danger-full-access'`，还要过那道二次确认）。
理由：这正是用户心智 ——「我不想每次都被问」=「换到不问的那一档」；而且不发明新粒度。

### `cancelled` 的出口

用户关掉浮层 / 轮次被停止 → 回 `cancelled`（官方词汇里有）。**不要吞掉**，它是 durable 事件。

## 5. 执行顺序（每步都能单独跑通）

1. **补丁 #6 + runner + 前端通路**，先用一个**假的 `approval/request`** 自测「浮层出现 → 点允许 → Promise resolve」。
2. 真机：档位设「工作区内修改」→ 让它写 `~/.agents/skills/...` → **浮层出现 → 允许一次 → 写入成功 → 档位仍是「工作区内修改」**。
3. 再决定 `always` 走哪个方向。

## 6. 边界（官方明写，别踩）

1. **审批只在未结束的轮次内有效**；空闲时发起会抛异常 → 浮层必须挂在轮次内。
2. 每次询问写 `approval/asked` + `approval/decided` 一对 durable 事件 → 不要重复写。
3. 失败方向永远是 **fail-closed**（没应答者 = 拒绝），不要为了「好用」把它改成默认允许。
4. 手机端 `approval.respond` **已经在协议里** → 通路接通后手机也能审批，是白捡的收益。
