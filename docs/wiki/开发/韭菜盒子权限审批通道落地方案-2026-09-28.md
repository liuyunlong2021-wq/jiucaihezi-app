# 韭菜盒子权限审批通道落地方案（2026-09-28）

> 状态：**设计定稿，未实施**。要写的代码约 50 行、跨 5 个文件。

## 1. 问题

DH 路径下**没有任何东西应答 `approval/request`**，所以「工作区内修改」档越界时是**直接拒绝**，不是询问：

```
sandbox escalation to "danger-full-access" requires approval,
but no approval channel is available
```

官方语义：没有应答者 → waterfall 落到默认值 `Promise.resolve("unavailable")` → fail-closed
（`dsh-user-approval/lib/index.js` 的 `decide`）。**这是刻意的安全底线，我们照抄。**

现状证据：

- 5 处 vendor 补丁里没有一处注册应答者。
- DH 分支（`runDeepSeekHarness`）没有审批回调；`run.approval` 只在自研 Direct 内核的
  `confirmTool` 里被赋值（`MemoryWorkbench.vue:2084`）。
- 历史会话里 6 次 `approval/asked` 全部静默拒绝。

## 2. 官方契约（全部有出处，不需要再探测）

| 事实 | 出处 |
|---|---|
| 应答者 = `ctx.on("approval/request", (request, next) => …)`，返回结果即作答，`next()` 转交下一位 | `dsh-acp/lib/index.js:1116`、`dsh-api-remotes/lib/index.js` |
| 结果词汇是**闭集**：`allowed-once \| rejected \| cancelled \| unavailable` | `dsh-user-approval/lib/types/types.d.ts` |
| 非词汇返回值会被框架**归一化成 `unavailable`** | `decide()` 的 `.then(outcome => OUTCOMES.includes(outcome) ? outcome : "unavailable")` |
| `signal` 一定存在（tool 层写死 `signal: exec.signal`），abort 时服务自己判 `cancelled` | `dsh-tools/lib/index.js` 的 `serviceAsk`、`decide()` 末尾 |
| 审计对 `approval/asked` + `approval/decided` **由服务自己写** | `ApprovalService.request()` |
| 没有打开轮次时 `request()` 会抛 | `hasOpenTurn` |
| 官方 UI 只有两个按钮：`拒绝` / `允许一次` | `dsh-client-ui-approval/lib/client.js` 的 zh 字典 |
| 弹窗主文案 `pending.reason ??「工具 {toolName} 请求越权执行」` | 同上，`escalation` |

## 3. 要写的代码

### 3.1 vendor 补丁 #6 —— `scripts/prepare-deepseek-harness.mjs`

两段，锚点纪律照补丁 #1（构造器）与 #5（`case "shutdown"` 之后）。

**a. 注册应答者**（放构造器，`this.disposers.push(...)`）：

```js
this.disposers.push(ctx.on("approval/request", (request, next) => {
  if (request.callId === void 0) return next();
  let settle;
  const answer = new Promise(resolve => { settle = resolve; });
  const requestId = `approval-${++this.approvalSeq}`;
  this.pendingApprovals.set(requestId, settle);
  // 必须清账：官方 decide() 自己会把 signal 和 answer 赛跑成 cancelled，
  // 但我们这条 promise 不 settle 就会在 Map 里留尸。
  request.signal?.addEventListener("abort", () => {
    if (this.pendingApprovals.delete(requestId)) settle("cancelled");
  }, { once: true });
  this.transport.notify("session.approval", {
    requestId,
    sessionId: String(request.agent.session.id),
    toolName: request.toolName,
    callId: request.callId,
    reason: request.reason,
  });
  return answer;
}));
```

**不加 `{ global: true }`** —— 官方两处根级监听器都是裸 `ctx.on`；`approval/request` 是
scope-filtered waterfall，监听器的 `this` 会被绑成该 agent 的 scope
（类型里写死 `this: Scoped<Agent>`，`dsh-api-remotes` 正是靠它取 `carrierKeyOf(this)`）。

**b. 回执方法**（新增 `case "session/approval": return this.approval(params);`，同补丁 #5 锚点）：

```js
async approval(params) {
  const settle = this.pendingApprovals.get(params.requestId);
  if (settle === void 0) throw new Error(`unknown approval request: ${params.requestId}`);
  this.pendingApprovals.delete(params.requestId);
  settle(params.outcome);
  return { ok: true };
}
```

新增字段：`pendingApprovals = new Map();`、`approvalSeq = 0;`

> **不需要**校验 `params.outcome`。官方 `decide()` 会把非词汇值归一化成 `unavailable`（也是 fail-closed），
> 我们自己再校验一遍是重复的。

## 4. 明确不做（与官方对齐）

| 不做 | 理由 |
|---|---|
| **`always`** | 官方只有 `拒绝 / 允许一次`。把「总是允许」接到「切 `danger-full-access`」是**窄按钮接宽授权**：弹窗讲的是这一条命令，动作是全会话不再问。何况 Direct 路径已有一个语义完全不同的 `always`（`memoryToolAlwaysAllowedConversations`，本会话记住、`delete` 除外）。想「以后不再问」走 `权限` 菜单 → 完全权限，那条路有二次确认。 |
| 自己写超时 | 官方 `decide()` 已用 `signal` 兜底，不是我们这层的事。 |
| 自己写 `approval/asked` / `approval/decided` | 服务自己写，重复写会破坏审计对。 |
| 显示该次调用的具体内容 | 官方有 `conversation.approval.detail` slot，我们缺工具详情通道，不影响正确性。 |
