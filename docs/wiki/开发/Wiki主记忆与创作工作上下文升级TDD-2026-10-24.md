# Wiki 主记忆与创作工作上下文升级 TDD

> 日期：2026-10-24。状态：完整升级方案待实施；用户另行收窄的文件树上传/新建 Wiki 文件夹两项已完成源码与自动验证，见 §8；其余工具升级、压缩、生产模型效果与平台验收未完成。
> 用户决定：Wiki 是主要记忆，用户保存与上传的资料必须能经 index 渐进找到；对话压缩只负责辅助衔接，改为适配创作。
> 最新实施顺序（同日用户明确）：第一步已有 DSH Skill；第二步先把 Wiki Memory 做成同等完整的原生工具能力；第三步再改上下文与摘要。此前把提前压缩放到第一实施阶段的顺序由本条替代。

## 1. 目标与边界

目标：每次请求主要携带当前创作所需资料，历史会话长度和全库规模不再直接决定常驻输入体积。Wiki 保存可追溯的原文、资料与产物；会话保存完整交流证据；模型上下文是可缩减、可重新读取的工作内容。

三个层次必须分开：

| 层次 | 保存什么 | 是否必须每次发给模型 |
| --- | --- | --- |
| Wiki 与原始素材 | 当前文件正文、来源、已保存稿件、索引 | 否，沿索引按任务读取 |
| Harness Session | 完整用户消息、回复、工具调用与结果 | 否，完整历史留给回看与恢复 |
| 当前工作上下文 | 当前任务、最近修改、未保存稿件、必要页面、短摘要 | 是，按预算和证据状态保留 |

“文件已保存”“用户已确认”“原作事实”“模型提案”保持独立。上传只说明提供了资料，不自动认定为作品设定；保存待审稿不自动认定为确认。索引摘要仅导航，不能代替正文取证。

本轮保留 DSH 0.2.1-rc.2、pi-ai、现有 Agent 循环/Session/权限/创作工具隔离、桌面独立能力。无需向量数据库、Embedding 服务、第二记忆数据库、后台摘要 Agent 或每轮模型分类请求。

### 2.3 官方压缩为临近容量设计，默认摘要偏编程

- 该实际路由声明 `contextWindow=1000000`、`maxTokens=128000`。官方默认阈值为 `floor(min(W*0.8, W-O-65536))`，本路由为 800000；默认保留近期预算约 139520 tokens。
- 官方工具结果裁剪也要在压缩触发后执行，未触发时不会主动裁剪。
- 默认摘要要求英文工程说明、技术概念、代码文件与错误修复，适配性不足。
- 最近两轮上游返回 `inputTokens=425399/427247`。这是上游用量字段，不是本地精确 tokenizer 校验结果，也不能单独用于断言计费或耗时根因。

### 2.4 自动索引尚未形成统一保证

- `manju-wiki.mjs` 正式归档、故事拆分和分析有各自的正文/索引维护及部分失败回执。
- `appendProjectDirectoryIndex` 被若干手动保存和文件树操作调用，使用修订检查追加双链，但没有统一的资料状态/摘要维护。
- `MemoryWorkbench.vue:importAttachmentFiles` 使用 `files.importText/importBinary` 保存原件和可读副本，未统一调用索引登记；底层 import 方法发文件变更事件，当前不能据此宣称已完成索引维护。
- `ProjectFileTree.vue:classifyImportedMemoryFiles` 对已在目标目录的文件直接跳过，索引登记位于后面的移动分支。因此不能保证所有上传文件都被索引覆盖。
- Markdown 编辑保存主要写正文；重命名、删除、外部编辑、同步与 AI 原生 fs 写入也需要逐入口验证，不能把“收到变更事件”等同于“index 已正确更新”。

## 3. 方案：把可恢复资料与不可恢复内容分开

### 实施前置：借用 Skill 的目录与加载机制

随包 DSH Skill 将目录发现、摘要候选、按需正文加载、包内引用与作用域隔离分开。Wiki Memory 采用对应的导航/内容分离：

| DSH Skill 的机制 | Wiki Memory 对应能力 |
| --- | --- |
| 轻量候选目录 | 已确定 Wiki 根的目录入口，按层返回直属索引 |
| 选定后加载正文 | 选定页后读取实际正文与版本，不把全库作为初始上下文 |
| 包内引用按需展开 | 沿当前任务需要的双链读取必要关联 |
| 作用域、路径与失效校验 | 项目隔离、唯一根、真实路径、文件变化后读取新版本 |
| 安装后可发现 | 保存/上传/修改后导航可达，部分失败可定位与重试 |

Wiki 工具能力要完整覆盖“发现—导航—读取—写入—索引回执”。读取入口复用现有 fs、安全与权限服务；写入沿用 `wiki_save_artifact` 和既有手动保存合同。实施时确定最小的 Wiki 导航工具合同，不能只加提示词就算完成；也不为每个页面注册一个工具。现有 Wiki 原生插件是承载位置。

Wiki 页面仍是数据与证据，不能因为借用 Skill 加载方式就作为系统指令执行；索引只负责定位，正文保存事实与稿件。这一步先独立验收，再改变历史压缩策略。

最有价值的节省：已经在文件里、可准确重新读取的内容，退出当前工作后不必继续留在模型上下文，也不必再让摘要模型复述一遍。

但替换旧内容必须满足可恢复条件：真实路径、读取版本、来源事件和范围齐全；当前正在编辑、未保存、未确认修改及尚未处理的工具结果受保护。不能用“都在 Wiki”推断每条对话信息已落盘。

### 3.1 入口只给导航，索引逐层展开

1. 三创作模式明确采用 Wiki 主记忆；普通无关聊天不预读 Wiki。
2. 使用现有根识别与多根歧义规则，改用有限目录探测，避免每轮列举全项目。只有确认需要处理整个项目时才做完整遍历。
3. 常驻提示只提供已确定的 Wiki 根、根 index 路径、版本及简短读取原则；不再把多层索引正文拼进用户消息。真实用户消息保持原样，仍可提取来源原文。
4. 首次需要资料时读取根 index，然后按任务进入分支 index、目标正文。目标直接关系按现有合同只展开必要一层；不因出现双链就递归遍历全库。
5. 任务明确引用已知的真实文件时可直接读取该正文，避免为遵守形式重复走整条导航。不能凭空猜一个文件存在。
6. 同一目录/页面版本未变且内容仍在当前上下文时不重复读取。只有路径/版本仍在而正文已被释放时，必须重读，不能认为模型仍“知道”。

超长 index 采用有游标/范围标记的分段读取，明确还有多少未读，不能默默截断后假装没有其他条目。自动生成目录索引只导航直属子项；不为省 token 重写用户手写索引或搬迁现有目录。

这一改动优先复用 `read/glob/grep` 和原生 Wiki 规则，不新增通用工具。索引缺损时允许在指定目录做有限文件定位，报告索引缺口，不扫描全库来补偿错误。

### 3.2 保存与上传时维护索引，不花模型调用做目录登记

把现有索引能力统一为一个可重复执行的目录登记过程，接入现有文件服务/归档与导入入口，不新建另一套业务目录。

| 写入入口 | 必须完成的登记 |
| --- | --- |
| AI `wiki_save_artifact` | 沿用正文、直属索引与必要祖先目录入口；保留现有部分成功回执 |
| 用户手动保存/新建 | 新页登记；已有页变化更新受管理的标题/导航信息，保留手写内容 |
| 文件树上传、聊天附件、拖入 | 原件登记；可读副本成功时登记二者关联；失败时原件可发现且标记未解析 |
| 重命名、移动、删除 | 只更新受影响的受管理导航项，不清空用户注释；现有正文链接不做猜测性批改 |
| AI 普通 write/edit、外部编辑与同步 | 在已有变更/刷新链路检测失效目录并修复；不能仅靠 Vue 页面在线 |

原件仍留在当前 `.raw/...`，不重复复制进 Wiki。已有 Wiki 的 `原始材料/index.md` 提供真实路径导航；没有 Wiki 的项目沿当前合同登记素材目录，不因上传强制建立另一套作品库。建库后补齐可达入口。

索引项至少包含真实链接、标题、来源/可读状态和一句导航说明。可直接复用已有归档摘要；普通上传只按文件名、文档标题、格式和状态生成确定性导航，不调用 LLM 编写可能失真的语义梗概。图片/音视频只登记文件元数据，不冒称已理解内容。

正文写成功、索引失败：保留正文，报告具体未登记路径，并可幂等重试。索引只指向已存在目标；正文仍在转换时不得宣称可读副本完成。并发写沿用 revision/CAS 与既有操作队列，生成的 index 变更不递归触发自己，批量变更合并处理。

现有项目不启动全盘后台重建或模型重算。进入目录时做增量核对；显式修复才覆盖更大范围。用户自写 Markdown、历史记录和目录不删除。

### 3.3 当前工作内容按任务保护，Wiki 事实按版本重读

工作内容保存：当前集/章/实体、用户最新目标、修改要求、禁止事项、正在修改的稿件、必要来源路径。来自显式选择、真实读取和消息，不增加额外模型分类。

例如“继续改第一集”优先沿第一集、总纲及其直接来源读取；不默认加载其他 23 集正文或全体人物。没有显式任务锚点时交由现有 Agent 从根索引定位，不用关键词猜测器替用户选集。

用户新增修改高于旧稿当前表述，但不自动成为已保存设定。当最新用户要求与 Wiki 冲突时，在当前任务中明确“待写回的修改”，不能因 Wiki 优先而丢弃本轮纠正。不同 Wiki 页面彼此冲突仍报告，不能只凭更新时间裁决。

读取记录包含项目、canonical 路径、revision/内容指纹、实际范围、来源事件 seq。修改文件后旧内容不再作为当前事实；下一次使用先重读。路径相同但版本不同的文件不能互相替代。

### 3.4 可恢复的旧工具结果改成短定位记录

分两步实施，避免一开始就改造所有历史：

1. Wiki 阶段：不再注入重复多层索引，完成导航与读取版本证明；保持现有历史压缩策略。
2. 后续上下文阶段：有来源版本证明后，在完整工具调用/结果配对安全的边界，把退出当前工作、已可恢复的旧读取结果替换为短记录。保留原事件和原结果供历史回看，用官方 Session surface 替换语义持久化，不能仅在发往模型的最后一层删消息；再接入创作摘要与提前压缩。

短记录示意：`已读 wiki/改编方案/项目总纲.md，版本 <指纹>，范围 <行号>；正文已释放，使用前重新 read 最新版。` 这是历史读取证明，不是该文件当前内容的副本。

当前任务正文、错误回执、工具授权/确认信息、不可重新读取的结果、未保存稿件不按此规则释放。不能套用官方“保留头尾”裁剪假定正文中段无关。全库读取任务必须实际覆盖需求，不能用预算把阅读完成度冒充为已读。

Skill 与 Wiki 长规则适用相同原则：当前仍有效的规则须可见；退出适用范围后旧结果可被摘要覆盖。不能仅提示“不要重读”却让旧规则正文永久占据请求。

### 3.5 创作摘要只保存未落盘的衔接信息

默认结构改为简短中文：

```markdown
## 当前任务
项目/集章/目标；下一步。
## 用户最新要求
保留原意和必要原句，注明禁止保存等边界。
## 未保存与待确认
稿件定位、差异、尚未处理的问题；不把提案写成事实。
## Wiki 定位
必要权威页面路径及用途；事实需要时重读正文。
## 连续性提醒
尚未落盘且继续任务必需的信息、冲突和风险。
```

删除代码助手的固定工程章节。已保存的完整世界观、旧集稿、资料正文和全部索引不再抄入摘要；待写回的用户纠正不能因“Wiki 里有旧稿”而省略。

不可用短摘要替代唯一稿件：最近正在修改的未保存正文保持原文；超大稿件超出近期保留预算时，需在会话内部保留可精确定位的原文并验证按来源事件恢复的能力后，才允许释放。不得偷偷写入用户 Wiki。尚无可靠恢复路径时宁可超出软预算，不能先裁掉再让模型重写。

复用官方 `BasicCompactionEngine.summarize()` 扩展点适配创作模板，锁、配对、取消、替换、冷恢复和压缩失败处理沿官方；以随包 rc.2 实际 API 为准，不为模板重写整个 Runtime，也不直接手改 node_modules 作为交付。

### 3.6 独立控制创作历史预算

以已讨论的 **100000 tokens 触发、近期原文约 20000 tokens** 为首期实验值；摘要正文目标约 1000–2000 tokens，生成额度需为推理预留余量，不能混同正文长度与模型总输出计量。

- 模型真实 `contextWindow` 仍如实声明；不得虚报容量来触发压缩。
- 用现有 `thresholdRatio`/`retainTokens` 与路由容量推导策略，在小窗口上进一步服从输出预留与 headroom 约束，不硬套 100K。
- 预算约束的是可缩减历史；正在创作所需原文可能更大，应分段读取或按任务保留，不能截断用户明确要求的完整资料。
- 三创作模式使用新策略；普通模式、同一 Runtime 中其他会话不被污染。队列、编辑重跑、冷恢复及切换模式均携带同一策略。
- 稳定头部保持稳定；根/文件版本变化才更新短状态。避免每轮重排提示和过于频繁压缩损失前缀缓存。
- 压缩失败保留原文并明确状态，不无限重试，也不能报告压缩成功。首次治理大历史需计入单次摘要请求成本。

DSH 上游默认会在摘要失败后继续原历史，这是待测行为；不能宣传为任何情况下输入都低于 100K。若发生真实窗口不足，沿官方溢出错误与恢复链路处理。

## 4. 实施顺序与 TDD

1. **G0 保留与测量**：增加匿名合成项目/会话 fixture，锁定当前工具表、输入来源和 Wiki 能力。验证：能复现多层注入、未登记附件与错误摘要模板，建立请求体基线。
2. **G1 Wiki 原生导航与渐进加载**：复用 Skill 的目录/按需加载思路，在现有 Wiki 原生插件中明确最小工具合同；根导航替代多层消息拼接。验证：发现、索引、真实正文、直接关联与项目隔离完整，主发送/排队/恢复一致；现有压缩策略保持。
3. **G2 Wiki 写入与索引闭环**：先补上传、手动保存、AI 文件写入和生命周期变更的红测，再接入同一目录登记与失败回执。验证：每份成功资料都能从已知根逐层找到，无模型目录请求，无递归刷新与双重写入；G1/G2 合起来才算 Wiki 工具能力完成。
4. **G3 上下文与创作摘要**：Wiki 能力验收通过后，才按 Agent/路线接入创作摘要、提前压缩和有证明的旧结果释放，保护当前稿件。验证：真实 SDK + 本地模型替身检查实际请求与重启结果，不能仅断言字符串。
5. **G4 创作质量与成本验收**：同模型、同协议、相同任务对照；再运行完整回归/类型/桌面构建。真实模型、原生平台和发布分别登记，未执行不算通过。

按用户最新顺序完成 G1/G2，再进入 G3。Wiki 自身的多层索引自动注入在 G1 随导航工具接入退出，不需要提前更改摘要、裁剪或历史保留机制。
