# 电商工作台绝对独立成功总结

> 日期：2026-07-24
> 定位：未来新增独立工作台的复用设计
> 对应现行合同：[[开发/电商工作台绝对独立SDD]]

## 1. 成功的含义

这次的“独立”不是给 Chat 换一个页面，也不是把创模式界面藏起来。它是把电商定义为一个完整、独立的产品 surface：它有自己的入口、输入、一次模型调用、当前结果和可选的媒体确认；删去 Chat 运行时也不需要补任何兼容层。

关键判断很简单：如果一个工作台必须创建 Chat 消息、借用模式会话、切换模式，或等待 OpenCode，那个工作台就还不是独立的。

## 2. 可复用的设计骨架

未来新增独立功能时，先按这个最小骨架实现：

```text
独立入口
  -> 独立页面挂载
  -> 当前用户输入 + 原始附件 + 显式 Skill
  -> 单轮模型直连
  -> 当前结果或项目定位记录
  -> 可选：用户确认后接公共执行能力
```

### 2.1 独立入口必须切断运行时

入口直接挂载工作台组件，并且与 `ChatPanel` 互斥。不要为了复用布局先进入 Chat 再隐藏它，不要调用 `chatModeStore`，也不要把工作台状态存进模式会话。

布局可以共享，运行时不能假共享。电商复用应用壳、Rail、项目选择和右侧创作面板，但没有任何 Chat 或模式状态参与请求和结果。

### 2.2 模型调用必须是显式、单轮的合同

独立工作台的请求输入应能由用户一眼说明：当前字段、当前附件、当前选择的模型和当前选择的 Skill。请求只由这四类事实组成。

- Skill 可以用。直连不等于没有 Skill；直连是没有 Agent 工具循环和隐式上下文。
- Skill 作为静态 `system` 规则，不能自行读文件、查 Wiki 或调用工具。
- `tools: []` 和 `allowToolCalls: false` 是硬边界。
- 不加载聊天记录、项目资料、最近任务或隐藏记忆；跨次内容只能由用户明确放进当前输入。

这样模型行为、费用和错误都能归因到当前一次操作，而不是来自不可见的会话积累。

### 2.3 公共能力应复用，运行时不能绑定

电商证明了“共享能力”和“共享运行时”是两件事。

| 可以复用 | 不应复用 |
| --- | --- |
| 模型目录和 Provider 配置 | Chat 消息、当前模式、会话 ID |
| Skill 内容解析 | 工具循环、MCP、审批链 |
| Direct Engine / 原始附件合同 | OpenCode sidecar 与 `ses_*` |
| MediaPlanCard、CreationPanel、mediaTaskStore | 创模式的 `creative_*` 会话 |
| 项目文件服务、画布结果 | 自动项目/Wiki 上下文 |

复用公共模型目录时要像电商一样使用公共目录加载路径，而不是绕到 OpenCode：`fetchModels({ skipOpenCode: true })`。复用媒体时只交给现有 `CreationPanel -> mediaTaskStore`，不重写提交、轮询和落盘。

### 2.4 记录只解决追溯，不扩张成新系统

电商为运行保存 `jc-media/ecommerce/<run-id>/record.json`，并在当前结果上提供“定位文件”。这足够回答“这次运行在哪里”，无需再建历史面板、双写 Wiki Markdown、迁移旧数据或给媒体结果做额外回写层。

新工作台也应先问：用户真的需要浏览历史，还是只需要结果和定位？后者就只保存定位记录。记录格式只承载该工作台的事实，不能伪装成 Chat 会话。

## 3. 实施顺序

1. 写出输入、输出和成功标准，确认它不需要任何 Chat 或模式状态。
2. 做独立入口和互斥挂载，先保证页面不会初始化 Chat。
3. 用现有 Direct Engine 建单轮请求，先写“没有历史、没有工具”的请求合同测试。
4. 接公共模型目录与 Skill 内容；只传用户明确选择的内容。
5. 需要付费或异步执行时，先展示可审阅结果，用户确认后才接公共执行能力。
6. 只增加可定位的项目记录；除非真实需求出现，不做历史 UI 或迁移。
7. 做结构性隔离测试，再做真实 Provider 和真实媒体任务人工验收。

## 4. 反模式

- 用 `v-show` 隐藏 ChatPanel，然后把它叫独立工作台。
- 点击工作台入口时强行切到创模式，或创建 `creative_*`/`ses_*` 会话。
- 把工作台结果追加进 Chat 消息，借 Chat 充当历史和状态机。
- 因为独立就复制模型目录、请求客户端或媒体任务系统。
- 把 Wiki、文件树、历史运行自动塞进模型上下文，让结果无法解释。
- 只为“以后可能需要”就加双写 Wiki、媒体回写、迁移或历史列表。

## 5. 验收清单

- 入口不调用任何模式切换，工作台挂载时 `ChatPanel` 不存在。
- 请求只含当前字段、原始附件、用户选择的模型和显式 Skill。
- 请求没有工具，工具调用被明确禁止。
- 模型目录和媒体任务使用公共能力，但不触发 OpenCode、Chat 或创模式会话。
- 当前结果可定位到项目文件；没有未被要求的历史系统。
- 自动回归覆盖挂载、请求合同、模型目录和媒体交接；真实 Provider/付费媒体在目标端人工验收。

## 6. 结论

电商工作台的价值不在于又增加了一种模式，而在于证明了产品可以由多个相互独立的工作台组成：它们共享稳定的底座能力，却不把各自的流程绑到 Chat。以后新功能先从这个骨架出发，只有确实需要多轮对话、工具或历史时，才明确选择并接入那些能力。
