# 通用记忆工作台 Wiki 任务执行提速 TDD

> 日期：2026-08-26  
> 状态：已实施，自动验收通过；三次真实模型性能验收待执行  
> 范围：记忆工作台 Direct Runtime、Wiki 检索、Wiki Skill 与任务耗时验收

## 1. 目标

让“根据指定文档总结规则并增量写入 Wiki”这类高频任务，在不降低来源证据、冲突停手、写后验证和跨平台能力的前提下，从开放式多轮模型循环收口为最多四个工具轮：

```text
1. 一次多词 Wiki 检索
2. 并行读取来源页、目标页和来源索引
3. 串行写入正文、来源索引及确有变化的 hot/log
4. 并行重读验证并回答
```

用户实测基线为：相同模型下，Codex 约 `2 分 30 秒`完成，记忆工作台 `30 分钟`仍未完成。该数据来自用户本轮观察，尚无逐请求耗时记录，不当作可重复性能测试已通过。

## 2. 根因

根因不是模型权重不同，而是简单运行时把编排工作交回给了昂贵的模型循环：

```text
总耗时 ≈ 模型请求次数 × 单次模型延迟 + 工具执行时间
```

当前有四个可验证的放大点：

1. `directEngine.ts` 每个工具轮都重新发送 Chat Completions，默认保留 `64` 轮安全上限。
2. `directTools.ts` 对同一模型回复中的所有工具使用一个顺序 `for` 循环，互不依赖的只读操作也不并行。
3. `wikiRuntime.ts` 的每次搜索都枚举 Wiki 全部 Markdown，并逐文件 `await read()`。
4. `jc-cha-wiki` 要求将 `1-3` 个短词分别检索，同一批文件可能被完整读取多次。

当前项目 Wiki 约有 `347` 个 Markdown、`14 MB`。本机 `rg` 同时搜索三个词约 `0.02` 秒，说明内容规模本身不足以解释 30 分钟；真实 App 中的文件 IPC 耗时仍需通过本 TDD 的观测数据确认。

## 3. Codex 对照

对照 OpenAI 官方 `openai/codex` 主分支提交 `21c58c90f2298587c6519e077d0692ce4c563d37`：

- `codex-rs/core/src/tools/parallel.rs` 让支持并行的工具共享读锁，不支持并行的工具使用独占写锁。
- 同一运行时记录工具排队、处理和总耗时，可以区分“等待执行”和“工具本身慢”。
- `codex-rs/core/src/client.rs` 在同一 turn 复用模型会话、WebSocket、`previous_response_id` 和 sticky routing。
- OpenAI Function Calling 官方合同允许支持的模型在一轮中返回多个并行函数调用。

本 TDD 只借鉴前两项的最小实现。Responses API、WebSocket 和服务端会话复用等第一阶段实测仍不达标时再评估。

## 4. 边界

### 本轮实施

- 在现有 Wiki `search` 动作中增加一次 `1-3` 个短词的批量查询，保留单字符串兼容。
- 将同一模型回复中互不依赖的项目内只读工具并行执行，保持工具结果原始顺序。
- 将修改、删除、Terminal、项目外读写和需要审批的工具作为串行屏障。
- 在既有 Direct Runtime 事件与工作台运行状态上增加最小耗时数据。
- 修改 Cha Skill 的检索合同，让多个初始短词在同一次 Wiki 调用中提交，互不依赖的页面读取在同一工具轮发出。

### 本轮不做

- 不新增 RAG、向量库、Embedding、BM25、后台索引、数据库或新依赖。
- 不新建 Wiki 工作流引擎、规划器、第二模型或通用 DAG。
- 不并行写入、审批、Terminal 或任意可能产生顺序依赖的工具。
- 不改变 Raw 的来源登记、冲突停手、`hot.md` / `log.md` 条件更新和写后重读合同。
- 不先迁移 Responses API 或 WebSocket；当四轮目标已达成但真实耗时仍不达标时再单独设计。
- 不全局将 `64` 轮上限改为 `12`；媒体、3D、MCP 和 Terminal 的现有长任务不能被削弱。

## 5. 只读并行合同

首批只允许以下明确无副作用的工具并行：

```text
read
glob
grep
wiki_search
wiki(action = inspect | search | status | validate | audit | evidence)
```

其他工具默认串行。执行器按模型返回顺序分段：连续只读调用组成一个并行段；遇到串行调用时等待已有并行段完成，单独执行该调用，再继续下一段。

工具完成顺序可以不同，但回填给模型的 `role: tool` 消息必须与原始 `tool_calls` 顺序一致。任一调用取消时，使用现有 `AbortSignal` 停止未完成工具，不进入后续写入段。

## 6. 耗时数据

复用现有 `runDirectChatCompletion()` 和 `onToolEvent`，不新建遥测服务。每轮只记录：

```text
模型请求序号
模型请求总耗时
工具轮次数
工具名称与执行耗时
整轮总耗时
```

不记录用户消息、工具参数、文件正文、API Key 或模型 reasoning。首版只在现有运行步骤与开发日志中使用，不持久化到 Raw、Wiki 或服务器。

## 7. 红灯测试

### 7.1 Wiki 一次多词检索

1. `wiki search` 接受 `query: ["Codex", "工具循环", "写入合同"]`，返回每个词的候选页和行号。
2. 同一文件同时命中多个词时，`workspace.read(path)` 仍只执行一次。
3. 传入旧的单字符串时输出合同不变；空数组、空词、超过三个词和非字符串项明确失败。
4. `active/all`、归档排除、`log.md` 排除、标题加分和 `limit` 边界不变。

### 7.2 只读工具分段并行

1. 同一模型回复中的两个 `read` 都在任一个完成前开始，最终 tool 消息仍按 A、B 顺序。
2. `read A -> write B -> read C` 严格得到“A 完成 -> B 完成 -> C 开始”。
3. `wiki action=search` 可并行，`wiki action=replace/extend/scaffold/graph/closeout` 默认串行。
4. 取消、工具失败、审批拒绝和立即重复失败保护的现有结果不变。

### 7.3 轮次与耗时

1. 模型每发起一次 HTTP 请求，请求计数严格加一，重试与工具轮分开记录。
2. 工具结束事件包含非负 `durationMs`，失败和取消也有终态耗时。
3. Direct Runtime 最终结果包含模型请求数、工具轮数和总耗时，不包含正文或参数。
4. 全局 `64` 轮上限与其他调用者保持不变。

### 7.4 Skill 合同

1. Cha Skill 明确一次提交 `1-3` 个初始短词，不再要求“分别检索”。
2. 互不依赖的候选页、来源索引和指定文档在同一工具轮读取。
3. 查到足够证据即停、冲突并列、无答案不补写、默认只读和来源展示合同不变。

## 11. 真实模型前向验收

建立一个脱敏固定样本：一份来源文档、一个已有部分规则的目标 Wiki 页、一张来源索引和可预期的最终正文。修改前后均使用相同的：

```text
模型精确 ID
Provider / 渠道
reasoning effort
系统提示与 Skill 版本
项目样本
新建对话
```

修改后独立执行三次，全部满足：

1. `3/3` 完成，无超时、无轮次上限和无空回答。
2. 每次最多 `4` 个工具轮，不依赖未授权的 Terminal。
3. 三次中位总耗时不高于 `5 分钟`，单次不高于 `8 分钟`；且相对同环境修改前中位数至少提速 `3 倍`。
4. 预期规则全部保留，重复不重写，冲突不自行覆盖，来源索引映射正确。
5. 只修改预期 Wiki 页、来源索引及确有状态变化的 `hot.md` / `log.md`，不修改 Raw 或其他项目文件。

`Codex 2 分 30 秒` 只作外部参考，不伪装成同渠道基准。没有完成上述三次真实前向，不得将本 TDD 记为性能验收通过。

## 12. 后续升级闸门

- 若工具轮已不高于四轮，但模型请求占比仍过高，再评估 Responses API、WebSocket、`previous_response_id` 和 prompt cache。
- 若模型请求已达标，但 Wiki 文件读取占比过高，再评估 Desktop 原生批量搜索或项目内容快照。
- 若仍频繁出现无进展循环，基于真实轨迹增加 Wiki 任务专用停滞保护；不全局降低长任务上限。
- 若多词、同义词和链接扩展仍经常找不到已有页面，才按现行闸门评估全文检索或 BM25；不因性能问题直接引入向量库。

- 红灯在旧实现上确认失败，最小实施后转绿。

- 三次真实模型前向同时达到正确性、轮次和耗时目标。
- 实施结果如实记录已验证与未验证边界，不用单元测试代替真实模型性能验收。

## 14. 实施结果（2026-08-26）

### 14.1 已实施

- `wiki search` 同时接受旧单字符串和 `1-3` 个字符串数组；数组查询只扫描、读取每个 Wiki Markdown 一次，逐词返回候选页和行号。
- `buildToolResultMessages()` 按模型返回顺序分段：连续的项目内 `read/glob/grep/wiki_search` 和只读 Wiki action 并行；写入、Terminal、MCP、项目外读取及其他操作默认串行。
- 并行完成顺序不影响回填顺序；取消会等待当前并行段收口且不进入后续写入段。
- 工具结束事件增加非负 `durationMs`，工作台运行步骤显示工具耗时；Direct Runtime 最终结果只返回真实 HTTP 请求次数、各请求耗时、工具轮数和总耗时，不记录正文或参数。重试层逐次上报，三次 HTTP 尝试不会误记为一次。
- 记忆模式提示要求互不依赖的项目内只读工具在同一回复发出；Cha Skill 改为一次提交 `1-3` 个初始短词，并在同一工具轮读取互不依赖的候选页、来源索引和指定文档。
- 全局 `64` 轮上限、审批、Raw/Wiki 写入合同、MCP、媒体、3D、Web、Desktop 与 Mobile 工具清单未削弱。

### 14.2 红灯与自动验证

- 新增红灯在旧实现上确认 `6` 个 Node 合同和 `1` 个 Skill 合同失败，分别覆盖并行、耗时、数组检索、非法输入与 Skill wording；实施后转绿。
