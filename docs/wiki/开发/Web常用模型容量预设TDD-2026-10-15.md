# Web 常用模型容量预设 TDD

日期：2026-10-15；分支：`1001-shoujiweb`。用户先授权修改，随后授权修复图片误判并提交、推送、发布Web1.0.3。

## 根因与范围

上一轮为了移除“所有云模型默认1M”，将未知容量统一改成32K，却没有补常用模型预设。中转目录只有模型ID时，GPT6.1等已知型号也被当成未知；旧缓存恢复还存在两条不同的迁移路径。Runtime确实按32K裁剪，不只是提示文案错误。

只修改当前Web支线的容量表、模型Store、聊天/索引预算、设置入口与提示。Wiki、Raw、创作路线与动态上下文策略不变，不引入探测服务、新依赖或付费模型请求；桌面main不写入。

## 容量合同

1. 用户按“供应商ID＋模型ID”保存的手动容量最高优先，可恢复自动预设。
2. 无手动设置时保留接口明确声明的窗口/输出限制；字段缺失才使用精确型号预设，不能把已声明的256K擅自抬到1M。
3. 常用GPT型号使用已核验的1,050,000窗口及128,000输出；截图内其他常用云端ID/别名采用用户认可的1,000,000产品预设，不冒充通道实测。
4. Haiku4.5独立使用200,000窗口、64,000输出。其余未核验输出能力的中转预设仍采用4,096默认输出预算，用户可覆盖。
5. 只规范化大小写、已知厂商前缀及GPT完整日期快照；不通过包含`gpt`/`claude`猜系列容量。未知型号、`codex-auto-review`、未登记免费型号继续保守兜底。
6. Ollama/MLX不继承云端1M；实际本地容量仍须显式元数据或手动配置。
7. 上下文与输出各自保留来源，避免接口只声明输出时，在下一次读取中被预设覆盖。手动数据须为安全正整数，输出小于总窗口；存储失败不更新内存态。
8. 启动和断网缓存恢复共用迁移；旧32K估算和无来源旧1M按当前表重算，接口明确声明值保持。聊天与记忆索引使用同一解析结果，索引输出另取摘要预算与模型上限的较小值。
9. 已知容量不再报未知；清理旧容量提示不清除路径权限、Jev等其他提示。

## 后续：图片误判与Web1.0.3

- 用户确认正式站GPT6.1仅上传一张图片即报本地上下文超限。根因：正式站仍为旧32K兜底，预算还将`image_url`中的Base64当普通文字计数；不是模型返回容量不足。
- 同一估算入口用于历史和最终请求；只在估算副本中替换图像载荷，按头部像素预留视觉预算，发送用的原图片/URL、detail和正文不变。PNG、JPEG、GIF、三种WebP头部受支持，只读取前64K编码，不下载远程URL、不解码整图。
- `shortcut`：没有中转站精确图像计数接口，使用32px块×3＋余量、最低4096的产品保守估算；未知头部/远程图预留65536。不是官方账单token算法，特殊型号及极端长宽比仍可能误差；模型/通道最终限制仍由服务端校验。保留文字/工具超限与请求字节限制，错误增加输入估算/预算/总窗口数值。
- 补Haiku5.5独立1M/128K预设，支持点号/横线、anthropic前缀及明确`:batch`别名，不把Haiku4.5抬成1M。[用户提供的OpenRouter规格](https://openrouter.ai/anthropic/claude-haiku-5.5:batch)。
- 新增4条图片断言先在旧代码失败；修复后PNG/JPEG/GIF/WebP、未知头部、重复计数、纯文本/工具仍拒绝超限、历史保留和4MB图片到实际GPT请求且字节不变通过。相关133/133；Web构建、类型检查、产物审计通过。完整结果见发布记录。
- 原生与真实中转调用/计费未验。正式发布回执与线上产物核验见[[运维/Web1.0.3发布记录-2026-10-15]]。
- 估算依据：[OpenAI图像计数说明](https://developers.openai.com/api/docs/guides/images-vision)。官方按型号/detail有不同patch与tile规则；本次未假称实现逐型号精确计费算法。
