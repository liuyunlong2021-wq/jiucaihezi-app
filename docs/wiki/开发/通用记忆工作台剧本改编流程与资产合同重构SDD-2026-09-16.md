## 1. 根因

改编链路已有正确的职责边界（Runtime 负责确定性、Skill 负责语义），但**事实层与产出层共用同一目录，且资产合同在三处不一致**，导致改编 Skill 在当前产品上必然停摆。以下每条都有代码或文档证据。

> 本节描述 2026-09-16 修复前的状态。当时逐集改编 Skill 叫 `jc-gaibian-duanju`，现已更名为 `jc-gaibian-luobi`。

### 1.1 资产目录三套并存

| 来源 | 角色目录 | 粒度 |
| --- | --- | --- |
| `src/runtime/memory/adaptationWikiScaffold.ts:16` | `资产/角色/` | 目录 + `index.md` |
| `src/runtime/memory/storyAnalysis.ts:60` | `资产/人物/` | 平铺 `人物/林默.md` |
| `~/.agents/skills/jc-gaibian-duanju/SKILL.md` | `资产/角色/` | `角色/林默/角色档案.md` |

两份已实施通过的 TDD 各自写死了不同目录：[[开发/通用记忆工作台改编Wiki建库与双链输入TDD-2026-09-10]] §3.3 是 `资产/角色|场景|道具/`，[[开发/通用记忆工作台故事拆分与语义沉淀TDD-2026-09-09]] §62 是 `资产/人物|场景|道具|关系/`。

### 1.2 索引重复条目与死链

`adaptationWikiScaffold` 的索引写相对 Markdown 链接（`- [场景](场景/index.md)`），而 `storyImport.ts:168` 的 `hasLink` 只识别 `[[…]]` 双链。因此 `commit_story_analysis` 在 `资产/index.md` 追加时判不出已存在，会再插一份：

```text
## 子目录
- [角色](角色/index.md) - …
- [场景](场景/index.md) - …
- [道具](道具/index.md) - …
- [[人物/index|人物]] - …
- [[场景/index|场景]] - …   ← 重复
- [[道具/index|道具]] - …   ← 重复
- [[关系/index|关系]] - …
```

「角色」指向空目录（死链），「场景/道具」各出现两次。

### 1.3 改编方案目录没有任何产出方

`总体改编方案.md`、`逐集改编方案.md`、`原始材料/主线/原著分集情节点` 在 `src/` 全仓 **0 命中**；建库只写出内容为「用途：…」的 `改编方案/index.md`。而 `jc-gaibian-duanju` 把它们列为「必须读取的证据」，缺失即停止创作。

结论：**在新建库上改编 Skill 无法启动**，中间缺一整环。

### 1.4 提取 Skill 的输出进不了下游

`jc-zichantiqu` 只输出一段 Markdown（四个二级标题），没有路径、Properties、双链，也不落盘；下游只认 Wiki 正链。两个 Skill 都叫「资产」，一个是报告，一个是档案。中间那次搬运没有任何工具支持。

### 1.5 事实层会被就地改写

当前设计里「改编资产」直接覆盖 `资产/` 下的规范实体页，而这些页面由 Runtime 从原文证据沉淀、带来源哈希。覆盖后：事实层与产出层分叉、无法重放、方向改错无法回滚，且 `assetPage()` 重写整页会冲掉改编段。

### 1.6 一致性靠逐集重推

改编方向是一段散文，每集都要模型重新推导「手机 → 什么」。N 集就有 N 次自由发挥机会，且没有任何进度位回答「改到第几集」。

## 2. 最小形态

| 层 | 位置 | 权限 | 产出方 |
| --- | --- | --- | --- |
| 事实层 | `wiki/原始材料/<作品>/`、`wiki/资产/` | 只读 | Runtime |
| 差异层 | `wiki/改编方案/改编思路.md` | 可编辑 | 用户 |
| 产出层 | `wiki/剧本/<集>.md` | 可重写 | 改编 Skill |

不做的事：不建改编资产目录、不做 delta 表、不做结构化约束 schema、不新增 Skill、不写校验器。

跨集一致性只由两件事保证：每集读同一份 `改编思路.md`；每集读上一集已成稿剧本。

## 3. 唯一资产合同（定案）

**平铺 `wiki/资产/<类型>/<名称>.md`，类型固定为 `角色 | 场景 | 道具 | 关系`。**

理由：

1. Runtime 的实体发现 `directMarkdownPages`（`storyAnalysis.ts:145`）只扫直属子项；改成分层目录要同时改发现、建档、索引三处，成本高一个量级。
2. 一个资产一个文件已能承载来源事实、关系、状态与造型说明；将来确需多份档案时再升级为目录，升级点就是 `directMarkdownPages` 的扫描深度，位置明确。
3. 与 `storyAnalysis` 现值只差一个词（`人物` → `角色`），改动是常量级。

需要同步修改的位置：

- `src/runtime/memory/storyAnalysis.ts:60` `characters: '人物'` → `'角色'`；
- `src/runtime/memory/adaptationWikiScaffold.ts:16` `DIRECTORIES` 补 `资产/关系`，`indexContent('资产')` 补关系条目；
- [[开发/通用记忆工作台改编Wiki建库与双链输入TDD-2026-09-10]] §3.3 目录树与 §4.3 双链样例；
- `jc-gaibian-duanju` 的正链样例改为 `[[wiki/资产/角色/林默|林默]]`。
- 该 Skill 已更名为 `jc-gaibian-luobi`，并在 `jc-gaibian-silu` 落地后交出「写改编思路」职责。

**迁移**：建库与分析不得与旧路径并存。检测到 `资产/人物/` 或分层旧路径时报告冲突并列出路径，交由用户决定，不自动搬运、不静默双写。

## 4. 改编思路文件（唯一新增）

`wiki/改编方案/改编思路.md`，自然语言，不强制结构：

```markdown
# 改编思路

## 整体方向
把当代都市改成架空古代，保留原著的冲突结构与人物关系。

## 关键替换
- 手机 → 飞鸽传书；刑警 → 捕快；咖啡 → 茶

## 分集走向（可选）
- 第 1 集：……
```

由 `jc-gaibian-silu` 产出并回读确认；之后每集由 `jc-gaibian-luobi` 原样读取。

原设计中的「四张表 + 设定映射表 + 资产 delta + 独立的分集情节点文件」已删。理由：消费者是下一集的模型，一段人写的自然语言与结构化表格信息量相同；delta 要解决的跨集一致问题，由「读同一份思路 + 读上一集剧本」直接覆盖，不需要额外元数据。

## 5. 流程

```text
定改编思路（人写一次）→ 第 1 集 → 用户过目 → 第 2 集 → 用户过目 → ……
```

每集输入固定四样：改编思路、本集原文节点、按需的资产页面、上一集剧本。

不额外加阶段闸门：用户每集过目本身就是闸门，也是唯一必要的那个。

## 6. 冲突分级

现状把两类冲突都当异常停止，而其中一类是设计预期内的。

- **设计内冲突**（改编设定 vs 原文事实）→ 正常，放行；
- **意外冲突**（本集设定 vs 已成稿剧本、正链不唯一、改编思路未覆盖的替换）→ 停止并列出路径。

## 7. Skill 分工

改编拆成两个 Skill，职责不重叠；另有一个不接入主链路的旁路。

| Skill | 职责 | 触发场景 |
| --- | --- | --- |
| `jc-gaibian-silu`（改编-思路） | 定改编方向，产出并维护 `改编思路.md`；方向变更时评估影响面 | 「改编方向」「怎么改」「换一个方向」 |
| `jc-gaibian-luobi`（改编-落笔） | 已有方向后逐集落笔并写回剧本 | 「改编第 X 集」「继续下一集」 |
| `jc-zichantiqu` | 未建库时的一次性旁路提取 | 用户直接提供 Markdown |

拆开的理由是**入口缺失**：原 `jc-gaibian-duanju` 的触发词是「adapting the next episode」，用户说「我要把这部小说改成短剧」「我想改成架空古代」时没有任何 Skill 被激活。定方向是改编里最值钱也最容易返工的一步，必须有独立入口。

`jc-gaibian-luobi` 不再自己写 `改编思路.md`；文件不存在时它给出 A/B/C 选项把用户引到 `jc-gaibian-silu`，避免同一份文件出现两套写法。

早期设计的 `jc-gaibian-fangan` 已被 `jc-gaibian-silu` 取代（同一位置，命名对齐 `jc-gaibian-luobi`）。

Skill 目录用拼音 id，界面显示名在 Skill 管理面板的别名里设为「改编-思路」「改编-落笔」。别名是纯 UI 元数据（`skillsManageStore` + localStorage），不写进 SKILL.md，也不进后端。

## 8. 开发步骤

第一步与 Skill 完全解耦，可独立落地。两边均已完成；仅剩真实链路人工验收。

另外，同时存在两套资产提取能力（Runtime 节点分析与 `jc-zichantiqu`）是真正的重复建设。现行分工：**主链路只用 Runtime 那套，`jc-zichantiqu` 保持独立旁路**。

## 9. 验收标准

- 空项目建库 → 拆分 → 节点分析后，`资产/` 只有 `角色|场景|道具|关系`，无空目录、无死链、无重复导航条目。
- 已存在旧 `资产/人物/` 的项目，无论点建库还是跑节点分析，都先报冲突且零写入。
- 建库后追加一次节点分析，`资产/index.md` 每个目录只被导航一次。
- 在新建库上启用 `jc-gaibian-luobi`，能完成「写下改编思路 → 改编第 1 集 → 用户过目 → 第 2 集」闭环，中途不停在缺失文件上。
- 用户说「我想把这部小说改成短剧」时，`jc-gaibian-silu` 被激活并先出启动闸门，用户选择前零写入。
- 剧本中每条角色、场景、道具正链都能唯一解析到 `资产/` 下的真实页面。
- 整个过程不需要修改任何一份 `资产/` 页面。
- Web、Mac、Windows、iPhone、iPad 上建库、拆分、双链插入与跳转一致。

## 10. 非目标

- 不做结构化约束表、设定映射表、资产 delta 或改编资产落盘。
- 不做机械校验器；结果由用户判断。
- 不实现同一原著的多套改编版本并行。
- 不实现资产分层目录（`<名称>/<类型>档案.md`）。
- 不新增关系数据库或第二份关系表。
- 不在 APP 内硬编码任何具体写作或改编规范。
- 不做旧项目自动迁移，只检测并报告冲突。
