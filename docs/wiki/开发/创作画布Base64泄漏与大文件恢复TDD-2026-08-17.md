# 创作画布 Base64 泄漏与大文件恢复 TDD

> 状态：已实施（自动验证、Desktop 保存回归与用户实际打开通过）
> 日期：2026-08-17
> 范围：`.jccanvas` 序列化、现有异常画布恢复

## 1. 故障与根因

`/Users/by3/Documents/大哥MV/jc-canvas/大哥MV图.jccanvas` 实测为 `37,130,628` 字节，含 21 个素材、23 个顶层节点和 14 个误写入的 `data:image/...;base64` 子节点 URL。

单图标注把图片从顶层 `Image` 改为 `Group > Image(name=canvas-image)`。现有 `createCanvasDocument()` 只删除与 asset ID 直接对应的顶层图片 `url`，未删除同一图片组内的运行时 URL，使 Desktop 读取的原图 Base64 进入 `.jccanvas`。

30 MB 是损坏保护线，不是画布素材数量上限。不通过调大阈值规避该故障。

## 2. 持久化合同

1. 图片、视频和音频字节只存在项目媒体文件中。
2. `.jccanvas` 只保存 asset 的项目相对路径、场景布局和标注，不保存 Base64、Blob URL 或运行时媒体 URL。
3. 图片节点可以是顶层 `Image`，也可以是标注容器中的 `canvas-image`；两种结构使用同一序列化规则。
4. 恢复时继续使用 `assets[id].resource.path` 生成运行时 URL，不影响原图、标注、布局或选中参考图。

## 3. 最小修复

- 只修改纯文档边界 `createCanvasDocument()`：当顶层节点对应图片 asset 时，递归删除该节点及其子节点的 `url`。
- 不改 LeaferJS 绘制、标注合成、媒体目录、上游提交或 30 MB 保护线。
- 对现有 37 MB 文件先保留原样备份，再以相同合同清理误写 URL；素材、场景节点、标注和路径数量必须不变。

## 4. TDD 验收

1. 红灯：`Group(id=assetId) > Image(name=canvas-image, url=data:...)` 经现有序列化后仍包含 Base64。
2. 绿灯：顶层图片和标注图片组的任意层级均不保存 `url`，asset 相对路径保留。
3. 非媒体 Leafer 节点、编号、文字、箭头和画笔数据保持不变。
4. 已有顶层图片去 URL、画布读写、任务回写和复制测试保持通过。
5. 异常文件修复后小于 30 MB，JSON 可解析，且 `scene` 数、asset 数、asset 路径和标注数与修复前一致。

## 5. 边界

本轮不引入分片画布、缩略图缓存、新数据库或视口虚拟化。几百张图片的显示性能需要真实测量后再单独立项；本轮只保证画布文件不随媒体字节大小增长。
