# 通用记忆工作台阶段 2/3 任务完成优先最终修复 TDD

> 日期：2026-08-28  
> 状态：待实施  
> 范围：阶段 2 统一任务协议、阶段 3 Wiki Agent 适配  
> 核心原则：循环是实现手段，用户任务完成才是成功条件

## 0. 最终决定

产品不需要讨论“固定几轮”或“开放循环”哪一种形式更先进。正确标准只有四个：

1. 模型获得完成任务所需的最小真实资料；
2. 程序只执行已选择、已校验、已授权的动作；
3. 用户要求的正文、文件、入口和派生关系全部完成，或明确说明未完成原因；
4. 程序回执、验证和恢复结果是真实的，模型文字不能代替它们。

任务可以在一次模型请求内完成，也可以在需要时继续请求。任何上限只用于防失控，不得作为成功条件。

## 1. OpenClaw 参考边界

参考：[OpenClaw Agent Loop](https://github.com/openclaw/openclaw/blob/main/docs/concepts/agent-loop.md)。只采用与本产品直接相关的原则：

- 每个任务有独立运行身份和生命周期；
- 模型、工具、程序回执分离；
- 写入使用当前任务的写入权，旧任务不能覆盖新结果；
- 取消、超时、失败和完成是不同终态；
- 工具结果由程序产生并限制范围。

不采用 OpenClaw 的 Gateway、多渠道消息、长期 Session、插件系统、定时任务、数据库 Agent 状态或通用工作区 Agent。当前产品仍复用 `DirectEngine`、现有审批器和平台文件适配器。

## 2. 阶段 2：统一任务协议

### 2.1 任务边界

每次显式能力任务创建一个短生命周期 `runId`，只保存本任务的计划、观察、回执和验证结果。任务结束后释放，不进入下一任务。

无 `@` 的普通请求不创建能力 Agent，不读取 Wiki、Skill、历史聊天或项目工具。

### 2.2 TaskEnvelope 合同

所有能力复用同一外壳：

```ts
interface TaskEnvelope {
  version: 1
  runId: string
  source: 'model' | 'program'
  status: 'needs_observation' | 'ready_to_execute' | 'complete' | 'failed'
  capabilities: string[]
  reads: TaskRead[]
  actions: TaskAction[]
  observations?: TaskObservation[]
  answer?: string
  errors?: TaskError[]
  receipt?: TaskReceipt
}
```

程序在执行前必须校验：

- Agent 已注册且属于用户显式选择的能力；
- read/action ID 唯一，能力命名空间明确；
- action 类型、路径、参数和依赖合法；
- 依赖无环；
- 模型不能填写 `observations`、`receipt`、`errors`；
- observation 的 `readId/actionId` 必须引用真实计划；
- observation Agent 必须与被引用动作匹配；
- receipt 的成功和失败 ID 必须来自真实 actions，不能重复，且覆盖实际执行范围。

`complete` 可以携带已执行 actions 的历史记录，但不得包含待执行动作；程序完成任务时必须带真实 receipt。`failed` 必须带真实错误和已执行范围。

### 2.3 生命周期

程序只需提供轻量事件：

```text
run_started -> observation -> plan_ready -> action_started
-> action_finished -> run_completed / run_failed / run_cancelled / run_timeout
```

生命周期用于 UI、日志和恢复判断，不引入新的 Runtime 或状态机框架。

### 2.4 高风险确认

所有 Agent 共用计划确认原则：

```text
dry-run 预览 -> 计划哈希 -> 用户确认 -> 执行
```

计划内容、目标路径、旧值、影响范围或依赖任一变化，原确认立即失效。任意非空字符串不能作为确认凭证。

## 3. 阶段 3：Wiki Agent

### 3.1 Wiki Agent 的职责

Wiki Agent 是薄控制器，不复制 Provider、SSE、重试器、审批器或文件服务。它只负责：

- 确定唯一 Wiki 根目录和入口；
- 管理本任务证据及其指纹；
- 选择和执行 Wiki 只读动作；
- 生成并提交 Wiki ChangePlan；
- 维护入口、双链、来源、日志和回滚；
- 根据真实验证结果判断任务是否完成。

Skill 仍负责小说、剧本、日记、制度或提示词等方法规则；Wiki Agent 不把任何业务领域写死。

### 3.2 最小任务状态

```ts
interface WikiAgentState {
  runId: string
  wikiRoot: string
  entryPath?: string
  requiresMutation: boolean
  evidence: Array<{ path: string; fingerprint: string }>
  retrievalSignatures: string[]
  failedSignatures: string[]
  pendingPlan?: WikiApplyInput
  applyResult?: WikiApplyResult
  validationResult?: WikiValidationResult
}
```

状态只服务当前任务，不保存旧聊天、Raw 对话、模型推理或 API 凭据。

### 3.3 任务流程

```text
入口预检
  -> ReadPlan
  -> 并发读取实际页面
  -> 必要时补充读取
  -> SynthesisAndChangePlan
  -> dry-run
  -> 必要时用户确认
  -> 一次 Wiki apply 事务
  -> 重读和结构验证
  -> 程序生成 receipt
  -> 完成或真实失败
```

循环次数不参与成功判定。只要仍存在未完成副作用，就不能把普通正文当作完成；如果已经满足完成条件，应立即结束。

### 3.4 ReadPlan 规则

- 首次只提供短入口、用户任务和已选 Skill/MCP 摘要；不扫描全 Wiki；
- 模型先选择必要页面，程序并发读取真实内容和指纹；
- 补读必须声明解决哪些首次缺失项；
- 没有新增页面时，不能把资料不足改成资料充足；
- 首次缺失项未被真实新证据覆盖时，必须停止并列出缺失；
- 相同检索签名不重复执行；没有新增路径或指纹的检索不能无限继续；
- 查询和创作默认只读，不自动更新 `hot.md`、`log.md` 或来源索引。

### 3.5 ChangePlan 与确定性提交

模型只输出语义计划，程序负责机械闭包：

- `mkdir/create/replace/append/move/trash`；
- 最近分区 `index.md` 和根入口；
- 精确 WikiLink 和受影响入链；
- 来源登记和已有 `log.md`；
- 指纹冲突、重复写入和目标碰撞；
- dry-run、串行事务、失败恢复和写后验证。

正文成功但入口失败不能返回成功。恢复失败必须返回 `recovery-required` 和恢复清单位置。

### 3.6 完成与失败

任务完成条件由目标决定：

| 目标 | 完成条件 |
| --- | --- |
| 查询 | 基于实际 Wiki 证据回答，缺失项明确列出 |
| 创作 | 必要资料已读取，结果和来源真实可追溯 |
| 写入 | 正文、入口、派生关系和验证全部完成 |
| 移动/整理 | 旧导航、 新导航和精确入链全部复检通过 |
| 回收 | 已确认、可恢复、现行入链已处理 |
| 巡检 | 指定范围检查完成，未授权问题不自动修复 |

失败时程序返回已完成、未完成、未执行和恢复状态；不伪造整体成功。必要时可把真实失败观察交给模型重新计划，但相同错误和相同计划不得原样重试。

## 4. 四个 P1 的最终修复顺序

### P1-1：确认链路

修改 `memoryToolPolicy` 与 `wikiRuntime` 的衔接，使 `apply` 内的 `move/trash/replaceAll` 都走计划预览和哈希确认。测试取消、过期、篡改和伪造确认均零写入。

### P1-2：补读可靠性

修改 `wikiTwoPhase` 的缺失项合并逻辑，保留首次缺失，要求补读路径真实覆盖缺失后才能进入综合。增加空补读、无关补读和正确补读测试。

### P1-3：程序回执闭环

修改 `taskProtocol` 与 Wiki 执行收尾：程序执行后生成带 `runId`、observations、receipt、指纹和验证结果的 `complete/failed` envelope。增加 ID 越界、重复、漏报和部分失败测试。

### P1-4：Wiki Agent 状态控制器

把状态、检索去重、失败签名、完成判断和生命周期收敛到 `wikiAgent` 控制器；底层仍调用现有 `DirectEngine` 和 `wikiRuntime`。不增加新的通用 Agent Runtime。

## 5. 实施顺序与门禁

1. 确认哈希和审批路由 -> 高风险动作未确认时零写入。
2. 补读缺失继承 -> 资料不足不能误进入综合。
3. TaskEnvelope 真实回执 -> 回执只能引用真实执行范围。
4. Wiki Agent 状态收敛 -> 查询、创作、写入、整理、巡检均按完成条件结束。
5. 运行回归测试、类型检查、Tauri 测试和真实模型矩阵。

阶段 2通过条件：能力隔离、计划校验、依赖、观察、回执和确认合同全部通过。

阶段 3通过条件：入口优先、精确读取、必要补读、完整 ChangePlan、索引/双链/来源/日志、事务恢复、写后验证和真实完成判定全部通过。

## 6. 明确不做

- 不再争论固定循环还是开放循环；只保留防失控的边界；
- 不恢复 64 轮、全局自主规划、长期记忆或全库默认扫描；
- 不为 Wiki、File、MCP、Terminal、Media、3D 各自复制 Runtime；
- 不把 OpenClaw 的多渠道和服务端会话引入本地 Markdown 工作台；
- 不把模型声称“已完成”当作程序事实。

## 7. 当前状态

本 TDD 是阶段 2/3 的最终修复指导，不代表代码已经完成。当前自动测试和类型检查通过，但上述四个 P1 仍需按顺序实施并重新验收；真实模型和真实平台结果必须单独记录。
