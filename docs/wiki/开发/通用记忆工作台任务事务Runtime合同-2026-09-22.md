# 通用记忆工作台任务事务 Runtime 合同

> 日期：2026-09-22
> 状态：**现行实施合同；Skill Creator 与 `@文件` 文本提交切片已落地，长任务批次调度待实施**
> 范围：记忆工作台内会改变文件的任务，首批覆盖 Skill Creator 与 `@文件` 长任务
> 不变边界：[[记忆工作台文件能力合同与TDD-2026-09-13]] 继续决定授权；本合同只决定授权后怎么稳定完成任务。

## 1. 核心决定

产品只建一个**任务事务 Runtime**，放在模型工具循环与 `ProjectFileService` / Desktop 文件命令之间：

```text
用户目标与授权
  -> 模型理解语义，返回结构化变更意图
  -> Runtime 检查目标、版本、边界和完成条件
  -> Runtime 写入或执行变更
  -> Runtime 读回验证
  -> Runtime 根据真实回执直接收尾
```

唯一原则：**模型负责判断与生成，Runtime 负责状态、副作用、验证和恢复。**

不再让模型承担以下工作：

- 记住哪些文件已处理、哪些待处理；
- 依靠历史工具消息恢复长任务；
- 写入后再用自然语言宣布“已完成”；
- 把完整原文、编辑参数和旧读取结果一轮轮背回模型上下文。

## 2. 不是“一个 Runtime 重写全产品”

任务事务 Runtime 是共享提交内核，不是新的工作流引擎、Agent 或第二套工具系统。

| 层 | 职责 |
| --- | --- |
| 对话 / Skill | 解释用户意图，产出内容或结构化变更提案 |
| 能力适配器 | 定义该任务的目标、提案结构和验收规则；例如 Skill 章节替换、Wiki 索引维护 |
| 任务事务 Runtime | 账本、并发读、串行写、版本检查、读回验证、恢复与程序回执 |
| 平台文件层 | 复用现有 `ProjectFileService`、Desktop 命令和 Web 项目存储，不新建文件协议 |

首期接入：

1. Skill Creator 的草稿写入、读回验证与冻结出卡。
2. `@文件` 的单文件编辑、多文件批处理和需要多次读取的长任务。
3. 已有确定性提交的故事拆分、语义沉淀和 Wiki 写入，后续只复用公共回执，不重写业务逻辑。

暂不接入：纯问答、纯读取、媒体生成、3D 编辑和无法统一读回验证的外部 MCP 副作用。它们继续使用现有 Runtime；有真实需求时再接入共享回执。

## 3. 三类持久化严格分开

```text
.raw/
├── 对话记录/                         # 只保存已完成的用户/助手可见对话
├── jc-media/文档/skill-<skill-id>/ # 可见、可编辑、可安装的持久 Skill 草稿
└── 临时任务/<run-id>/               # Runtime 可恢复账本，成功后清理
    └── manifest.json
```

- `对话记录` 不存工具轨迹、中间草稿、失败占位或模型隐藏推理。
- `jc-media/文档` 存用户需要看见、编辑或安装的产物，不是 Runtime 日志目录。
- `临时任务` 只存恢复所需的最小账本：`runId`、任务类型、授权范围、源文件指纹、步骤状态、待提交动作和程序回执。
- 不保存 chain-of-thought，不把完整工具调用历史复制成第二份对话。
- 简单任务只在内存中执行；只有不能一次提交、需要分批或需要跨重启恢复时，才懒创建 `临时任务/<run-id>/`。

## 4. 统一任务生命周期

```text
prepared -> proposed -> committing -> verifying -> completed
                                      \-> blocked
```

`blocked` 是恢复点，不是把错误文案当产品目标。Runtime 应先在安全边界内自动续跑：重读已变更文件、重算未完成批次、重生成不合格提案；只有用户权限、外部资源或真实冲突无法自动解决时才停下。

每个写任务的程序回执至少包含：

```ts
type TaskReceipt = {
  runId: string
  status: 'completed' | 'blocked'
  targets: Array<{
    path: string
    operation: 'create' | 'replace' | 'move' | 'delete'
    before?: string
    after?: string
    verified: boolean
  }>
}
```

`before` / `after` 是修订号或内容指纹，不把全文写入回执。实现可在不改合同的前提下增加批次进度和简短错误字段。

## 5. 提交与验证

1. 模型返回的是**变更提案**，不是执行成功证明。
2. Runtime 在首次副作用前固化目标、授权范围与源指纹；目标已变更时重读并重算，不静默覆盖。
3. 互不依赖的读可并发；写、移动、删除和同一目标的任何变更必须串行。
4. 单文件优先用修订号或 `expectedContent` 乐观锁；多文件在平台无法提供原子事务时使用可恢复提交，不伪装全局原子性。
5. 每个动作完成后由 Runtime 重新读取或查询目标，检查存在性、修订号/指纹、替换次数和能力适配器定义的语义断言。
6. 只有所有必需动作 `verified: true` 才能进入 `completed`。
7. 进入 `completed` 后不再请求模型生成结束语；App 直接用回执构造可见结果。因此模型最终 `content` 为空不会把已完成任务变成失败。

## 6. `@文件` 长任务

`@文件` 是授权与能力开关，任务事务 Runtime 是执行层，两者不替代。

- 用户明确选中的文件由 App 首读；目录或“全部文件”任务由 Runtime 建立完整清单，不让模型决定是否遗漏。
- 每个源文件记录指纹和 `pending / completed / blocked`；已验证的批次不因 App 重启重复读写。
- Runtime 按当前模型上下文预算分批，并优先保持文件、页、章节或工作表完整；模型不维护分批游标。
- 只把当前批次、必需证据和上一个相关结果发给模型；旧工具轨迹不作为恢复机制。
- 多文件变更先得到完整动作计划，再由 Runtime 依次提交、逐项验证；应用重启后从第一个未验证动作继续。
- 进度以文件/动作账本计数，不以“模型 9 次、工具 7 轮”作为完成度。

### 6.1 三条执行路径

Runtime 根据用户本轮明确目标选择最短路径，用户不需要切换模式：

| 路径 | 触发条件 | 执行 |
| --- | --- | --- |
| 快速 | 一个或少量明确文件 | 预读一次，模型给出答案或动作，Runtime 提交并验证 |
| 渐进 | 授权目录内寻找相关资料 | Runtime 逐层给真实直属清单，模型只能选择清单内下一层路径 |
| 全量 | 明确出现“全部、整个、所有、递归”等穷尽要求 | Runtime 递归建立完整账本，按自然文件边界分批，任何文件都不能由模型静默遗漏 |

快速任务不落盘账本。渐进任务跨多个批次、全量任务或需要跨重启恢复时，必须惰性创建 `.raw/临时任务/<run-id>/`。

### 6.2 账本与暂存协议

```text
.raw/临时任务/<run-id>/
├── manifest.json
└── staged/                 # 仅在提案不能当轮提交时存在
    └── <action-id>.txt
```

`manifest.json` 是 Runtime 私有文件，文件树不展示、模型不能直接读写。它不得保存对话、隐藏推理或完整工具轨迹。

```ts
type FileTaskManifest = {
  schemaVersion: 1
  runId: string
  taskFingerprint: string
  status: 'prepared' | 'processing' | 'committing' | 'verifying' | 'completed' | 'blocked'
  mode: 'fast' | 'progressive' | 'exhaustive'
  scope: string[]
  units: Array<{
    id: string
    path: string
    segment?: string
    sourceFingerprint?: string
    status: 'pending' | 'processing' | 'proposed' | 'completed' | 'blocked'
    error?: string
  }>
  actions: Array<{
    id: string
    kind: 'write' | 'edit' | 'mkdir' | 'move' | 'delete'
    path: string
    destination?: string
    before?: string
    after?: string
    status: 'pending' | 'committing' | 'verified' | 'blocked'
    verified: boolean
    error?: string
  }>
}
```

正文较大且不能当轮提交时放进 `staged/`，`manifest.json` 只记录相对暂存路径和指纹；任务结束后清理整个任务目录。被中断的任务保留，恢复时从第一个未验证 unit/action 继续。

### 6.3 模型批次协议

Runtime 决定清单、分段与下一批，模型不维护游标。每个批次只接收任务要求、选定 Skill、当前批次和必要的上一批摘要，并返回：

```json
{
  "unit_results": [
    { "unit_id": "file-003", "status": "completed", "output": "该单元结果" }
  ],
  "actions": [
    { "kind": "write", "path": "资料/结果.md", "content": "完整目标正文" }
  ]
}
```

- `unit_id` 必须来自 Runtime 当前批次；缺失、重复或越界结果整批拒绝。
- 模型不填写成功回执、源指纹、批次游标或下一批路径。
- 单批模型请求可以设有限重试；整个长任务不受“总共三次模型请求”限制，也不使用无账本的 64 轮开放循环。
- 同一批没有新增合法结果时可纠正一次；仍无进展才把该批标为 `blocked`。

### 6.4 提交、恢复与收尾

1. Runtime 在副作用前把动作、源指纹和 `committing` 状态写入账本。
2. 同一目标动作串行；不同目标只允许并发读取、转换和模型处理，不并发写入。
3. 提交前重新读取源文件。指纹变化时只把受影响 unit 退回 `pending`，不静默覆盖。
4. 写入后进入 `verifying`，重新读取目标并逐字比较目标正文，或校验替换次数、存在性和前后指纹。
5. 只有读回通过才把动作标为 `verified`；App 关闭后从第一个非 `verified` 动作继续。
6. 全部 unit 到达 `completed/blocked`、全部必需动作 `verified` 后，Runtime 生成最终程序回执并直接结束，不请求模型补结束语。
7. `blocked` 文件逐项列出；已完成文件和模型内容结果不得因局部失败而丢失。

### 6.5 当前实施切片

第一切片先覆盖项目内 UTF-8 文本的 `write`、`edit`、`write_text_batch`：动作前记账，写后逐字读回，成功后 Runtime 直接返回累计回执。目录渐进披露、Office/PDF 归一化、跨重启批次调度和移动/删除恢复在后续切片接到同一账本，不另建第二套协议。

## 7. Skill Creator 是第一个适配器

Skill Creator 必须按以下链路执行：

```text
读已安装 Skill
  -> Runtime 创建或刷新文件树草稿
  -> 模型返回完整新文件或唯一章节替换提案
  -> Runtime 乐观锁写草稿
  -> Runtime 读回并运行结构/任务断言
  -> Runtime 冻结已验证快照
  -> App 直接显示现有安装卡
```

- 模型不再被要求调用 `write_text_batch` / `write` / `edit` 把草稿写回。
- `skill_creator_improve_description` 之类产出新正文的能力，必须把正文交给 Runtime 提交，不再返回“请模型写回”。
- `save_skill` 仍是冻结与出卡边界，但只能消费 Runtime 已读回验证的草稿版本。
- 安装中央 Skill 仍需用户点击安装卡；Runtime 不绕过这个现有安全边界。

## 8. 实施顺序与验收

1. ✅ Skill Creator 已收回草稿写入、读回验证和冻结出卡。
   验收：替换 `STEP 3` 后草稿只有该章节变化，读回断言通过，无额外模型收尾请求，安装卡可用。
2. ✅ 同一提交内核已接到 `@文件` 的 `write`、`edit`、`write_text_batch`。
   验收：`write/edit/write_text_batch` 成功后自动读回，Runtime 直接生成程序回执，不因模型空正文丢失成功结果。
3. 🟡 已增加惰性动作账本、累计回执和已验证动作幂等恢复；完整文件清单、模型分批与跨重启自动调度待实施。
   验收：中途重启后从未验证项继续，已验证文件不重复写，源指纹变化时不静默覆盖。
4. 最后才让已有故事/Wiki 事务适配共享回执和进度。
   验收：现有业务测试不变，不复制原有提交逻辑。

### 自动回归门禁

1. 模型产出合格变更提案后，即使后续模型正文为空，文件仍写入、读回并显示已验证回执。
2. 读回内容与提案不一致时不冻结、不出卡。
3. 同一个已验证动作重放不产生第二次变更。
4. 不同目标可并发读，同一目标的写按计划顺序执行。
5. 长任务重启只处理未完成项；源文件变化时重算受影响项。
6. `对话记录` 不出现工具日志、临时账本或隐藏推理。
7. Desktop / Web 都通过现有项目文件层完成项目内事务；不伪造未执行平台的通过结果。

## 9. 明确不做

- 不建通用 DAG、可视化工作流编辑器、任务数据库或多 Agent 调度器。
- 不用无限模型轮数替代任务账本。
- 不把对话 Raw 变成 Runtime 事件日志。
- 不为了“全产品统一”搬迁已稳定的媒体、3D 或故事业务引擎。
