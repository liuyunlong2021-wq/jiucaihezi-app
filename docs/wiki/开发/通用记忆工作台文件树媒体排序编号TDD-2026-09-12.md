# 通用记忆工作台文件树媒体排序编号 TDD

> 状态：已实施（自动化验证通过，待真实项目手动验收）
> 日期：2026-09-12
> 范围：文件树单层文件夹内的媒体文件按生成时间重排编号
> 目标场景：漫剧制作时一集一个文件夹，生成大量图片/视频后按顺序编号，方便后续图生视频

## 1. 决策

只做一件事：**右键一个文件夹 → 「媒体排序编号…」→ 预演确认 → 把该文件夹内的图片/视频/音频改名为 `001_第一集.png`、`002_第一集.png`…**

- 编号格式：`三位编号_父文件夹名.原扩展名`，固定三位数字 + 下划线；超过 999 个自动扩位。
  - 实操反馈修正（2026-09-12）：原本写的是 `001_原名.png`，但生成器给出的原名是无意义串（`102d7fc8…`、`0cd3bd75-7ffe-4…`），编号后仍然看不出是哪一集。改为**一律用父文件夹名当基础名**，编号负责顺序、基础名负责集号；分隔符仍用下划线，与磁盘上已有的 `001_xxx.png` 保持一致。
- 排序依据：**已有编号一律尊重现有编号顺序**，未编号的按生成时间接在后面；对话框里可切换为「全部按生成时间重排」以纠正错误编号。
- 只处理**单层**（不递归子目录），只处理图片/视频/音频（不含 `.glb`/`.gltf` 等 3D 文件）。
- 先预演再执行，绝不用「保留两份」策略制造 `001_x (1).png`。

用户已明确不做的：生成时直接落到指定文件夹（P2-6）。同一批文件树媒体整理的另外两项也已在本次落地：上下键（焦点）跟随预览（P0-1）、多选移动到新建文件夹（P0-3），它们复用现有预览路由与批量移动合同，没有为它们新建抽象层。仍未做的：树内「只看媒体」过滤与文件夹媒体计数（P1-4）、文件夹作为参考序列送创作面板（P1-5）。

## 2. 当前根因

### 2.1 为什么现在需要手工排序

`buildMediaFilename()` 生成的媒体文件名是 `语义词_6位十六进制.扩展名`（`src/utils/mediaFilename.ts`），**没有任何序号**。同一个文件夹里几十张分镜图按名称排序是随机的，图生视频选参考图时拿不到「第 1 镜、第 2 镜」的顺序。文件系统顺序也不能用。

### 2.2 可复用的现状（本 TDD 不新造）

| 能力 | 现状 | 落点 |
| --- | --- | --- |
| 媒体识别 | `classifyProjectResource()` 已把图片/视频/音频/模型归为 `media` | `src/utils/projectResource.ts` |
| 单文件重命名 | `projectFiles.rename(resource, newName)`，带同名检查与变更事件 | `src/services/projectFileService.ts` |
| 文件时间 | `ProjectResource.updatedAt` | 同上 |
| 生成顺序 | 任务记录 `MediaTask.createdAt`；创作产物 `metadata.taskId` + `metadata.projectPath` | `src/stores/mediaTaskStore.ts`、`src/utils/creationMediaCache.ts` |
| 右键菜单 | 目录节点菜单已存在（`ctxRename`、`ctxDelete`、`ctxNewFolder`…） | `src/components/filetree/ProjectFileTree.vue` |
| 弹窗范式 | `pft-collision-overlay` / `pft-delete-overlay`（Teleport + `role="dialog"` + `aria-modal`） | 同上 |
| 输入范式 | `safePrompt(title, defaultValue, { forceDom: true })` | 同上 |
| 受保护路径 | `isProtectedMemoryPath()` | 同上 |

结论：需要新增的只有一个**纯函数模块**加一个**预演弹窗**，其余全部复用。

### 2.3 时间来源的优先级

只用既有数据，不新建表：

1. 文件名末尾的任务后缀（`buildMediaFilename` 写入的是 `task.id` 去掉非字母数字后的**后 6 位**）→ `mediaTaskStore.tasks` 中匹配任务的 `createdAt`。这条链路跟着文件名走，文件被移动或复制后仍然有效。
2. 以上没有 → `ProjectResource.updatedAt`（文件时间），预演里逐行标注「文件时间」。
3. 都没有 → 排到最后，按名称稳定兜底。

> 实施时没有把 `metadata.projectPath → metadata.taskId` 当主链路：文件名后缀已经覆盖同一批产物，少依赖一张资产表。

## 3. 边界

- **只处理单层**：目标文件夹的直接子项，不进入子目录，不改子目录里的文件。
- **只处理媒体**：`image` / `video` / `audio`；其余类型（`.md`、`.jccanvas`、`.json`、`.glb`…）一律不动，也不参与编号。
- **受保护路径不处理**：命中 `isProtectedMemoryPath()` 的文件跳过并在预演里说明。
- **不递归、不跨目录**：编号只保证同一文件夹内的相对顺序。
- **不重命名目录**。
- 已知边界：如果某个媒体文件被 `.md` 用**相对路径**引用，改名会让该链接失效。画布里的媒体引用基于资源 id（`jc-media://`），不受影响。一期不做引用扫描，在预演弹窗里以固定提示说明。
- `keep-both` 冲突策略**不适用于本功能**：编号必须唯一，任何目标名冲突都必须先由用户处理。
- 交换型冲突（目标名恰好是另一个待改文件的当前名）会先把涉事文件改成 `__pft_reorder_tmp_*` 再落到最终名；**该阶段失败会把文件留在临时名下**，错误提示会要求手动改回或重新编号。

## 4. TDD 验收设计

### 4.1 纯函数：`src/utils/mediaReorder.ts`

新增以下导出，全部无 I/O、无 Vue 依赖：

- `mediaKindOf(path, mimeType?)` → `'image' | 'video' | 'audio' | null`（按扩展名与 mime 判断；`glb`/`gltf` 返回 `null`）
- `orderPrefixOf(name)` / `stripOrderPrefix(name)` → 读写已有的 `^\d{3,}[_-]` 前缀
- `orderName(index, name)` → `${String(index).padStart(3, '0')}_${stripOrderPrefix(name)}`
- `temporaryReorderName(index, name)` → 交换型冲突用的临时名，保留扩展名
- `fileNameTaskSuffix(fileName)` → 取文件名末尾 `_` 后的任务后缀，用于反查 `createdAt`
- `planMediaReorder({ resources, createdAtOf, mode, isProtected })` → `{ renames, unchanged, conflicts, needsTempPass, numberedCount, unnumberedCount, fileTimeCount }`
  - `renames`：`{ path, name, nextName, timeSource: 'task' | 'file' | 'none' }[]`，已按最终顺序排列，**只含真正要改名的文件**
  - `mode`：`'respect'`（默认，尊重现有编号）或 `'created'`（全部按生成时间重排）
  - `unchanged`：`nextName === name` 的文件，**不产生 rename 调用**
  - `conflicts`：目标名与同目录另一个参与文件的**当前名**相同的情况
  - `needsTempPass`：存在上述冲突时置真，执行时必须先改成临时名再落到最终名

**红灯：**

- `orderName(1, 'a.png')` === `'001_a.png'`；`orderName(7, '001_a.png')` === `'007_a.png'`（前缀被剥离，不叠加）
- `orderName(1000, 'a.png')` === `'1000_a.png'`（超 999 自动扩位）
- 重复执行：对已编号结果再跑一次 `planMediaReorder`，`renames` 为空、`unchanged` 为全部
- `created` 模式：按 `createdAt` 升序；同一 `createdAt` 时按 `updatedAt` 再按名称稳定排序
- `respect` 模式（默认）：全部已编号时按现有编号排序，重复执行零变更；全未编号时按生成时间；混合时已编号的按编号在前、未编号的按时间在后；编号有空洞时收敛为连续
- 时间兜底：`createdAtOf` 返回 `undefined` 时用 `updatedAt`，`timeSource` 为 `'file'`
- 无任何时间信息：排到最后且 `timeSource` 为 `'none'`，与有文件时间的文件相比仍按时间在后（`Infinity` 差值不得被当成「无法比较」）
- 重复编号：`001_a.png` 与 `001_b.png` 按名称稳定排序后收敛为 `001_a.png`、`002_b.png`
- 非媒体文件（`.md`、`.jccanvas`、`.glb`）不出现在 `renames` 里，也不影响编号连续性
- 目录项不出现在 `renames` 里
- 受保护路径被跳过
- 0 个或 1 个媒体文件 → `renames` 为空
- 交换型冲突：文件夹内同时存在 `a.png` 与 `001_a.png` → `needsTempPass` 为真
- 目标名与同目录**非参与文件**同名 → 记入 `conflicts`，不静默覆盖

**绿灯：**

- 上述全部通过，且函数不引用 `Date.now()`、不依赖调用顺序（同一输入两次调用结果相同）

### 同批落地的另外几个文件树媒体动作

- **P0-1 方向键跟随预览**：树里 ↑↓ 移动焦点后，焦点是媒体文件时发 `filetree:focus-media`（只带资源，不做 I/O）；预览面板**只在已经打开媒体预览时**才跟随，其它情况忽略，避免在树里翻文件时把创作面板或编辑区顶掉。
- **P0-3 移动到新建文件夹**：有选择时右键出现「移动到新建文件夹...」，复用 `safePrompt` + `projectFiles.createFolder` + 现有 `planBatch({ kind: 'move' })` / `prepareBatchCanvasLifecycle` / `executeBatch`，不新增批量协议；新文件夹建在原目录下，媒体根目录（`jc-media`）仍拒绝建子目录。
- **成功提示通道**：树原先只有一个 `errorMsg`（红字），而且列表写了 `v-show="!errorMsg"`——任何写进这个通道的文字都会把整棵树藏起来。移动/编号的成功文案因此被当成错误。现在拆出 `statusMsg`（复用现有 `pft-success` 绿色样式，与错误行 `v-else-if` 互斥），成功文案走它；「已编号 x/y 个，随后失败」仍留在 `errorMsg`，因为那确实是失败。
- **目录排序（二次修正）**：第一次只改了 `buildTree`，而 `buildTree` 只处理根目录；子目录的子节点走 `ensureDirectoryLoaded`（展开）和 `refreshDirectory`（刷新），这两条路径**完全没排序**，顺序就是后端给的——桌面端 Rust 按 `file_name()` 字节序排，中文名排在 ASCII 之后，所以中文文件夹永远掉到底部。现在把比较器抽成 `sortTreeChildren()`，三条路径都过它。
  - 同时把整体排序改成**按父逐个排序**：原来的写法把扁平列表整体按 mtime 排，会让深层的子目录排到父目录之前，`nodeMap` 里找不到父节点就静默丢节点。按父排序还保住了「父在前」这个前提。
  - 副作用：任何改动（包括编号改名、移动文件）都会让所在目录在同级里浮到最上面。
- **选中行观感**：`.pft-node.selected` 原先是硬编码 `rgba(213,199,135,0.16)`——那是**橄榄主题 primary `#D5C787` 写死**的，叠到绿色主题的淡绿面板上就是发浑的黄绿。现在改成 `color-mix(in srgb, var(--olive) 18%, var(--paper))` 的不透明主题色，并配 `color: var(--olive)`，与 `memory-model-group button.selected` 同一套写法；`hover` 也改成 `background-color`，不再把 `.pft-node-guides` 的 `background-image` 竖向参考线一起冲掉。
- **文件名被划成文字选中**：行上已经有 `user-select: none`，但 WebView 里从行外起拖仍可能把文件名划成原生选中，而全局 `::selection` 是半透明绿，叠在选中底色上就出现「里面还有一个小亮框」。现在 `.pft-name` 自己声明 `user-select/-webkit-user-select: none`，并在列表 `mouseup` 时清掉落单的选区。
- **编号基础名**：`planMediaReorder` 新增必填 `baseName`（父文件夹名），`orderName(index, folderName, fileName)` 输出 `三位编号_文件夹名.原扩展名`；文件树在算计划**之前**就设好 `mediaReorderFolder`（原先先算计划后设文件夹，顺序是错的）。
- 测试：`projectFileTreeMediaWorkflow.test.ts` 与 `projectFileTreeMediaReorder.test.ts` 为源码合同用例（含「三条加载路径都过 `sortTreeChildren`」「成功文案不得写进 `errorMsg`」两条回归钉子）；`mediaReorder.test.ts` 全量重写成父文件夹名基准（含「重跑零变更」与 created 模式下的交换型冲突）。
