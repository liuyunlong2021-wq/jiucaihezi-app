## 0. 核心决定

产品是一个显式能力工作台，不是持续记忆的通用聊天 Agent。

```text
没有 @
  -> 只发送当前用户消息
  -> 模型直接回答

有 @
  -> 只激活用户选择的能力 Agent
  -> 当前用户消息 + 被选能力的最小上下文发送给模型
  -> 模型输出结构化计划
  -> 程序执行只读动作或副作用
  -> 真实观察回传模型
  -> 模型输出最终内容和结构化操作
  -> 程序执行并生成回执
```

四条不可违反的边界：

1. 无 `@` 不读取历史、不读取 Wiki、不加载 Skill、不提供项目工具。
2. 有 `@` 只提供被选能力；程序不得根据自然语言自动扩权。
3. Skill 负责方法、格式和质量规则；Agent 负责能力协议；Runtime 负责确定性执行。
4. 模型的操作说明必须是可校验的结构化数据，不能依赖自然语言猜测或模型声称“已经完成”。

## 1. 术语与职责

### 1.1 Skill

Skill 是渐进式披露的方法包，不是 Agent，也不拥有文件系统、会话、循环或 Provider。

- 首轮只提供 Skill 的名称和触发描述。
- 用户明确选择具体 Skill 后，程序加载其 `SKILL.md`。
- Skill 的 references、scripts、assets 只在 Skill 规则需要时加载。
- Skill 可以要求某个能力，但不能自动获得用户没有 `@` 选择的能力。

### 1.2 能力 Agent

能力 Agent 是某一类工具的薄协议适配器，不复制 Runtime。

| Agent | 负责的能力 | 不负责的内容 |
| --- | --- | --- |
| `Wiki Agent` | `index.md` 读取、Wiki 事实、ChangePlan、入口、双链、来源、日志、回滚 | Skill 的小说/公司/日记业务规则 |
| `File Agent` | 用户选定文件的读取、写入、编辑、创建、移动 | 项目全盘扫描、Wiki 语义 |
| `Terminal Agent` | 用户确认后的命令计划、执行和结果 | 自动执行未授权命令、长期 Shell 会话 |
| `MCP Agent` | 用户选定 MCP 工具的 schema、调用和真实结果 | 自动选择其他 MCP、伪造外部结果 |
| `Media Agent` | 媒体提示词动作、生成、轮询、结果保存 | 自动改变 Wiki 事实、隐藏失败 |
| `3D Agent` | `.jcscene` 创建和增量修改、场景结果 | 任意项目文件写入、视觉状态作为事实源 |

Agent 只实现以下最小接口语义：

```text
describe()       -> 能力名称、边界、输入/输出 schema
prepare(input)   -> 需要读取的最小资源或可执行计划
execute(plan)    -> 程序执行并返回真实 Observation
finalize(input)  -> 最终回答和后续 ActionPlan
receipt(result)  -> 程序生成确定性回执
```

不为每个 Agent 创建第二套 Provider、SSE、重试器、审批器、文件服务或状态机。

## 2. `@` 路由合同

### 2.1 解析规则

`@` 是唯一能力激活入口，解析由程序完成：

- `@Wiki` 激活 Wiki Agent。
- `@Skill` 不是有效能力；必须是具体 Skill 名称。
- `@MCP` 不是有效能力；必须是具体 MCP 工具或服务器下的明确工具集合。
- `@文件` 必须绑定用户选定的具体文件或文件集合。
- `@媒体`、`@3D`、`@Terminal` 激活对应 Agent。
- 同一任务允许多个具体能力并存，去重后保持用户选择顺序。
- 未识别的 `@` 不得静默降级为全工具；程序返回可操作错误。

### 2.2 上下文最小化

| 连接 | 发送给模型的最小内容 |
| --- | --- |
| 无 `@` | 当前用户消息和用户明确附带的正文附件 |
| `@Wiki` | Wiki 根 `index.md`，后续仅发送 ReadPlan 实际读取页面 |
| `@Skill` | 具体 Skill 的 `SKILL.md`，按需加载引用资源 |
| `@MCP` | 具体 MCP 的名称、工具描述和参数 schema |
| `@文件` | 用户选定文件的路径、类型和实际读取结果 |
| `@媒体` | 可用生成能力、模型参数和已确认素材 |
| `@3D` | 选定场景文件和合法增量操作 schema |
| `@Terminal` | 终端能力边界、待审批命令和执行结果 |

禁止把全 Wiki、全 Skill、全项目文件、全部 MCP 或旧聊天记录作为默认上下文。

## 3. 统一任务协议

### 3.1 传输外壳

所有 Agent 复用同一结构化外壳；每个 Agent 只校验自己的 payload。

```ts
interface TaskEnvelope {
  version: 1
  status: 'needs_observation' | 'ready_to_execute' | 'complete' | 'failed'
  capabilities: string[]
  reads: Array<{
    id: string
    agent: string
    kind: string
    arguments: Record<string, unknown>
  }>
  actions: Array<{
    id: string
    agent: string
    kind: string
    arguments: Record<string, unknown>
    dependsOn?: string[]
    requiresApproval?: boolean
  }>
  observations?: Array<{
    id: string
    readId?: string
    actionId?: string
    agent: string
    ok: boolean
    result?: unknown
    error?: { code: string; message: string }
  }>
  answer?: string
  errors?: Array<{ code: string; message: string; actionId?: string }>
  receipt?: {
    ok: boolean
    completedActionIds: string[]
    failedActionIds: string[]
  }
}
```

约束：

- `needs_observation` 只能包含只读 `reads`，不得执行副作用。
- `ready_to_execute` 的 `actions` 必须通过对应 Agent schema、路径和审批校验。
- `complete` 必须包含 `answer`，不得声称未执行的动作成功。
- `failed` 必须包含真实 `errors` 和已执行范围；部分成功必须通过 `receipt` 明确列出。
- `capabilities` 是程序根据 `@` 解析出的不可扩大集合；模型返回的 Agent 不在集合内时拒绝整份计划。
- `observations` 只能由程序填充，模型不得伪造工具结果、退出码或写入成功状态。
- `dependsOn` 只表示程序执行顺序，不允许形成环。
- 程序按依赖图并发执行互不依赖的只读动作，写入和审批动作串行执行。

### 3.2 模型阶段

默认采用有限的“计划 -> 观察 -> 完成”协议，不采用通用 `while` 工具循环：

1. 第一次模型请求输出 `reads` 和必要的初始 `actions`。
2. 程序执行只读动作，收集真实 Observation；需要审批的动作暂停在计划阶段。
3. 第二次模型请求接收用户任务、Skill 规则和真实 Observation，输出 `answer + actions`。
4. 程序校验并执行 actions，生成回执；不再请求模型确认“是否成功”。

没有外部观察依赖的简单任务可折叠为一次模型请求。只有 Skill 明确声明存在依赖观察时，才允许增加一个新的计划/观察阶段；不得用固定 12、64 或无限轮数替代完成条件。

### 3.3 Wiki 专项映射

Wiki 的既有协议是统一外壳的领域实现，不重写：

```text
WikiReadPlan
  -> reads: wiki_context(action=read)

WikiSynthesisAndChangePlan
  -> answer + wiki action=apply/scaffold
```

Wiki Agent 继续硬保证路径、`index.md`、双链、来源、`log.md`、回滚和写后验证；`hot.md`、`overview.md`、health 和图谱质量规则由具体 Skill 决定是否维护。

## 4. Skill 与 Agent 组合

### 4.1 `@Skill`

只使用具体 Skill。模型收到 Skill 方法后，若 Skill 不要求外部能力，直接按 Skill 输出；若 Skill 要求能力而用户未选择，返回缺少连接，不自动扩权。

### 4.2 `@Wiki + @Skill`

```text
用户任务 + Skill 方法
  -> Wiki Agent 读取 index.md
  -> ReadPlan 选择最少事实页面
  -> 程序读取并返回真实内容
  -> 模型按 Skill 规则生成 answer + WikiChangePlan
  -> Wiki Runtime 一次确定性提交
```

Skill 决定“如何写小说/剧本/日记/制度/提示词”；Wiki Agent 不把这些领域字段写入通用协议。

### 4.3 `@MCP/@媒体/@3D/@Terminal/@文件 + @Skill`

Skill 规定步骤和质量标准，能力 Agent 提供对应动作 schema。示例：

```text
@资料研究Skill + @MCP
  -> MCP 只读查询
  -> 模型依据真实结果回答或生成下一步动作

@小说创作Skill + @Wiki + @媒体
  -> Wiki 提供故事事实
  -> Skill 提供创作规则
  -> Media Agent 生成资产动作
  -> Wiki Agent 保存经确认的正文和提示词
```

Skill 可以声明 `requires: ['mcp', 'wiki']`，程序只检查用户是否显式连接，不替用户连接。

## 5. 多 Agent 组合

多 Agent 组合由程序建立一个动作图，不由 Agent 互相调用，不创建总控大循环。

```text
用户 @Wiki @Skill @MCP
  -> 程序确定三个已选 Agent
  -> 模型得到 Skill + Wiki 入口 + MCP schema
  -> 输出统一 TaskEnvelope
  -> 程序并发只读
  -> 模型得到 Observation
  -> 输出统一 ActionPlan
  -> 程序按 dependsOn 执行
  -> 统一回执
```

组合约束：

- 只有用户显式选择的 Agent 可以出现在 actions 中。
- Agent action 必须带命名空间，禁止同名工具覆盖。
- 互不依赖的读取并发；文件写入、Wiki apply、Terminal、付费媒体动作串行并遵循审批。
- 外部动作成功不等于 Wiki 写入成功；每个 Agent 单独报告状态。
- 任一动作失败时停止其依赖后继，保留已执行结果和恢复信息，不伪造整体成功。
- Wiki 写入仍由 Wiki Runtime 的事务负责，不允许 File Agent 绕过 Wiki apply 修改 Wiki 入口。

## 6. 安全、状态与错误

- 无 `@` 的请求不得携带历史 `conversationTurns`，不得构造项目工具定义。
- 每个任务只保留内存中的计划、Observation 和回执；任务结束立即释放。
- 不读取 `.raw/对话记录`，除非用户明确指定精确路径并选择文件能力。
- 所有路径必须在用户授权项目内；Terminal、移动、回收、覆盖和付费媒体动作遵循现有审批。
- Agent schema、路径、参数、依赖环和工具选择在执行前校验；失败时零执行或按 Agent 事务回滚。
- 程序回执是唯一成功依据，模型文本不能替代执行结果。

## 7. 实施顺序

每个阶段必须先有一条能复现失败的红灯测试，完成实现后才进入下一阶段。阶段门禁失败时停止扩展，不通过增加兼容分支掩盖失败。

### 阶段 1：冻结无 `@` 合同

- 删除普通任务的历史、Wiki、Skill 和工具注入。
- 保留当前用户消息和明确附件正文。
- 红灯测试：无 `@` 不产生项目工具调用，不读取文件，不发送旧对话。
- 门禁：请求快照中没有 `conversationTurns`、Wiki/Skill/MCP/File/Media/3D/Terminal 定义，且只发生一次模型请求。

### 阶段 2：抽取共享任务协议

- 新增最小 `TaskEnvelope`、Agent registry、schema 校验和依赖排序。
- 复用 DirectEngine、审批、重试、取消、指标和平台适配器。
- 不创建第二套 Agent Runtime。
- 门禁：越界路径、未知 Agent、能力扩权、非法依赖环和伪造 `observations/receipt` 均在执行前被拒绝。

### 阶段 3：固化 Wiki Agent 适配

- 将现有 `WikiReadPlan` 和 `WikiSynthesisAndChangePlan` 映射到统一外壳。
- 保持索引优先、精确读取、一次 ChangePlan、入口/双链/来源/日志/回滚合同。
- 删除 Wiki 专属旧循环和自然语言写入判断。
- 门禁：纯查询最多两次模型请求；写入要么正文与所有受影响入口同批成功，要么恢复并返回真实回执。不得重写一套 Wiki Runtime。

### 阶段 4：File Agent

- 先实现选定文件的只读和确定性写入。
- 禁止全盘扫描和绕过 Wiki Runtime 的 Wiki 写入。
- 门禁：只读任务零副作用；写入任务路径、冲突和写后指纹可验证。

### 阶段 5：Terminal Agent

- 先输出命令计划，审批后执行一次。
- 返回 stdout、stderr、退出码和实际执行范围。
- 门禁：未审批命令不执行；取消和超时均有真实回执，不保留隐式 Shell 会话。

### 阶段 6：MCP Agent

- 只暴露用户选中的具体 MCP 工具。
- 统一参数校验、超时、取消、错误和结果回填。
- 门禁：抽象 `@MCP`、未选择工具和 schema 不匹配均不调用外部服务。

### 阶段 7：Media Agent 与 3D Agent

- 复用现有媒体任务 Runtime 和 `.jcscene` Runtime。
- 生成、轮询、保存和展示均返回真实状态。
- 门禁：任务状态、结果路径和失败原因可追溯；不把媒体或 3D 结果自动写入 Wiki。

### 阶段 8：多 Agent 组合

- 支持 `@Wiki + @Skill + @MCP` 等显式组合。
- 用无环 `dependsOn` 执行计划，补齐跨 Agent 结果回填和部分失败回执。
- 不增加全局自主规划、长期会话、Embedding 或 Deep Research。
- 门禁：只并发互不依赖的只读动作；任一失败只阻断其后继，整体结果明确列出已完成和未执行动作。

## 8. 测试与验收

### 8.1 协议测试

- 无 `@`：只发送当前消息，工具集合为空。
- 未知 `@`、抽象 `@Skill`、抽象 `@MCP`：明确报错。
- 具体 Skill：仅加载该 Skill 及按需资源。
- 具体 MCP：只暴露选定工具。
- TaskEnvelope：拒绝未知 Agent、非法 action、路径越界、依赖环和未授权能力。

### 8.2 Agent 测试

- Wiki：入口优先、最小读取、ChangePlan、索引、双链、来源、日志、回滚和验证。
- File：选定文件读写、冲突和写后验证。
- Terminal：审批、退出码、取消和敏感信息脱敏。
- MCP：具体工具路由、超时、失败和结果回填。
- Media：生成、轮询、取消、保存和失败展示。
- 3D：创建、增量修改、路径限制和场景回执。

### 8.3 组合验收

| 场景 | 预期 |
| --- | --- |
| `写一段说明` | 无工具、无历史，直接回答 |
| `@Wiki 查询项目状态` | 入口优先读取，返回真实来源 |
| `@Wiki + 具体 Skill 继续创作` | Skill 方法与 Wiki 事实同时生效 |
| `@MCP 查询并总结` | 只调用选中的 MCP，结果回传模型 |
| `@Wiki + @MCP 查询后写入` | MCP 结果和 Wiki ChangePlan 分离执行 |
| `@Skill + @媒体` | 按 Skill 规则生成媒体，不自动写 Wiki |
| `@Wiki + @Skill + @3D` | Wiki 事实、Skill 规则、3D 动作分别回执 |
| 任一动作失败 | 停止依赖后继，显示真实部分失败，不伪报完成 |

## 9. 删除与禁入项

实施阶段必须以测试先行，确认无调用者后删除：

- 无 `@` 模式下的历史上下文拼接和自动工具注入。
- Wiki Agent 的开放式检索状态机、固定 12/64 轮和关键词写入判断。
- 每个 Agent 自己复制 Provider、Runtime、会话、审批或文件服务。
- 自动扫描全 Wiki、全项目、Raw 或全部 Skill。
- 未经用户选择的能力自动扩权。
- 以模型自然语言“已完成”代替程序执行回执。

## 10. 完成定义

本 TDD 完成必须同时满足：

1. 无 `@` 是真正无上下文、无工具的单次模型请求。
2. 有 `@` 只获得选择的 Agent 和最小上下文。
3. Skill 只提供规则，不引入第二套 Runtime。
4. Wiki Agent 的既有两阶段协议成为统一协议的首个完整实现。
5. File、Terminal、MCP、Media、3D 均能独立执行并返回真实回执。
6. 显式多 Agent 组合能按依赖执行，失败可解释、不可伪成功。
7. 全部 focused 测试、类型检查、Tauri 测试和真实平台验收通过；未执行的平台不得写成已通过。
