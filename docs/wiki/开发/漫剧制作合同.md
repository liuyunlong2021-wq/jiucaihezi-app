## 1. 目标与范围

漫剧制作是韭菜盒子协作漫剧本地工作台中的一条可随时启用的制作路线。用户点击输入框下沿的“漫剧制作”后，产品以 `jc-manju-zhizuo` 作为总入口，在既定 Skill 集合内选择当前任务所需能力。完整原创短剧写作、改编方向和逐集文学剧本已拆至相邻的独立“短剧写作”路线；漫剧制作从已确认剧本继续进行视觉开发、工程台本与模型提示词，也可从一句灵感脑暴用户指定的工程片段。

该入口负责将项目资料整理、改编、风格确定、视觉资产、工程台本和视频提示词衔接起来。用户可从任意阶段接手，也可只做一个局部任务；入口不强迫从第一步重跑，也不因流程顺序自动生成用户未要求的产物。

## 3. 路由优先级与新手起步

漫剧入口保留为独立制作路线，不提供提示词模型选择器、分类模型、评分器或自动制作流水线。开启入口只限定 Skill 工作范围，不执行任务、不创建文件、不提交媒体。短剧文学剧本由独立入口承接；需要工程台本时切回漫剧制作。

按以下顺序处理本轮意图，命中后不再自动挑选其他路线：

1. **明确指定 Skill 或模型**：直接执行指定业务入口。H3 对应 `h3-prompt-writing`，Seedance／SD2.5 对应 `jc-seedance`；本轮指定优先于历史。
2. **明确续改已有产物**：使用该产物对应的 Skill 和原格式；除非用户要求转换，不因默认 H3 改写 Seedance 产物。新任务不继承上次模型选择。
3. **明确指定交付物**：自然语言“整理项目资料”“写短剧”“设计角色”“三格参考图”“设计场景／道具”“定画风”“工程台本”等视为指定对应业务入口，用户不必记住 Skill 名。明确脑暴、给发展选项、逐句／逐动作选择，或要工程脚本却只有灵感、画面与零散节点时进入 `jc-manju-brainstorm`；已有完整剧本只做工程转换直接使用 `jc-gongchengjuben`。
4. **明确求起步引导**：只有“不知道从哪开始”“第一次做”“带我做”等明确请求才启用引导，不能因消息短或材料少推断用户是新手。
5. **其他未明确指定的创作请求**：默认用 `h3-prompt-writing` 生成 MiniMax H3 视频提示词，不再询问默认模型。

必要输入缺失时只问实质影响当前交付的缺项；其余采用目标 Skill 默认规则并标明必要假设。Skill、模型或交付物存在实质冲突时只澄清冲突，不擅自覆盖用户指定。明确要求多个任务时才按必要依赖执行多个 Skill，不自动补跑其他制作阶段。

新手先复用消息与附件；不知道现有材料时只问：“你手上已经有故事、小说或剧本了吗？没有的话，说一句你想拍的故事也可以。”按材料及目标推荐当前一步：一句想法且想试做片段 → H3；小说／长故事且要分集 → 项目资料；梗概且要短剧文学剧本 → 切到“短剧写作”；已有剧本且需视觉方向 → `jc-film-style`；剧本与方向齐备且要逐镜安排 → 工程台本；已有镜头／台本且要视频提示词 → 默认 H3，明确 Seedance 则用 Seedance。

只问“该从哪开始”时给一个建议及简短理由，不执行制作；明确“带我做”且材料足够时执行推荐的第一步。引导不授权整套制作或付费生成。对外使用交付物名称，必要时完成后给一个下一步建议，不自动执行、不每轮重复教学。

## 3.1 阶段依赖与可接续性

以下仅说明资料依赖，不是路由器的自动执行顺序。只处理用户要求的任务：

1. **沉淀项目资料**：建立故事梗概、分集梗概、故事背景、世界规则文档；每位人物各有独立小传文档，关系写入相关人物小传。
2. **确定创作方向**：通过 `jc-film-style` 确认全项目共同方向，后续资产、表演、工程台本和提示词按已确认内容执行。
3. **接收短剧文学剧本或当前脑暴片段**：小说改编方向和逐集剧本在“短剧写作”路线完成；漫剧制作复用用户已确认的文学剧本。完整文学创作仍切换路线处理，改编稿与原作资料分开，已确认的分集变化再回写分集梗概；用户指定的灵感工程片段可在本路线逐节拍创作，无需另建完整文学剧本。
4. **并行准备资产与工程台本**：角色、场景、道具资产可并行；工程台本以剧本、分集任务、人物资料、世界规则和创作方向为依据，不必等待资产图完成。资产参考图后来补入时，只用来校准可见外观、空间和道具，不擅自改写已确认剧情。
5. **按指定范围制作视频提示词**：只处理用户指定的镜头／片段，复用已确认资料。输出对应模型格式，不把不同模型格式拼成一条提示词。

如果用户已有某阶段产物，从该阶段继续；无需为了流程完整重做已有成果。资料不足以完成当前交付物时，只询问会实质影响该交付物的缺项。

## 3.2 灵感与逐节拍脑暴（2026-10-13）

- `jc-manju-brainstorm` 贯穿当前授权片段的风格、资产和工程台本，以用户要求、已确认项目资料与前后节拍状态为依据。它不接管完整短剧／分集文学创作，也不改变视频模型默认路由。
- 没有方向时使用 Film style 的轻量选向，给适合当前画面的候选、亮点、代价与推荐；允许自填、混搭、暂用推荐与跳过。角色／场景可沿用、脑暴或暂用占位，不强制生图、建库或补齐完整总纲。
- 每个未定对白、动作与攻防节拍都有具体候选：台词／可见行动、策略／动作逻辑及下一步影响。支持逐句、整组、候选整场、自由输入与混搭；用户已明确写定的节点直接复用，仍可按要求展开表演或镜头选择。
- 用户选定后即时落笔并给下一个选择点。只有“按推荐继续／直接完整写”等明确委托才允许在指定范围代选；无回复、超时与跳过资产不视为剧情选择。脑暴中的字母、混搭、继续属于当前任务续做，不落入 H3 默认。
- 招式呈现与对手反馈／结果分别选择，动作沿用工程技能的因果与连续性规则。已锁定胜负时在其范围发散；改变结果明确作为修订提案。用户原句默认逐字保留，新原创候选选定后作为工程化依据。
- 中途插入角色／场景／道具时保留当前节拍与状态，选定后按请求交接专业技能，再回到原位置。文字方案选定与实际参考图选定分别记录，不用图片未显示内容证明隐藏事实。
- 最终工程稿沿用既有影像基调、镜头格式与连续时间码，候选不混入正式稿。候选整场与局部草稿不自动按正式产物归档；正式产物仍使用共享 Wiki 工具。用户明确保存过程时，按原生 Wiki 普通写入规则保存在独立创作记录，区分已选、暂定、候选；不新增正式产物类型或自动建库。
- 工程台本默认“一个镜头，一个核心戏剧任务”，该任务的直接子动作与台词可同镜，不按动词数量拆镜。普通回应镜头只写主体新增动作与台词表演提示，不补既有状态、无依据反应或收尾。潜台词和因果链用于内部导演判断，细节按实际执行需要选用，不配齐表情、手势、身体、次级运动和余韵。
- 一个编号对应一次连续拍摄，不能有镜内反打、插入特写或剪辑视角跳切；新主要主体、新独立任务及实际剪辑另起编号。长时间码、跟移和同一说话人不构成合镜理由；只有用户明确要求或选定多任务长镜头方案才允许多个独立任务连续编排，仍无隐藏剪辑。脑暴预览及专项统一遵守；锁定时间不足时报告具体缺口并给方案，不自行调整；未锁定预算可按自然容量拆镜重分。
- 脑暴候选可以用镜头组组织；选定后的工程预览和正式稿一律逐镜写出独立编号、时间码、规格及内容，编号跨组连续。组名不替代镜头，禁止用合并编号或组级综合段落代替组内多镜。
- 镜头内部继承上下文，正文直接写主体的新动作与台词，不重新铺陈已知站位、距离、前景关系和上一句刺激。单人覆盖与过肩只写主体及可见道具，不添加另一人不可见的身体、动作、视线或接触位置；朝向按当前画面和实际站位表达。必须展示的实际接触另用部位可见的交互特写或多人镜头，保留原稿接触事实。
- 工程写作先确定每镜主体、类型、取景部位及入镜物件，再从内部可见清单写正文，不能将整场互动直接转述。单人画面及表演括号不带画外角色名字、代称、所有格或物件来源；物件入镜不代表递物者／持物人的手入镜，角色能看到的画外物件也不自动入镜。原台词不受叙述范围限制。默认匿名过肩规格减少画外身份引入；已锁定的具名规格保留，但不许可正文扩大单人范围。
- 2026-10-13 一致性审计已合并正文重复约束，专项方法不再强制多阶段表演、拔刀结构展示、具名术法多镜准备或复杂运镜。全景与固定镜头数量为风格参考，不强凑、不删除必要镜头；完整审计与静态验证边界见 [[开发/工程剧本Skill一致性审计-2026-10-13]]。
- 每轮工程任务重新读取现行工程规则，不将历史副本和旧稿范例作为最新合同。交付前逐镜逐句审查：确定主体和景别可见范围，检查句内每项动作及执行者，包括“看见对方做了……”的嵌套动作，不只看整句主语；直接从主体新动作起笔，不以交代行动原因重播上下文。删除自行添加的画外表演、不可见肢体与重复收尾；原稿必需动作移到可见镜头，随后回查台词动作和时间。仅交付修订稿，不能以“自检通过”代替实际修订；这是模型自审，非程序级语义拦截。
- 新技能正文与三份按需参考随内置清单打包；工程技能增加脑暴输入交接，Film style 保留完整总纲合同并增加片段轻量选向。实现验证见 [[hot]] 与 [[来源索引]]，真实 App 模型及安装包验收单独记录。

## 4. 项目资料与一致性

- 项目资料至少分别保存：故事梗概、分集梗概、故事背景、世界规则；人物小传按人物拆分为独立文档，并记录人物关系。
- 分集梗概逐集说明核心目标／戏剧任务及主要因果，供改编、工程台本与表演使用。不得用阶段大纲或重复的关键戏摘要取代它。
- 原作事实、推断、改编建议和用户确认的新设定须能区分；暂定内容标注为建议，不能伪装成原作事实。
- 后续内容发现冲突时优先指出冲突来源和受影响产物；依据用户本轮决定修订相关文档，不静默覆盖其他已确认内容。
- 长期项目可维护简短 `制作进度.md`，记录阶段、产物路径、已确认方向、镜头模型选择和待办；不得复制整份原作或重复保存整份提示词。

## 5. 视频模型与提示词选择

- 视频模型在提示词阶段按用户本轮指定的镜头／片段选择。一个项目、单集或单轮请求可以混用 MiniMax H3 和 Seedance；已选择一种模型不锁定后续镜头。
- 明确点名的业务 Skill 或模型优先于历史。MiniMax H3 走 `h3-prompt-writing`；Seedance 2.5／SD2.5 走 `jc-seedance`。没有提示词模型选择器；普通聊天模型选择和影音面板实际型号选择保持原样。
- 按第 3 节优先级路由。续改原产物保留原 Skill 与格式；明确其他交付物或新手求起步不能被 H3 默认覆盖。新的未指定创作任务默认 `h3-prompt-writing`，不继承上次模型，不推荐或锁定全片模型。
- 对话只保留漫剧启用状态及既有 Skill 选择；旧 `videoModel` 字段可留在历史数据中，但不恢复、不传递、不参与路由。不新增当前制作阶段或项目默认模型状态。
- 同一请求混合模型时，按镜头范围分别交付并标明目标模型；切换时从同一工程台本与资产重写所选范围，保留其他模型已完成的提示词，不重做前序资料、风格、资产或工程台本。
- 时间戳遵循目标 Skill 格式和用户习惯：Seedance 可以有或没有，用户明确要求优先；H3 遵循 H3 自身格式。全片时间码与片段内部时间码不得混淆或回写覆盖。
- 每次提交前核对提示词 Skill、镜头范围与实际选定型号属于同一模型系列；不同模型格式不可互换。

## 6. 提示词交付边界（2026-10-21）

漫剧制作只交付文字、资料与提示词，不调用图片、视频、音频生成或任务提交工具；实际生成由用户在独立创作面板操作。已有图片可读取、分析并写修正提示词，不生成、等待、重绘或伪造任务号与验收结果。该边界属于路线编排，不删除桌面现有创作面板和媒体能力。

## 6.1 漫剧制作插件运行时合同（2026-10-08 更新）

### 责任与依赖

- 插件负责当前 Agent 的内置 Skill 登记、产物保存工具登记、启动确认与释放；路由和制作规则仍由第 2–6 节及各 Skill 正文定义。
- 复用 `pinManjuSkills()`、官方 Cordis 插件、SkillRegistry 和既有发送前绑定入口。在当前 `rec.handle.agent.ctx` 下挂载子插件，明确声明 `inject: ['skills', 'tools', 'fs', 'sandboxPolicy']`，在自己的 `apply(ctx)` 中登记内置 Skill 和 Agent 级保存工具。
- Agent scope 来自官方 AgentLoop，其依赖没有 `skills`；SDK Server 声明 `skills` 不改变 Agent scope 的依赖。不得继续直接访问 `agent.ctx.skills`，也不为此给官方 AgentLoop 增加产品专属依赖。
- `ctx.get('skills')` 是官方测试使用的合法服务查询 API，可用于诊断；本产品登记和释放由上述子插件承载。沿用现有内存登记，不新增 Provider、插件加载框架或第二套登记账本。

### 启动与发送顺序

1. 根据本轮对话状态确定是否启用及点名集合；普通对话不挂载漫剧插件。
2. 读回 `manju-route.json` 和清单内全部内置包，验证路由器身份、包身份、清单及同时点名的兼容性；全部准备成功后才开始登记。
3. 在当前 Agent scope 下挂载子插件，登记确切内置版本；等待启动，并确认 `apply` 已执行且全部登记已完成。仅有 `await ctx.plugin(...)` 返回不算成功：缺少服务时插件可能稳定在未激活状态。
4. 接续既有点名 Skill 工具限制；Skill、保存工具、限制和当前 Agent 有效性均确认后，才记录已绑定状态并进入官方 Skill 注入和模型请求链。

内置正文登记到内存不等于全部注入模型上下文；继续只注入点名入口，其余正文和资源按现有路线按需读取。点击按钮和插件登记均不生成产物或提交媒体。

### 作用域与生命周期

- 子插件注册上下文继承当前 Agent 的 scope，只进入该 Agent 层；查询使用当前 Agent 作为 `scope`。内置版本覆盖外层同名项目／个人版本，不修改原文件、全局目录或其他独立 Agent 的查询结果。
- 一次有效绑定保留一个子插件句柄；重复发送且绑定未变时复用。绑定随实际 Agent 实例变化：恢复 Session 得到新 Agent 后重新登记，不能仅凭旧 Session ID 或点名集合复用旧绑定。
- 退出漫剧、改变绑定或替换 Agent 时，在下一次发送前释放旧绑定；Agent 销毁时由父作用域释放子插件。按钮导航状态保存与运行时发送前释放的时机应明确区分。
- 子插件句柄是内置登记的统一释放入口，替代逐 Skill 的产品自建释放数组；既有工具限制仍沿用现有释放机制。组合清理即使其中一个释放失败，也必须尝试另一个，避免遗留工具掩码或 Skill 登记；已成功绑定的清理允许重复调用。
- 启动抛错、部分登记、工具限制失败或异步准备期间 Agent 失效时，显式释放子插件并回滚本次限制，不留半套绑定或成功缓存。保留插件句柄后再等待启动，以便启动失败时仍可清理。

### 失败与兼容

- 缺少 `skills` 服务、未实际启动、包校验或登记／限制失败，均在模型请求前明确报错，保留原因并标明阶段；不得吞错后按普通对话继续，不得显示绑定成功。
- 失败不自动关闭用户的漫剧选择；重试重新执行准备与启动，不能命中失败绑定。沿用既有失败轮次展示，不新增失败消息存储格式。
- 白名单、内置版本优先、普通 Skill 选择、渐进读取、文件能力和媒体权限按原合同执行，不恢复旧漫剧工作台产品壳。
- DSH 升级须回归依赖声明、子插件 scope 继承、启动确认与释放。修改限于产品适配及必要 SDK 接缝，不扩张成 AgentLoop 或 SkillRegistry 私有实现。

## 6.2 漫剧产物与文件树联动合同（2026-10-08）

### 保存时机与范围

- 点击漫剧入口、读取 Skill、讨论方向或提供起步建议均不创建文件。完成用户明确要求的正式产物后，由 Agent scope 内原生 Wiki 插件提供的 `wiki_save_artifact` 按共享映射保存；用户说“只在对话里”或“不要保存”时不调用工具。小说入口使用同一个工具和目录映射。
- 工具只接收产物类型、正文、集数、实体名称、模型与片段等结构化字段，不接收模型任意路径。工具只把文件写到当前 DSH Session 的项目 `cwd` 下，使用 Harness `fs`、`sandboxPolicy`，并校验目标仍位于该项目内。该工具不启用通用 `@文件`、终端或其他全项目写入能力。
- 运行时路由仅在 Desktop 的漫剧 Agent scope 中挂载；Web 不恢复记忆工作台，Mobile 控制器目标不变。文件树收到保存回执后刷新、选中并打开对应 Markdown 文件。
- 保存源文件不自动复制附件或媒体到 `原始材料/` 或 `.raw/`；媒体生成仍遵循 §6 的明确提交边界。

### 根目录与布局

- 漫剧与小说共用 `public/skills/wiki-artifacts.json` 的根选择及标记合同。唯一有效根目录直接复用；双根时停止写入并说明冲突；无有效根时首次实际归档才创建 `wiki/`。本仓开发知识库通过 `docs/wiki/CLAUDE.md` 的签名排除，不会被当作作品资料库。未知但已有内容的 `wiki/` 不被当成空库。
- 首次实际保存时以不覆盖方式建立根索引、`制作进度.md` 和共享目录索引；不创建空白业务文档。实体、作品或集目录只在对应产物保存时创建。用户现有有效 Wiki 不迁移、不复制。
- 固定结构与产物映射如下：

### 冲突与回执

- `create` 为默认写入模式，遇到同路径文件就报告冲突、不覆盖。用户明确要求修订已有产物时，先读取原文、合并完整新版，再以版本保护的 `update` 替换；同一实体档案需要新增独立章节时使用 `append`，不改写旧章节。
- 主产物写入后必须读回核对。索引或小说章节确认记录转换失败时保留已保存正文并在工具结果中报告具体警告；成功回执返回项目相对路径与创建／更新／未变状态。
- `wiki_save_artifact` 在正文读回成功后返回路径与 `created`／`updated`／`unchanged` 状态。索引或小说确认记录后续步骤失败时标记 `saved_with_warnings`，列出真实失败路径，正文保留并可幂等重试。
- 只在工具返回 `saved` 或 `saved_with_warnings` 且回执路径通过项目内 Markdown 检查后，通过 `project-filetree:locate` 刷新、选中并打开对应文件。文件树仅响应同一个项目的回执，不定位到已切换的其他项目。

Wiki 现为三个创作入口共用的原生能力，负责同一根 Wiki 索引与归档规则，不再依赖选择 `wiki-memory` Skill。业务 Skill 继续提供创作正文和产物元数据；共享工具随项目 Agent 注册，不随路线切换消失。保存以真实工具回执为准；独立 `present` 只声明文件交付，不能冒充归档或用户确认。迁移与验收见 [[开发/Wiki原生能力与独立成果交付TDD-2026-10-21]]。

## 7. 后续升级的兼容规则

后续改动应先说明它属于入口、路由清单、Skill 合同、阶段依赖、偏好持久化还是媒体提交链路，并沿该边界修改：

- 新增或移除 Skill：同步更新 `public/skills/manju-route.json`、内置资源／注册范围、路由器引用、对应测试和本合同；退出漫剧路线时仍须释放本路线的 Skill 绑定，不得改写个人同名 Skill。
- 更换模型：新增或调整末端提示词 Skill 和相应型号映射，不改变共同资料、风格、资产与工程台本阶段；旧型号是否仍支持应有清楚的兼容与迁移说明。
- 更改默认模型：只改变新的未指定创作任务的后备入口，不能覆盖本轮指定、已有产物续改、明确交付物或新手起步，也不能强制重做已完成片段。
- 更改媒体提交：保留明确用户触发、既有权限、实际 schema 和提交回执语义；不能把“不等待”悄悄改成轮询或后台跟踪。
- 修改已验证的前序 Skill：先读其源 Skill 和对应回归合同，局部变更并说明行为差异；不要为方便路由器而无关重写其成熟规则。
- 修改插件绑定：按第 6.1 节维护依赖、启动、隔离与释放，补真实上下文和 SDK 发送链回归；旧作用域用例通过不能作为已修复证据。
- 每次升级都更新本合同的现行结论、TDD／测试证据和未验收边界；仅有设计或本地自动测试时，不得写成真实模型、跨平台或生产验收通过。
