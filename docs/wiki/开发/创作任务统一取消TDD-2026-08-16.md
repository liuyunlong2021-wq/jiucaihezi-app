# 创作任务统一取消 TDD

> 状态：已实施（自动验证通过，真实平台待验收）
> 日期：2026-08-16
> 范围：创作面板、对话媒体任务、统一媒体任务 Store、Web/Desktop 请求与轮询

## 1. 目标

1. 图片、视频、音频、3D 和文本媒体任务在 APP 接受生成结果之前，可从创作任务历史和对话任务气泡执行同一个“取消”动作。
2. 取消后 APP 立即停止等待、后续轮询、结果落盘和画布回写；迟到的成功或失败响应不得覆盖 `cancelled`。
3. 能确定请求尚未发出时阻止提交；请求已经发出但尚未取得任务 ID 时，只能标记为计费未知；取得任务 ID 后，只有上游明确确认取消才可显示“上游取消成功”。
4. 取消语义不猜测扣费结果，不把“停止本地等待”伪装成“上游已取消”。

不新建第二套任务系统，不为不同模型分别实现取消按钮，不因取消自动重试或重新生成。

## 2. 已确认现状与根因

- `mediaTaskStore.cancelTask()` 已是共享入口，但当前只把任务状态改为 `cancelled` 并持久化，没有中断正在执行的提交或 `pollTask()`。
- 对话任务气泡在 `pending/running` 时已有取消按钮；创作面板任务历史只展示进度，没有取消入口。
- `_executeTask()` 的计时器会在状态变为 `cancelled` 后停止更新，迟到结果也有取消保护，但底层请求和轮询仍会继续占用网络与服务资源。
- `pollTask()` 的 10 秒等待和 GET 请求没有接收外部 `AbortSignal`，因此用户取消后仍可继续请求直到成功、失败或超时。
- Web 原生 `fetch` 可响应 `AbortSignal`；Desktop 非流式请求通过 Tauri `http_request` 执行，现有 IPC 没有取消命令。前端可以立即停止等待和后续处理，但不能声称已经撤回一个可能到达服务器的 Rust HTTP 请求。
- 当前 KIK 适配器没有上游取消路由。KIK、NewAPI 或其他渠道是否支持任务取消，必须以各自官方接口和实际响应为准。

## 3. 产品合同

### 3.1 可取消范围

- `pending`、`running` 且生成结果尚未被 APP 接受：显示取消按钮并允许取消。
- 生成结果已被 APP 接受、正在保存到项目：立即隐藏取消按钮；任务保存完成后才进入 `success`。
- `success`、`failed`、`cancelled`：不显示取消按钮。
- 图片、视频、音频、3D、文本以及 `chat/creation` 两种来源共用相同规则。
- 同一任务重复点击取消必须幂等，不重复发事件、不重复请求上游。
- `pending` 不能单独证明任务尚未提交；只有本次运行时明确知道执行器尚未启动，才能显示“未提交”。

### 3.2 取消阶段与显示文案

| 取消时刻 | APP 行为 | 任务文案 | 计费表述 |
| --- | --- | --- | --- |
| 执行器尚未开始 | 不调用提交接口 | `已取消（未提交）` | 可确认本次请求未由 APP 发出 |
| 提交请求已开始、尚无任务 ID | 立即停止本地等待；Web 中断 fetch，Desktop 忽略迟到响应 | `已停止等待（上游可能已接收）` | `是否计费以上游账单为准` |
| 已取得任务 ID、没有已确认的上游取消能力 | 停止轮询和结果写入 | `已停止跟踪（上游可能继续生成）` | `是否计费以上游账单为准` |
| 上游取消接口明确返回成功 | 停止轮询和结果写入 | `上游取消成功` | 仍以真实账单为准，不承诺退款 |

不得仅凭 `upstreamTaskId` 缺失断言“未提交”：请求可能已到达上游但响应尚未返回。不得仅凭任务失败或取消断言“未扣费”。

### 3.3 交互合同

- 创作任务历史与对话任务气泡均使用图标取消按钮，标题为 `取消任务`，不新增确认弹窗。
- 点击后按钮立即消失，任务进入 `cancelled`，进度条停止；用户不需要等待网络响应才能关闭面板或继续操作。
- 已取消任务保留在历史中，用对应阶段文案说明结果；仍可按既有规则重新生成，但取消本身不自动重试。
- 成功、失败和已取消的创作任务只要保留 `planSnapshot`，都显示“重新生成”；点击后只回填模型、参数和提示词，不自动提交。
- 取消不得删除已存在的项目文件、远程结果或历史记录。

## 4. 最小技术设计

### 4.1 Store 继续作为唯一所有者

- 复用 `mediaTaskStore.cancelTask(taskId)`，不增加面板级取消状态。
- Store 维护运行时 `AbortController` 映射，按任务 ID 注册；该映射不持久化。
- Store 以纯运行时集合区分“执行器尚未启动”和“结果已被接受、正在保存”；两者都不写入任务历史。
- `cancelTask()` 只处理可取消任务：中断控制器、标记 `cancelled`、停止画布写入、等待持久化并发送一次 `media-task-settled`。
- 一旦结果 URL 或文本已返回，项目保存继续完成，不尝试撤销已经进入底层的原子文件写入，也不增加删除补丁。
- `_executeTask()` 在 `finally` 清理控制器、活动任务 ID 和计时器；任何 catch 或迟到结果发现任务已取消时直接退出，不改成 `failed/pending/success`。

### 4.2 一条信号贯穿提交与轮询

- `executeCreationSubmitRequest()` 接收可选 `AbortSignal`，向现有图片、视频、音频、本机 ComfyUI 和 RunningHub 路径透传。
- `apiCall()`、`apiCallMultipart()`、`apiCallBinary()` 与 `pollTask()` 接收同一可选信号，同时保留现有超时；取消与超时必须可区分。
- `pollTask()` 的间隔等待必须可中断；取消后不得再发下一次 GET。
- Abort 只产生 `cancelled`，不得进入现有网络失败恢复逻辑，也不得显示“重启后将继续恢复”。
- 对遗留的非 Creation 执行分支也传入同一信号，确保共享 Store 的任务行为一致；不复制另一套轮询器。

### 4.3 Desktop 边界

- 第一验收目标是：用户取消后 APP 立即结束等待，停止后续轮询、保存、画布写回和 UI 计时。
- 当前 Tauri `http_request` 的单次在途请求可能继续到自身超时；迟到响应必须被丢弃。这种情况使用“上游可能已接收”文案。
- 不为本次需求立即增加 Rust 请求注册表或新的依赖。只有实测证明在途 Desktop 请求造成显著资源问题，才单独设计可撤销的 Tauri HTTP command。

### 4.4 上游取消边界

- 本阶段不猜测或伪造 KIK/NewAPI/RunningHub 的取消 URL。
- 只有某渠道有已验证的官方取消接口，且能明确返回取消成功时，才在对应适配器增加上游取消；未支持的渠道仍统一执行“停止跟踪”。
- 上游取消属于可选增强，不影响所有任务拥有本地取消按钮这一基础合同。

## 5. TDD 验收

### 5.1 红灯测试

1. Store：执行器正在等待时调用 `cancelTask()`，现有实现只改状态，执行器未收到中断信号。
2. Poller：轮询间隔中取消，现有实现仍会发下一次 GET。
3. 迟到响应：任务取消后执行器返回成功，必须保持 `cancelled`，不得保存结果或发送完成事件。
4. 恢复逻辑：取消导致的 Abort 不得被写成 `pending` 并在重启后恢复轮询。
5. 创作历史：`pending/running` 任务当前没有取消按钮；终态任务不得出现取消按钮。
6. 对话气泡：继续调用共享 `cancelTask()`，不得建立组件私有取消逻辑。

### 5.2 绿灯测试

1. 所有媒体类型和两种来源的活动任务均可取消；成功、失败、已取消任务不可取消。
2. 执行前取消时提交执行器调用次数为 `0`，文案为 `已取消（未提交）`。
3. 提交中取消会触发一次 Abort，任务立即结束为 `cancelled`；迟到响应不改变状态、不写文件、不写画布。
4. 轮询中取消后等待立即结束，取消点之后轮询请求数不再增加。
5. 取消持久化后刷新页面仍为 `cancelled`，不会进入 `_resumePolling()`。
6. 创作历史和对话气泡按钮都只调用 `mediaTaskStore.cancelTask(task.id)`；重复取消无副作用。
7. 现有成功、失败、恢复轮询、重新生成和媒体保存测试保持通过。
8. 已提交但回到 `pending` 的任务不得显示“已取消（未提交）”；结果保存期间 `cancelTask()` 返回 `false`，且最终结果正常落盘。
9. `cancelTask()` 返回前取消状态已经持久化；对话气泡分别显示文本成功与准确的取消阶段文案。
10. 成功、失败、已取消任务的“重新生成”都只回填，不自动调用提交接口。

### 5.3 真实平台验收

1. Web：图片、视频各测试一次提交中取消和轮询中取消，Network 面板不再出现后续轮询，任务保持已取消。
2. Desktop：图片、视频各取消一次，界面立即停止；在途 Rust 请求即使迟到返回，也不得落盘或改写任务状态。
3. KIK：取得任务 ID 后取消，APP 显示 `已停止跟踪（上游可能继续生成）`；后台账单与上游任务记录单独核对，不把本地状态写成扣费结论。
4. 对话气泡和创作历史对同一任务显示一致状态，任一入口取消后另一入口立即同步。

## 7. 禁入边界

- 不承诺“点击取消一定不扣费”或“取消一定退款”。
- 不把 Abort、用户取消和网络错误混成同一失败状态。
- 不在每个模型定义中增加取消开关，不为每个面板复制控制器。
- 不因用户取消删除已有文件、历史任务或远程结果。
- 不猜测上游取消接口，不修改 NewAPI 源码来伪造取消成功。
- 不让已取消任务在刷新后恢复轮询，也不让迟到响应重新激活任务。
