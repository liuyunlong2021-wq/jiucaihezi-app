# 短剧改编收尾收敛与漫剧风格交接TDD

> 2026-10-28。状态：**源码已实施，定向回归通过；真实界面点击与真实模型回合未验收**。两件事合并为一份改动，因为它们都在「短剧改编 → 漫剧全自动」这一段链路上：①收尾回合产物已达标，却因进度被标 blocked 而暂停整批；②漫剧全自动因缺 `项目风格/影片比例与风格.md` 启动不了，而短剧路线没有生产它的权限。现象来自用户实测（塔防—晨曦树精项目第 1 批收尾、已出 20 集，以及「开始全自动成片」确认卡）。

## 1. 现象

### 1.1 收尾暂停但产物已完成

- 程序把状态标成 `已暂停 · 第1批 · 收尾 · 已出20集`，暂停原因写着「收尾资料已完成；运行时拒绝推进至 complete……故保留 materials 阶段」。
- 同一回合里，分集梗概已覆盖第 1–20 集、五份人物小传的造型表起始行已回填集号，即**收尾产物全部落盘**。
- 进度文件 `改编方案/执行进度.json` 停在 `materials` + `blocked`。

### 1.2 全自动成片卡在「未确认比例」

- `ManjuAutoPanel.vue` 显示红字「项目风格里还没有确认影片比例，请先确认比例与风格。」，「开始全自动」按钮禁用。
- 再往下没有入口：用户无法在卡上或菜单里补这一步。

## 2. 根因

### 2.1 状态机只允许逐级推进，删减式改编没有级可走

- `src-tauri/resources/deepseek-harness/manju-wiki.mjs:1741`：`短剧流水线不能跳过前置阶段`，要求 `previous.stage ∈ {stage-1, stage}`。
- 但 `public/skills/jc-duanju-pipeline/SKILL.md` 的进度合同写明：**删减式改编由程序按标注组装，`scheme`／`cuts`／`writing` 不需要模型保存**。
- 删减式路线也不产出 `改编方案/分集规划.md`，所以连逐级补 `scheme`（`manju-wiki.mjs:1795` 要求它）都补不上。
- 结果：`materials` 之后没有合法去处，`complete` 永远到不了。程序里也没有任何自动推进阶段的代码（全仓搜不到程序写 `cuts`／`writing`／`complete`）。

### 2.2 运行器把 blocked 判在 done 之前

`src/runtime/duanjuAuto/autoRunner.ts`：

```ts
const progress = await deps.readProgress()
if (progress?.status === 'blocked') blocked = `${step.label}：${progress.reason}`
else done = await step.done()
```

`blocked` 优先，且命中后不再看 `done()`。于是「梗概已覆盖全部集号」这个真正的完成条件被跳过，整批暂停。模型是在如实报告状态机拒绝，运行器却把它当成收尾失败。

### 2.3 比例与风格没有任何生产入口

- `src/composables/useManjuAuto.ts:127-129`：`ratio` 只从 `项目风格/影片比例与风格.md` 用 `/(\d+)\s*[:：]\s*(\d+)/` 提取；文件不存在或无数字比例即判未确认。
- 该文件的唯一生产 Skill 是 `jc-film-style`（`public/skills/jc-film-style/SKILL.md:11`），它只在 `manju` 白名单里，`short-drama` 白名单没有；`jc-duanju-pipeline` 的全自动指令也没有任何一步要求写风格。
- `docs/wiki/开发/短剧改编全自动与漫剧衔接TDD-2026-10-27.md` 的「漫剧衔接」只做了剧本路径扫描，未涉及风格与比例。

## 3. 方案

三处改动都取最小面，不新增开关、不改产物格式。

| 编号 | 文件 | 改动 | 理由 |
| --- | --- | --- | --- |
| A | `manju-wiki.mjs` | 新增 `annotationsComplete()`：读 `改编方案/分集清单.json`，当已组装出集且 `adapted` 覆盖 `1..总集数` 时，允许 `complete` 从 `materials`／`scheme`／`cuts`／`writing` 直接进入 | 删减式改编的这些阶段由程序组装，模型无产物可登记；判定基于已有事实文件，不新造状态 |
| B | `autoRunner.ts` | 判定改为 `done` 优先：先算 `step.done()`，未达标才因 `blocked` 暂停 | 产物达标不该被状态字段拖住；`blocked` 仍能在真正缺产物时暂停 |
| C | `ManjuAutoPanel.vue`、`useManjuAuto.ts`、`MemoryWorkbench.vue` | 缺比例时提供「去确认比例与风格」按钮：发一条 `jc-film-style` 指令保存 `film_style`，回合结束后重跑 `prepare()` 刷新确认卡 | 补入口而不猜配置；比例决定后续所有生图/生视频，必须用户确认，不填默认值 |

不做的：

- 不为缺比例自动填 `16:9`（猜测当配置）。
- 不改移动端（`MobileManjuAutoPanel.vue`）：移动端 App 已冻结。
- 不改 `scheme` 阶段要求 `分集规划.md` 的既有校验：手动旧流程仍需逐级推进。

## 5. 验收边界

- 自动化只证明判定顺序与放行条件正确；**真实模型是否在收尾回合顺手保存 `blocked`、`jc-film-style` 生成的风格文档是否带数字比例，仍需真实回合验收**。
- 已完成的第 1 批不需要重跑：`执行进度.json` 里的 `blocked` 是历史记录，改动只影响后续回合的暂停判定。

## 6. 回滚

三处改动互相独立，可分别回退；A、B 只改判定，不动任何 Wiki 产物格式。

## 7. 第二轮实测：真正的断点在文件列表上限

用户实测「分集剧本就在 `E:\1028全自动教程/wiki/项目资料/分集剧本`」，但确认卡仍报「还没有分集剧本」，切到全自动成片时模型也报「流水线检查确认没有可恢复的集进度」。据此写探针直接复刻 `dev_list_files` 的遍历语义，在真实项目上取证：

```
项目文件总数(实际): 1010
list() 返回条目数: 1000 其中文件: 951 目录: 49
前 1000 条里匹配到分集剧本: 0 集
风格文档在列表里: false
列表里最深的 5 条: wiki/资产/人群/index.md … wiki/资产/道具/index.md
```

根因：`dev_list_files` 的 `max_entries` 被限制在 1000，**目录也占一条额度**，且按目录名深度优先。`wiki/资产` 排在 `wiki/项目资料`、`wiki/项目风格`、`wiki/制作流水线` 之前，资产目录一多就把额度用完，后面三类文件全部丢失。项目文件数正好 1010，已经在临界线上。

因此同一条上限同时打断三处衔接（都不是模型问题）：

| 位置 | 后果 |
| --- | --- |
| `useManjuAuto.prepare` | 扫不到 `项目资料/分集剧本` → 确认卡误报「还没有分集剧本」；读不到 `项目风格` → 误报「没有确认影片比例」 |
| `useManjuAuto.readJson` | 先 `list()` 再判断进度文件是否存在 → 续做误判「没有进度」，已完成集会被重做 |
| `useDuanjuAuto.readText`（分集梗概） | 梗概实际已写，runner 读不到 → 收尾 `done()` 恒为 false，与 §2.2 叠加后整批暂停 |
| `useDuanjuAuto.removeStale` | 删不掉 stale 集的剧本与切分卡 |

修正（都改成不依赖整树列表）：

- `useManjuAuto.prepare`：整树列表只作基础，另按关键字 `分集剧本`、`影片比例与风格`、`集进度.json` 调 `searchPaths(owner, query, 2000)` 补齐（该命令整树遍历、上限 2000，且每条都带过滤）。
- `useManjuAuto.readJson`、`useDuanjuAuto.readJson/readText`：直接读文件，失败即视为不存在。
- `useDuanjuAuto.removeStale`：按父目录 `listDirectory` 查找要删的文件。

另外把扫描根写进确认卡（`draft.owner` + 命中集数），下次再出现这类失败可以一眼看出扫的是哪个目录、命中几集，不用再猜。

回归：`vue-tsc -b` 通过；`manjuProduction` 13/13（新增「项目文件超过 1000 条时，判定存在不能再依赖整树列表」）、`duanjuAuto autoRunner` 13/13、`manjuAuto autoRunner` 36/36、`mobileControllerUi` 21/21、`memoryWorkbench` 121/122（既有 iOS plist 失败）。

**未验收**：真实 app 里重新弹卡是否已扫到 20 集、续做是否不再重做——需要重启桌面端后由用户实测。

## 8. 第三轮：把场景/道具资料目录统一成一套

§7 只让归档器同时接受两种目录名（兼容旧库），但双轨本身还在产生：`wiki-artifacts.json` 里 `manju_layout.types` 把 `scene_research`／`prop_research` 覆盖成 `项目资料/场景说明`、`项目资料/道具说明`，而默认 `types`、`short_drama_layout` 与两套 `directories` 模板用的都是 `项目资料/场景`、`项目资料/道具`。同一个库里因此会同时出现 `原作/场景/` 与 `改编版/场景说明/`。

本轮统一到 `场景`／`道具`（与默认类型路径、两套目录模板、`资产/场景` 命名一致）：

- 删除 `manju_layout.types` 的 `scene_research`／`prop_research` 覆盖，改为继承默认路径。
- `manju_layout.directories` 的 `项目资料/场景说明`、`项目资料/道具说明` 改为 `项目资料/场景`、`项目资料/道具`。
- 四份 Skill 的读取指引改为「按实际索引读取」：`jc-scene-prompt`、`jc-prop-prompt`、`jc-renqun`、`jc-manju-pipeline`（第 2 条与 materials 阶段）。内容概念处（`场景说明"陈设"`、`场景说明的"人群"`）保持不动。
- `researchCandidates()` 仍接受 `场景说明`／`道具说明`：旧库文件不迁移，读取照旧可用。

验证：`wiki-artifact-writer` 34/34、`manju-skill-scope` 14/14、`manjuProduction` 13/13、`vue-tsc -b` 通过；`production-capabilities` 15/13 与既有基线一致。
