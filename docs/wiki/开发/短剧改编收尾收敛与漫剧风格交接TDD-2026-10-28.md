# 短剧改编收尾收敛与漫剧风格交接TDD

> 2026-10-28。状态：**源码已实施，定向回归通过；真实界面点击与真实模型回合未验收**。两件事合并为一份改动，因为它们都在「短剧改编 → 漫剧全自动」这一段链路上：①收尾回合产物已达标，却因进度被标 blocked 而暂停整批；②漫剧全自动因缺 `项目风格/影片比例与风格.md` 启动不了，而短剧路线没有生产它的权限。现象来自用户实测（塔防—晨曦树精项目第 1 批收尾、已出 20 集，以及「开始全自动成片」确认卡）。

## 1. 现象

### 1.1 收尾暂停但产物已完成

- 程序把状态标成 `已暂停 · 第1批 · 收尾 · 已出20集`，暂停原因写着「收尾资料已完成；运行时拒绝推进至 complete……故保留 materials 阶段」。
- 同一回合里，分集梗概已覆盖第 1–20 集、五份人物小传的造型表起始行已回填集号，即**收尾产物全部落盘**。
- 进度文件 `改编方案/执行进度.json` 停在 `materials` + `blocked`。

### 1.2 全自动成片卡在「未确认比例」

- `ManjuAutoPanel.vue` 显示红字「项目风格里还没有确认影片比例，请先确认比例与风格。」，「开始全自动」按钮禁用。
- 再往下没有入口：用户无法在卡上或菜单里补这一步。

## 2. 根因

### 2.1 状态机只允许逐级推进，删减式改编没有级可走

- `src-tauri/resources/deepseek-harness/manju-wiki.mjs:1741`：`短剧流水线不能跳过前置阶段`，要求 `previous.stage ∈ {stage-1, stage}`。
- 但 `public/skills/jc-duanju-pipeline/SKILL.md` 的进度合同写明：**删减式改编由程序按标注组装，`scheme`／`cuts`／`writing` 不需要模型保存**。
- 删减式路线也不产出 `改编方案/分集规划.md`，所以连逐级补 `scheme`（`manju-wiki.mjs:1795` 要求它）都补不上。
- 结果：`materials` 之后没有合法去处，`complete` 永远到不了。程序里也没有任何自动推进阶段的代码（全仓搜不到程序写 `cuts`／`writing`／`complete`）。

### 2.2 运行器把 blocked 判在 done 之前

`src/runtime/duanjuAuto/autoRunner.ts`：

```ts
const progress = await deps.readProgress()
if (progress?.status === 'blocked') blocked = `${step.label}：${progress.reason}`
else done = await step.done()
```

`blocked` 优先，且命中后不再看 `done()`。于是「梗概已覆盖全部集号」这个真正的完成条件被跳过，整批暂停。模型是在如实报告状态机拒绝，运行器却把它当成收尾失败。

### 2.3 比例与风格没有任何生产入口

- `src/composables/useManjuAuto.ts:127-129`：`ratio` 只从 `项目风格/影片比例与风格.md` 用 `/(\d+)\s*[:：]\s*(\d+)/` 提取；文件不存在或无数字比例即判未确认。
- 该文件的唯一生产 Skill 是 `jc-film-style`（`public/skills/jc-film-style/SKILL.md:11`），它只在 `manju` 白名单里，`short-drama` 白名单没有；`jc-duanju-pipeline` 的全自动指令也没有任何一步要求写风格。
- `docs/wiki/开发/短剧改编全自动与漫剧衔接TDD-2026-10-27.md` 的「漫剧衔接」只做了剧本路径扫描，未涉及风格与比例。

## 3. 方案

三处改动都取最小面，不新增开关、不改产物格式。

| 编号 | 文件 | 改动 | 理由 |
| --- | --- | --- | --- |
| A | `manju-wiki.mjs` | 新增 `annotationsComplete()`：读 `改编方案/分集清单.json`，当已组装出集且 `adapted` 覆盖 `1..总集数` 时，允许 `complete` 从 `materials`／`scheme`／`cuts`／`writing` 直接进入 | 删减式改编的这些阶段由程序组装，模型无产物可登记；判定基于已有事实文件，不新造状态 |
| B | `autoRunner.ts` | 判定改为 `done` 优先：先算 `step.done()`，未达标才因 `blocked` 暂停 | 产物达标不该被状态字段拖住；`blocked` 仍能在真正缺产物时暂停 |
| C | `ManjuAutoPanel.vue`、`useManjuAuto.ts`、`MemoryWorkbench.vue` | 缺比例时提供「去确认比例与风格」按钮：发一条 `jc-film-style` 指令保存 `film_style`，回合结束后重跑 `prepare()` 刷新确认卡 | 补入口而不猜配置；比例决定后续所有生图/生视频，必须用户确认，不填默认值 |

不做的：

- 不为缺比例自动填 `16:9`（猜测当配置）。
- 不改移动端（`MobileManjuAutoPanel.vue`）：移动端 App 已冻结。
- 不改 `scheme` 阶段要求 `分集规划.md` 的既有校验：手动旧流程仍需逐级推进。

## 7. 第二轮实测：真正的断点在文件列表上限

用户实测「分集剧本就在 `E:\1028全自动教程/wiki/项目资料/分集剧本`」，但确认卡仍报「还没有分集剧本」，切到全自动成片时模型也报「流水线检查确认没有可恢复的集进度」。据此写探针直接复刻 `dev_list_files` 的遍历语义，在真实项目上取证：

```
项目文件总数(实际): 1010
list() 返回条目数: 1000 其中文件: 951 目录: 49
前 1000 条里匹配到分集剧本: 0 集
风格文档在列表里: false
列表里最深的 5 条: wiki/资产/人群/index.md … wiki/资产/道具/index.md
```

根因：`dev_list_files` 的 `max_entries` 被限制在 1000，**目录也占一条额度**，且按目录名深度优先。`wiki/资产` 排在 `wiki/项目资料`、`wiki/项目风格`、`wiki/制作流水线` 之前，资产目录一多就把额度用完，后面三类文件全部丢失。项目文件数正好 1010，已经在临界线上。

因此同一条上限同时打断三处衔接（都不是模型问题）：

| 位置 | 后果 |
| --- | --- |
| `useManjuAuto.prepare` | 扫不到 `项目资料/分集剧本` → 确认卡误报「还没有分集剧本」；读不到 `项目风格` → 误报「没有确认影片比例」 |
| `useManjuAuto.readJson` | 先 `list()` 再判断进度文件是否存在 → 续做误判「没有进度」，已完成集会被重做 |
| `useDuanjuAuto.readText`（分集梗概） | 梗概实际已写，runner 读不到 → 收尾 `done()` 恒为 false，与 §2.2 叠加后整批暂停 |
| `useDuanjuAuto.removeStale` | 删不掉 stale 集的剧本与切分卡 |

修正（都改成不依赖整树列表）：

- `useManjuAuto.prepare`：整树列表只作基础，另按关键字 `分集剧本`、`影片比例与风格`、`集进度.json` 调 `searchPaths(owner, query, 2000)` 补齐（该命令整树遍历、上限 2000，且每条都带过滤）。
- `useManjuAuto.readJson`、`useDuanjuAuto.readJson/readText`：直接读文件，失败即视为不存在。
- `useDuanjuAuto.removeStale`：按父目录 `listDirectory` 查找要删的文件。

另外把扫描根写进确认卡（`draft.owner` + 命中集数），下次再出现这类失败可以一眼看出扫的是哪个目录、命中几集，不用再猜。

回归：`vue-tsc -b` 通过；`manjuProduction` 13/13（新增「项目文件超过 1000 条时，判定存在不能再依赖整树列表」）、`duanjuAuto autoRunner` 13/13、`manjuAuto autoRunner` 36/36、`mobileControllerUi` 21/21、`memoryWorkbench` 121/122（既有 iOS plist 失败）。

**未验收**：真实 app 里重新弹卡是否已扫到 20 集、续做是否不再重做——需要重启桌面端后由用户实测。

## 9. 第四轮：`比例不支持：9:16` 把整集拦在出片前

续做时第 1 集停在 `phase=blocked`，`reason` 是 `比例不支持：9:16`，20 集全部待做。

根因不在模型侧，在参数组装：项目风格存的比例是短式 `9:16`，而 `jc-minimax-h3-ref2v` 的 `ratio` 字段只登记 `9:16 (Portrait Widescreen)`（`ResolutionSelector` 只认带后缀的枚举，见 `JC_H3_RATIO_OPTIONS` 注释）。`mediaParams.buildMediaParams()` 把配置里的比例**原样透传**，`submit_creation_task` → `validateMediaPlan` → `validateSelectField` 就抛 `比例不支持：9:16`；`autoRunner` 的 `submitEpisodeVideos` 外层 catch 把它写成本集暂停原因。

复现（红）：直接用真实登记验证，确认报错文案与截图一字不差——

```text
ERR: 比例不支持：9:16        # jc-minimax-h3-ref2v
OK image 未报错               # jc-qwen-image-2.1（它登记的就是短式 9:16）
```

修复（`src/runtime/manjuAuto/mediaParams.ts`）：

- `MediaParamProfile` 增加 `ratios?: string[]`；`profileFromSpec` 取比例字段的 `options[].value`（缺省回落 `capabilities.ratios`），`profileFromCapability` 取 `parameter_schema` 里 `ratio`／`aspect_ratio` 的 `enum`。
- `buildMediaParams` 用 `fitRatio()` 把项目比例收敛到模型枚举：先全等，再按 `' ('` 前半截匹配（`9:16` → `9:16 (Portrait Widescreen)`）；已经是枚举原值时不再套一层；模型没这个比例则抛 `比例 7:5 该模型不支持，可选 …`，比后端的 `比例不支持：9:16` 更能指导操作。
- 图片模型不受影响：`jc-qwen-image-2.1` 登记的就是短式比例，全等命中，原样透传。

验证：`manjuAuto mediaParams` 8/8（新增 3 项：短比例收敛、无匹配时报可读原因、远程能力档案同样收敛）、`manjuAuto autoRunner` 36/36、`assetScheduler` 17/17、`videoScheduler` 13/13、`vue-tsc -b` 通过。

**未验收**：真实续跑出片未执行（上一轮 503／`PermissionError` 是本机 ComfyUI 与适配器进程完整性问题，已另行修复并单张出图验证）；本轮只证明参数能过校验。

## 10. 第五轮：适配器重启把在途视频任务判成「上游任务失败」

第 1 集四段视频全部 `failed`，卡片只有一句「上游任务失败」。取证后不是模型侧问题：

- `comfy-adapter/logs/adapter.log`：新进程启动行之后紧跟着四条
  `GET /v1/videos/task_20261029_<hex> 404 Not Found` —— NewAPI 拿着**适配器自己的任务号**回来问。
- App 侧任务记录里 `error = { category: unknown, stage: poll, message: 上游任务失败, raw: { terminalCreationTask: true } }`，
  没有任何 `fail_reason` —— 是轮询拿不到状态被判死，不是上游报的错。
- ComfyUI 只产出过 1 段（`ComfyUI_00077_.mp4`，10:36:56），后 3 段没进队列。
- 计划任务 `\comfy-adapter` 的 `LastRun = 10:38:38`，正对上。

根因：`adp/tasks.py` 的 `TaskStore` **只在内存里**（原 docstring 明确写着「进程重启后任务丢失是预期行为」），
而 NewAPI 唯一持有的对账凭据就是这个任务号。适配器一重启，任务号变成 404，
上游只能等到超时判失败 —— 一次重启就把整轮出片清零。

修复（`comfy-adapter`）：

- `TasksCfg.state_file`（默认 `state/tasks.json`，已进 `.gitignore`）。
- `TaskStore` 增加 `path`：启动载入、`flush()` 原子落盘（tmp + replace）；`create`／状态迁移／取消／结束时都 flush。
  落盘走 `Task.to_record()`，`params` 经 `_safe_params` 裁剪 —— prompt 与参考图 base64 不落盘。
- `Task.comfy_prompt_id`：`generate(on_prompt=...)` 在拿到 ComfyUI `prompt_id` 时回调写入。
- `GenerationService.resume(model, prompt_id)`：接管已提交的任务，只等结果不再提交；
  ComfyUI history 与 queue 都查不到时**立刻**报错，避免上游干等 `job_timeout`（1800 秒）。
  提交之后的取产物逻辑抽成 `_await_and_collect()`，两条路径共用。
- 启动时 `TaskStore.recover()` 分派：有 `prompt_id` 的 `asyncio.create_task` 接管，
  没有的判 `failed` + `code: adapter_restarted`（重启前没提交到 ComfyUI，ComfyUI 那边不会有产物）。

验证（先红后绿）：

- 新增 `comfy-adapter/tests/`（stdlib `unittest`，`python -m unittest discover -s tests -t .`）9 项：
  任务跨重启存活、在途任务保留 `prompt_id`、大字段不落盘、`recover` 按 `prompt_id` 分派、
  过期任务不恢复、坏文件不挡启动、无 path 不碰磁盘、`resume` 查不到时快速失败、查到时不重复提交。
- 真机验证（停计划任务 → 手写状态文件 → 启动）：一条带真实 `prompt_id`（`ad336817-…`）的 running 记录被接管，
  从 ComfyUI history 取回 9,088,183 字节 mp4 落到 `static/20261029-dd673f6ffded4975.mp4`，
  `GET /v1/videos/<id>` 回 `completed`；另一条无 `prompt_id` 的按预期判 `failed/adapter_restarted`。
- `newapi-plugins/__tests__/comfy.test.mjs` 24/24（状态词表未脱钩）。

**仍未验收**：真实「视频跑到一半重启适配器」的接管（用 history 里已有的 prompt 验证的是同一条代码路径，但没有覆盖「ComfyUI 正在跑」的实时形态）。

## 11. 第六轮：失败资产被反复重提、出片中的集被后面几集的审图挡住

用户实跑时两个观感问题，都有实测数据支撑：

**① 第 1 集资产「一直在重复出」**。`资产注册表.json` 里三个资产 `submits=12`；媒体任务库对齐时间后是
09:57、09:58、09:59、10:13 四轮（前 3 轮全是 `HTTP 500: fail_to_fetch_task`，即当时适配器写盘被拒；10:13 修好后一次成功并锁图）。

根因：`handleCheckpointSaved` 在文字流水线每存一次进度就调用 `submitAssets` → `submitEpisodeAssets`，
而 `needsSubmit` 对 `status === 'failed'` **无条件返回 true**，于是同一次运行内反复重提。`MAX_ATTEMPTS`
只在闸门 `awaitEpisodeAssets` 的轮询分支里生效，管不到这条路径，也没有退避 —— 适配器一坏就是打桩机。

**② 「视频只出来一条」**。第 1 集 4 段在 10:32–10:34 提交后被 10:38 的适配器重启打死（§10），
而续做时它们**没有被重提**：`checkVideos()` 在主循环里排在「本集通过审图 → 提交本集视频」之后，
第 2 集正卡在审图（`phase=review`），第 1 集就永远等在那儿。

修复：

- `submitEpisodeAssets(..., { retryFailed })`：默认 `true`（新一轮运行、闸门入口仍给失败项一轮新机会，
  重提时 `attempts` 重置为 1）；只有高频的进度保存路径显式传 `false`（`handleCheckpointSaved` →
  `submitAssets(..., { retryFailedAssets: false })`）。
