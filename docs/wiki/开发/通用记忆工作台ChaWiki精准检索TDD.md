# 通用记忆工作台 Cha Wiki 精准检索 TDD

> 日期：2026-08-05
> 状态：已实施并通过自动验证；四类真实模型前向验收待可用 Claude 运行环境
> 范围：`public/skills/jc-cha-wiki/`、查询与项目地图原生工具、对应测试和现行 Wiki 合同

## 1. 根因

`jc-cha-wiki` 的唯一核心能力，是根据用户问题从现有 Wiki 找到可信答案。当前包却有 56 行主 Skill、3 份重复 Reference 和 245 行 Python 查询脚本，并把开发项目目录、固定必读页、固定四段输出、状态计数和全库关系图绑定成一套流程。

这造成四个问题：

1. App 已有跨 Web/Desktop 的原生 Wiki 搜索、读取和关系图工具，随包 Python 脚本重复实现同一能力，还会产生 `__pycache__`。
2. 当前搜索是逐字匹配；把完整自然语言问题一次传入，容易零命中。现有 Skill 没有把“拆词、多次召回、读原页、交叉验证”固定成查询合同。
3. `hot.md`、`CLAUDE.md` 和开发目录优先级是旧开发 Wiki 假设，不适合任意个人或企业知识库，也违背“没有固定必读页”的现行决策。
4. 当前 `graph` 会扫描全部 Wiki 并直接覆盖固定的 `关系图.canvas`。这与 [[通用记忆工作台项目地图SDD]] 的“围绕主题生成局部地图、保留既有布局、不自动铺开全库”合同冲突。

## 2. 对照结论

Obsidian 官方 Help 提交 `8a59e12f6bcffb487ae8d6a40773e41e9c6017bc` 表明：

- Search 通过搜索词、短语、AND/OR、路径、文件名、内容、标签和属性缩小候选范围；搜索结果不是答案本身。
- Graph 的节点是笔记，边来自真实内部链接；官方明确说明局部关系图通常比全局关系图更有用。
- Backlinks 用于发现引用当前页面的相关页面；它是补充证据入口，不代表引用内容自动正确。
- Obsidian 没有规定查询前必须读取某个页面，也没有规定 AI 回答格式。

`claude-obsidian/wiki-query` 可借鉴“读取相关原页、引用来源、资料不足时明确说不知道”，但不照搬其 `hot -> index -> 固定页数`、Quick/Standard/Deep 模式、自动回写答案或可选 BM25/Ollama 链路。

本阶段不增加向量库、Embedding、BM25、RAG、后台索引或新依赖。真实使用数据证明逐字搜索加模型查询规划不足时，再单独设计检索基础设施。

## 3. 唯一职责

把用户的问题转成最少的 Wiki 检索与阅读动作，并根据实际页面给出可追溯的答案。

Cha Wiki 负责：

- 事实查询、解释、比较、汇总和当前状态回答。
- 基于实际页面内容进行数量统计。
- 用户明确要求时，保存 Markdown 统计表或生成标准 `.canvas` 局部关系图。

Cha Wiki 不负责：

- 把新事实写入 Wiki、规划目录、巡检全库或修正错误；分别交给 `jc-raw-wiki`、`jc-everything-wiki`、`jc-jian-wiki`、`jc-xiu-wiki`。
- 默认读取 Raw、附件、项目全部文件、历史会话或互联网。
- 自动保存回答、更新 `hot.md`、追加 `log.md`、补链或修正文档。
- 生成 `.base`；App 支持解析和显示后再设计。

## 4. 触发与范围

当用户询问当前项目 Wiki 中的事实、状态、关系、统计或历史时触发，例如“查询 Wiki”“公司报销规则是什么”“这个项目现在做到哪了”“统计已确认客户”“生成这几个页面的关系图”。

普通常识问答、网页搜索、读取用户刚上传但尚未进入 Wiki 的材料，不应仅因出现“查询”“搜索”而触发。

默认只回答现行知识；用户明确问历史、演进、旧方案时才纳入归档。现行与历史依据 Wiki 自身的目录、页面标题、状态说明和时间语义判断，不硬编码业务目录或固定必读页。若同时存在 `wiki/` 与 `docs/wiki/`，先请用户确认唯一知识库。

## 5. 精准检索合同

1. 从问题提取实体、事项、属性和时间范围，先选择 1-3 个辨识度最高的短词分别检索；首轮不足时再补同义词、旧称、文件名或路径词，不把整句问题当成唯一搜索词。
2. 搜索结果只作为候选。必须读取支持答案的原页面和相关段落；只有引用页或反向引用会改变答案时，才继续读取一层相关页面。
3. 查到足够证据就停止，不规定固定页数，不默认遍历全库。用户要求全面盘点时才扩大范围，并如实说明实际读取边界。
4. 对当前状态、数字或比较结论，核对涉及的全部必要页面；文件数不能代替完成度、客户数、角色数或业务状态。
5. 多页冲突时并列给出页面与冲突点，不自行选择“看起来更新”的版本。Wiki 没有答案时明确说“当前 Wiki 未记录或证据不足”。
6. 公司或项目专属问题不得用模型训练知识补成项目事实。通用知识确有帮助时，必须与“Wiki 已记录内容”分开表述。
7. 最终答案直接适配用户问题，不强制“结论、证据、风险、下一步”四段；但关键事实必须标出真实 Wiki 页面，不能只复述搜索片段或文件列表。

## 6. 派生视图合同

### 统计

- 默认在对话中回答，并说明统计口径和实际读取范围。
- 只有用户明确要求保存时才写 Markdown 表格；它是可重新生成的派生报告，不替代源页面，不自动更新 `log.md`。

### 关系图与 Canvas

- 只有用户明确要求可视化关系，且页面间存在稳定关系时才生成。
- 默认生成围绕用户指定主题或种子页面的一层局部图；用户明确要求时最多扩展到两层，不自动生成全库图。
- 节点使用标准 JSON Canvas `file` 节点并指向真实项目相对路径，点击后可在 App 打开源文件；边只来自已确认的 Wiki 内部链接，不臆造关系。
- 使用用户指定输出路径；未指定时生成带主题名称的 `.canvas`，不再固定覆盖 `关系图.canvas`。
- 更新已有 Canvas 时保留未涉及节点、既有坐标和用户布局；覆盖、删除节点或改变既有边必须先预览并确认。
- Canvas 是衍生产物，不进入 Wiki 事实检索，不成为唯一事实源，不追加 `log.md`。

## 8. 原生工具最小修正

查询继续复用现有 `wiki_search`、`read` 和项目文件工具，不新建搜索服务。Skill 通过一次一个短词的多轮查询适配当前逐字搜索，本轮不重写搜索算法。

标准 `.canvas` 继续复用现有 Wiki `graph` 动作，但实施时必须收紧：

- 以用户确认的种子页面作为输入；没有范围时拒绝生成全库图。
- 只纳入种子与允许深度内真实存在的链接页。
- 输出可点击的 `file` 节点，而不是只有标题的文本节点。
- 输出路径可指定；已有文件默认预览，确认更新时保留无关节点与坐标。

不删除现有原生 `search`、`status`、`graph` 兼容入口；Cha Skill 不再依赖只能按开发目录计数的 `status` 结果回答项目状态。

## 9. 红灯测试

实施前新增 `public/skills/tests/test_cha_wiki_precision.py`，并在旧实现上确认失败：

1. Skill 包最终只有 `SKILL.md`，通过官方 `quick_validate.py`，正文不超过 50 行，frontmatter 无 `triggers`。
2. `description` 命中项目 Wiki 事实、状态、统计和关系查询，不把普通网页搜索或一般常识问答纳入。
3. Skill 明确“短词拆分、多次召回、读取原页、必要时一层扩展、查够即停”，不规定固定读取页数。
4. Skill 不含固定 `hot.md -> index.md` 读取顺序、`CLAUDE.md` 必读、开发项目目录优先级、Quick/Standard/Deep 模式或固定四段回答。
5. 答案必须引用真实 Wiki 页面；缺口和冲突必须如实报告，不用训练知识补写项目事实。
6. 默认查询不写文件、不更新 `hot.md`、不追加 `log.md`、不扫描 Raw；统计只在用户明确要求时保存 Markdown。
7. `.base` 不生成；Canvas 仅在用户明确请求且有稳定关系时生成。
8. 原生 `graph` 没有种子页面时拒绝生成且不写文件；指定页面后只生成局部图，节点为真实 `file` 路径，边来自可解析内部链接。
9. 新建局部图不覆盖固定 `关系图.canvas`；更新已有图保留无关节点和原坐标，未确认时只预览。
10. `public/skills/index.json` 只登记 `SKILL.md`，现行 Skill 与 Wiki 文档不再引用已删除 Reference 或 Python 脚本。

## 11. 完成标准

- 明确事实、同义表达、跨页汇总、当前状态、冲突和无答案六类查询均能给出符合证据的结果。
- 普通查询零写入；显式统计或关系图请求只生成用户要求的可再生派生文件。
- 局部 Canvas 在 Web/Desktop 中可打开源页面，不覆盖用户已有全局关系图或布局。
- 旧 Reference、Python 查询器和缓存文件不再随 App 分发；现有 Wiki、Raw、正文和用户 Canvas 未被迁移、删除或静默覆盖。
- 自动测试全部通过；“单页事实”“同义词跨页”“冲突”“Wiki 未记录”四类独立模型前向检查作为发布前人工验收项。
