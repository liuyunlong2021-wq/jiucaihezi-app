# 通用记忆工作台故事拆分与语义沉淀 TDD

> 日期：2026-09-09
> 状态：合同已确认，分阶段实施中

## 1. 用户目标

用户不需要手动创建 Wiki、目录、分段文件或索引。文件树顶部提供一个“故事拆分”入口；用户选择故事后，程序完成导入、结构识别、预览、无损拆分、建目录和建索引，随后直接进入语义分析阶段。

核心边界：程序负责执行，模型负责判断。模型不得负责机械拆分、批量命名、创建目录、维护 Index、决定提交顺序或恢复中断任务。

## 2. 唯一流程

```text
故事拆分（Runtime）
  → 原文节点 Wiki
  → 语义分析（模型只返回结构化语义结果）
  → 校验与沉淀（Runtime）
  → 创作前置检索
```

### 2.1 文件树入口

- 在文件树顶部的新建文件、新建文件夹、刷新右侧增加“故事拆分”按钮。
- 一个入口接收支持的故事资料格式；所有资料必须先经过统一转换层生成完整 Markdown，拆分器只接收转换后的 Markdown，不为 TXT、PDF 或 Word 设置旁路。
- 对话模型不参与文件选择、格式转换和结构拆分。
- 选择文件后自动识别边界并展示节点总数、首尾样本、输出位置和异常；主操作只有“开始拆分”。高级识别规则按需展开。

### 2.2 边界识别

Runtime 按确定性规则识别 Markdown 标题、独立数字段号和标题中的显式编号；编号统一归一为整数后只用于候选评分与异常校验，原始标题保持不变。支持阿拉伯数字及全角形式、中文简繁数字与大写数字、ASCII/Unicode 罗马数字，以及 `第十二章`、`第十二話`、`Chapter XII`、`001、标题`、`中风一`、`中寒二（附…）` 等前缀、独立和后缀形式。自动选择时按同级标题形成的编号序列完整度和节点数量评分，不得因封面一级标题先出现就抢占更完整的章节层级。找不到边界或多种高分规则接近且会改变切片时停止，请用户选择；序号重复、跳号或倒序不改变原文物理顺序，可以继续拆分但必须显示具体编号并由用户确认。缺号只产生警告，程序不得补造边界。

来源写“章”就保留为章，写“集”就保留为集；只有数字段号时称为“原文节点”。程序不得把原文节点擅自解释为改编集数。

## 3. 确定性存储合同

沿用项目中唯一的 `wiki/` 或 `docs/wiki/`，不得创建平行 Wiki。以作品名“霸总的功夫女友”为例，最小落盘结构为：

```text
wiki/
├── index.md
└── 原始材料/
    ├── index.md
    └── 霸总的功夫女友/
        ├── index.md
        ├── 来源.md
        ├── 原文.md
        └── 原文节点/
            ├── index.md
            ├── 0001.md
            ├── 0002.md
            └── ...
```

- `来源.md` 保存来源类型、原文件名、整体哈希、识别规则、节点数和异常。首次导入时间由存储层文件元数据提供，避免重跑同一导入时制造内容差异。
- `原文.md` 保存转换后的完整 Markdown 真源，使 Wiki 不依赖不同步的 `.raw/` 缓存。
- 原文节点保存连续、无损的原文切片；不得总结、改写或清洗事实。
- 只创建实际需要的目录。角色、场景、道具和分析目录在第一次产生内容时创建，不预建空壳。
- 每个新目录同时创建自己的 `index.md`，并更新直属父 `index.md`；祖先导航未变化时不重写。
- 第二阶段第一次产生结果时，在作品目录创建 `节点分析/`，在 Wiki 根按实际内容创建 `资产/人物/`、`资产/场景/`、`资产/道具/` 或 `资产/关系/`；不把规范资产复制到每个作品节点下。

### 3.1 编号与身份

文件名和稳定 ID 只使用原文物理顺序生成的 `0001.md`、`0002.md`。原文标号单独保存为 `source_label`，不得用重复或错误的来源标号决定路径。

```yaml
---
type: story-source-node
id: story.<work-id>.node.0001
order: 1
source_label: "1."
source: "[[../原文]]"
source_range: "lines 1-28"
source_hash: "<sha256>"
---
```

同一原文、识别规则和输出位置必须生成同一方案与内容。重复执行跳过相同文件；目标内容不同不得覆盖。

## 4. 拆分提交与恢复合同

- 拆分方案属于 Runtime，不依赖对话 executor 内存，也不要求模型跨轮保存或重放 `planId`。
- 用户关闭预览后重新打开时，Runtime 从原文和设置重新计算同一方案。
- 同一项目同时只允许一个故事拆分提交；Web、Desktop 和外部编辑造成的版本变化必须在覆盖前被发现。
- 写入顺序固定为：原文与来源 → 原文节点 → 节点 Index → 作品 Index → 直属父 Index → 完成标记。
- 完成标记最后写入。中断前已写入的相同文件允许下次跳过并续跑；没有完成标记不得向用户宣称拆分完成。
- 无法提供真正跨文件原子事务的平台采用可恢复提交，不通过回滚覆盖用户文件来伪装原子性。

## 5. 语义分析合同

### 5.1 职责

Runtime 根据来源节点与分析页的对应关系选择待处理节点、读取本批原文和相关规范实体，并向模型提供固定结构输入。模型只返回结构化语义结果，包括场次、人物、地点、道具、关系变化、证据和待确认项；模型不直接决定文件路径、Index 内容或提交顺序。

Runtime 必须校验：

- 节点 ID 和来源哈希仍然匹配；
- 引用证据确实存在于对应原文切片；
- 已有实体链接真实且唯一；
- 新实体没有与现有 ID 或别名冲突；
- 状态只使用 `complete` 或 `needs_review`。

校验通过后，Runtime 创建或更新分析页，按需创建新的来源型规范实体页并维护直属 Index。唯一匹配到用户已有的规范实体时只建立链接，不自动改写其正文；本章新增证据先保留在分析页，只有用户明确确认后才能增量更新已有实体。发生歧义时写入分析页的待确认部分，不把模型推断合并成用户确认事实。

### 5.2 Runtime 与模型的唯一衔接接口

第二阶段只开放两个故事语义动作，不让模型直接拼装批量文件写入：

1. `prepare_story_analysis`：Runtime 接收作品锚点和可选批量上限，比对 `原文节点/` 与 `节点分析/`，选择尚未完成的节点；返回节点 ID、来源哈希、原文切片和现有规范实体候选。它只读取，不改变分析状态。
2. `commit_story_analysis`：模型返回结构化语义判断；Runtime 重新读取来源和实体状态，通过全部校验后派生分析页、资产页及直属 Index 的真实路径并提交。该动作不得接收模型提供的写入路径。

模型提交的每个节点至少符合以下逻辑结构；数组允许为空，但字段不得靠自由文本替代：

```json
{
  "node_id": "story.work.node.0001",
  "source_hash": "<sha256>",
  "summary": "本节点摘要",
  "scenes": [],
  "characters": [],
  "props": [],
  "relations": [],
  "evidence": [],
  "needs_review": []
}
```

每项事实或关系必须引用 `evidence` 中可在当前原文切片逐字匹配的证据。Runtime 不接受模型自报的“已存在”“已写入”或“已完成”；只相信提交时重新读取到的项目状态。

`commit_story_analysis` 的回执至少包含 `committed`、`skipped`、`needs_review`、`conflicts` 和 `affected_paths`。模型只能根据该回执向用户报告结果；用户说“继续分析”“继续”“执行下一步”时，Runtime 必须重新调用 `prepare_story_analysis` 取得下一批，不能复用上轮临时路径或完成判断。

### 5.3 唯一状态真源

分析页是分析状态的唯一真源。来源节点不保存会过期的 `analysis_status: pending`。

- 不存在对应分析页：未分析。
- 分析页为 `complete`：已完成。
- 分析页为 `needs_review`：等待确认。

Runtime 通过比对来源节点与分析页确定下一批，不要求模型扫描整个 Wiki，也不根据 Index 摘要猜测状态。Index 可以展示状态，但不作为状态真源。

### 5.4 语义提交顺序

同一项目的语义提交使用项目级锁和版本条件。提交顺序固定为：新增规范实体页 → 实体直属 Index → 章节分析草稿 → 分析直属 Index → 完成标记。已有规范实体默认只链接、不改写。只有目标页面和双链目标都已存在时，分析页才能标记 `complete`。

中断或冲突后，Runtime 重新读取真实状态，只继续未完成节点；不得因为一次失败后重试成功仍向 UI 报告失败。回执必须包含实际影响路径。

## 6. 与 Skill 的关系

- `wiki-memory` 规定取证、消歧、事实与推断边界。
- Runtime 负责故事拆分、目录、路径、Index、状态、锁、版本校验和恢复。
- 模型负责语义识别、实体消歧建议、关系变化判断和创作。
- 原生“故事拆分”可用时，Skill 不得要求模型调用多轮文件写入模拟第一阶段。

## 7. 验收门槛

1. 空 Wiki 中导入带 33 个独立数字段号的故事，一次操作生成完整来源树和父级导航。
2. 重复号、跳号和倒序保留在 `source_label`，文件仍稳定为 `0001.md` 至 `0033.md`。
3. 拆分中断后重试不覆盖不同内容，只补齐缺失文件；完成标记最后出现。
4. 两个拆分任务同时提交到同一项目时只有一个进入提交阶段。
5. 外部编辑目标文件后，提交检测冲突并保留用户内容。
6. 模型语义结果没有真实证据、目标链接歧义或来源哈希变化时，Runtime 拒绝写成 `complete`。
7. 已完成节点不会再次进入“分析下一批”；`needs_review` 不被当作完成。
8. Web 与 Desktop 生成相同路径、节点 ID、来源哈希和 Index 结构。

## 8. 非目标

- 本阶段不自动决定原文节点与改编集数的映射。
- 本阶段不建立向量数据库、RAG、知识图谱数据库或后台常驻 Agent。
- 本 PDF、Word 等格式继续复用现有文档转 Markdown 能力，不建设第二套转换器。
