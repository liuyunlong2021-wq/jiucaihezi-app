# DSH 会话写锁与官方生命周期对齐方案

> 日期：2026-10-06
> 状态：代码、自动回归及 macOS Apple Silicon 本地修复包已完成；用户原对话及跨平台原生复测待完成
> 用户决定：产品与 DSH 官方处理方式对齐。
> 上游查证基线：`deepseek-ai/deepseek-harness` master，`5badb15009ae1756c3afe0ae0cef1faafc290ccc`。
> APP 当前 SDK：`@deepseek-ai/dsh-sdk-client@0.2.0-rc.2`。

## 1. 目标与结论

用户在最新 APP 中反复遇到 `session "jc-v1-…" is already owned by an active write handle`，报错对话无法继续，切到其他对话才能使用。

按官方语义处理会话：复用已有 Agent；合并同 Session 的创建／恢复；真正跨进程占用时明确提示；结束生命周期时等待官方释放完成。会话历史仍由官方 Session 保存。

当前错误只证明写所有权已被占用，尚不能证明持有者是孤儿进程。实施前必须区分同运行时的活 Agent、创建／恢复竞态、旧运行时尚未退出、其他 DSH 进程占用。

## 2. 官方依据

以下固定到查证提交；官方仓库讨论仅作用户现象参考，不把社区插件或评论视为官方内置方案。

- [SDK Server](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/sdk/server/src/server.ts)：`getOrCreateSession()` 先复用 `sessions`，再复用 `sessionCreations` 的 Promise；prompt 经活性检查后交给原 Agent 的 `followup()`。shutdown 阻止新创建，等待已有创建，然后 dispose 所有自己拥有的 AgentHandle。
- [官方 Web Session 控制层](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/api/session-controller/src/agent.ts)：先查 live Agent，按 Session 合并恢复；恢复失败后再次查 live Agent，接住其他调用已经完成激活的竞态；真正的 `SessionAlreadyOwnedError` 归一为 `session/writer-held`。
- [Agent 所有权合同](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/packages/core/agent/README.md)：创建者拥有 AgentHandle 与 disposer；拿到裸 Agent 不代表取得销毁权。
- [持久化合同](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/docs/subsystems/persistence.md)：写句柄独占；`close()` 幂等、不可取消，完成收尾后释放写所有权。只读观察可在其他写入者存活时进行。
- [官方 writer-held 反馈修复记录](https://github.com/deepseek-ai/deepseek-harness/blob/5badb15009ae1756c3afe0ae0cef1faafc290ccc/.agents/notes/archived/bug-fix/2026-09-16-session-writer-held-feedback.md)：将占用反馈与其他恢复失败区分。
- [同类讨论 #7156](https://github.com/deepseek-ai/deepseek-harness/discussions/7156)、[同类报告 #6993](https://github.com/deepseek-ai/deepseek-harness/discussions/6993)：显示普通 Web 会话可能激活 Agent，Agent 空闲时也会持有写句柄；这些讨论没有证明 APP 本次故障的具体触发原因。

需区分官方两条入口：Web Session 控制层已经支持恢复已有持久会话；本次查证的官方 SDK Server 首次遇到 ID 仍调用 create，未提供同等冷会话恢复。因此不能直接删除 APP 恢复适配，否则会削弱重启后继续历史对话的能力。

## 4. 实施合同

### 4.1 先确认触发链

对本次 Session 检查运行中的 APP／runner／DSH、归属窗口和 realm，以及发送前后是否更换 runtime。记录 Session、runtime 标识、PID、配置切换原因、shutdown／退出结果与官方错误类型；避免输出 API Key、请求正文与完整敏感配置。

在实际 SDK 中复现导致占用的路径后再改对应分支。代码已有复用，因此不能未经复现就再加一份缓存、锁表或恢复服务。

### 4.2 会话解析遵循官方流程

1. 复用当前运行时已经登记且仍存活的 Agent。
2. 同 Session 正在创建／恢复时，复用同一个 Promise。
3. 需要冷恢复才调用官方 `agents.resume()`；不存在才创建，其他错误不降级成新会话。
4. 恢复竞争失败后复查当前运行时的 live Agent；确有符合身份与路由约束的 Agent 则复用，否则保留占用错误。
5. 消息通过原 Agent 的官方投递接口进入原 Session。

创建／恢复成功后必须保留真正的 AgentHandle。复用他人拥有的裸 Agent 时，不能伪造 disposer，也不能在 APP 收尾时销毁其生命周期；参照官方所有权政策确定是否允许该身份进入普通会话路由，尤其保留子代理边界。

### 4.3 运行时交接遵循官方释放顺序

通过官方 shutdown／close 完成 Agent dispose 与持久化收尾。只有旧 runtime 终止得到确认后才能由新 runtime 接续写同一 Session。官方退出路径无法完成时，使用现有原生宿主对自己拥有的进程树收尾，并检查执行结果。

页面启动的旧 realm 清理必须与新 runtime 启动建立顺序。检查 `try_lock()` 清理被跳过的情况；不能把“未能执行清理”当成“没有旧进程”。具体修改限于能复现的触发链，不引入另一套 Session 锁。

正常完成一轮不等于 Agent 生命周期结束；空闲 Agent 可以保留写句柄。切换对话不应被用作解锁方案。

### 4.4 对齐官方占用反馈

保留错误身份，在 APP 中将真正的 writer-held 显示为“这个对话正被另一个运行时占用，请关闭占用它的实例后重试”。若可靠证据表明是本应用的某个窗口，可显示该窗口位置。

持有者释放后，可在原对话重新发送。占用失败不删除对话、历史、过程或修改 Session ID。没有官方消息受理回执的请求才允许用户重试；已被接纳的消息不能自动重复投递。

不新增删锁文件、锁超时抢占、无限重试或未知进程自动强杀机制。官方单写者保护继续生效。

## 5. 步骤与验证目标

1. 查证实际 SDK 与 runtime 交接，复现用户故障 → 验证：取得真实持有者和触发链，而非只有源码推测。
2. 仅修复偏离官方合同的路径 → 验证：实际 SDK + 本地模型替身，验证同 Session 连续发送、并发创建／恢复、退出与重新恢复；使用真实官方 lease。
3. 对齐占用反馈并回归保留能力 → 验证：两个独立 DSH 进程争用同 Session 时只有一个可写；占用者释放后另一方可续原历史，未重复投递；原生重载／关窗／换配置场景无遗留写入者，另一个窗口不受影响。

补充边界：读历史不会新建写入者；失败、取消与重启后历史仍可读；权限、审批、Skill 和漫剧桥接在同 Session 复用与恢复后仍有效。测试优先使用真实 SDK 的行为断言，不能只用源码字符串断言证明生命周期正确。

macOS、Intel Mac、Windows 的原生操作与安装包验证分别记录。未执行的平台不得写成通过。无需调用付费生成模型验证会话锁。

## 6. 交付与完成标准

交付最小代码改动、根因复现证据、对应回归和用户原对话复测记录。修复完成意味着同一 Session 能连续使用，并在正常交接后继续历史；真实外部占用被正确提示；占用解除后原对话可继续。

本方案不承诺 DSH 会自动夺取仍由其他活实例持有的会话。本次用户报错的具体持有者尚未直接确认；以下是隔离环境复现和修复的证据。

## 7. 实施记录

2026-10-06 用户授权立即执行后，先以真实 SDK + 本地回环模型复现：配置侧已激活同一 Session，SDK 冷恢复补丁仍试图 resume，报出同样的英文写锁错误。修改后复用活 Agent，连续两轮只产生两笔模型请求，并保留第一轮历史。

恢复适配保留官方 SDK 的会话缓存与共享创建 Promise，新增官方 API Session 的 live 查询／失败后复查；复用时检查工作区、当前模型路由和子代理所有权。借用记录不制造 disposer；SDK shutdown 释放自己的审批／Skill 桥接，并仅 dispose 自己创建／恢复的 AgentHandle。

同时修复以下宿主生命周期缺口：

- runner 退出被 `child.try_wait()` 回收后，`child.id()` 变为 None，导致后代进程树收尾被跳过。原生登记表现在保留原始 PID，Unix 真进程测试确认父进程已经退出后仍可结束后代。
- stdin 异步写入持有全局进程表锁，背压可阻断回收；清理 `try_lock()` 又可能静默跳过。现在写入只锁自己的管道，进程表只保护短元数据操作；真实满管道测试确认回收可执行。
- 关闭请求发送不受 15 秒关闭期限约束；全量停止提前清空登记表。关闭期限现在覆盖发送，完成回收前保留登记；失败保留句柄并允许后续收尾重试。
- 页面启动回收与新 runner spawn 没有建立等待顺序。现在共享清理 Promise，spawn 必须等待成功；失败可重试。页面 realm 跨模块热替换保持，整页重载才换代。

runner 到 UI 保留可取得的 SDK 错误名，并按 `session/writer-held` 分类。当前 SDK 协议只透传英文 message 的情形，严格匹配官方完整错误格式作为兼容判断；其他错误不被归类为占用。界面明确说明释放占用后可在原对话重试，不自动重复投递消息。

实际双进程／双 runner 回归：A 写第一轮，B 遭官方 lease 拒绝但仍可读历史；A 通过官方 close 释放后，B 同一个运行时继续原 Session，历史中只有成功受理的用户消息，没有那条被拒绝的消息，也没有重复模型请求。
